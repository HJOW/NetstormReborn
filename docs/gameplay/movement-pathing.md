# 이동 경로 탐색: 끊긴 길 재탐색과 스톰 에너지 줄기 경로

> 2026-10-01 작성. **설계 결정과 구현 점검 기록**이며 코드는 바꾸지 않았다(원본 게임·클론 GUI도 실행하지 않았다). 아래 "클론 현황"은 `src/Netstorm.Core/Simulation/`의 코드를 읽고 정리한 것이고, 새 테스트를 돌려 확인한 것은 아니다. 기존 테스트 결과는 [희생 의식 문서](sacrifice.md)의 검증 상태를 따른다.

## 1. 원본의 문제 (사용자 보고, 2026-10-01)

이동형 유닛(수확하는 사제, 포획·운반하는 수송 유닛 등)은 "특정 위치로 이동", "채집", "적 사제 포획" 명령을 받을 때 경로를 **한 번 정하고** 그대로 따라 이동한다. 이동 중에 지나갈 다리가 붕괴하거나 다리 근처의 건물형 유닛이 파괴돼 길이 사라져도 **옛 경로를 그대로 따라가다가 추락해 이동형 유닛이 파괴되는** 문제가 원본에 있었다.

### 1.1 원본의 낙하 규칙 (사용자 확인, 2026-10-01) — 클론도 **그대로 구현한다**

사용자가 원본에서 확인한 동작이다. 위 "옛 경로 추적"과 달리 이 규칙은 **고치지 않고 재현**한다.

| 상황 | 원본 결과 |
|---|---|
| 지상 보행형 이동 유닛이 다리가 끊어져 **허공이 된 칸으로 이동**했다 | 아래로 **낙하한 뒤 파괴**된다 |
| 지상 보행형 이동 유닛이 **서 있는 상태에서** 그 칸의 다리가 끊어졌다 | 마찬가지로 낙하한 뒤 파괴된다 |
| **사제**가 위 두 상황에 놓였다 (서 있던 다리가 끊김, 또는 서 있던 칸을 받치던 건물형 유닛이 파괴됨) | 파괴되지 않고 **허공에서 곧바로 기절 상태**가 된다. 기절한 사제는 **공중형 이동 유닛(비행 수송)으로 포획할 수 있는 상태**가 된다 |
| 허공에 떠 있는 **기절한 사제**의 그 자리에 **다리를 다시 건설**해 서 있을 수 있는 칸이 생겼다 | 사제의 **체력이 절반 이상이면 기절에서 다시 회복**된다(자유 상태로 복귀). 포획되지 않은 상태였을 때의 이야기다 |
| 같은 상황의 사제 이외 지상 보행형 유닛 | 해당 없음(이미 낙하해 파괴되었으므로 다시 서 있을 일이 없다) |

- 이 동작은 사용자 보고이며 exe에서 낙하·기절 전환 코드를 직접 확인하지는 않았다. 원본 단서는 [bridge-pieces.md 9절](../exe/bridge-pieces.md#9-남은-일)의 "새 수명 ≤ 5 인 칸 위 이동체 낙하(`FUN_004202f0`~`FUN_00426120`)"다.
- 허공에 뜬 사제의 자리에 다리를 다시 놓았을 때의 회복은 사용자 보고다(2026-10-01). 보고에 없는 부분은 **미확인**이다: 회복이 다리가 놓인 즉시인지 약간 뒤인지, 체력 "절반 이상"의 경계(정확히 절반일 때), 체력이 절반 미만이면 기절이 그대로 유지되는지(이 경우 기존 신전 회복 규칙을 따르는 것으로 가정), 다리가 놓이는 순간 사제 주변 칸 중 어디까지를 "다시 서 있을 수 있음"으로 보는지(사제가 서 있는 그 칸만 본다고 가정), 사제가 서 있던 칸이 건물형 유닛이 만든 받침(`createsisland`)이었고 같은 자리에 건물형 유닛을 다시 지어도 같은지.
- 사용자 보고에 없어 **미확인**인 것: 낙하에 걸리는 시간(즉시인지 짧은 낙하 연출 뒤인지), 허공에 뜬 기절 사제가 이후 낙하·소멸하는지 계속 떠 있는지, 허공의 사제가 자기 신전 근처에서 회복하는지, 낙하하는 사제가 들고 있던 결정이 어떻게 되는지, 낙하 때 소리·효과, 다리 칸이 아니라 적 소유 다리나 섬 위가 "지지 칸"인지. 구현 전에 영상·원본 관찰로 확인하고 확인되기 전에는 3.4절의 임시값을 쓴다.

### 1.2 경로 고정 문제

- 이 증상(옛 경로를 그대로 따라감)은 사용자 보고이며, 원본 exe에서 경로 저장·갱신 코드를 직접 찾아 확인하지는 않았다. 관련 원본 단서는 [bridge-pieces.md 9절](../exe/bridge-pieces.md#9-남은-일)의 "새 수명 ≤ 5 인 칸 위 이동체 낙하(`FUN_004202f0`~`FUN_00426120`)"다. 낙하 판정 자체를 아직 칸 단위로 옮기지 않았다.
- 같은 결함이 사제 운반에도 있었다는 사용자 확인은 [sacrifice.md](sacrifice.md)에 이미 기록돼 있다.

## 2. 결정 1 — 이동 중 길이 끊기면 **경로를 다시 찾는다** (원본 결함을 재현하지 않음)

**클론은 원본의 이 결함을 의도적으로 고친다.** 이동 작업은 "처음 정한 경로"가 아니라 "목표"를 기억하고, 길이 바뀌면 현재 위치에서 같은 목표로 길을 다시 찾는다.

규칙(구현 지침):

1. 이동·수확·포획·운반·사제의 제단 이동은 모두 같은 규칙을 쓴다. 명령이 몇 개든(앞으로 일반 "이동" 명령이 생겨도) 한 곳의 공통 재탐색 규칙을 거친다.
2. 길이 바뀌었는지는 다리 격자 버전(`BridgeGrid.Version`)으로 본다. 다리가 놓이거나, 금 가거나, 무너지거나, 건물형 유닛 파괴·회수로 약해질 때마다 버전이 오른다.
3. 재탐색은 **이동 직전**에 한다. 붕괴·약화는 틱 끝(다리 붕괴 단계)이나 전투 단계에서 일어나므로, 다음 틱의 이동 단계에서 길을 확인한 뒤 움직이면 이동체가 이미 사라진 칸으로 들어서는 일이 없다.
4. 새 길이 있으면 **현재 칸에서** 새 경로로 이어서 간다. 이동 진행량은 0으로 되돌린다.
5. 새 길이 없을 때의 처리는 3절에서 정한다.
6. **재탐색은 낙하 규칙(1.1절)을 없애지 않는다.** 재탐색은 "옛 경로를 따라 허공으로 걸어 들어가는" 일만 막는다. 이동 중이든 서 있든, **지금 서 있는 칸의 다리가 끊어지는 것**은 경로를 아무리 잘 찾아도 일어날 수 있는 상황이므로 낙하 규칙은 3.4절대로 반드시 구현한다.

## 3. 클론 현황 점검 — 경로 재탐색은 이미 있고, **낙하 규칙이 없다**(구현 필요). 그 밖에 보완할 점 3가지

### 3.1 이미 되어 있는 것 (코드로 확인)

| 이동 | 위치 | 재탐색 |
|---|---|---|
| 사제 수확 왕복 | `BattleSession.Harvest.cs` `UpdateHarvests` | 다리 버전이 바뀌면 목표(가이저·신전)까지 다시 찾는다 |
| 수송 유닛의 포획·제단 운반·내려놓기, 사제의 제단 이동 | `BattleSession.Sacrifice.cs` `UpdateUnitMoves`, `UnitMoveTask` | 다리 버전이 바뀌면 `MoveGoal`(목표 오브젝트 또는 고정 칸)까지 다시 찾는다. 내려놓기(`DropPriest`)도 2026-10-01 수정으로 포함 |
| 틱 순서 | `BattleSession.cs` `Step` | 명령 → 수확 이동 → 수송·사제 이동 → … → 전투(건물 파괴로 다리 약화) → … → 다리 붕괴. 붕괴 직후 다음 틱 이동 단계에서 버전 차이를 먼저 확인한다 |

경로 쪽은 원본의 "옛 경로를 따라가다 추락" 결함이 새 클론에 옮겨져 있지 않다. 그러나 **이동체가 지지 칸을 잃고 낙하·파괴되는 처리(1.1절)는 클론에 전혀 없다**(이동체 낙하 미구현). 칸이 사라진 이동체는 그대로 허공에 서 있고, 재탐색이 허공에서 이웃 칸으로 걸어 나가게 해 주기까지 한다(3.2절 2번). 이것은 원본과 **다른 동작이므로 구현해야 할 누락**이다.

### 3.2 보완이 필요한 점 (코드 수정은 이 문서 범위 밖, 후속 구현 대상)

1. **재탐색 실패 시 조용히 작업이 사라진다.**
   - 수확 사제는 길이 없으면 작업이 통째로 취소되어(`_harvestTasks.Remove`) 다리가 다시 이어져도 스스로 돌아오지 않는다. 수송·운반 이동도 같다.
   - 어떤 이벤트도 내지 않아 플레이어가 이유를 모른다.
   - **권장 결정:** 길이 없으면 작업을 취소하지 말고 **"길 막힘 대기"** 상태로 둔다. 다리 격자 버전이 바뀔 때마다 다시 시도하고, 길이 열리면 같은 작업을 이어간다. 목표 오브젝트가 사라졌거나 이동체가 기절·포획되면 그때 취소한다. 대기로 들어갈 때 `MoveBlocked`류 이벤트(대기 시작·재개)를 한 번씩 낸다. 대기 중 사제는 제자리에서 있고 점유를 유지한다. (구체적인 대기 한도 시간·재시도 간격은 정하지 않았다. 처음에는 "버전이 바뀔 때만 재시도, 한도 없음"으로 시작하고 필요하면 조정한다.)
   - 이 결정은 [희생 의식 문서](sacrifice.md)의 "재탐색 실패 시 운반 중단"을 바꾸므로, 구현할 때 해당 문장과 `DropPriest_RecomputesRouteWhenBridgeIsCutMidTransit` 테스트(실패 시 이동이 멈추는지 확인)의 기대값도 함께 갱신한다.
2. **이동체가 서 있는 칸 자체가 사라졌을 때의 규칙이 없다 → ✅ 결정됨: 원본과 같이 낙하 규칙을 구현한다(3.4절).**
   - 현재 재탐색은 시작 칸이 지나갈 수 있는 칸인지 보지 않는다. 시작 칸이 빈 허공이어도 이웃 섬·다리로 걸어 나갈 수 있어 사실상 "허공에서 구조되는" 동작이 된다(코드 읽기로 확인, 테스트 없음). 원본에서는 이 상황에서 지상 유닛이 낙하해 파괴되고 사제는 허공에서 기절한다(1.1절, 사용자 확인). 즉 이 구조 동작은 **원본과 다르므로 없애야 한다.**
   - 낙하 규칙이 있어도 **다리가 사라지기 전에 경로를 피하는 것**(아래 3번)은 여전히 가치가 있다. 피할 수 있는 경우에는 피하고, 서 있는 칸이 무너지는 경우처럼 피할 수 없을 때만 낙하가 일어난다.
3. **금 간 칸을 피하지 않는다.**
   - 경로는 네 방향 최단 칸 수 하나만 기준이며 다리 상태(금 간 칸·수명)를 보지 않는다. 곧 사라질 칸을 지나는 경로를 고를 수 있다.
   - **권장:** 재탐색 비용에 금 간 칸 가중치를 둔다(금 간 칸은 일반 칸보다 높은 비용, 같은 비용이면 기존 방향 순서로 결정성 유지). 단단한 칸은 가중치를 낮출 수도 있다. 구체적인 가중치 값은 원본 낙하 판정(`FUN_004202f0`~`FUN_00426120`) 분석 뒤에 정한다.
4. **이동 구현이 두 갈래다.** `PriestHarvestTask`(수확)와 `UnitMoveTask`(수송·사제 이동)가 같은 이동·재탐색 논리를 따로 복제한다. 일반 "이동" 명령을 추가하기 전에 공통 이동 작업 클래스와 하나의 `FindMovePath`(지금 이름은 `FindHarvestPath`)로 합치는 것을 권장한다. 그래야 재탐색·대기 정책이 한 곳에서만 바뀐다.

   그 밖에 결정성(같은 초기 상태·같은 명령열 → 같은 결과)을 지키기 위해 재탐색의 이웃 순서·동률 처리는 지금처럼 고정한다. 새 가중치를 도입해도 동률일 때는 기존 순서(북·동·남·서)를 따른다.

### 3.3 구현 때 추가할 테스트 (제안)

- 수확 중인 사제가 다리를 반쯤 건넌 뒤 그 다리 구간이 무너지고 **우회로가 있으면** 같은 목표로 우회한다.
- 우회로가 없으면 **대기** 상태가 되고, 다리를 새로 이으면 같은 틱 또는 다음 틱에 재개한다(작업 소멸 없음).
- 건물형 유닛 파괴로 근처 다리가 약해져도 같은 재탐색 규칙이 적용된다.
- 같은 명령열을 두 번 실행해 체크섬이 같다(결정성). 대기·재개 상태는 체크섬에 들어가야 한다.
- 낙하 규칙은 3.4절의 시험 목록으로 따로 고정한다.

### 3.4 낙하 규칙 구현 요구 (원본 재현, **구현 필수**)

**지지 칸**: 지상 보행형 이동 유닛이 서 있는 칸이 섬 칸이거나 다리 칸이면 "지지된다". 그렇지 않으면 허공이다. (적 소유 다리 위를 지지로 볼지는 미확인 — 우선 소유와 무관하게 다리 칸이면 지지된다고 본다. 그러면 경로 탐색이 쓰는 "내 다리만 통과"와 다르다는 점에 주의한다.)

**언제 검사하나 (결정성을 위해 고정)**
1. 한 틱의 모든 다리 변화(명령의 회수, 전투의 건물 파괴로 인한 약화, 붕괴 단계)가 끝난 **틱의 마지막**에 한 번 검사한다. 이동 단계에서는 검사하지 않는다(이동 직전 재탐색이 허공으로 들어서는 이동을 막는다).
2. 검사 대상은 지상 보행형이면서 포획·운반 중이 아닌 유닛 전부다. 오브젝트 번호 순서로 처리한다.
3. 비행형·공중 수송(`balloon`)·비행체는 대상이 아니다. 운반 중인 사제는 운반 유닛을 따라간다(운반 유닛이 비행형이면 지지 칸이 필요 없다).
4. 이동 중 "다음 칸으로 이동했더니 그 칸이 허공"은 재탐색이 막으므로 정상 흐름에서는 생기지 않는다. 그래도 막지 못한 경우(예: 재탐색이 대기 상태로 넘어가지 못하고 이동한 경우)에는 같은 검사가 잡는다.

**결과**

| 대상 | 결과 |
|---|---|
| 지상 보행형 유닛(사제 제외) | 낙하 → **파괴**. 공통 정리 `RemoveEntity`(선택 해제·점유 해제·이동 작업 취소·포획 관계 정리)를 거친다. 낙하 시간은 미확인이라 **임시로 즉시 파괴**하고 `UnitFell`류 이벤트를 낸다. 파괴로 인한 다리 약화·보상은 전투 파괴와 같은 경로를 쓸지 별도로 정한다(원본 미확인) |
| 사제 | 파괴하지 않는다. **그 자리(허공)에서 곧바로 기절 상태**가 되고, 수확·이동 작업은 취소한다. 기절한 사제는 비행 수송으로만 포획할 수 있다(지상 수송은 경로가 허공을 지나지 못하므로 도달 불가) |
| 허공의 기절 사제 자리에 지지 칸이 다시 생김 | **체력이 절반 이상이면 기절을 풀고 자유 상태로 복귀**한다(사용자 확인). 절반 미만이면 기절을 유지한다(임시 가정, 이후는 기존 신전 회복 규칙) |

**사제 기절·복귀 구현 시 점검할 기존 코드 (읽기 확인)**
- 기절은 `GameEntity.IsStunned` 플래그로 표현된다(`CanCapture`는 `IsStunned`만 본다). 허공 낙하 기절은 체력이 아니라 플래그를 직접 켜는 새 경로가 필요하다. 이 경로로 켠 기절은 체력이 절반 이상일 수 있으므로, 평소 기절(체력이 절반 이하로 내려가서 걸림)과 구별되는 **"허공 기절" 표지**(예: 허공에 있는 동안 계속 참인 상태 또는 별도 플래그)가 필요하다. 그래야 지지 칸이 생길 때 "허공 기절은 체력 절반 이상일 때 풀림"을 적용할 수 있다.
- **복귀 검사:** 3.4절의 틱 끝 검사에서 허공이 된 사제만 보는 것이 아니라, **이미 허공에 떠 있는 사제의 칸이 다시 섬·다리 칸이 되었는지도 매 틱 확인**한다(다리 격자 버전이 바뀐 틱만 확인해도 된다). 지지 칸이 생겼고 체력이 절반 이상이고 포획 상태가 아니면 `IsStunned = false`, 수확 작업은 자동으로 재개하지 않는다(사용자가 다시 명령해야 한다고 가정), 이벤트 `PriestRecovered`류를 낸다.
- **다리 배치 판정 충돌:** 다리 배치는 다른 오브젝트가 점유한 칸을 거부한다(`BridgeGrid`의 `_isOccupied`, `BattleSession` 점유 판정). 허공에 뜬 사제는 현재 점유를 유지하므로 **그 사제의 칸에는 다리를 다시 놓을 수 없다.** 원본은 다시 놓을 수 있었으므로, 허공에 뜬 사제는 지상 점유에서 빼거나(`Map.RemoveOccupant`) 다리 배치 판정에서 허공 사제를 무시해야 한다. 점유에서 뺄 경우 같은 칸에 다른 유닛이 놓이지 않는지도 같이 본다.
- 기절 사제 회복(`UpdateCombat`)은 자기 신전이 완공돼 있으면 체력이 차고 기절이 풀린다. 허공에 선 채 이 회복으로 **기절이 풀리면 허공에서 자유 상태가 되므로** 허공의 사제에는 이 신전 회복을 적용하지 않는다(임시. 원본 동작 미확인). 허공에서 기절이 풀리는 길은 지지 칸 복귀 하나뿐이다.
- `ReleasePriest`는 풀려난 사제를 `NearestStandable`로 가장 가까운 섬·다리 칸에 옮긴다. 수송 유닛이 허공 위(비행 수송)에서 파괴됐을 때 사제가 지면으로 순간이동하는 구조 동작이 되어, 원본 규칙(허공에서 기절)과 다를 수 있다. 구현 때 "내려놓는 칸이 허공이면 그 자리에서 기절 상태로 둔다"로 바꿀지 확인한다.
- 비행 수송의 사제 포획(`PickUpPriest`, `ArriveMove`)은 직선 경로와 `IsBeside` 판정을 쓰므로 허공의 사제를 집는 데는 큰 문제가 없어 보이나 테스트로 고정한다.
- 미션 이벤트 `PriestDead`·`Failed`(내 사제 없음)는 사제가 파괴될 때 발동한다. 허공 사제는 파괴되지 않았으므로 원본도 같은지 확인이 필요하다(허공에 뜬 채 영원히 포획되지 않는 사제가 미션 판정을 막지 않는지).

**시험 목록 (구현 때 추가)**
- 서 있는 지상 유닛(골렘 등)의 칸이 붕괴하면 그 틱 끝에 파괴되고 선택·점유·이동 작업이 정리된다.
- 이동 중인 지상 유닛은 우회로가 없을 때 대기 상태로 남고(재탐색 실패), 허공으로 걸어 들어가 낙하하지 않는다.
- 서 있는 사제의 칸이 붕괴하면 파괴되지 않고 기절하며, 수확 작업이 취소된다.
- 비행 수송이 허공의 기절 사제를 포획·운반할 수 있고, 지상 수송은 길이 없어 포획 명령이 `NoRoute`가 된다.
- 허공의 사제는 신전이 있어도 회복하지 않는다(임시 규칙).
- 허공에 뜬 사제(체력 절반 이상)의 칸에 다리를 다시 놓으면(허공 사제가 배치를 막지 않아야 한다) 기절이 풀려 자유 상태가 된다. 수확 작업은 재개하지 않는다.
- 같은 상황에서 체력이 절반 미만이면 기절을 유지한다. 체력이 정확히 절반일 때의 처리는 원본 확인 뒤 고정한다.
- 허공에서 기절한 채 포획돼 운반 중인 사제는 지지 칸이 생겨도 복귀하지 않는다(포획 상태가 우선).
- 사제 이외의 지상 유닛은 낙하해 파괴되므로 복귀 규칙이 적용되지 않는다.
- 비행형·공중 수송·비행체는 지지 칸 검사를 받지 않는다.
- 운반 중이던 지상 수송이 낙하해 파괴되면 포획 사제가 풀리되 허공이면 기절 상태가 된다(원본 확인 후 확정).
- 같은 명령열을 두 번 돌려 체크섬이 같다(기절·허공 상태가 체크섬에 들어가야 한다).

## 4. 결정 2 — 유닛 생산의 스톰 에너지 줄기(Stream of Power)는 **목적지에 어떻게든 도달해야 한다**

### 4.1 원본 동작

유닛을 생산 창에서 지도에 놓으면 워크샵(또는 아웃포스트, 템플)에서 **스톰 에너지(SP) 줄기가 지그재그로 날아가 배치 위치에 닿고**, 닿은 뒤에 유닛이 나타난다. 이 줄기도 경로를 탐색한다. 매뉴얼 근거: [game-manual.md](../sources/game-manual.md)("Stream of Power") · [PDF 매뉴얼](../sources/pdf-manual.md)("Power Stream이 적절한 에너지와 합쳐지면 유닛이 즉시 생성된다") · [도움말 정리](help-manual.md)(`The Stream of Power`). 줄기가 닿아야 하므로 본섬과 다리로 이어지지 않은 곳에는 생산할 수 없다는 조건이 붙는다.

- 줄기의 속도·궤적·소요 시간과, 줄기가 날아가는 도중 길(다리)이 끊겼을 때의 원본 동작은 **미분석**이다. 원본 exe에서 줄기 오브젝트를 만드는 곳(`Stream`·`Spirit` 계열)을 찾아 분석해야 한다.

### 4.2 클론 현황

- `BattleSession.Commands.cs` `ExecutePlaceUnit`은 판정을 통과하면 **그 틱에 유닛 오브젝트를 바로 만든다.** 줄기 오브젝트·이동 시간·경로가 없고, 유닛은 즉시 나타난다. 배치 판정(에너지 반경·빈 섬 연결 `IsConnectedToHome`)은 있다.
- 따라서 이 절은 **새로 구현할 기능의 설계 요구**이며 현재 코드와 충돌하는 결함이 아니다.

### 4.3 설계 요구: 줄기는 이동 불가 상태에 빠지지 않는다

유닛 이동과 달리 **줄기는 길이 끊겨도 포기하지 않는다.** 유닛 생산을 요청해 SP를 이미 낸 상태에서, 줄기가 "도착 불가"로 끝나 유닛이 영영 안 나오는 일은 허용하지 않는다. 설계 방안:

1. **1순위 — 지상(다리) 경로.** 출발지(워크샵·아웃포스트·템플)에서 배치 위치 둘레까지 `FindMovePath`와 같은 규칙으로 길을 찾는다. 길이 바뀌면 현재 위치에서 같은 목표로 재탐색한다(2절 규칙과 동일).
2. **2순위 — 공중 경로 전환.** 재탐색이 실패하면 줄기는 **그 지점부터 허공을 가로질러 직선(또는 완만한 곡선)으로 날아간다.** 이후에는 지상 경로를 더 찾지 않고 목적지까지 계속 이동한다. 줄기는 에너지 효과이므로 지형을 통과하는 표현은 허용한다. 줄기의 모양 변화(지그재그 → 직선)는 "경로 잃음" 신호가 될 수 있으므로 화면에서는 같은 줄기가 계속 날아가는 것처럼 보이게 하고, 색·형태를 바꿀지는 원본 화면 확인 뒤 정한다.
3. **도착 보장.** 줄기가 목적지에 닿으면 유닛을 만든다. 도착 전에 일어날 수 있는 변화는 아래처럼 처리한다.

   | 도중 변화 | 처리 |
   |---|---|
   | 길이 끊김(다리 붕괴·건물 파괴) | 2순위 공중 이동으로 전환, 도착까지 계속 |
   | 출발한 워크샵·아웃포스트·템플이 파괴됨 | 이미 날아간 줄기는 계속 도착시킬지(SP는 이미 소비됨), 소멸시키고 환불할지 **결정 필요.** 기본 권장: 이미 출발한 줄기는 도착시킨다. 단, 이것이 에너지 판정(공급원 반경)을 우회하는 수단이 되지 않도록 도착 시 판정은 하지 않는다 |
   | 목적지 칸이 사라짐(다리 끝에 놓았는데 그 칸이 무너짐) | 목적지가 유효하지 않으면 줄기를 소멸시키고 SP를 환불한다(유닛이 허공에 생기지 않게). 환불 여부·금액은 원본 동작 확인 뒤 정한다 |
   | 줄기를 쏜 플레이어·유닛 소유 변화 | 해당 없음(도착하면 쏜 플레이어 소유로 생성) |

4. **결정성.** 줄기의 이동은 고정 틱에서 같은 규칙으로 진행하고(소수 좌표 이동, 비행체 이동과 같은 방식), 상태(출발지·목적지·진행량·경로 모드)는 세션 체크섬에 넣는다. 같은 초기 상태·명령열은 같은 틱에 같은 유닛을 만든다.
5. **다른 줄기·유닛과 충돌 없음.** 줄기는 지상 점유를 만들지 않고 목적지 칸만 예약한다. 예약된 칸에는 같은 틱에 다른 유닛을 놓을 수 없다(배치 판정이 이미 막고 있어야 한다).

### 4.4 구현 때 확인할 것

- 원본에서 줄기가 날아가는 시간(초)과 속도, 유닛이 나타나는 정확한 순간(도착과 동시인지, 몇 프레임 뒤인지).
- 줄기를 비행체처럼 소수 좌표로 보여줄지 칸 단위로 보여줄지. 비행체 이동 코드(`FlyerFlight.cs`, [비행체 문서](flyers.md))를 재사용할 수 있는지.
- 줄기가 이동 도중 건물형 유닛과 충돌하는지(하지 않는 것으로 가정).
- 줄기가 다리 위를 지그재그로 가는 모양을 그릴 때 경로 재탐색으로 모양이 갑자기 바뀌지 않도록 하는 방법(화면 표현 문제).
