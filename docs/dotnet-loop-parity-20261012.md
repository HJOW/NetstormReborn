# dotnetpj 실제 화면 루프·직전 그리기 기준 제한

작업 PC: `HJOW-Athlon`, 2026-10-12. [9-1 A](../LEFT_JOBS.dotnetpj.md#original-parity-plan)의 화면 갱신 후속 단계다. **A 전체 완료는 아니다.** [앞 단계](dotnet-frame-parity-20261011.md)의 실제 프레임 명령·다리 스캔에 실제 화면 루프를 연결했다.

## 문제와 원본 근거

변경 전 `NetstormGame.ApplyFramePacing`은 MonoGame의 고정 화면 간격을 14ms로 설정했다. 처리 지연 뒤에는 여러 `Update`를 합성해 실행하고 한 번 그릴 수 있으며, 긴 경과 시간에는 프레임워크의 상한이 적용될 수 있었다. `BattleSession.FrameSeconds`에 전달하는 값도 실제 불규칙 간격을 항상 보존하지 않았다.

원본 10.78 `00436450`은 게임 시계 정지 중에는 기다리지 않는다. 실행 중에는 벽시각 − 직전 그리기 시각이 `1 / maxFPS` 이상인지 확인하고, 실제 현재 시각을 저장한 뒤 그린다. 늦은 프레임은 즉시 그리며 옛 예정 시각을 따라잡지 않는다. `00460d70`은 `timeGetTime()`을 읽는다. 현재 PC의 기존 정밀 디컴파일과 [cpppj `Client::Frame`](../cpppj/src/client/ClientMain.cpp), [GameClock](../cpppj/src/o/GameClock.cpp), [메인 루프 분석](exe/main-loop.md) 2~5절을 대조했다. 새 디컴파일·원본 게임 실행은 없었다.

## 구현

- MonoGame을 가변 화면 루프로 두어 정상 루프에서 갱신·그리기를 한 번씩 호출한다. MonoGame의 초기 준비 갱신은 별도이며 안정된 루프의 짝을 검사한다.
- `FrameWallClock`은 Windows에서 원본과 같은 WINMM `timeGetTime()`을 읽는다. DWORD 감김은 펼쳐 사용하며, 게임 스레드에서만 호출한다. 시스템 타이머 해상도를 바꾸지 않는다. 다른 플랫폼에는 밀리초 단위 Stopwatch 경로를 둔다.
- `FrameLoopClock.BeginFrame`에서 실제 시각을 한 번 고정한다. 첫 갱신은 로딩 시간을 제외하고, 이후 실제 밀리초 차이를 상한 없이 세션·카메라·애니메이션·자동 검사에 전달한다. 알림의 그리기 타이머도 같은 경과 시간을 사용한다.
- 그리기 직전에 직전 그리기부터 지난 시간과 `1 / maxFPS`를 비교한다. 게임 시계 정지·무제한·늦은 프레임은 대기를 생략한다. 대기 뒤의 실제 그리기 시각을 다음 기준으로 저장한다. 현재 대기는 Sleep/Yield로 CPU를 양보한다.
- `GameClockPaused`는 세션 정지·튜토리얼 창·지식 창의 실제 시간 중단 상태를 그리기 제한에 전달한다.
- 명시적인 UI 검사 명령 `stall 1~5000`과 `trace-detail`을 추가했다. 실제 지연을 한 번 삽입하고 외부 검사에서 그 다음 프레임의 수치를 읽는다. 일반 실행에는 지연을 삽입하지 않으며 진단 수치를 사용자 화면에 표시하지 않는다.

## 검증

Release 빌드 경고·오류 **0**. 전체 단위 **983개**(Assets **331** + Core **652**), 실패·건너뜀 **0**. 새 `FrameLoopClockTests` **15개**는 첫 프레임, 불규칙/1.2초/0초 간격, 제한 경계, 정지/무제한, 늦은 그리기 기준 갱신, 정지 뒤 재개 기준, 큰 단조 시각·역행 거부를 검사한다. 새 원본 x86 기대값은 추가하지 않았으며 dotnetpj 원본 대조 누적 **49,007개**는 유지한다. 그리기 제한 분기는 정적 대조이며 원본 전체 루프의 실측 대조가 아니다.

새 실제 클론 창 **4회/68개 게임 내 단언 + 외부 32개 검사**가 통과했다. `tools/clone_loop_smoke.py`는 초기 지연의 최대값으로 판정하지 않고 **삽입한 지연 바로 다음 프레임**을 읽는다.

| 언어·화면 | maxFPS | 실행 중 700ms 지연의 실제 간격 | 정지 중 700ms 지연의 실제 간격 | 실행 세션 시각 증가 |
|---|---:|---:|---:|---:|
| 영어 1024×768 | 75 | 716ms | 706ms | 0.769초 |
| 한국어 1024×768 | 75 | 715ms | 706ms | 0.773초 |
| 영어 1280×720 | 30 | 715ms | 705ms | 0.850초 |
| 한국어 1280×800 | 0 | 718ms | 706ms | 약 0.770초 |

세션 증가량은 지연 앞뒤 진단 사이의 다른 화면 간격도 포함한다. 두 지연 직후 모두 직전 그리기의 갱신 수가 **1**이었다. 정지 중에는 틱·프레임 시각·스캔 커서·월드 표시 좌표가 같았으며 재개 뒤 사제가 실제 목표에 도착했다. 수치는 이 PC의 해당 실행 결과이며 다른 환경의 루프 간격을 보장하지 않는다.

기존 GUI **16회/386개 게임 내 단언**도 통과했다.

## 남은 범위

1. **A 나머지:** 이동·전투·건설·생산·수확·의식·AI·튜토리얼·애니메이션의 24Hz 틱과 화면 보간은 남았다. `FixedTimestep`의 따라잡기 **8틱 상한**도 유지한다. 긴 프레임에서 `FrameSeconds`가 모두 증가해도 `Seconds`는 뒤처진다. 입력이나 화면 루프를 고쳤다고 전체 게임 로직이 원본 시간이 된 것은 아니다.
2. PathProcess 전체의 경로 생성/꼭짓점 도착 시각·보행 진행/종료는 cpppj에서도 후속이다. 정지 중 새 경로의 보간 잔여량, 전체 절대 시각 이동과 원본 타이머는 이 근거를 확인하며 옮긴다.
3. 이번 제한은 정수 밀리초 차이로 비교한다. 원본 벽시각의 시작 오프셋·double 변환/감산 비트와 중첩 정지 누계를 통째로 이식한 것은 아니다. 정확히 나누어떨어지는 제한 경계의 부동소수 차이와 절대 게임 시계 연결은 후속 대조 대상이다.
4. **D 미판정:** 원본의 바쁜 대기와 현재 Sleep/Yield의 흔들림을 실제 원본 루프와 비교하지 않았다. 모든 환경에서 14ms라고 단정하지 않는다. 비활성 전체화면의 그리기 생략·원본 `sleepPerLoop`·우선순위도 별도 후속이다. Linux와 수직 동기를 켠 전체 동작을 새로 검증하지 않았다.
5. 이후 C의 기존 사용자 결정 항목 → B → D·E·F, Failed/TryAgain 창 폭, Graph/실제 표면 identity와 실제 캠페인 완주→저장→재실행→다음 미션 해제를 이어간다.

앞 단계 cpppj 변경을 유지했다. AGENTS.md·원본 자료 변경·커밋/푸시는 없었다. 마지막 디컴파일 수행 PC는 공통 최신 기록의 **HJOW-Athlon, 2026-10-12**(`gumptree` 9/9/9개 내보내기) 그대로다.
