## 실제 경로와 소유자

Program의 ClientPaletteGlobals가 같은 UIntBox를 Screen과 Game에 전달한다. 기존 네 인자 Game API도 화면의 저장소 자체를 인계하며 값을 복사하지 않는다. 다른 Client의 같은 값 상자와 명시 null은 base Game 생성 전에 거부한다. HostStartupColorMaps의 독립 API는 첫 Prepare에서 저장소를 인계하고, 이후 재구성과 새 화면도 같은 저장소를 요구한다. RawColorSortStartup의 기존 값 API는 같은 상자의 view다.

Screen의 saved는 고정 1,024BYTE이며 ScreenColor 256칸이 같은 메모리를 본다. 실제 FILE은 이 배열에 직접 기록한다. 776BYTE 파일의 768회 개별 RGB 읽기·예약BYTE 보존, 1,024BYTE의 단일 읽기, 짧은 읽기·예외 뒤 이전 tail, 두 번의 길이 조회와 적용 후 파일 반납을 유지한다. 기존 값형 로더와 새 Native 입구는 동일 clear/현재·논리 팔레트/색표/명암 후단을 사용한다. loaded의 callback 변경을 정상 복귀나 finally에서 되쓰지 않는다.

실제 Game의 DrawStartupScreen이 명시 파일 callback을 공급한다. 최초 경로는 실제 적용 위치에서 현재 GamePalSpec/fortPal로 계산하고, fort 전환은 기존 Cloud 부모가 완성한 NUL 경로를 받아 그대로 읽는다. 현재 ModeSet에 따른 clear 선택·구름 생성·난수·색표 준비 순서는 유지한다. 이전 eager GamePalette 읽기를 제거하여 Native 진입 전에 편의 decoder가 먼저 실패하거나 중복으로 화면 팔레트를 읽지 않는다.

입자용 Palette는 별도 불변 자산으로 필요할 때만 읽는다. CPP ClientMain의 GameAssets가 최초 palettePath로 별도 자산을 만들고 RawCampaignParticles가 그 Palette를 빌리는 경로를 대조했다. 따라서 HostMissionConstruction/Burning을 현재 날씨의 Screen.LogicalPalette로 바꾸지 않았다. 이 고정 자산 접근은 실제 화면 파일 로딩 완료와 구별하며, 모든 입자 색표의 원본 동일성 완료를 뜻하지 않는다.

잘못된 파일 길이의 실제 Game callback은 ErrorLog.RecordAssertion으로 연결했다. 기본 복귀 정책이면 기존 saved로 적용을 계속하며 진단 자체가 throw하면 선행 효과와 파일 정리를 보존한다. 편의 API의 기본 명시 예외는 유지한다. 원문 줄940은 기존 관측 근거이며 정확한 원문 expression/파일 문자열은 새로 확정하지 않았다. 로그의 한국어 설명과 `.\Screen.cpp`는 호스트의 진단 표기다.
