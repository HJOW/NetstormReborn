# webpj L3 확장: 네 번째 다리 조각과 다리 붕괴 스캔 초기화 (WB04-E1301, 2026-11-24)

[L3](webpj-l3-tutorial1-20261123.md) Tutorial1 단계표를 540프레임에서 680프레임으로 늘려 **네 번째 다리 조각**(카메라를 아래로 옮긴 뒤 놓기)까지 cpppj 와 대조했다. **결과: 화면은 처음부터 0픽셀이었고, 덤프에서 웹이 cpp 와 달랐던 원인(웹이 State 정리의 다리 붕괴 스캔 초기화를 빠뜨림)을 찾아 고쳤다.** 고친 뒤 200·300·345·364·400·470·540·680프레임 모두 화면 0픽셀이고 덤프 5개가 환경 의존 행(`sp`·`player:*`) 밖에서 같다.

## 입력(1024×768, Tutorial1)

세 번째 조각(500프레임)과 540프레임 뒤에 이어 붙인 단계이다. 놓을 자리는 cpp 오라클을 5초 안팎으로 90번 돌려(격자 x 205~285, y 190~280, 간격 10) 빨간 거절 모양이 0 인 좌표를 찾아 정했다. 격자에서 유일하게 놓인 좌표가 (255,210)이었다.

| 프레임 | 동작 | 인자 | 결과 |
| --- | --- | --- | --- |
| 560 | click-if | `MORE` | 단계 B→C 안내 창('Rotating Bridges') 다음 쪽 |
| 580 | click-if | `OK` | 안내 창 닫기 |
| 600 | click | `screen:30,735` | 미니맵을 눌러 카메라를 아래로 옮김(세 번째 조각이 화면 아래 끝에 닿아 있어 그냥은 이을 수 없다) |

## 발견: 웹은 매달린 다리를 영영 금 가게 하지 않았다

웹 e2e 를 처음 돌리자 화면은 모든 체크포인트(`c680` 포함)에서 0픽셀이었지만 `c680` 덤프에서 `pool` 해시와 `slot:15011`·`slot:15012` 만 달랐다. 두 슬롯은 세 번째 조각의 끝 칸이고 다른 점은 슬롯 +12 의 **수명 단어**(수명 비트는 3~6비트, 마스크 0x78) 하나였다: cpp `0x1d`(수명 3)·웹 `0x25`(수명 4). 화면이 같았던 까닭은 금 간 프레임으로의 교체가 수명이 5 이상에서 5 미만으로 넘어가는 순간에만 일어나는데(`applyLife` 의 `remaining < 5 && previous >= 5`) 이 칸은 이미 4 에서 3 으로 줄어 프레임이 바뀌지 않기 때문이다.

프레임별로 cpp·웹 덤프를 모아 좁히면(545·560·580·600·620·639~680) cpp 는 **600~620프레임 사이**(네 번째 조각을 놓기 *전*)에 두 칸의 수명이 줄었고 웹은 끝까지 변하지 않았다. 다리 붕괴 스캔(`RawBridgeDecayScan`, 슬롯 15000~23001 을 주기 10초로 한 바퀴씩 훑어 매달린 다리의 수명을 1씩 깎는다)의 상태를 읽어 보니:

- cpp `report` 의 `bridge_scan_global`: 범위 `15000 23001`·커서가 프레임마다 약 20씩 전진·기한 19.2 → 612프레임쯤 바퀴를 마쳐 커서가 15000 으로 돌아가고 기한 29.2. 새 바퀴 첫 프레임에 슬롯 15011·15012 를 방문해 수명을 깎았다.
- 웹: 범위가 **-1·-1**, 커서 -1 그대로. 기한만 19.2 → 29.2 로 갱신되고(첫 프레임의 스캔 자체 재설정) 범위가 비어 있어 어떤 칸도 방문하지 않았다.

원인: cpp 는 미션 시작 정리(`UberGump::CleanupNativeStateWorld(1)` → 효과 `Reset422490`, `ResetStateBridgeDecayScan`)에서 스캔 `first=15000·last=23001·cursor=15000·next=주기+게임 시각`을 다시 잡는다. 웹은 이 State 전체 정리를 아직 State 기계에 연결하지 않았고(`_clearPlayerSpForState` 주석), 정리 대상 중 난수·SP 쪽만 같은 자리에서 흉내 냈기 때문에 `Reset422490` 이 빠져 있었다. 이전 L3/L2 비교가 다 통과한 것은 매달린 다리가 없거나 스캔이 첫 바퀴를 돌 시점에 덤프를 찍지 않았기 때문이다. 실제 플레이에서는 **끝이 어디에도 이어지지 않은 다리가 시간이 지나도 금 가지 않고 영원히 남는** 차이였다.

## 수정과 확인

- `www/netstorm.js` `_clearPlayerSpForState()`: SP 비우기 뒤에 `resetStateBridgeDecayScan(storage.bridgeDecayScan, storage.bridgeDecayPeriod, clock.time().game)` 를 같이 실행한다(저장소·게임 시계가 없으면 생략). 이 함수는 인트로·메인 메뉴·미션 시작 세 정리 자리에서 부르므로 원본이 정리마다 스캔을 다시 잡는 것과 같다. 난수는 쓰지 않아 기존 난수 소비 순서는 그대로이다.
- 단위 시험 `tests/state-cleanup-bridge-scan.test.mjs`(3개): 범위·커서·기한(주기 + 게임 시각, 게임 시각을 float 로 줄이지 않음), SP 와 함께 초기화, 저장소·시계 없음. 초기화 호출을 끈 변형은 3개 모두 실패한다.
- 프레임별 스캔 상태(범위·커서·기한)가 100~680프레임 16곳에서 cpp 와 같다(커서 16720·18380·19900·21900·22380·…·22900→15040→16340, 기한 19.2→29.2).
- e2e `l3-tutorial1.spec.js` 가 680프레임까지 통과하고, 같은 오라클을 쓰는 `l2-tutorial1`·`fixed-time`·`menu-clouds`·`tell-escape`·`arrow-camera` 도 통과한다.
