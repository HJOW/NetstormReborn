# 0.781 장기 패킷 기록과 Root 소유자

ClientPacketRecord가 같은 실제 FrameTimeBox와 사용자 데이터 정책으로 선택적 기록 파일과 요청 DWORD를 보관한다. Root는 원문 PacketRecordOwner처럼 첫 조회 때 단일 소유자를 만들며 조회만으로 파일/폴더를 만들지 않는다. 현재 Source/Runtime/UI 정리 뒤 자기 파일을 닫는다. 435220 옵션 부모의 Requested reset은 실제 부모 연결 때 남겨 두고 임의 초기화 위치에 추가하지 않았다.

Open은 Close→enabled1→첫NUL 앞 이름의 leaf 검사→사용자 Diagnostics/w+b 순서다. 열기 실패의 FILE0/enabled1은 보존하고 선택된 쓰기에서 명시 오류를 낸다. Close는 enabled0→파일 닫기→FILE0이며 Requested를 바꾸지 않는다. Write는 진입 주소/sender 캡처 뒤 enable 관문을 지나 방향1BYTE·현재 wall8BYTE·프레임 low32 4BYTE·주소4BYTE·sender4BYTE를 쓴다. 그 뒤 현재 패킷+2 WORD 길이만큼 본문을 쓰고 flush한다. 인자length를 사용하지 않으며 잘못된 본문 길이여도 이미 쓴21BYTE 접두를 되돌리지 않는다. fwrite/flush/fclose의 무시 반환에 대응하는 IOException 처리도 원문처럼 앞선 효과를 취소하지 않는다.

실제 시스템 ucrtbase.dll의 _wfopen(w+b)로 읽기/쓰기 공유와 닫기0을 독립 관측했다. 제품과 관측 독자 모두 FileShare.ReadWrite를 사용한다. 이 플래그는 다른 읽기/쓰기를 허용한다([Microsoft FileShare 설명](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare?view=net-10.0)). _wfopen의 wide 경로와 오류 NULL 경계는 [Microsoft CRT 설명](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/fopen-wfopen?view=msvc-170)도 확인했다. 원본 게임을 실행한 관측은 아니다.

신규2건 포함 최종 집중13건이 통과했다. 실제 임시 사용자 파일로 두 방향의 고정 원문 바이트 형식, 현재 프레임/주소/sender,64비트 번호 low32,부분 버퍼 앞뒤와 미작성 꼬리,인자length 대신 현재 선언 WORD,파일 생성 지연/leaf/NUL,불량 본문보다 먼저 쓴 접두,파일 열기 실패의enabled1,NULL FILE 쓰기 거부,요청과 활성 파일의 분리를 확인했다. 프레임/초기화·사용자 경로 검사도 함께 통과했다. 첫 실행은 검사 독자의 ReadAllBytes 공유 모드가 기존 쓰기 핸들을 거부해1실패/1통과였고, 독자를 같은 읽기/쓰기 공유로 수정했다. 제품 형식/고정 기대 바이트를 바꾸어 통과시키지 않았다. 최초 필터의 미일치 클래스명도 최종 검사에서는 실제 NativePrefix/SharedFrame/UserDataRoot 클래스로 교체했다. 기존 nullable 경고 외 새 경고는 없다.

기존396fixture 항목/헤더/기대값을 모두 유지하고 PORT_MAP에4쌍을 추가했다. 이 구성요소의 별도 원문 fixture는 없으며 C# 결과로 새 기대값을 생성하지 않았다. 대표3시작 모두 종료0·덤프 전체바이트/지표0.780 일치·원본1392파일 불변이다. cpp_sync와 최종 감사 종료0이다. CPP/디컴파일 변경·게임의 외부 접속은 없고 실제 포획/희생·특정 적 공격·시나리오 승리는 재현하지 않았다.
