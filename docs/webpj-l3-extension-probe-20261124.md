# webpj L3 단계표 확장 탐색: 다리 조각 연속 배치 (WB04-E1299 탐색, 2026-11-24)

[L3](webpj-l3-tutorial1-20261123.md)의 400프레임 뒤를 이어 다리 조각을 연속으로 놓아 cpppj 와 대조했다. **반영(커밋)하지 못한 탐색**이다: 첫 어긋남이 나와 고치기 전에는 시험이 실패하므로 단계표·오라클 변경은 `git stash`(`l3-extension-wip-E1299`, 단계표·오라클 메타·e2e)와 아래 입력 목록으로만 보관했다.

## cpp 오라클으로 정한 입력(1024×768, Tutorial1)

기존 단계표(≤400프레임) 뒤에 다음을 더하면 cpp 가 다리 조각 두 개를 더 놓는다(각각 5초 안팎으로 실행해 탐색했다. 같은 입력의 두 번 실행은 PNG 가 바이트까지 같고 덤프는 환경 의존 행 `sp 1`만 다르다).

| 프레임 | 동작 | 인자 | 결과 |
| --- | --- | --- | --- |
| 420 | click | `screen:20,44` | 생산 창의 첫 칸 다리 조각을 집는다 |
| 440 | click | `screen:425,675` | 두 번째 조각이 섬 가장자리의 첫 다리 끝에 놓인다(다른 후보 `425,690`·`410,690`·`440,690`·`425,705`는 빨간 거절 모양) |
| 480 | click | `screen:20,44` | 다시 첫 칸 조각을 집는다 |
| 500 | click | `screen:440,705` | 세 번째 조각이 이어서 놓인다(후보 `425,715`·`425,725`·`450,690`·`465,675`·`470,685`는 거절) |
| 470·540 | snapshot·session-dump | `e470`·`c540` | 두 번째 놓은 뒤 화면, 세 번째 놓은 뒤 화면과 덤프 |

네 번째 조각은 화면 아래 끝(y>730)에 닿아 카메라를 옮겨야 놓을 수 있어 탐색을 멈췄다(F4/방향키로 카메라를 옮긴 뒤 이어야 한다).

## 웹과의 대조

- 논리 화면: 400·470·540프레임 모두 **0픽셀**(웹 e2e `l3-tutorial1.spec.js` 확장판으로 확인).
- 덤프 `c540`: `frame`(게임 시각)·`regular:2`·`pool`·`slot:15000`·`object:15000`이 다르다. 게임 시각을 10~540프레임 사이 20곳에서 비교하면 **410~520프레임은 모두 같고 530프레임부터 웹이 0.05초(2프레임) 앞선다**(cpp 18.475, 웹 18.525). 즉 세 번째 조각을 놓은 뒤 520~530프레임 어딘가에서 cpp 는 게임 시계가 2프레임 멈춰 있었고 웹은 흘렀다. 같은 시점에 새 다리(slot 15000)의 `+0x3a` 바이트가 웹 3·cpp 2 로 한 단계 앞서 있어 다리 품질(금이 간 정도) 단계 전환도 웹이 2프레임 빠르다. 화면 0픽셀은 이 전환이 아직 그림에 안 드러나서이다.
- 다음 확인(고칠 때): 520~530프레임을 프레임마다 덤프해 cpp 가 게임 시계를 멈추는 사건(튜토리얼 안내 창 열림 직전 관문, 다리 3개째 판정 `C1.` 조건 등)을 찾는다. 웹 쪽 후보는 튜토리얼 게이트의 프레임 지연 판정과 월드 정지 구간이다.

## 재개 방법

`git stash list`의 `l3-extension-wip-E1299`를 `git stash pop`하면 단계표(+7단계)·`oracle.json`·e2e(체크포인트 이름, `L3_DUMP_DIR` 웹 덤프 저장)가 돌아온다. 새 오라클 PNG(`e470.png`·`c540.png`·`c540.tsv`)는 stash 에 들어가지 않는 새 파일이라 위 입력을 `tools/cpp-oracle.mjs`의 `runCppScenario`(기준선 exe `extracted/webpj-oracle/225553df/Netstorm.exe`, 고정 25ms)로 다시 만들면 된다. 다시 만든 PNG 는 같은 바이트이다.
