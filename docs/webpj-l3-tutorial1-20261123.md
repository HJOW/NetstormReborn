# webpj Tutorial1 L3 입력 단계표 대조 (WB04-E1284~E1286, 2026-11-23)

L2(시작 시점의 덤프·화면)를 닫은 뒤([난수·시각 맞춤](webpj-state-install-rng-20261123.md)) 같은 입력을 cpppj 와 웹에 넣어 이후 프레임의 상태를 비교하는 L3 의 틀을 만들었다. 입력 단계표 하나를 두 쪽에 그대로 적용하므로 단계를 늘릴수록 게임 규칙의 어긋남을 프레임 단위로 잡아낼 수 있다.

## 구성

- 입력 단계표 `tests/fixtures/cpppj/candidate-225553df/tutorial1-l3/steps.json`: `[프레임, 동작, 인자]` 목록이며 동작 이름은 cpppj `--ui-script` 와 같다(`click-if` 라벨 클릭·`click`/`right` 화면 좌표 클릭·`key`·`session-dump`·`snapshot`).
- 오라클 `c200`·`c300`(Session 덤프 `.tsv`와 논리 화면 `.png`)과 출처 `oracle.json`: 기준선 실행 파일(`225553df`, 소리 끔, 고정 25ms)을 HJOW-Athlon 에서 `runCppScenario` 로 돌려 얻었다(cpppj 실행은 임시 스크립트였고 저장소에는 넣지 않았다. `tools/cpp-oracle.mjs` 의 `runCppScenario` 를 단계표와 함께 부르면 된다).
- 웹 `e2e/l3-tutorial1.spec.js`: 고정 시각 L2 와 같은 시작(메뉴 1프레임 → 미션 시작) 뒤 단계표를 적용하고 체크포인트마다 화면 **0픽셀**·덤프는 `sp`·`player:*` 행(환경 의존) 외 차이 없음을 확인한다.

## 현재 단계표와 결과

95 `MORE`(첫 안내 창) → 110 `OK`(스크롤 연습 창) → 200 체크포인트 → 260 `F4`(집으로 복귀, 튜토리얼 다음 단계) → 300 체크포인트("Bridges" 창) → 320 `OK` → 340 생산 창의 다리 조각 클릭(`click screen:20,44`) → 345 화면(조각을 집은 직후) → 360 섬 남쪽 가장자리에 놓기(`click screen:430,660`; 같은 단계표를 서쪽 가장자리 `310,585` 에 놓아 보면 붉은 칸이라 놓이지 않았다) → 364 화면 → 400 체크포인트. **E1286:** 놓을 수 있는 자리를 cpppj 에서 18곳을 훑어(`pool` 행의 다음 SID 가 오른 클릭) 찾았다. 새 다리가 생기고 생산 창의 첫 조각이 사라지는 400프레임까지 웹이 같다.

웹은 200·300·345·364·400프레임 모두 화면 0픽셀이고(345 는 집은 조각이 커서를 따라다니는 표시까지, 364·400 은 놓은 새 다리까지) 200·300·400프레임 덤프의 `random`·`frame`·`regular`·`object`·`slot`·`pool` 행이 cpppj 와 같다. 게임 시각도 프레임 단위로 같아(예: 280프레임까지 13.350, 두 번째 안내 창이 열려 정지하는 시각 13.45) 안내 창 전환·관문 재개·F4 처리의 프레임 수가 원본과 같다.

## 입력 프레임 규칙(실측)

cpppj 는 단계 프레임 N 의 시작에 입력을 큐에 넣어 그 프레임에서 처리한다. 웹은 DOM 사건이라 동작마다 주입 위치를 맞춰야 같은 프레임에 처리된다.

| 동작 | 웹에 넣는 프레임 | 까닭 |
| --- | --- | --- |
| 안내 창 단추 클릭(`click-if`·`click`·`right`) | N + 1 | 실측으로 정한 값이다(추정: 웹은 DOM 클릭을 사건 즉시 처리하고 cpppj 는 입력 큐를 프레임 안에서 소비해 창 닫힘·관문 재개가 한 프레임 뒤에 이어진다). 프레임 단위 일치를 위한 하네스 규칙이며 실제 플레이에는 영향이 없다 |
| 키(`key`)·화면 좌표 클릭(`click`) | N − 1 | 웹 입력 큐는 사건을 다음 프레임에 소비하므로(추정) 한 프레임 앞서 넣어야 cpppj 의 프레임 N 처리와 같다(`click` 은 E1299 에서 N+1 → N−1 로 정정) |

이 규칙 없이 모든 입력을 같은 프레임에 넣으면 단계 하나가 지날 때마다 0.025~0.075초씩 어긋난다(예: 키를 +1 에 넣으면 정지 시각이 3프레임 늦다). 어긋난 값으로 게임 상태를 비교하지 않도록 규칙을 시험에 고정했다.

## 확장: 다리 조각 연속 배치(WB04-E1299, 2026-11-24)

400프레임 뒤에 두 조각을 더 놓는 입력을 단계표에 더했다: 420 `click screen:20,44`(생산 창 첫 칸 조각 집기) → 440 `click screen:425,675`(섬 가장자리 첫 다리 끝에 놓기) → 470 화면 `e470` → 480 집기 → 500 `click screen:440,705`(이어서 놓기) → 540 화면·덤프 `c540`. 입력 위치는 cpp 오라클을 5초 안팎으로 여러 번 돌려 거절 모양(빨강) 없이 놓이는 좌표를 찾아 정했다([탐색 기록](webpj-l3-extension-probe-20261124.md)). 결과: 웹의 논리 화면이 `e470`·`c540` 모두 cpp 와 **0픽셀**이고 `c540` 덤프도 환경 의존 행 밖에서 같다. 그 사이 세 번째 조각을 놓은 뒤 단계 B→C 안내 창(`Rotating Bridges`)이 cpp 와 같은 프레임(525)에 열리고 게임 시계가 같은 시각(18.475)에 멈춘다.

**입력 프레임 규칙 정정.** 처음에는 모든 `click` 을 N+1 에 넣었으나 세 번째 조각에서 530프레임부터 게임 시계가 2프레임(0.05초) 어긋났다. 원인은 규칙이었다: **화면 좌표 클릭(`click`: 생산 창 조각 집기·월드에 놓기)은 키처럼 N−1** 에 넣어야 cpp 의 프레임 N 처리와 같다(`click-if`(안내 창 단추)는 N+1 그대로). cpp `report` 의 `mission_gate`(단계·잠금)를 프레임별로 읽어 cpp 는 단계 B→C 가 501프레임, 웹은 503프레임이었고(잠금 감소 속도는 둘 다 프레임당 2로 같음) 웹의 월드 클릭이 cpp 보다 늦게 처리된 것이 원인임을 확인했다. N−1 로 바꾸면 498~530프레임의 덤프 차이가 모두 0이다(N+1·N 에서는 500~502·526~530프레임이 다르고, N−2 는 499~500·525~530이 다르다). 기존 체크포인트(200~400)도 같은 규칙에서 그대로 통과한다.

## 확장: 네 번째 조각과 다리 붕괴 스캔 초기화(WB04-E1301, 2026-11-24)

540프레임 뒤에 560 `MORE`·580 `OK`(단계 B→C 안내 창 닫기) → 600 미니맵 클릭(`screen:30,735`, 카메라를 아래로) → 620 조각 집기 → 640 `click screen:255,210`(네 번째 조각 놓기) → 680 화면·덤프 `c680` 을 더했다. 자리는 cpp 오라클 90회 격자 탐색으로 정했다. 화면은 0픽셀이었고 덤프에서 **웹이 State 정리의 다리 붕괴 스캔 초기화(`Reset422490`)를 빠뜨려 매달린 다리의 수명이 줄지 않던 차이**를 찾아 `_clearPlayerSpForState` 에 더해 고쳤다([기록](webpj-l3-bridge-decay-reset-20261124.md)). 이제 200~680프레임 체크포인트가 모두 화면 0픽셀·덤프 일치이다.

## 앞으로

단계표를 늘려 같은 방식으로 비교한다: 튜토리얼 단계 C→D(간헐천이 열리고 다리를 간헐천까지 잇기), 사제 선택·이동, 건설·생산. 어긋나는 첫 프레임이 곧 고칠 규칙 차이이다. 이 틀이 LEFT_JOBS M3/L3 의 시작이다.
