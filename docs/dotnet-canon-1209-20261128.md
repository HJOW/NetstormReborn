# 1.209 DesktopGL 창의 실제 HWND와 DirectSound 초기화

실제 SDL 창의 HWND를 기존 DirectSound 초기화에 연결했다. 생성자 예외 정리 보강 뒤 최종 증분 빌드 오류0·집중17/17·같은 실제 Main 종료0을 확인했다. 별도 Explicit 실제 음향 장치1/1, 앞선 대표3진입/비음소거1진입과 최종 Main의 기존 덤프·화면 보존은 아래에서 검사 경계별로 구분한다. 장기 음악/옵션/SceneMusic/전체 State 조립 완료는 아니다.

## 실제 창 핸들 연결

MonoGame DesktopGL의 `Window.Handle`은 SDL이 생성한 창 포인터다. Windows DirectSound 초기화에 그 값을 HWND로 그대로 넘기던 경계를 고쳤다. `WindowsSdlWindow.NativeHandle`은 같은 적재 SDL DLL의 실제 버전을 채우고 `SDL_GetWindowWMInfo`로 Windows HWND를 얻는다. 조회 성공·Windows 하위 시스템·비영 HWND·`IsWindow`를 확인하며 추가 DLL 참조만 반납한다. SDL 창이나 Windows 창의 수명은 소유하지 않는다. 호출자는 최종 창 생성 뒤 UI 스레드에서 같은 DLL이 소유한 생존 SDL 창만 전달한다. 임의/이미 반납한 포인터를 안전하게 검사하는 API는 아니다. 공식 근거: [MonoGame 3.8.5.1 SDLGameWindow](https://raw.githubusercontent.com/MonoGame/MonoGame/v3.8.5.1/MonoGame.Framework/Platform/SDL/SDLGameWindow.cs), [SDL2 SysWM 정의](https://raw.githubusercontent.com/libsdl-org/SDL/release-2.32.10/include/SDL_syswm.h).

`ClientHostGame.ColorMaps.cs`의 최초 음향 생성 분기를 명시적인 null 검사로 두고 해석한 HWND를 기존 HostMissionAudio 생성자에 전달한다. 같은 위치에서 SDL 포인터/실제 HWND를 기록하고, HostMissionAudio는 실제 `_device.Initialize` 반환에 따라 성공 HWND 또는 실패 위치를 기록한다. 이번 단위는 기존 `Enabled` 조건부 초기화 정책을 유지한다. 최초 sound0/music1·공통 Mute·장기 음악 owner의 새 조립 정책은 [후속 계획](dotnet-audio-owner-followup-1206-20261128.md)의 별도 범위다.

새 SDL 검사는 직접 만든 숨긴32×32 창에서 SDL/Windows 핸들이 서로 다르고, 반복 조회가 같으며, HWND가 현재 프로세스에 속하고 보이지 않음을 확인한다. 자기 창과 추가 SDL video 참조만 반납한다. SDL 전역 초기화/종료는 비병렬 collection으로 제한한다. 다른 한 검사는 비영 SDL 포인터가 없으면 native 조회 전에 거부한다.

`extracted/dotnet-ui-hwnd-1209-baseline/run.json`은 음소거 대표3미션 thewarbegins·tutorial1·surrounded, `extracted/dotnet-ui-hwnd-1209-unmuted/run.json`은 비음소거 thewarbegins 1회를 보존한다. 모두120프레임·고정25ms·종료0이며90프레임 덤프는 각각 기존1.173 DN `f090.tsv`와 바이트가 같다. 비음소거 입력은 sound1·soundVolume1·music0·musicVolume1이다.

## 같은 실제 Main의 진단 보존

root는 PowerShell STA에서 같은 동결 Netstorm.dll의 실제 Program.Main을 호출하고, Main의 using/Game.Dispose가 끝난 뒤 검사 WARN 한 번으로 기존 메모리 ring을 파일에 보존했다. 제품 State·장치 준비 표식·Runtime을 외부에서 바꾸지 않았다. PowerShell 호스트에는 제품 apphost의 native 탐색표가 없어 같은 배포의 SDL2.dll/openal.dll을 명시 적재해 참조를 유지했다. 호출 명세/스크립트는 `extracted/dotnet-ui-hwnd-1209-ring/invocation.json`·`extracted/dotnet-1209-ring.ps1`에 있다.

성공 실행은 root 실행 세션4895 종료0이며 `extracted/dotnet-1209-ring-pass.log`와 `extracted/dotnet-ui-hwnd-1209-ring/user-pass/logs/20261128151451.log`에 보존했다. 실제 INFO는 SDL=`0x2422F769C60`에서 HWND=`0x1F50680`을 얻었고, 뒤 장치 초기화 성공 로그도 같은 HWND=`0x1F50680`을 기록한다. 이 성공 문장은 `_device.Initialize`의 실제 bool 반환에서 선택된다. 해당 주소는 이 실행의 관측값이지 고정 주소가 아니다. 성공 로그의 WARN 한 개는 Main 종료 뒤 진단 보존 표식이며 장치 오류가 아니다.

생성자 예외 정리 보강과 최종 빌드 뒤 같은 실제 Main wrapper를 다시 실행해 종료0을 확인했다. 최종 자료는 `extracted/dotnet-ui-hwnd-1209-ring/final-evidence.json`·`extracted/dotnet-1209-ring-finalbuild.log`·`extracted/dotnet-ui-hwnd-1209-ring/user-finalbuild/logs/20261128151632.log`다. SDL=`0x13B2E239C60`→HWND=`0x23F0042`와 같은 HWND의 실제 장치 초기화 성공을 기록했으며, fatal/device_failure 배열은 비어 있다. 이 최종 실행도90프레임 덤프가1.173 DN과 같고 여섯 화면이1.189와 각각0픽셀 차이다. 최종 Netstorm.dll SHA는 `b33e64423f75ce749120da13ae57aa2035ffb559c599df512b989b834a88177d`이며 apphost와 나머지 관리 DLL4개는 앞선 직접 진입 기록과 같다. 이 wrapper 추가 실행 전후 보호 파일 SHA를 별도로 수집하지 않았으므로, originals1,392파일 불변 판정은 앞선 baseline/unmuted 묶음의 근거로만 둔다.

진단 wrapper의 앞선 실패는 별도로 남긴다. SDL 탐색 실패2회는 `dotnet-1209-ring.log`·`dotnet-1209-ring-rerun.log` 및 각 user/user-rerun 로그에 있으며 AppContext 설정만으로 SDL2.dll을 찾지 못한 호스트 구성 실패다. 배포 native DLL을 명시 적재한 뒤, 스냅샷 경로에 저장소 루트가 중복된 실패2회가 `dotnet-1209-ring-native.log`·`dotnet-1209-ring-final.log` 및 user-native/user-final 로그에 있다. 이 실패 네 건을 성공으로 바꾸거나 위 직접 apphost 진입 결과와 합치지 않는다.

## 최종 보강과 남은 범위

성공 Note가 생성자 내부 장치 초기화 뒤 예외를 던지면 아직 외부에 설치되지 않은 owner가 장치를 남길 수 있어, 같은 생성자에 자기 `_device.Dispose` 후 최초 예외/스택을 유지하는 최소 보호를 추가했다. 정리 예외는 원래 예외의 진단에만 덧붙이고 실패한 로그를 다시 호출하지 않는다. 보강 뒤의 정상 경로 빌드/집중/실제 Main 결과는 위 최종 자료로 확인했다. 실제 로그 쓰기 실패의 fault 주입과 공통 nonthrow 로그 adapter는 장기 음향 owner 후속에서 별도로 검사한다.

실제 HWND 입구와 기존 효과음 장치의 성공 관측을 음악 스트리밍 제품 연결 완료로 확대하지 않는다. HostMissionAudio의 두 음악 채널/Runtime/Selection 장기 조립, 옵션 재해석·공통 Mute 및 별도 메뉴 음향 통합, SceneMusic의 공통 RNG/현재 getter/날씨/Start·Frame, 전체 State/Replace 왕복과 실제 AI 진행·남은 미니맵1픽셀은 후속이다. 이 단위는 보호 자료 수정 작업을 하지 않았으며 보호 SHA의 직접 확인 범위는 앞서 구분한 두 묶음이다.
