# Tutorial1 시작 상태의 L2 대조: 실제 앱 덤프 (WB04-E1129)

4D-10b(L2 판정)의 남은 일이었던 "브라우저 Client 의 실제 Session 덤프 호출과 Tutorial1 대조"를 처음으로 수행했다. 앱에 검사 전용 `Netstorm.sessionDump()` 를 추가해(원본 `UberGump::SessionStateDump`, `core/session-state-dump.js` 의 판번호 1 형식 사용) 실제 Chromium 에서 Tutorial1 을 시작한 직후의 덤프를 저장된 cpppj 기준선(`tests/fixtures/cpppj/candidate-225553df/tutorial1/oracle/tutorial1/load.tsv`, 고정 25ms 시각·프레임 90)과 행별로 비교했다.

## 결과

웹은 실제 시각으로 돌아 시계·난수가 기준선과 다르므로 **시간 의존 값을 뺀 구조 일치**를 확인했다. 기준 1,963행·웹 1,961행이며 슬롯 841개 중 **753개가 원문 바이트까지 완전 일치**한다.

| 구분 | 내용 |
| --- | --- |
| 일치 | `kernel`(프로세스 6개와 각 Form·부모), `alliances`, `hidden_players`, `graph` 251칸, `totals`, `totalmade`, SP 초기화와 소유자 1~8 값, `process` 목록, 슬롯 대부분 |
| 다름(시간·난수) | `frame`(시계), `random`(난수 상태), `regular:1~6`(정기 프로세스 시각), `pool`(풀 해시), SP 행의 분산 오프셋·소유자 0 값(실행마다 난수) |
| 다름(슬롯) | 애니메이션 프레임(+36..39, 88개 슬롯 중 82개)·위상(+33)·앰비언트 객체 나이(+31)·SID 15001 의 +42(시간에 따라 오르는 카운터)·해시 체인 연결(+4·+5)과 앰비언트 바람 객체(SID 0 의 개수 바이트, 15·16·17: 기준선에는 3개, 웹에는 시점에 따라 1~3개) |
| 원인 미분류 | Player 기록 9개의 앞 4바이트(원본 힙 주소 잔재처럼 환경마다 다른 값으로 보임), Player 1 의 +0x68·+0x69(기준선 0x02c0, 웹 0) |

- 이로써 월드 객체(저장 Fort 의 섬·사제·신전·간헐천·섬 사물 등)·Player 배치·동맹·Graph·장부·Kernel 이 cpppj 와 같다. 이전 단위(E873·E874)가 Node 에서 확인한 "안쪽 613개 일치·경계 45개 후보" 구간도 실제 앱 덤프에서는 슬롯 원문이 일치해, 앱 설치 경로가 같은 테마·소유 상태를 만든다.
- 결정론을 더 올리려면 앱에 고정 프레임 시계(`ClientTimeSource.enableFixed`)와 cpppj 와 같은 시작 프레임 수·고정 유닉스 초를 맞춘 실행 모드를 더해야 한다. 그러면 `frame`·`random`·정기 프로세스 시각·풀 해시·앰비언트 객체·SP 오프셋의 차이도 비교 대상이 된다. 이 단위에서는 만들지 않았다.

## 시험

새 `e2e/l2-tutorial1.spec.js`(Chromium)가 위 허용 범위를 그대로 단언한다 — 허용하지 않은 행의 차이·누락·추가, SP 소유자 1~8 값·초기화 여부, 허용 밖 Player 바이트, 허용 밖 슬롯 바이트·누락·추가, 슬롯 수 차이 3개 초과가 있으면 실패한다. 연속 여러 번 실행해 같은 모양으로 통과함을 확인했다(첫 실험 중 SID 15001 의 +42 카운터와 앰비언트 슬롯의 내용이 실행마다 달라 허용 범위에 넣었다).

## 남은 일 (4D-10b)

- 고정 시각 실행 모드로 `frame`·`random`·정기 프로세스·풀 해시까지 같게 만들어 행 전체 일치 판정을 한다.
- 두 번째 기준선 덤프 `later.tsv`(프레임 130, 시작 뒤)와 L3 입력 단계표 대조, 첫 프레임 논리 화면(`load.png`) 대조는 아직이다.
- Player 기록의 앞 4바이트와 Player 1 의 +0x68·+0x69 원인 규명.
