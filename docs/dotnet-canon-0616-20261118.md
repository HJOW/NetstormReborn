# 0.616 지면 테이블 파일 일치와 섬별 J-기준점 발견 (원인 좁히기)

- 일시: 2026-11-18, HJOW-Athlon
- 범위: R4-2 지면 프레임 불일치의 원인 좁히기. DN 테이블이 실제 자산 바이트와 같은지 파일 기준으로 고정하고, cpp 덤프의 섬별 J-기준점 분리(서쪽 섬 280·동쪽 섬 244)를 증거로 남긴다. 제품 코드 변경은 없다.
- 목표: 0.615에서 CRT·J 경로를 고정한 뒤, 다음으로 의심되는 테이블·성장 지도·후처리 덮어쓰기를 하나씩 확정·제외한다.

## 원인

- 0.614 L2에서 지면 좌표 집합·타입·소유자는 일치하나 프레임이 0/1353 일치였다. 0.615는 CRT 상자(`511160713`→99회→`296677442`)와 J-경로를 실제 미션 상수로 고정했다.
- 정적 대조 결과 `TerrainBuilder` 표·`ChooseTerrainFrame`·`FrameAt/Stamp/Create/Initialize`·`MarkEdges`·`RiftTypeFrames.Run/FrameTable`·LCG·별칭/매핑 초기값은 cpp와 일치하고, `TerrainStamp` oracle(`terrainstamp-x86.tsv` 780행)도 통과하므로 스탬프 논리는 입증됐다.
- 후처리 덮어쓰기는 제외됐다. `Generate`는 `ReadTerritory→PlaceAll→Generate→Objects` 순서에서 적재 깊이 0으로 실행되므로 `IslandPostPop.Prefix`의 `WriteFrame`이 닿지 않고(깊이 상수 `SetWorldLoadingDepth` 확인), 표면·섬·운반체 분배도 지면 프레임을 쓰지 않는다.

## 좁히기 (증거)

- `assets/game-data/netstorm.tarc` 내 `isle.type`(지면 타입 97=70+27)을 독립 파싱한 결과 317클러스터·첫 J-clock `JJ00` 172번이다. DN `WorldFrames[97]`도 `Run('J').First=172`로 파일과 일치한다(신규 L1로 고정).
- cpp 덤프의 잔차-1 셀을 JFirst 후보값으로 묶으면 서쪽 섬(x 81~125) 666셀은 280·동쪽 섬(x 129~157) 397셀은 244로 갈린다. DN은 양쪽 섬 모두 172 단일 기준이다. 동일 테이블·동일 논리라면 섬별 기준점은 나올 수 없으므로, cpp의 섬별 스탬프 입력(코드·매핑·프레임 벡터·호출 순서)이 DN과 어딘가 다르다. 이것이 0.617의 직접 대상이다.
- DN J-분류는 cpp와 1275/1353셀(94%) 일치하므로 성장 지도의 대세는 같다. 차이는 J-chosen·non-J 선택과 위 섬별 기준점에 있다.

- `dotnet test dotnetpj/Netstorm.sln -c Release`: Assets 366/366 통과(0.566 기준선과 동일), Client 1273/1273 통과(0.608 기준 1267 + 0.614 신규 6), Core 2895 통과 + `PlayerTechnologyTests.ActualTypeBindingsAndStalledBoundary` 1 실패(자료 루트 미설정 환경 실패, 0.609既知) 뒤 테스트 프로세스가 비정상 종료(exit -1)했다.
