# cpppj 후속 복원 계획

> 작성: 2026-10-05. 같은 날 갱신: **1단계(설정·경로) 완료, 2단계(맵 데이터·타입 연결)는 파일 읽기·타입 번호·플래그까지 완료.** 근거: [설정 계층 복원](exe/cpp-config-reconstruction.md), [타입 표·요새 파일 복원](exe/cpp-fort-reconstruction.md).
> 현재까지의 복원을 기준으로 한 **향후 작업 계획**이다. 아래 체크되지 않은 단계는 아직 완료하지 않았다. 구현 근거는 [공용 계층 복원](exe/cpp-reconstruction.md)과 [타입·그래픽 복원](exe/cpp-assets-reconstruction.md), 작업 이력은 [LEFT_JOBS.md](../LEFT_JOBS.md)에 있다.

## 목표와 기준

cpppj는 원본 게임을 분석·디컴파일하여 **Windows 10/11에서 실행 가능한 C++ 게임**으로 복원한다. 게임 규칙·화면·사운드·애니메이션은 패치판 10.78을 기준으로 삼고, CD판 10.72는 함수 해석·자료형·판본 차이를 확인하는 비교 자료로 사용한다. CD판의 동작이나 팬게임의 커스텀 요소를 패치판 규칙에 섞지 않는다.

원본 수준의 동작과 요소별 애니메이션 속도를 먼저 맞춘다. 영어·한국어, 전체화면과 4:3·16:9·16:10, 전체화면 가장자리 스크롤, 전체화면 설정 후 정상 재실행을 구현한다. 60·120프레임 지원은 원본 속도 검증 후 진행한다. MCP는 안정된 게임 루프와 입력·상태 조회에 연결한다. 멀티플레이는 후순위이며, cpppj의 Linux 빌드는 공용 코드의 이식성 검사로 활용한다. Linux 제품 지원은 dotnetpj의 후순위 목표다.

## 출발점: 구현된 범위

2026-10-05 복원·검증 기록을 기준으로 한다.

| 계층 | 현재 구현 | 남은 범위 |
|---|---|---|
| 파일·설정·번역 | TAFF/VFS 읽기, 번역 블록, **설정 객체 층·조회·치환·값 쓰기·섹션·시작 순서·경로 지정값·저장 내용** | 설정 파일 위치 탐색, 클론 설정의 저장 위치, 언어 전환 UI |
| 타입·그래픽 | `.type` 속성·클러스터, 판본별 로드 순서, SHP/RLE, 팔레트, 기본 8비트 합성·BMP, **전체 타입 번호 체계·플래그 1/2·그룹·목록 플래그** | 생성자 등록·전투 수치·float 변환, 색 변환·그림자 효과, 실제 화면 장치·Renderer |
| 맵 데이터 | **`.fort` 섹션·타입 번호 변환·오브젝트·내용물·기술·덱·자원 읽기, 미션 스크립트와 요새 경로** | 영역 배치에 따른 청크 위치, 오브젝트 생성·소유자 결정, 나머지 섹션 해석, 미션 종류·스크립트 명령 |
| 실행 기반 | Kernel 슬롯 순회, BaseProcess 실행 인터페이스, GameClock 일부, `maxFPS` 설정값 | SID·파생 프로세스·수명 관리, OS 시계 연결, 전체 메인 루프 |
| 실행 결과 | 콘솔 자산·설정·요새·미션 검사, 프레임 내보내기 | 게임 창·입력·게임플레이·오디오·MCP |

검증 기록은 CTest에 등록한 단일 실행 파일 내부의 **30개 테스트**, 원본 x86에서 얻은 **4,955개 입력 기대값**(공용 1,806＋VFX 709＋설정 2,440)이다. 실제 파일 검사는 `cpp_recovery_smoke.py`·`cpp_assets_smoke.py`·`cpp_config_smoke.py`·`cpp_fort_smoke.py` 넷이다.

자산 검사 기록은 두 판본 합계 타입 217개, 일반 이미지 6,777개·15,940,472픽셀, 특수 레코드 173개다. 이 검사는 자산 해석과 기본 합성에 대한 근거이며, 게임 전체 동작의 일치를 뜻하지 않는다. `SOURCE_MAP.md`의 파일 존재 여부와 디컴파일 A~D 등급도 모듈 완성도나 의미 복원의 증거로 세지 않는다.

## 진행 순서와 완료 기준

첫 번째 실행 가능한 화면 목표는 **원본 자산으로 TEST01을 읽어 1024×768 창에 정적으로 표시하는 것**이다. 이어서 프로세스·입력을 붙이고 캠페인 1-1의 플레이를 완성한다. 창·글꼴·오디오 기반은 데이터 분석과 일부 독립적으로 진행할 수 있지만, 게임 규칙 검증은 앞 단계의 타입·좌표·시계가 준비된 뒤 진행한다.

| 단계 | 의존 단계 | 작업 결과 | 완료 기준 |
|---|---|---|---|
| 1. 설정·경로 | 현재 공용 계층 | Config 객체 층·치환·형식 변환·설정 저장 | 실제 설정으로 자산·언어·미션 경로를 계산하고 원본 규칙과 대조 |
| 2. 맵 데이터·타입 연결 | 1, 현재 타입 로더 | `.fort`·미션 머리 값, 타입 번호·해시·플래그 | TEST01과 캠페인 1-1의 배치·소유자·자원·타입을 구조화하여 검사 |
| 3. 첫 게임 창 | 2, 현재 그래픽 로더 | Windows 창·Renderer·카메라·커서·글꼴 | TEST01 정적 화면·스크린샷, 이동·클리핑·종료·재실행 확인 |
| 4. 실행·애니메이션·명령 | 1~3 | SID·파생 프로세스·메인 루프·입력 | 원본 순서로 갱신하고 선택·이동·애니메이션·일시정지 재현 |
| 5. 캠페인 1-1 플레이 | 4 | 건설·자원·공격·사제·미션 진행 | 시작→플레이→승패→결과까지 재현 가능한 시나리오로 검사 |
| 6. 나머지 원본 동작 | 5 | 유닛·AI·튜토리얼·캠페인·메뉴·사운드·저장 | 원본 기능 목록과 미션별 검사표를 채우고 주요 판본 차이 기록 |
| 7. 요구사항 마무리 | 3부터 병행, 6에서 전체 확인 | 한국어·전체화면·화면비·60/120프레임 | 아래 화면·언어·속도 기준을 Windows 10/11에서 통과 |
| 8. MCP·배포 | 4에서 인터페이스 준비, 5~7에서 검증 | 상태·화면·명령 API, 실행 패키지 | 프로토콜·자동 시나리오·새 설치 환경 검사 |

### 1. Config 객체 층과 자산 경로 — ✅ 완료 (2026-10-05)

- [x] 원본의 객체 스택·이름 접두어·조회 우선순위와 임시 `local.1`~`local.3` 수명을 복원한다. 텍스트 내부의 첫 일치 규칙과 객체 간 조회 순서를 구분한다.
- [x] 중첩 `{키}`, 기본값, 역따옴표 이스케이프, 없는 키, 숫자·불리언 변환을 복원한다. 재귀·길이 제한은 원본/CD 차이와 새 구현의 보호 처리를 각각 기록한다.
- [x] `fortSpec`·`languageSpec` 등의 경로를 Config로 계산하고 VFS에 연결한다. `GameAssets`의 공통 `gifcloud` 지정도 설정·판본에 따라 선택하도록 확장한다.
- [x] 동일 키 삭제 후 추가하는 값 쓰기와 새 옵션 파일 저장을 구현한다. 검사 명령은 원본 폴더 안에 쓰기를 거부한다. **클론이 사용자 설정을 어디에 둘지는 3단계(플랫폼 결정)에서 정한다.**

결과: [설정 계층 복원](exe/cpp-config-reconstruction.md). x86 기대값 2,440개, 실제 두 판본 설정 버퍼 바이트 대조, 저장 왕복. 원본 동작 정정 1건(찾지 못한 키는 `{키}`로 남는다).

처음 정한 완료 결과는 설정 조회·치환을 검사할 수 있는 CLI와 실제 `setup.cfg`·`options.cfg` 사례다. [Config 분석](formats/config.md)에서 확인된 규칙을 독립 기대값으로 만들고, 외부 호출 없이 실행할 수 있는 함수는 x86 검증을 확장한다.

### 2. `.fort`와 게임 타입 의미 — 파일 읽기·타입 번호·플래그 완료, 월드 연결 남음 (2026-10-05)

- [x] `TypeNames` 이름 해시와 저장 타입 번호 변환을 구현한다. `.type` 로드 순서와 내장 프로세스 타입을 구분하고, 판본별 번호 체계를 확인한다. 알 수 없는 타입을 다른 타입으로 바꾸거나 조용히 버리지 않는다.
- [ ] 타입의 실제 플래그 비트·생성자 등록·저장 필드 조건·float 변환을 복원한다. 현재 문자열·double 속성 읽기만으로 게임 타입 의미가 완성됐다고 판단하지 않는다.
  - [x] 플래그 1·2 비트(단어 표·`group`·후처리), 저장 필드 조건, 목록 플래그, 종류 단어, 발자국.
  - [ ] 생성자 등록(타입별 함수 포인터 표), 사거리·비용 등 수치 필드와 float 변환, 요구 에너지 문자열.
- [ ] Territory·Chaff·Technology·Deck·Money와 미션 스크립트 머리 값의 소유자·시작 SP·AI·브리핑을 연결한다. 스크립트 명령 실행은 단계 5에서 붙인다.

### 3. Windows 창과 정적 미션 화면

- [ ] 창·입력·그리기·오디오·글꼴에 필요한 플랫폼 API를 정하고 작은 빌드 시제품으로 확인한다. 라이브러리와 배포·의존성 확보 방법은 이 단계의 결정 문서에 남긴다. 현재 선택된 라이브러리는 없다.
- [ ] `Screen` 장치와 `Renderer`를 연결한다. 디코딩한 프레임 캐시, 팔레트·색 변환표, 그림자, 겹침 순서, 원점·좌표·클리핑을 복원한다. 반전·확대 등은 실제 호출 경로를 확인하여 추가한다.
- [ ] 1024×768·4:3에서 TEST01의 섬·다리·유닛을 정적으로 표시하고, 카메라 이동·원본 커서·영어 비트맵 글꼴을 연결한다. 한국어용 D2Coding 글꼴 계층도 이때 준비한다.
- [ ] 창 크기 변경·포커스 상실·최소화·종료·재실행 시 자원 수명을 검사한다. OS 호출은 `platform/`에 두고 게임 공용 계층의 OS 의존성을 늘리지 않는다.

완료 결과는 **실행 가능한 정적 맵 창과 비교 스크린샷**이다. 투명색·그림자·그리기 순서·카메라 경계가 드러나는 장면을 고정한다. 픽셀 대조는 원본 자산을 기준으로 삼고, 촬영 영상의 HDR 밝기 차이와 창 테두리·레터박스는 별도로 처리한다.

### 4. 프로세스·메인 루프·입력

- [ ] `BaseProcess`의 SID·참조·생성/제거 수명과 필요한 파생 클래스를 복원한다. Kernel의 슬롯 재사용·실행 중 생성/제거·순회 순서가 실제 객체에서도 유지되는지 검사한다.
- [ ] `GameClock`을 플랫폼 시계에 연결하고 [메인 루프](exe/main-loop.md)의 시각 고정→입력·명령→프로세스→그리기 순서를 복원한다. 현재의 `maxFPS=75`·밀리초 기준 14ms 제한값만으로 전체 루프 구현 완료를 선언하지 않는다.
- [ ] 각 타입의 방향·난수 프레임 선택·폴백·상태별 애니메이션 시간을 복원한다. 반복 실행에서 비교할 수 있도록 검사 시 난수 시드·명령·시각을 고정할 수 있게 한다.
- [ ] `UserInput`의 좌표 변환·선택·우클릭 명령·카메라·메뉴 입력을 연결한다. 사제 이동을 첫 동작 사례로 삼고, 경로·충돌·선택 표시를 확인한다.

완료 결과는 **동작하는 TEST01 화면과 명령·상태 변화 기록**이다. 일시정지·재개·시계 래핑, 프로세스 수명, 서로 다른 표시 속도에서 애니메이션 시간이 유지되는지를 검사한다. 요소별 원본 시간은 기계어·영상 근거로 정하며 모든 애니메이션에 같은 속도를 적용하지 않는다.

완료 기준은 미션 로딩부터 승패·결과까지 이어지는 **재현 가능한 플레이 시나리오**다. 같은 입력에서 위치·자원·HP·명령·이벤트 시각을 기록하여 원본 근거와 비교한다. 화면이 비슷한 것만으로 게임 규칙 복원을 완료 처리하지 않는다.

## 디컴파일 신뢰도를 높이는 작업 방식

1. 구현할 동작과 원본 함수 범위를 먼저 좁힌다. [모듈 맵](exe/modules.md)과 `decomp_refine.py --show <주소>`로 패치/CD 대응을 확인한다.
2. 호출 규약·인자·반환·구조체 필드·전역·부호를 역어셈블과 함께 확인한다. 주소가 비슷하거나 자동 매칭 점수가 높다는 이유만으로 같은 의미라고 판단하지 않는다. 판본별 오프셋·크기·기능 차이를 보존한다.
3. 순수 함수는 원본 x86 제한 실행과 C++의 반환·출력 메모리를 대조한다. 외부 호출 대체가 필요한 경우 대체한 범위를 기록하고 그 호출의 실제 동작까지 검증했다고 주장하지 않는다.
4. 파일 형식은 두 판본의 실제 자료와 독립 판독기로 대조한다. 런타임은 입력·게임 시각·난수·상태 기록을 고정하여 차이를 좁힌다. 영상·스크린샷은 화면·타이밍 근거로 보완한다.
5. 함수 주소·근거·검증 범위·미확정 항목을 코드 주석과 복원 문서에 남긴다. 검증 기대값·생성 도구·판본 해시를 함께 갱신한다. 새 코드의 상수·함수·반복문에는 한국어 설명 주석을 달고 UTF-8을 사용한다.

자세한 절차는 [C++ 복원 규칙](cpp-build.md)과 [디컴파일 신뢰도](exe/decompile-reliability.md)를 따른다. 완성도는 파일 수나 함수 수보다 실제 동작과 완료 기준으로 판단한다.

## 검사와 원본 실행 규칙

기본 빌드·회귀 검사는 다음과 같다. 파일 계층을 바꾸면 `cpp_recovery_smoke.py`, 타입·그래픽·자산 경로를 바꾸면 `cpp_assets_smoke.py`, 설정 계층을 바꾸면 `cpp_config_smoke.py`, 타입 표·요새·미션 읽기를 바꾸면 `cpp_fort_smoke.py`로 실제 자료 비교를 추가한다. 설정 조회·치환 코드를 바꾸면 `decomp_config_oracle.py`의 기대값도 함께 본다. 문서만 수정할 때는 링크·UTF-8·차이를 검사한다.

```powershell
cmake -S cpppj -B cpppj/build -DCMAKE_BUILD_TYPE=Release
cmake --build cpppj/build --config Release
ctest --test-dir cpppj/build --build-config Release --output-on-failure
python tools/cpp_recovery_smoke.py
python tools/cpp_assets_smoke.py
python tools/cpp_config_smoke.py
python tools/cpp_fort_smoke.py
```

AGENTS.md와 `originals/`·`originalCD/`의 기존 파일은 수정·삭제하지 않는다. 보고서·추출물은 `extracted/`, 클론 사용자 설정·저장은 별도 경로에 둔다. 원본 실행을 수반하지 않는 빌드·정적 분석·단위 테스트·제한된 x86 함수 검증·MCP 프로토콜 검사는 계속 진행할 수 있다.

원본 또는 복사본 게임을 실제 실행하는 분석 단계는 [AGENTS.md](../AGENTS.md)의 확인 규칙을 따른다. 해당 단계의 목적·필요성을 설명하고 명시적 확인을 받아야 하며, 일반적인 개발 지시나 이전 실행 이력으로 새 실행을 허용받았다고 간주하지 않는다. AGENTS.md가 정한 호스트/IP 예외와 사용자가 직접 요청한 원본 수동 제어·플레이 녹화 분석 예외는 그대로 적용한다. cpppj 자체의 창·게임 실행 검증은 원본 실행과 구분한다.
