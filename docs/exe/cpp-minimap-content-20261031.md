# 미니맵 내용물 갱신과 Renderer 진단 경로 — 단위639

현재 PC와 마지막 전체 정밀 디컴파일 PC는 HJOW-Athlon이며 마지막 전체 정밀 날짜는 2026-10-23이다. 사용자 재개 지시로 목표를 다시 진행한다. 기존 정밀 자료와 보호 PE는 읽기만 했다.

## 미니맵

10.78 `481320`은 카메라가 같아도 셀 큐 또는 전체 갱신 DWORD가 있으면 `480270`을 호출한다. `480270`은 드래그 중이 아니면 crop 계산 뒤 기본 `+8(0)`을 요청한다. 현재 `RawMetadisplayDirty`와 `RawMinimapControls`의 연결이 이 순서를 이미 구현하므로 제품 변경은 필요 없었다. 드래그 중 자동 재생성 억제는 유지한다.

실제 공통 Gump·팔레트·128×128 bitmap·공간 해시에 지면 하나를 넣고 소유자1→2→중립→삭제를 검사했다. 카메라는 고정한다. 같은 Client의 전체 갱신 DWORD를 소비하며 각 상태에서 미니맵 영역 하나만 요청한다. 요청 영역만 지우고 다시 그린 표면은 전체 출력과 padding을 포함해 바이트가 같고, 지면의 실제 표시점 색도 원문 소유자 전용 팔레트와 일치한다. 다음 프레임에는 같은 요청이 반복되지 않는다. 독립 셀 bitmap의 기존 원문 4,722행 대조와 Pop/Unpop·부분 큐 검사를 함께 재사용했다. 실제 플레이나 자연 완주 검사는 아니다.

## 격자·항목별 진단

[읽기 전용 도구](../../tools/decomp_renderer_controls_audit.py)는 정밀 함수 범위의 실제 x86 메모리 피연산자를 열거한다. [관측 보고서](../../cpppj/renderer-controls-audit-20261031.json)의 초기값은 항목별 진단 `0059a8cc=0`, 묶음 숨김 `0059a8b4=0`, 진단키 `0055a484=0`, 정렬 `00540ce8=1`이다.

항목별 진단에는 Draw의 읽기 한 곳만 있고 직접 writer가 없다. 묶음 숨김 writer `4d908b`는 UserInput의 진단키 관문 안에 있으며 일반 F2 건물 숨김과 다르다. 진단키의 직접 writer `4353fa`는 설정 재해석에서 0을 쓴다. 이들은 일반 메뉴에 새 기능으로 노출하지 않는다.

격자 관문은 Draw의 `499d02`가 읽는 Renderer `+40`이다. `49a1d0` 생성자는 0x20e DWORD를 0으로 지우므로 이 필드도 0이다. `4993c0`의 뷰 재초기화는 이 필드를 쓰지 않는다. Renderer 주변 함수와 전역 Renderer 포인터 사용처를 함께 읽었으며 일반 경로에서 켜는 writer는 찾지 못했다. 직접 피연산자 열거만으로 모든 간접 alias의 부재를 증명한 것으로 확대하지 않는다. 기본 플레이에는 격자를 추가하지 않는다. 10.72 생성자 `4570f0`도 같은 초기 0 지우기를 하지만, 이번 분석을 10.72 전체 Draw 복원으로 세지 않는다.
