## 시계 기준과 검사 도구 교정

원문 `00460e70`은 누적 정지 시간 `0055b4f8`만0으로 쓴다. [현재 GameClock](../../cpppj/src/o/GameClock.cpp)과 [기존 독립138행 검사](../../cpppj/tests/GameClockResetTests.cpp)가 같은 동작을 보존하며 이번에 제품을 고치지 않았다. cleanup 뒤 다음 프레임의 게임 시각에는 이전 안내의 정지 시간이 다시 나타날 수 있으므로, 서로 다른 세대의 Start를 단순 차감해2초 미만을 요구하지 않는다.

새 검사는 이전 세대의 마지막 **비정지** `time`에서 `wall-game` 누적 정지 오프셋을 읽어 이전 기한을 벽시각으로 환산한다. 만료 직전 표본이 기한 이전5초 이내이고 다음 월드의 첫 관측이 환산 기한 이후5초 이내여야 한다. 다음 Start도 원문의 Reset 전후 시각 범위 안에 있어야 하고, 각 세대 자체의 기한은 원문대로 정확히360초여야 한다. 실제 경과 시간·세대 증가·새 HUD·세 번째 진행을 함께 요구하므로 시계 기준 차이를 조기 재시작으로 숨기지 않는다.

최초 `storm-v1`은 자연 두 만료와 세 번째 안내까지 관측했지만 **775.840초/종료1**이며 통과가 아니다. 마지막 오류는 `Unable to open for writing: ...states.tsv`다. 실행 중 외부에서 같은 전체 재작성 파일을 읽은 시점과 겹쳤으나 OS 오류 번호가 없어 공유 거부를 확정하지 않는다. 파일의 잘린 중간 읽기도 최종 관측으로 쓰지 않는다. 이 계획에는 미지원 조건부 snapshot과 세 번째 실제 Start에 상대적이지 않은 고정735초 조건도 있었으므로 함께 폐기했다. 이 두 계획 오류가 최초 실행의 직접 종료 원인이라고 주장하지 않는다.

최종 `storm-v2`는 stdio MCP의 완성된 응답만 클라이언트 쪽 파일에 append한다. 실행 중 게임이 재작성하는 보고 파일은 열지 않는다. 종료는 실제 세 번째 Start와 비정지 관측에 상대적으로 결정하고 캡처는 별도 MCP 도구로 요청한다. 각 실행의 도구·명령·보고·stderr·최초 결과를 보존하며 실패 결과를 덮어쓰거나 통과 횟수에 합산하지 않는다.

## 후처리 최초 실패와 별도 재판정

storm-v2 게임 자체는 정상 종료0이지만 최초 후처리에는 기존 도구에서 복사한 두 가정이 남아 있었다. 모든 관측의 전면 활성1을 요구해 첫 비활성 표본(frame2525)에서 실패했고, 메인 Native DialogCount도 무조건0으로 기대했다. 실제 전면 상태는 첫 세대 활성76/비활성93, 둘째0/170, 셋째0/30이며 시작 전/종료 후 HTML 수는 모두0/1/0이다. 사용자가 다른 창을 활성화할 수 있는 MCP 자연 대기에 전면 유지를 요구할 근거가 없고, Native 메인의 동일 카운터는 누수가 아니다.

최초 `result.json`(passed=false)·적재 도구를 보존하고 **같은 종료 원시**에 새 `result-v3.json`과 `observations-result-v3.json`을 만들었다. 창 활성0/1을 그대로 기록하고 메인 HTML/모달 수를 진입 전 전체 값과 대조하도록 판정만 고쳤다. 360초·실제 경과·세대/새 HUD·세 번째 게임/벽시각 진행·정상 종료 조건은 유지했다. `guide-audit.json`도 별도로 통과했다. 도구의 실행 시점/분석 시점 SHA와 최초 결과 SHA를 JSON에 구별했으며 이 재판정 때문에 게임을 새로 실행하지 않았다. 총 게임 프로세스는2개, 정상 완료 사슬은storm-v2 한 개다.
