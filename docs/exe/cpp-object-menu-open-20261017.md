# cpppj 단위139 — 공통 객체 메뉴 Open과 위치 계산

현재 PC 및 마지막 정밀 디컴파일 PC는 **HJOW-Athlon**, 마지막 디컴파일 날짜는 **2026-10-16**이다. 기준 커밋은 `aff315d`다. 보호10.78 PE와 같은 PC의 정밀 C/함수표를 읽었다. 새 디컴파일·원본 게임 실행은 없으며 전체화면 DirectDraw 수정은 제외한다.

## 원본의 처리 순서

`RawObjectMenuOpen::Open`은 가상+ac `004adb30`을 복원한다. 현재 extra의 값1 비트가 켜졌으면 0을 반환한다. TYPE flags2의 `0x400000`이 켜졌으면 같은 좌표의 제단을 찾고, 실제 풀의 `[1, capacity)` 안이면 그 제단의 가상+ac에 같은 입력 사건을 전달해 **그 반환 DWORD 전체**를 반환한다. 제단이 없거나 범위 밖이면 기존 객체 메뉴를 계속 작성한다. free/dead/void의 새 거부 조건은 추가하지 않았다.

일반 경로는 BeginFancy→현재 객체 요약4ada70→실제 가상+a8→현재 TYPE 재조회 순서다. 마지막 flags2에 `0x30100`이 있으면 아래 위치 함수를 호출하고, 없으면 **작성 뒤의 현재 사건 좌표**로 객체 부착475cf0을 호출한다. 마지막 반환은1이다. extra는 작성 뒤 다시 검사하지 않는다.

`RawObjectMenuOpen::Position`은 전체 `00425f90`을 복원한다. 현재 raw float 좌표를 먼저 투영하고, 같은 첫 contained Form `(1,0,0)`을 조회한다. Form이 없으면 투영점을 바로 부착한다. Form이 있으면 Form의 kind WORD→현재 TYPE+44 사정거리→실제_ftol의 signed64 하위DWORD→signed 상한2→`(distance+1)<<4` 순서로 여백을 만든다. 현재 controlled 메뉴의 **기본 폭+3c**와 현재 화면 폭을 읽어 좌우 넘침을 signed 비교하며 동률은 오른쪽을 고른다. DWORD 감김, INT_MIN의 부호 유지, NaN/무한대/범위 밖_ftol의 하위0을 보존한다. 화면 안 clamp나 일반 사각형 맞춤식으로 대체하지 않았다.

## 같은 Session 연결

`RawCampaignSession::MakeObjectMenuOpen`은 현재 같은 Pool/TYPE에 몸체를 만들고 다음 게임 조회를 기존 구현에 연결한다.

- 제단 조회는 같은 raw 좌표와 현재 `runeState.altarType`으로 `world.Find`를 호출한다.
- 투영은 현재 `cursorView`의 기존 `SoundToScreen`을 쓴다. SetParticleView/카메라 변경을 다음 호출에서 바로 읽는다.
- 내용물은 같은 `priests->Carrier().FindContained(sid,1,0,0)`이다.
- 사정거리는 기존 현재 `gunTypes[type].range`다.

GUI 생성·제목·실제 가상+a8/+ac·현재 메뉴 폭/화면 폭·객체부착은 caller가 실제 소비자를 공급해야 한다. 빠진 소비자는 선택된 위치에서 오류를 유지한다. 임의 성공 callback이나 합성 메뉴는 제품 코드에 추가하지 않았다. 새 factory는 아직 UberGump의 실제 우클릭 입구를 교체하지 않는다.

## 독립 원본 관측과 검증

`tools/decomp_object_menu_open.py`는 실제 두 부모와_ftol 명령만 격리 실행한다. 제목4ada70, 파생+a8/+ac, 장식 생성/부착, 투영, 종속 조회, TYPE 조회 및 현재 메뉴 조회는 **명시 경계**다. 따라서 실제 제목 전체나 자연 UI를 실행한 관측으로 확대하지 않는다.

기대값은 C++를 읽거나 실행하지 않고 원본 정상 반환의 전체 효과 인자·반환값·현재 필드에서 만들었다. **788개 고유 입력·53/64비트 합계1,576회 정상 반환·132,544명령·정밀도 차이0**이다. 실제 진입은 공통Open552회·위치1,216회다(일부 Open이 위치를 내부 호출한다). 모든 호출에서 비휘발 GP·스택/canary·x87 제어/스택 균형을 검사했다. 기존 fixture는 수정하지 않고 새 `object-menu-open-x86.tsv` 및 `object-menu-open.json`을 남긴다.

C++의 새 원본 재생 검사3개는 788입력의 반환·효과 순서·현재 필드, 도달한 소비자 누락, 판본/TYPE 계약을 확인했다. Session 집중 검사4개에는 기존3개와 새 실제 공통Open/현재 카메라 검사1개가 포함되며 전부 통과했다. 이 새 Session 검사는 자연 설치한 사제를 쓰고 게임 조회를 외부 값으로 대체하지 않는다. GUI는 명시 입력 경계이며 실제 제목/부착 Form/자연 메뉴 검증은 아니다.

첫 빌드는 새 fixture 경로의 string/const char* 형식 오류로 실패해 수정했다. 빌드2는 종료0이지만 새 검사 std::fill의 int→BYTE 경고가 있어 BYTE 값을 사용하도록 수정했다. 최종 Release 빌드3은 종료0·경고0·오류0이다. **전체 CTest는1,569개·실패0·종료0·207.45초**다. 로그 접두부는 `extracted/goal-object-menu-open-20261017-`다.

최종 원본 근거 감사58종 중 **47종 성공·기존 실패11종·새 실패0**을 확인했다. 기존11종의 지점은 단위138 기록을 따른다. 중간 감사에서 발견한 object-menu 보고서의 중첩된 현재 제품 핀2개는 실제 변경에 맞춰 갱신하고 과거 SHA를 보존해 재감사를 통과했다. 원본 기대값을 수정하지 않았다. 현재 제품을 가리키던 **25개 기존 보고서·68개 핀**만 갱신했으며 각 보고서의 integration_updates에 직전 값을 남겼다. 원본 전체 실행의 증거로 확대하지 않는다.

보호 실행 파일2개 및 tarc의 SHA3개가 이전과 같으며 기존 CMake 두 파일의 바이트 접두를 보존했다. 새 관측·제품·검사 파일을 LF로 고정하고 한국어 JSON 기록의 UTF-8도 확인했다. 이 단위는 실제 Client 입구를 교체하지 않아 클론 창 회귀를 반복하지 않았고, 직전 단위138의 최신 실행 파일 진입 결과를 이번 새 메뉴의 자연 실행 증거로 사용하지 않는다.

10.72의 기존 정밀 C 대응은 공통Open `004aebf0`, 위치 `004e35f0`이다. 이번 CPU 실행과 새 C++ 몸체는10.78 전용이다. CD 구현/fixture/원본 자료를 수정하지 않았으며 새 몸체는 CD 풀을 거부한다.

## 남은 연결

실제 제목4ada70·4ad780(type/count/owner/sid의 **4인자**), 파생별 가상+a8/+ac 분배, 같은 Session Pool의 GumpFormHost와 부모 삭제 알림, RawMenuControls의 객체부착 완료 입구, Client의 실제 DWORD 명령 소비자가 필요하다. 실제 우클릭 메뉴는 시간을 정지하지 않아야 한다. 현재 비활성 임시 메뉴를 완료된 것으로 간주하지 않는다.
