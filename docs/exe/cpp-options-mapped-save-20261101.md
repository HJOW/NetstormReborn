**2026-11-06 후속966:** 실제 CRT 파이프 부분전달/버퍼실패와 두 볼륨1176/1177 파일 상태의 복구를 검증했다. OS 자체1176/1177·물리디스크고장은 미관측으로 구분한다. [966기록](cpp-options-save-failures-20261106.md).

2026-11-01 / HJOW-Athlon. 마지막 전체 정밀 디컴파일은 같은 **HJOW-Athlon / 2026-10-23**이다. 디컴파일 결과를 수정하지 않았다. 사용자의 마지막 중단 작업 마무리 요청에 따라 이 단위의 검증·문서·커밋까지만 수행한다.

## 문제와 적용 범위

672의 전체 음향 검사 마지막 프로세스는 `options.cfg`의 `w+b` 열기에서 errno22/doserrno1224로 종료했다. 이전393·369·386에서도 같은 종류의 저장/도구 복구 문제가 있었다. Windows의1224는 활성 파일 매핑 때문에 요청한 작업을 수행할 수 없다는 오류다([Microsoft 오류 코드](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1000-1299-)). 기존672 오류를 일으킨 실제 매핑 소유자는 특정하지 않았으며 exFAT 고유 문제로 단정하지 않는다.

이번에는 게임/보호 원본 대신 새 임시 파일에 실제 읽기 전용 매핑을 만들었다. C:(NTFS)와 H:(exFAT) 모두 원문과 같은 `w+b` 요청이1224로 실패했다. 같은 조건에서 새 바이트를 완성한 뒤 `ReplaceFileW`로 교체하는 경로는 저장과 재적재에 성공했다.

`Client::SaveOptions`의 실제 writer를 `WriteClientOptionsDisk`로 분리했다. 일반 `w+b` 성공 경로와 설정 인코딩·현재 저장 위치·changed 수명은 유지한다. **1224인 경우에만** 같은 부모의 새 전용 폴더에 바이트를 쓰고 flush/commit/close를 확인한 뒤 교체한다. 상위 폴더를 임의로 만들거나 권한/경로 오류를 성공으로 처리하지 않는다. 원본과 다른 Windows10/11 호환 처리임을 코드 주석에 명시했다. 사용자 홈 저장 위치 이동은5차의 별도 작업이다.

`ReplaceFileW`는 기존 속성/ACL을 보존하는 Windows API이며 같은 볼륨의 백업 이름을 지정한다([Microsoft ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)). 실패하면 예외를 전달하고 미저장 changed를 유지한다. 이전 파일이 백업 이름으로 이동한 드문 실패에서는 목표 이름이 없을 때만 덮어쓰기 없는 복원을 시도한다. 실패한 교체의 복구 폴더와 새/이전 바이트는 자동 정리 목록에 넣지 않는다.

## 매핑 수명과 정리

최초 재개 검사에서 저장 자체는 성공했지만 즉시 임시 폴더가 없어야 한다는 두 단언이 실패했다. 추가 OS 관측에서 두 볼륨 모두 활성 매핑의 이전 파일은 `DeleteFileW`가 오류5로 거부함을 확인했다. 백업 없는 ReplaceFile도 내부 `~RF*.TMP`를 남겼고 MoveFileEx 교체는 오류5로 실패했다. 따라서 백업을 없애거나 실패를 무시해 해결할 근거가 없다.

성공 저장의 삭제 거부 파일은 명시 경로만 장기 목록에 보관한다. 다음 저장과 프로세스 종료 때 그 경로만 다시 정리한다. 재귀 삭제나 다른 저장의 폴더 검색을 하지 않는다. 검사는 매핑이 열려 있는 동안 남은 백업의 **전체 원래 바이트**와 새 파일 부재를 확인하고, 매핑 반납 뒤 다음 실제 저장에서 폴더가 없어짐을 확인한다. 이는 잘못된 즉시 삭제 기대를 실제 Windows 수명으로 교정한 것이며 백업 내용을 허용 없이 버리는 완화가 아니다.

외부 매핑이 프로세스 종료까지 살아 있거나 정리 목록 할당까지 실패하면 성공 저장의 백업 폴더가 남을 수 있다. 설정 저장은 완료된 상태다. 실패한 교체의 복구 폴더는 의도적으로 보존한다. 실제 디스크 부분 쓰기/flush 실패, ReplaceFile의1176/1177 복구 분기는 이번에 오류 주입으로 재현하지 않았다.
