# 반더 타워·맨 오 워 공유 빔의 정적 분석 메모

2026-10-16 단위91의 독립 분석이다. 현재 PC와 마지막 전체 정밀 디컴파일 PC는 모두 **VM-W11-Codex / 2026-10-16**이다. AGENTS.md와 양 LEFT를 읽고 기존 정련 자료 및 보호10.78 PE를 확인했다. 새 디컴파일, 원본 명령 재생, 원본/클론 게임·GUI 실행은 **0회**다. 이 문서는 기계어·가상 표·상수와 정련 C의 **정적 증거**이며, 빔의 실행 대조·구현 완료·화면 동일성 증거가 아니다. 단위91의 실제 미사일 작업·빌드·관찰 수와 합산하지 않는다.

## 표적 회피 분기의 명칭 정정

초기 분석 전달에서 공통 launch의 회피 대상을 TYPE156/Rain Walker라고 쓴 것은 잘못이다. 보호 PE의 실제 `00466ffc`는 **`cmp edx, dword ptr [005412a0]`**이며, 해당 전역 DWORD는 **146**이다. 공유 대응표의 TYPE146은 `rainBalloon` / **Cloud Floater / 클라우드 플로터**다. TYPE156은 `rainWalker` / **Crystal Crab / 크리스탈 크랩**, 전역 `005412c8`이며 이 분기가 읽는 전역이 아니다. [공유 대응표](../unit-source-name-map.md)의 숫자·내부 이름·표시 이름과 일치한다.

같은 구간의 `00467010`은 **`fild dword ptr [00540bbc]`**다. PE의 초기 값800을 signed 정수로 x87에 올려 비교하므로, 이 전역을 float 비트로 해석해서는 안 된다. `00467004~0046700b`는 `RandomFloat(0,1000)`을 호출하고 그 값이 현재 정수 임계값보다 작으면 회피 분기로 간다. 정련 C의 `_DAT_00540bbc` 형 추정만으로 float 전역이라고 판단하지 않는다.

## 반더 타워의 발사와 즉시 피해

TYPE148 `thunderArcher` / Vander Tower / 반더 타워의 stage5 생성자는 `004680f0`이며64BYTE를 사용한다. 공통 접두 `00467fb0` 뒤 outer 가상 표 `0050b170`, inner `0050b16c`로 바꾼다.

| --- | --- | --- |
| outer+18 | `00467330` | 썬·썬더 캐논과 같은 공통 Frame |
| outer+20 | `00468640` | `00501a54`의 float20 반환 |
| outer+24 | `00466a40` | 표시 전역 `00541198` 반환, PE 값80 |
| outer+28 | `00468120` | 효과 전역 `005410bc` 반환, PE 값19 |
| outer+30 | `00468040` | `00504190`의 float0.3 반환, 정확한 값0.30000001192092896 |

offset은16진수다. getter가 존재해도 TYPE148 launch는 일반 Missile 분기로 들어가지 않는다. 공통 `00466f50`은 처음 부모·표적 raw 포인터를 저장하고 표적 free/dead·HP를 검사한 뒤 `004571b0`으로 표적점을 계산한다. 그 뒤 처음 부모의 TYPE가 전역 `005412a8`=148이면 **현재 필드의 부모/표적으로 `00472700`을 호출**한다.

빔 생성 뒤 처음 표적 raw 포인터의 현재 상태를 확인한다. free/dead이면 `004d5000(source)`을 호출한다. 살아 있는 TYPE146 클라우드 플로터에 위 난수 회피 조건이 성립해도 같은 refresh 경계로 간다. 나머지는 `004d4f00(source,current target)`으로 **즉시 Hit**를 호출한다. 마지막 반환은 처음 표적 raw 포인터의 현재 free/dead 상태다. 따라서 빔의 Frame이 나중에 피해를 주는 구조로 바꾸면 원본 순서와 달라진다. 표적점·생성·refresh/Hit 사이의 재진입으로 필드가 바뀔 수 있으므로 snapshot 포인터와 현재 필드를 구별해야 한다.

## 같은 빔 생성자와 객체 수명

`00472700(source,target)`과 맨 오 워의 `00472690(source,target,sound)`는 표적이 살아 있을 때 같은 **`new(0x68)` → `00471d10`**을 호출한다. 반더 타워 wrapper는 `shortZap.wav`, 맨 오 워 wrapper는 인수 sound를 넘긴다. 현재 복원된 맨 오 워 RainFrame은 원본대로 sound=0을 넘기고 별도 TYPE 발사 소리 장부를 사용한다. 이 차이를 없애면 맨 오 워에 반더 타워의 소리가 추가될 수 있다.

두 wrapper는 표적이 이미 free/dead이면 생성하지 않는다. 그 경로의 원문 반환 레지스터에는 진입 때 계산한 **표적 raw 주소**가 남는다. 살아 있는 표적의 할당 실패 경로는0이다. 후속 oracle에서 단순히 모든 생성 생략을 nullptr 반환으로 정규화하지 않는다.

빔의 가상 표는 `0050c268`이다. Frame은 `+18 → 00472310`, Draw는 `+20 → 004724f0`, scalar deleting destructor는 `00471df0`, 실제 소멸자는 `00471e10`이다. 생성자는 다음 경계를 순서대로 사용한다.

1. `00488190 → 00487fd0`: 공통 표시 목록 등록과 부모 부착. 프로세스 타입은 `005410bc`=19 `lightningSystemProcessType`, 부착 flags는 `0x10`이다.
2. `00488100(this+24,120)`: **120×24BYTE** 입자 배열 확보·전체 초기화. 같은 컨테이너의 capacity는+24, total은+28, 배열 포인터는+2c다.
3. firstLive(+54)=0, 공유 팔레트 `00458480`을+50에 저장, 표시 깊이(+20)=-25.
4. `new(0x40) → 00471b20`: 경로 생성자64BYTE. 포인터는+58, 전체 길이×float0.025의 jitter 상한은+5c, sound token은+60에 저장한다.

공유 팔레트의 포인터는 이 빔 소멸자가 해제하지 않는다. 소멸 `00471e10`은 경로 생성자 버퍼를 먼저 free하고, `00423aa0`으로 입자 배열을 반납한 뒤 `00487880`으로 표시 목록 제거·base 소멸을 수행한다. `00471df0`의 flags bit0이 있으면 빔 객체 자체도 free한다. 원본104BYTE 할당의 모든 바이트가 생성자에서 초기화된다고 추정해서는 안 된다.

## 포구·표적 위치와 경로 생성

`00471b20`은 실제 중심 `004adea0`에 현재 pixel scale `0059a924/0059a928`을 곱해 양끝을 만든다. source TYPE148은 y−76, TYPE149는 y−48, TYPE144 맨 오 워는 x−5/y−48을 적용한다. target TYPE149/144는 y−48, 그 밖의 target은 y−16이다. 실제 상수는 `0050c260`=76, `0050c25c`=48, `00503d68`=5, `00503358`=16이다. TYPE148 표적에 source용76을 적용하지 않는다.

양끝·거리·atan2 각도는 **생성 시 snapshot**이다. 경로 생성자에는 이후 추적할 표적 SID가 저장되지 않으며 빔 Frame도 현재 표적을 조회하지 않는다. 이를 움직이는 표적에 계속 붙는 빔으로 구현할 근거는 없다. pixel scale은 PE의 BSS 초기0이 아니라 실제 viewport 초기화 `00497960` 등이 채우는 현재 전역이다.

경로 생성자64BYTE의 의미 필드는 시작/끝 좌표(+0/+4/+8/+c), 차이 벡터(+10/+14), 거리(+18), 각도(+1c), 기본 입자 수명2.0(+20), 다음 단계 상한(+24), 현재 step(+28), 누적 진행(+2c), 누적 각도(+30), 이전 입자 포인터(+34), 완료 플래그(+38), 소유 빔 포인터(+3c)다. `004720f0`은 시작 입자를 추가하고+24/+28을float0.15, +2c를0, +30을기본 각도로 설정한다.

`00472180`은 요청 진행값을 최대1로 제한하고 누적 진행이 그 값보다 작을 때 정점을 만든다. `00471fc0`은 cos/sin으로 다음 점을 계산하며 strength>float0.12이고 `RandomInteger(100)<85`이면 길이와 strength를 절반으로 줄여 재귀 가지를 만든다. 재귀 가지의 이전 점은 지금 추가한 입자다.

step 갱신에는 원본의 난수 호출 횟수 차이가 있다. step×float0.9와 최소float0.08로 다음 상한을 구한 뒤 `00472273`에서 난수를 한 번 뽑아 검사하고, 조건에 따라 `004722a4`에서 **다시 뽑은 값**을 step으로 저장한다. 이를 `max(0.08, Random(...))` 한 번으로 바꾸면 난수열이 달라진다. 끝점 추가와 완료 표시도 `00472180`의 실제 순서를 따라야 한다.

## Frame·그리기·효과음

첫 `00472310`은 현재 source raw 좌표×scale로 초기 표시 영역을 만들고 `00418400`으로 타이머를 초기화한다. 초기화 플래그(+48)를 세운 뒤 `004720f0`으로 첫 입자를 만든다. sound token이0이 아니면 **첫 Frame에서 한 번만** `004a9d70(raw source x,y,sound,0)`을 호출한다. 생성자에서 바로 재생하거나 매 Frame 재생하지 않는다.

후속 Frame은 `00418470(this+30, double0.5)`으로 시간 조각을 얻는다. 실제 시간 상한은double0.5×double0.1=**0.05초**이며, 저장 delta(+40)는10배, scaled delta(+44)는 여기에 현재 전역 `0059a934`를 더 곱한 값이다. 긴 경과는 한 Frame 안에서 여러 조각으로 처리한다. 누적 진행은double+38이며 경로 갱신에 넘길 때float로 저장한다. 모든 수명을 실제 게임 시간2초로 해석하면10배 차이가 생긴다. 정확한 화면 지속 시간은 하위 단계·Frame 양자화까지 실제 실행으로 확인해야 한다.

각 시간 조각에서 `00472180`으로 경로를 추가한 뒤 **total이 아닌 용량120 전체**를 순회한다. 각 life에서 저장 delta를 빼고 life>0인 점만 두 축의 난수 jitter를 적용하며, firstLive를 다시 구한다. 살아 있는 점이 있으면 원본 영역 포함 helper `004239f0`과 `00487ba0`으로 표시 영역을 갱신한다. 시간이 아직 남으면 다음 조각을 반복한다. 모두 소진되면 `0041bf10(this,0)`으로 **빔 Form**을 삭제하고 즉시 반환한다. 빔 Frame에는 표적 Hit 호출이 없다.

입자24BYTE는 x, y, strength, jitterWeight, life, **이전 입자 포인터**의 여섯 DWORD다. 정련 C가 마지막 DWORD를 float로 표현한 것은 실제 포인터 쓰기·역참조 기계어와 맞지 않는다. Draw `004724f0`은 firstLive 다음 점부터 total까지 살아 있는 점의 이전 포인터를 따라 선분을 만든다. 양끝에서 카메라 전역 `0059a938/0059a93c`를 뺀 값을float로 저장한 뒤 CRT 절삭 `004e49c0`을 적용한다.

기본 선 색 index는`0xc3`이다. strength≥float0.25이면 x+1 선을색`0x55`로 추가하고, strength>float0.5이면 y−1 선도색`0x55`로 추가한다. 최종 출력은 `004dade0`의 기존 소프트웨어 선 그리기 경계다. 별도 미사일 SHP나 임의 한 줄만으로 대체하면 재귀 가지·두께·난수 흔들림의 근거를 잃는다. 이번에는 팔레트의 실제 화면색·클리핑 출력·음향 파일 재생을 실행 검증하지 않았다.

## 맨 오 워 개체의 수명 종료와 전투 파괴

**공유 빔의 입자 소진과 맨 오 워 개체의60초 수명은 서로 다른 수명이다.** 기존 [비행 Frame 작업 기록](cpp-flyer-frame-20261016.md)의 `0045d630`은 boss 권한에서 만료 또는 extra20을 확인하면 부모에 `Destroy(0x200000)`을 전달한다. 공통 비행 본체의 extra20 경로도 같은 플래그를 사용한다. 훨리기그의 홈 귀환·충전·재출격 경로로 합치지 않는다.

보호 PE의 TYPE144 가상 표 `0050a388+14`는 `0045e7e0`이다. 이 파생 preDestroy는 그림자 SID(+8)가 있으면 먼저 그림자에Destroy0을 호출하고 `0044b4b0`으로 간다. 공통 preDestroy는 다음 두 효과를 구별한다.

| 플래그 | 그래픽 효과 경계 | 소리 |
| --- | --- | --- |
| `0x200000` | `004605f0 → 004604a0(mode1) → 004602c0` | `collapse.wav` |
| `0x100000` | `004605d0 → 0045a840(...,float0.04)` 및 `004604a0(mode0) → 0045ffb0` | `explosion.wav` |

이것이 수명 소멸과 전투 폭발을 다르게 처리해야 한다는 정적 근거다. `0x200000`을0이나`0x100000`으로 바꾸지 않는다. 이번에는 이 그래픽 생성자들의 전체 프레임·렌더링이나 실제 효과음을 실행 대조하지 않았으므로, 모양·지속 시간·소리의 최종 동일성을 주장하지 않는다.

## 현재 제품 경계와 후속 작업

이 분석 시점의 `RawCampaignArcherBindings`는TYPE71/128/131/140을 분배하며TYPE148 stage5는 미복원이다. `RawCannonFire::Launch`는 일반 Missile 생성 분기만 구현하고 있으므로TYPE148에 state 값만 바꿔 공급하면 잘못된 투사체가 생긴다. 전용 생성자·Step과 즉시 빔/Hit 경계를 원본대로 추가해야 한다.

`RawCampaignSession`의 맨 오 워 `hooks.launch`는 아직 `00472690 미복원` 예외다. Damageable preDestroy의collapse/explosion/sound는 서비스가 공급하지 않으면`FillMissing`으로 거부한다. 기존 `RawRenderRegistry`·공통 Host·표시 수집과 같은 풀·시계에 빔의 실제 객체·입자·그리기·소멸을 연결해야 하며, 효과를 빈 콜백으로 만들어 데모를 통과시키는 것은 복원 증거가 아니다. 단위91의 크로스보우 작업에서 이 메모를 함께 보관하되, 빔 구현 완료로 표시하지 않는다.

10.72 정련 자료에는 대응 후보 ctor`00412da0`, 명시 좌표 ctor`00412ff0`, Append`00413130`, 재귀 생성`00413190`, 경로 Step`004132c0`, Frame`00413440`, wrapper`00413890`이 있다. CD는36BYTE 슬롯, 생성자 안의 경로 초기화 inline과 일부 정수 비트 비교가 보여 주소만 치환한 같은 몸체로 단정하지 않는다. 이는 정적 참고이며 CD 원본 명령·바이트 동일성 대조 결과가 아니다.

## 근거 파일과 재현 범위

보호 PE의 메모리 이미지 주소로 가상 표 DWORD·상수·관련 x86 명령을 읽었고, 현재 PC 정련 C의 해당 함수 구간과 대조했다. 파일은 수정하지 않았다. 이 문서만 작성하며 다른 에이전트의 제품 수정은 이 분석의 쓰기 결과가 아니다.
