# 설정 복구 도구의 매핑 오류와 원인 조사 — 단위675

2026-11-01 / HJOW-Athlon. 마지막 전체 정밀 디컴파일은 같은 **HJOW-Athlon / 2026-10-23**이며 디컴파일 결과를 수정하지 않았다. 제품 C++은 바꾸지 않았고 제품 SHA는 674 그대로다. 사용자의 재개 요청에 따라 674가 남긴 Python 설정 복구 writer와 `options.cfg` 오류의 실제 원인을 처리했다.

## 결론

- `options.cfg`의 간헐 오류 errno22/doserrno1224는 **수정된 추적 파일을 `git diff` 계열이 매핑하는 동안 재현**된다. 실제 파일과 같은 954바이트, H:(exFAT)에서 같은 신호를 얻었다.
- 볼륨 형식 때문이 아니다. C:(NTFS)에서도 같은 신호가 났다.
- 과거 개별 실패 시점의 프로세스는 기록이 없어 사후 특정할 수 없다. 입증한 것은 같은 신호를 만드는 기전이다.
- Python 도구는 이제 1224가 재시도 끝까지 이어지면 제품 674와 같은 방법으로 교체 복원한다.

## 왜 Git을 의심했나

과거 OSError22 기록의 대상은 `originals/d/options.cfg`, `cpppj/src/o/SquidHash.cpp`처럼 모두 Git 추적 파일이고, 파일을 다시 쓰는 도중이었다. 격리 복사본에서는 통과했다는 기록도 있다. 제품·도구·원문 어디에도 설정 파일을 매핑하는 코드가 없으므로 매핑 주체는 외부 프로세스다.

## 대조 측정

격리 임시 저장소(`extracted/` 안과 스크래치패드)에서 CRT `w+b`로 다시 쓰기를 반복하며 git 명령을 동시에 실행했다. 대상 저장소의 추적 파일이나 원본은 쓰지 않았다. 실패 코드는 `OSError`에 남지 않으므로 ucrtbase의 `_doserrno`를 직접 읽었다.

| 조건 | 파일 크기 | 볼륨 | 쓰기 실패 |
| --- | --- | --- | --- |
| `git status` + 추적 파일 | 262144 | H | **446회** `errno22/dos1224` |
| `git status` + 추적 파일 | 262144 | C | **188회** `errno22/dos1224` |
| `git status` + Git 제외 파일 | 262144 | C·H | 0 |
| git 없음 (추적·제외 각각) | 262144 | C·H | 0 |
| `git status` + 추적 파일 (같은 크기 수정 2000개·40개 포함) | 954 | C·H | 0 |
| `git status` + 추적 파일 (크기가 바뀐 쓰기) | 954 | C·H | 0 |
| `git diff -- 대상` (수정 파일 300개) | 954 | H | **32회** `errno22/dos1224` |
| `git diff --numstat -z` (수정 파일 300개) | 954 | H | **4021회** `errno22/dos1224` |
| `git diff` 전체 (수정 파일 300개) | 954 | H | **3576회** `errno22/dos1224` |
| `git add --dry-run`, `git hash-object` | 954 | H | 0 |

처음 세운 가설인 "`git status`가 범인"은 실제 크기 954바이트에서 **지지되지 않았다**. `git status` 재현은 32KB를 넘는 파일 표본에서만 나왔다. 작은 파일을 막은 것은 `git diff` 계열이며, 전체 diff는 큐를 처리하는 동안 매핑을 오래 유지해 실패 횟수가 큰 폭으로 늘었다. 이는 예전의 "OSError22×3 뒤 복구"처럼 0.2초 넘게 이어진 실패와도 맞는다.

git 없는 대조군이 0건이므로 이 조건에서 Defender 실시간 검사나 색인기는 나타나지 않았다. 다만 Defender 제외 경로는 관리자 권한이 없어 확인하지 못했고, 다른 프로세스의 매핑 가능성 전체를 배제한 것은 아니다.

## 도구 수정

[`tools/cpp_smoke_files.py`](../../tools/cpp_smoke_files.py)의 `preserve_game_settings`를 다음과 같이 바꿨다.

1. 쓰기 시도마다 `_doserrno`를 지우고, 실패하면 실제 값을 로그에 남긴다. 이전 기록의 "실제 발생 OS 코드 수집" 후속이 여기서 해결된다.
2. 1224가 아니면 동작은 기존과 같다.
3. 1224면 일반 쓰기를 재시도하고, **마지막 다섯 번째 시도에서만** 같은 폴더의 전용 임시 폴더에 새 파일을 완성해 `ReplaceFileW`로 교체한다. 짧은 매핑은 재시도로 풀리므로 원본 폴더에 임시 폴더를 만들지 않는다. `os.replace`는 매핑 중인 대상에서 오류5로 거부되므로 쓰지 않는다.
4. 교체한 이전 파일이 아직 매핑 중이면 삭제가 거부된다. 그 폴더는 목록에 남겨 다음 호출과 프로세스 종료 때 명시 경로만 다시 정리한다.
5. 교체까지 실패하면 오류를 전달하고 복구 폴더를 보존한다.

## 검증

**수정 전 기준선:** 파일 핸들 없는 실제 매핑에서 수정 전 도구는 C·H 모두 5회 실패 뒤 `OSError(22)`로 끝나고 변경된 바이트가 남았다.

**실제 `git diff`와의 수정 전후 대조:** H 볼륨 임시 저장소, 같은 크기 수정 파일 2000개, 판본별 40초.

| 판본 | 회차 | 복원 실패 | 잘못된 바이트 잔존 | 임시 폴더 잔여 |
| --- | --- | --- | --- | --- |
| 수정 전 | 600 | **17** | **17** | 0 |
| 수정 후 | 1007 | **0** | **0** | 0 |

**단위 검사:** [`tools/test_cpp_smoke_files.py`](../../tools/test_cpp_smoke_files.py) 6개(새4·기존2) 통과. 새 4개는 C/H 각각 실행한 8조합이며 모의 예외가 아닌 실제 매핑을 쓴다. Python `mmap` 모듈은 복제 핸들을 유지해 공유 조건이 git과 달라지므로 `CreateFileMappingW`/`MapViewOfFile`로 파일 핸들 없는 보기를 만들었다.

**변이:** 사본에서 8종을 실행했다. 최초 실행은 7/8이었고 `stale-doserrno`가 미검출이었다. UCRT 파일 함수가 `_doserrno`를 지워 기존 시나리오에서는 낡은 값이 남지 않았지만, 실제 1224 직후 다른 errno22가 이어지면 동작이 달라지므로 동등 변이가 아니라 검사 빈틈으로 판단해 검사를 추가했다. 재실행은 8/8이다.

보호 범위는 674 after 기준과 대조했고 결과는 [보고서](../../cpppj/tool-settings-writer-20261101.json)에 있다. 게임/GUI·C++ 빌드/CTest·Native·fixture·MP 검사·전체34·ZIP은 실행하지 않았다. 도구 변경과 직접 관련된 실제 경계는 위 `git diff` 대조로 확인했고, 게임 실행은 이 변경의 근거를 늘리지 않으므로 지시대로 생략했다.

## 남은 한계

- 외부 매핑이 프로세스 종료까지 남으면 성공 교체의 임시 폴더가 원본 폴더에 남을 수 있다. stderr에 경로를 남기고 보호 파일 대조가 추가 파일로 드러낸다.
- `ReplaceFileW`의 1176/1177 분기는 실제 오류 주입으로 검증하지 않았다.
- 672 전체 음향 묶음의 실패 기록은 그대로 유지한다. 이번 단위는 그 묶음을 다시 실행하지 않았다.
- 작업 중 `git diff`가 설정 파일과 겹칠 수 있다는 사실이 밝혀졌지만, GUI 검사 중 Git을 멈추는 규칙을 새로 두지는 않았다. 제품과 도구가 모두 1224를 처리한다.
