# 메인 루프와 시간 모델 (입력 → 갱신 → 그리기 순서)

> 분석일: 2026-10-05 (`HJOW-Athlon`). 기준: 정밀 디컴파일([decompile-reliability.md](decompile-reliability.md))의 패치판 `extracted/refined/originals/Netstorm.c`와 CD판 `extracted/refined/originalCD/NETSTORM.c`, 그리고 exe 바이트(상수 값).
> **원본 게임은 실행하지 않았다.** 아래는 모두 정적 분석이며, 화면에서 직접 잰 값이 아니다. 추정은 "추정"이라고 적었다.
> 두 판본의 구조가 같으면 근거가 두 배가 되므로, 함수마다 CD판의 대응 함수를 함께 적었다. `python tools/decomp_refine.py --show <주소>` 로 나란히 볼 수 있다.

## 1. 결론

1. **한 바퀴의 순서는 "시각 고정 → 네트워크 → Windows 메시지 → 입력·명령 → 갱신 → 그리기"다.** 루프는 `WinMain`(`FUN_00438dc0`, Clientmain.cpp) 안에 있고 고정 틱이 아니라 **프레임마다 한 번** 돈다.
2. **게임 시각은 루프마다 한 번만 읽어 고정한다**(`FUN_00460e90`). 그 프레임의 모든 로직은 같은 "지금"(`DAT_0055b4d0`, 초 단위 double)을 본다. 113개 함수가 이 값을 쓴다.
3. **로직은 "프레임 간격을 곱하는" 방식이 아니다.** 프레임 간 시간차(`_DAT_0055b4e0`)를 쓰는 함수는 하나(`FUN_00467c80`, Gunanim.cpp)뿐이다. 대신 세 가지 방식이 쓰인다.
   * **절대 시각 보간** — 지상 이동(Pathprocess)과 미사일(Missile)은 출발·도착 시각을 미리 정해 두고 `(지금 − 출발) / (도착 − 출발)`로 위치를 구한다. 프레임 속도와 무관하다.
   * **"다음 시각 = 지금 + 간격" 타이머** — 애니메이션 프레임, 가이저 생성, 주기 검사 등 대부분. 실제 주기가 루프 주기의 배수로 올림된다.
   * **1/30초 고정 간격 따라잡기** — Animator3d 한 곳뿐이며, 멀티플레이 대기 화면의 섬 이동에만 쓰인다.
4. **프레임 제한은 `maxFPS`(기본 75)이고 바쁜 대기다.** `Sleep`이 아니라 시계를 반복해서 읽으며 `1 / maxFPS`초가 지나기를 기다린다. 게임 시계가 정지된 동안에는 제한하지 않는다.
5. 두 판본 모두 위 구조가 같다(루프의 호출 순서, `maxFPS` 기본값 75, 바쁜 대기, 1/30초 상수 참조 10회).

클론에 주는 의미와 적용 현황은 7절에 있다.

## 3. 시각 고정 (`FUN_00460e90`)

게임 시계 자체는 [dialog-pause.md](../gameplay/dialog-pause.md)에 정리되어 있다(`FUN_00460cd0` 게임 시각, `FUN_00460d70` 벽시계, 정지·재개). 여기서는 루프가 그 시계를 어떻게 쓰는지를 적는다.

* 시계의 원천은 `timeGetTime()`(밀리초)이고 초 단위 double 로 바꾼다: `초 = ms / 1000 + (ms % 1000) × 0.001`. **배속이나 상한은 없다.** 게임 시각은 여기서 누적 정지 시간을 뺀 값이다.
* 두 판본 모두 `timeBeginPeriod`를 임포트하지 않는다(WINMM 에서 쓰는 것은 `timeGetTime`과 `mmio*` 뿐). 따라서 시계의 눈금은 시스템 타이머 해상도를 따른다.

| 변수 (패치판) | 뜻 |
|---|---|
| `DAT_0055b4d0` (double) | **이 프레임의 게임 시각** — 정지 중이면 멈춘 값. 로직 대부분이 이 값을 본다 |
| `DAT_0055b4d8` (double) | 이 프레임의 벽시계 — 정지와 무관. UI 타이머(툴팁, 가장자리 스크롤 가속)와 네트워크가 쓴다 |
| `_DAT_0055b4e0` (double) | 직전 프레임과의 게임 시각 차이. 쓰는 곳은 `FUN_00467c80`(Gunanim) 하나 |
| `_DAT_0055b4e8` (double) | 첫 프레임의 게임 시각 |
| `DAT_0055b4a8` (int) | 프레임 번호 |
| `0x55b500`~ (double × 10) | 최근 10프레임의 벽시계 (순환 버퍼) |
| `_DAT_0055b4b8` | 이번 프레임 FPS = 1 / (지금 − 직전 프레임). 구할 수 없으면 −1 |
| `_DAT_0055b4c0`, `_DAT_0055b4c8` | 최근 10프레임 평균 FPS와 그 역수. 디버그 출력(`Frame #%d: AvgFPS %3.1f  ThisFPS %3.1f`)에만 쓴다 |

## 4. 프레임 제한 (`FUN_00436450`)

```c
// FUN_00436450 (패치판) — CD판 FUN_00486df0 도 같다
if (창이 비활성이고 전체화면이면) { /* 그리지 않는다. 제한도 없다 */ }
else {
    if (!게임_시계_정지중())                       // FUN_00460de0() == 0
        do { now = 벽시계(); } while (now - 직전_그리기_시각 < 1.0 / maxFPS);
    직전_그리기_시각 = 벽시계();
    그리기();                                       // 6절
}
```

* `maxFPS`의 코드 기본값은 **75**(`0x4b`)이고 설정 키 `maxFPS`로 바꿀 수 있다. 0 이하면 간격이 0 이 되어 제한이 없다. 간격은 `_DAT_005318e0 = 1.0 / maxFPS`다.
* **대기는 바쁜 대기다.** 남는 시간 동안 CPU 를 양보하지 않는다. `sleepPerLoop`(기본 0)을 주면 루프 끝에서 그만큼 `Sleep`한다.
* **게임 시계가 정지된 동안(안내 창·브리핑 등)에는 제한하지 않는다.** 정지 중에는 루프가 낼 수 있는 최대 속도로 돈다.
* 기준은 **직전 그리기 시각**이다. 갱신에 걸린 시간도 간격에 포함되므로, 한 바퀴가 `1 / maxFPS`보다 오래 걸리면 대기 없이 곧바로 그린다.
* (추정) 시계 눈금이 15.6ms(Windows 기본 타이머 해상도)인 환경에서는 13.3ms 를 기다려도 다음 눈금에서 풀리므로 실제 주기가 약 15.6ms(64fps)가 된다. 눈금이 1ms 인 환경(다른 프로그램이 타이머 해상도를 올려 둔 경우)에서는 약 14ms(71fps)다. [animation-timing.md](../videos/animation-timing.md)의 영상 측정(0.04초 타이머가 평균 41.9ms)은 뒤쪽에 맞는다.

## 5. 입력과 로직

### 5.1 입력·명령 처리 (`FUN_004d62b0`, Userinput.cpp)

16,945바이트(디컴파일 약 2,060줄)짜리 함수지만 구조는 단순하다. 대부분은 명령별 분기(`switch` 3개, `case` 48개와 긴 `if` 사슬)다.

1. (디버그) `DAT_005cae68`이 켜져 있으면 시험용 오브젝트 500개 생성.
2. **현재 마우스 상태 읽기** — `FUN_00452e00`(CD판 `FUN_004a6820`)이 `GetAsyncKeyState`·`GetCursorPos`·`GetWindowRect`로 `{상태 비트 | 키 코드 << 16, x, y}`를 만든다. 좌표는 창 안쪽 기준으로 바뀌고 화면 크기로 잘린다.
3. 버튼 상태가 창 밖에서 바뀐 경우를 맞추는 보정(상태 비교 뒤 이벤트를 넣는다 — 세부는 추정).
4. **가장자리 스크롤** — [edge-scroll.md](edge-scroll.md). 가속 시작 시각은 벽시계(`DAT_0055b4d8`)다.
5. 커서 위치 반영(`FUN_004a41c0`), 창 안팎 전환, 조작 모드(`DAT_005cae90`)에 따른 커서 선택.
6. **툴팁 대기** — 커서가 **0.5초**(`_DAT_00503350`, 벽시계) 동안 움직이지 않으면 그 자리의 창(플래그 `0x1000`)을 찾아 가상 함수 `+0x38`을 부른다.
7. **입력 이벤트 큐 비우기** — `FUN_00452f00`으로 이벤트를 하나씩 꺼내 큐가 빌 때까지 처리한다.
   * 화면 모드 전환 키(`0xd0000` = Enter 계열, Alt+Enter 로 추정 → `FUN_00435ba0`, `startInFullScreen` 저장), `0x7b0000`(F12).
   * 안내(Guide)가 먼저 가로챌 수 있다(`FUN_00463e40`).
   * 창(gump)에 전달(`FUN_00466200`). 창이 처리하면 다음 이벤트로 넘어간다.
   * 마우스 버튼(`0x10000` 왼쪽, `0x20000` 오른쪽)을 누르면 열린 팝업을 닫는다(`FUN_00466710`).
   * 키를 뗀 이벤트(비트 31)는 여기서 끝난다.
   * 남은 것은 등록된 명령 번호와 비교해 실행한다. 종료 명령이면 1 을 돌려준다.

이벤트 값의 구성: 비트 16~25 키·명령 코드, 비트 26 상태 플래그(`0x4000000`), 비트 27·28 수식 키(창 프로시저가 `GetKeyState`로 채운다), 비트 31 뗌. 이벤트를 넣는 함수는 13개다: 창 프로시저 쪽 3개(`FUN_00436550`, `FUN_00436020`, `FUN_00436190`)와 UI·스크립트 코드(버튼·메뉴가 명령을 넣는다).

**입력은 한 프레임에 한 번 처리된다.** Windows 메시지는 순서 7 에서 큐에 쌓이고 순서 9 에서 한꺼번에 비워진다.

### 5.2 프로세스 커널 (`FUN_00471a30`, Kernel.cpp)

```c
// FUN_00471a30 (패치판) — CD판 FUN_004ed5d0
for (각 슬롯 p in processes[1..39999])
    if (p != NULL) p->vtable[6]();       // 가상 함수 표 +0x18 = 실행 메서드
```

* 프로세스 표는 **39,999칸**이다(`DAT_0056b80c`~). 등록은 `FUN_00471950`(빈 칸을 앞에서부터 찾음, 꽉 차면 `Out of processes` 오류), 제거는 `FUN_004719e0`이다.
* 기반 클래스(Baseprocess.cpp, 가상 함수 표 `0x5019ec`)의 실행 메서드는 빈 함수다. 파생 클래스가 슬롯 6 을 채운다.
* **매 프레임 모든 프로세스가 표 순서대로 한 번씩 실행된다.** 스케줄러가 깨울 시각을 관리하지 않는다 — 각 프로세스가 고정된 게임 시각을 보고 스스로 할 일이 있는지 판단한다.

**지상 이동 (`FUN_0048a330`, Pathprocess.cpp — CD판 `FUN_0047e820`).** 경로는 꼭짓점 배열이고 꼭짓점마다 좌표(`+0x14`), **도착 시각**(`+0x9c58`, double), 방향(`+0x13898`)이 미리 계산되어 있다.

```c
if (now < 시각[cur]) {                       // 아직 다음 꼭짓점에 못 갔다
    scale = (now - 시각[cur-1]) / (시각[cur] - 시각[cur-1]);   // assert: 0 <= scale <= 1
    위치 = 꼭짓점[cur-1] + (꼭짓점[cur] - 꼭짓점[cur-1]) * scale;
    방향 = 방향[cur-1] 에서 방향[cur] 로 scale 만큼 회전;
} else {                                     // 꼭짓점 통과
    위치 = 꼭짓점[cur]; cur++;               // 한 프레임에 꼭짓점 하나만 넘긴다
    if (cur == 끝) return 도착;
    if (cur 이 짝수) 그 자리에서 소리 재생;   // 유형 정의의 +0x6c, 발소리로 추정
}
```

위치는 시각의 함수이므로 **프레임 속도가 달라져도 같은 시각에 같은 자리에 있다.** 프레임이 길게 끊기면 그 사이를 건너뛴 자리에 나타난다(꼭짓점은 한 프레임에 하나씩 넘기므로 여러 꼭짓점을 지나친 경우 따라잡는 데 몇 프레임 걸린다).

**Animator3d (`FUN_00418640`).** `_DAT_00501a10 = 0.0333…`(정확히 1/30초, CD판 `0x505cc8`도 같은 값).

```c
elapsed = now - 마지막_적분_시각;
```

밀린 시간을 횟수 제한 없이 따라잡는다. 이 클래스는 Ch.cpp(멀티플레이 대기 화면의 섬 배치·이동)에서만 만들어진다(`FUN_004192a0`·`FUN_00419730`의 호출자가 모두 Ch.cpp). **전투 중 유닛 이동과는 무관하다.**

**타이머.** 가장 흔한 형태다.

```c
if (next <= now) { 할 일; next = now + 간격; }     // 예: Flyer.cpp 0045d2c0, 간격 0.04
```

다음 시각을 **이전 예정 시각이 아니라 지금 기준**으로 잡으므로 실제 주기는 간격을 루프 주기의 배수로 올림한 값이 된다. "지금 + 상수" 꼴로 쓰이는 간격 상수는 20, 3, 0.2, 2, 10, 0.08, 4, 1, 30, 15, 60, 180, 0.02, 5초 등이다(디컴파일에서 집계).

## 7. 클론에 주는 의미와 적용 현황

클론은 24Hz 고정 틱(`FixedTimestep`)으로 규칙을 돌리고 화면은 `VisualCell` 보간으로 그린다([core-rules.md](../core-rules.md)). 원본은 고정 틱이 아니지만 **이 구조는 원본과 충돌하지 않는다.** AGENTS.md(2026-10-05)의 "기존 게임 수준의 프레임으로 먼저 만든다"에 따라 아래를 클론에 적용했다([map-viewer.md](../map-viewer.md#프레임-속도-agentsmd-2026-10-05-기존-게임-수준의-프레임-먼저)).

| 원본에서 확인한 것 | 클론 (2026-10-05) |
|---|---|
| 한 바퀴 = 입력·명령 → 갱신 → 그리기, `maxFPS` 75 상한, 실제 14ms 간격 | **적용.** 화면 루프가 14ms 간격으로 갱신 한 번 + 그리기 한 번을 돈다(`FramePacing`, 설정 `MaxFps` 기본 75, 실측 71.5fps). 이전에는 60Hz 고정 갱신 + 수직 동기였다 |
| 수직 동기를 쓰지 않는다 | **적용.** 설정 `VerticalSync` 기본 꺼짐 |
| 프레임 제한은 바쁜 대기 | **따라 하지 않음.** CPU 한 코어를 계속 쓰므로 MonoGame 고정 간격 루프의 대기를 쓴다. 간격만 같다 |
| 이동은 절대 시각 보간 (프레임 속도와 무관) | 이미 같다. 틱 사이를 화면 프레임마다 보간한다(`BattleSession.VisualCell`, `InterpolationAlpha`) |
| 애니메이션은 "지금 + 간격" 타이머 — 14ms 루프에서 0.04초 → 42ms, 0.08초 → 84ms | 이미 같다. 화면 루프 속도와 무관한 고정 간격(24Hz·12Hz 계열)으로 진행한다. 원본을 30fps·60fps 로 돌렸을 때의 느려진 주기는 흉내 내지 않는다 |
| 입력은 한 바퀴에 한 번 처리하고 같은 바퀴의 갱신에 반영 | 이미 같다. 입력은 화면 루프마다 읽고, 규칙에 영향을 주는 명령은 세션의 다음 틱 처음에 실행한다 |
| UI 타이머는 벽시계, 게임 로직은 게임 시계 | 이미 같다. 가장자리 스크롤 가속은 화면 루프의 경과 시간으로, 걷기·건물 애니메이션 시계는 게임 시간이 흐를 때만 진행한다. 툴팁(0.5초 대기)은 클론에 아직 없다 |
| 프레임마다 하는 동작: 가장자리 스크롤(프레임당 픽셀), Storm Power 숫자 따라가기(프레임마다 한 단계) | **적용.** 원본 루프의 실제 속도(1000 / 14 ≈ 71.43)로 환산했다. 이전 기준은 75 와 60 이었다 |
| 게임 시계가 정지된 동안 프레임 제한 없음, 비활성 전체화면에서는 그리지 않음 | 따라 하지 않음 (화면 결과에 차이가 없다) |

**이후 60·120프레임을 넣을 때 지킬 점.**

1. 위치는 시각으로 결정한다. 화면 루프 속도를 바꿔도 게임 속도·검사합이 달라지면 안 된다(지금 구조 그대로).
2. 애니메이션은 원본 기본 속도 기준의 고정 간격을 유지한다. 타이머가 "지금 + 간격"이라 원본은 루프 속도에 따라 주기가 달라지지만(계산값: 60fps 에서 0.04초 → 50ms, 30fps 에서 66.7ms, 120fps 에서 41.7ms), 기준은 원본 기본 설정에서의 42ms·84ms 다.
3. 프레임마다 하던 동작은 초당 값(원본 루프 속도 기준)으로 유지한다.
4. 원본의 밀리초 올림을 그대로 쓰면 `--max-fps 60` 은 17ms(58.8fps), `--max-fps 120` 은 9ms(111.1fps)가 된다. 정확한 60·120 이 필요하면 그 모드에서는 올림 없이 간격을 잡아야 한다.
