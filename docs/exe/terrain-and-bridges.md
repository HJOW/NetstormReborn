# 다리 저장 프레임과 지면 생성

> 2026-09-28 · 원본 실행 파일·타입 정의 분석, 개발용 렌더링 구현

## 다리: 저장 값은 각 칸의 프레임 번호

`Template` 저장 `004bd940`은 bridge 플래그가 켜져 있을 때 오브젝트의 `+0x24` 값을
1바이트로 저장하고, 읽기 `004bdc60`은 같은 위치에 복원한다. 이 필드는 애니메이션 프레임이다.
따라서 `.fort`의 `bridge` 값은 이웃 방향 비트나 생산 창 다리 조각 번호가 아니라
**이미 배치된 각 칸의 bridge 클러스터 번호**다.

| 저장 값 | bridge.type 클러스터 | 모습 |
|---|---|---|
| 0 | A01 | 기본 연결 |
| 35 | J01 | 세로 판자 |
| 41 | K01 | 가로 판자 |

손상·강화 프레임도 클러스터에 있으므로 저장 값을 그대로 사용한다.
원본 463개 파일의 모든 저장 다리 값이 실제 클러스터 범위에 들어간다.
`MapSpriteFrames.BodyFrame`은 클러스터 번호를 본체 레이어의 셰이프 프레임으로 사용한다.
셰이프는 레이어별로 모든 클러스터를 저장하며, `레이어 × 클러스터 수 + 클러스터 번호`로 접근한다.

VA `0x52f998`의 복합 패턴은 **새 다리 조각을 생성·배치할 때** 쓰는 별도 데이터다.
배치된 다리의 정적 렌더링에는 이 표를 적용하지 않는다. 이전 인수인계의
"저장된 bridge 값이 복합 패턴 번호" 추정은 정정했다.

## 지면 생성의 확인된 흐름

`Terrainbuilder`의 `004c10a0`은 각 영역 청크에 중심부와 연결 통로를 만든 뒤,
청크별 시드로 지면을 성장시키고 빈 틈을 두 차례 보정한다.

* 패턴의 방향 문자 A~P는 청크 연결 비트로 대응한다. VA `0x52f910`:
  `15,7,14,13,11,6,12,9,3,5,10,4,8,1,2,0` (북=1, 동=2, 남=4, 서=8).
* `Territory` 오프셋 3은 단순 외관 번호가 아니라 **청크 중심 위치와 성장 시드에 참여하는 값**이다.
* 중심 좌표는 청크 시작에 `(4 + (seed & 7), 4 + ((9999 - seed) & 7))`를 더한다.
* 중심 주변 4×4칸과 폭 2칸 연결 통로를 만든다. 각 영역의 두 번째 청크는 추가 10×10칸을 채운다.
* 초기 통로와 성장 단계는 각각 **월드 y·x 순서**로 청크를 처리한다. 영역 번호 순서가 아니다.
* 밀도 난수도 청크별 로컬 시드다. `004c117e~004c1199`에서
  `영역의 처리 전 청크 수 × 0x10e3 + 저장 시드`로 초기화하고 `004c133f`에서 `Next(30)`을 한 번 호출한다.
  추가할 칸 수는 `max(20, Next(30) + 50 - 초기 작성 칸 수 × 100 / 256) × 256 / 100`이다.
* `004c0ec0`은 영역별 청크 카운터에 `0x10e3`을 곱하고 저장 시드를 더하여 성장 시드를 만든다.
  이때 카운터는 초기 통로 단계에서 이미 영역의 청크 수만큼 증가했다.
* `004c0800`은 기존 지면에 접하는 3×3칸을 추가한다. 새 지면이 생기면 최대 실패 횟수 1,000을 초기화한다.
  후보마다 `Next(15)`를 x·y에 각각 사용하고 `Next(1)`도 소비한다. 다른 영역 청크로 확장하지 않는다.
* `004c0cf0`은 직선 방향에 기존 지면이 있는 빈 칸만 검사한다. `004c0c30`은 여덟 이웃에서
  같은 영역의 지면이 다섯 칸 이상 연속되고 마지막 방향이 홀수일 때 채운다. 결과를 즉시 반영하여 두 번 순회한다.
* 정수 난수 `004bca20`: 시드 0이면 `0x0bad0bad`, 다음 상태는 `state * 0x10003 + 3`의
  32비트 오버플로 결과, 출력은 상위 16비트의 나머지다.

## 지면 타일 선택

`004c04b0`은 직선 네 이웃과 대각선 네 이웃을 검사하여 두 방향 문자를 만든다.
비트→문자 표 VA `0x52f8fc`는 `PNOILJFBMHKEGDCA`다.
`isle.type`의 `AA`, `AB`, `BF`, `CG` 같은 클러스터 이름 앞 두 글자에 대응한다.

직접 대응되는 타일이 없으면 `0041cd20`은 양쪽 직선 이웃이 지지하는 대각선만 남기고
연결을 정규화한다. 원본 타일의 그림 참조에는 네 원소별 이미지가 있으며
`RA*`=비, `TH*`=천둥, `WI*`=바람, 나머지=태양으로 구별할 수 있다.

## 현재 구현의 검증 범위와 제한

`FortTerrainPreview`는 위 연결·시드 성장 흐름을 바탕으로 지면 미리보기를 생성한다.
Save the Island!, The War Begins! 두 맵의 반복 생성 결과가 같고 모든 타일 좌표·클러스터가 유효하다.
비 테마 타일이 다른 원소의 이미지로 바뀌지 않는 회귀 검사도 추가했다.
Windows에서 Save the Island!, The War Begins!, 느슨한 b0.fort를 각각 실행하여 PNG 캡처를 저장했다.
검증 이미지는 `extracted/screens/fort-map-terrain-*.png`에 있으며 추출 결과이므로 저장소에는 포함하지 않는다.

**원본 지면을 픽셀 단위로 재현했다고 확정한 구현은 아니다.** 현재 다음 차이가 있다.

* 원소는 해당 영역의 신전에서 추정한다. 완전한 저장 묶음이 없는 받침 미리보기는 소유자의 신전 테마로 그린다.
  원본의 플레이어 원소 선택 및 중립 영역 규칙을 직접 옮긴 것은 아니다.
* 아래 후속 작업에서 안쪽 `AA` 타일의 3×3 그림과 가장자리 타일의 원소별 후보 범위를 반영했다.
  실제 게임의 전역 난수 상태와 개별 변형 선택은 확인되지 않았다.
* 완전한 `noIsland` 3×3 묶음은 아래 후속 작업의 전용 받침으로 표시한다.
  나머지는 `noIsland` 셀과 `createsisland` 건물 발자국으로 미리보기한다.
  절벽 `fringe`와 흰 가장자리 장식은 아래 후속 작업에서 추가했다. 동적 받침 생성·그림자는 미완료다.
* 게임 모드별 특수 섬 생성, 일반 전투 섬 재배치, 패턴 셀의 세부 변형을 검증해야 한다.

## 본섬 마스크 대조와 밀도 시드 수정 (2026-09-28)

기존 구현은 밀도 난수를 시드 0에서 모든 청크에 연속 소비했다. 원본은 청크마다 영역 카운터와
저장 시드로 초기화한다. 이 차이를 수정하고 초기 통로·성장의 처리 순서를 월드 y·x에 맞췄다.
`FortTerrainPreview.IslandCells`는 작은 받침을 추가하기 전의 본섬 칸을 제공한다.

`tools/terrain_mask.py`는 원본 디컴파일·어셈블리에서 별도로 옮긴 Python 재현 도구다.
C# 결과와 256×256 전체 마스크의 SHA-256 및 영역별 칸 수를 비교하는 회귀 검사를 추가했다.
마스크는 y·x 순서의 영역 번호 1바이트이며 빈 칸은 255다.

| 맵 | 영역별 본섬 칸 수 | 마스크 SHA-256 |
|---|---|---|
| Save the Island! | Terr00: 1384, Terr07: 698 | `68e699f55ad34041f316f4466f6c33d2edb6807833a648462a64ebbc2c505cc8` |
| The War Begins! | Terr00: 954, Terr01: 551 | `b24af563875ef935aa1053d521a6abf8490c4ddea840ac1845b43223fd0436d1` |

원본 캡처 위에 본섬 경계를 겹쳐 두 맵의 돌출부·패인 부분·연결부를 시각적으로 대조했다.
타일 그림 자체의 외곽은 곡선이고 절벽·장식이 돌출하므로, 칸 마스크 경계와 픽셀 외곽은 다르다.
일반 `isle` 타일의 사각형 `(-15,-10)~(0,0)`을 적용해 경계를 표시했다.
**두 구현 사이의 전체 마스크 일치와 원본 캡처의 형태 대조까지 검증했으며,
원본 실행 중 지면 메모리와 직접 비교하거나 원본 외관의 픽셀 일치를 측정한 것은 아니다.**

재현 명령 (저장소 루트, 기존 Python 의존성 `Pillow` 사용):

```powershell
python tools/terrain_mask.py savetheisland --capture "screenShots/Save the Islands! - Started.png" --client 4 32 1024 768 --offset -2438 -907
python tools/terrain_mask.py thewarbegins --capture "screenShots/The War Begins! - Started.png" --client 3 29 1024 768 --offset -979 -795
```

결과는 `extracted/terrain/<맵>.mask`, `.json`, `.png`, `-overlay.png`이며 저장소에는 포함하지 않는다.
수정된 뷰어 캡처는 `extracted/screens/fort-map-terrain-corrected-*.png`에 있다.
분석 도구는 저장 위치를 사용하는 미션의 원점 (1,1)을 전제로 한다.

## 별도 절벽 fringe 생성 및 본체 프레임 수정 (2026-09-28 후속)

`Terrainbuilder`의 `004bfe50`을 디컴파일·어셈블리로 확인하고 `FortTerrainFringe`에 생성 규칙을 옮겼다.

* 선택된 `isle` 클러스터의 `fringe` 플래그(클러스터 메타데이터 비트 1)가 있을 때만 별도 절벽을 생성한다.
* `0049aa90`은 두 방향 문자가 일치하는 절벽 후보를 찾는다. 없으면 `0041cd20`으로 정규화,
  원래 첫 방향 + `A`, 원래 첫 방향만 일치하는 후보 순서로 폴백한다.
  실제 `EI` 지면은 `EA` 절벽, `HN`은 `HA`, `IO`는 `IA`로 대응한다.
* `004bffc7~004bfff6`은 지면과 같은 x, **지면 y + 4칸**에 절벽 기준점을 둔다.
  `0x502314`의 실수 4.0은 월드 좌표 단위다. 화면으로는 44px이고,
  `EA01` 프레임의 ymin=-43이 적용되면 지면 기준점 바로 아래부터 절벽이 보인다.
* 생성 문맥의 금지 플래그는 `004c0390`에서 설정한다. 전투 모드는 `0x10`으로 `unlit`을 제외한다.
  문맥 ID가 0인 별도 경로에서는 `0x18`로 `lit`도 제외한다. 현재 뷰어는 전투 문맥의 조건을 사용한다.
* 원본은 전역 난수로 후보를 뽑아 금지 플래그면 다시 뽑는다. 뷰어는 허용 후보 중 좌표로 고정한
  변형을 사용하므로 원본과 변형·난수 소비 순서가 같다고 보장하지 않는다.

지면·절벽·건물 순서로 그리는 개발용 표시를 추가했다. 당시 작은 받침도 미리보기 지면의
`fringe` 플래그에 따라 절벽을 붙였으며, 아래 후속 작업에서 완전한 저장 묶음을 전용 받침으로 교체했다.
Save the Island!·The War Begins!에서 아래로 돌출된 바위가 표시되며 원본 캡처와 위치를 시각 대조했다.
결과는 `extracted/screens/fort-map-fringe-savetheisland.png`, `fort-map-fringe-thewarbegins.png`다.
이 단계에서는 흰 가장자리 장식·정확한 깊이 정렬·원소 및 변형 선택에 차이가 있었다.

이 대조 중 본체 프레임 계산 오류도 수정했다. C# 뷰어는 `클러스터 × 레이어 수`를 사용했으나
이는 [기존 포맷 명세](../formats/shp.md)와 달랐다. `Clientboard.cpp`의 그리기 목록 생성 코드
(디컴파일 36518행)는 그림자를 `타입 +0x114의 클러스터 수 + 오브젝트 +0x24의 프레임`으로 찾는다.
따라서 본체는 클러스터 번호 그대로다. 가이저의 기본 `B00`은 본체 49번인데 기존 계산은
그림자 영역의 98번을 선택했다. 본체 49번과 대응 그림자 100번을 비교하는 회귀 검사를 추가했다.

추가 검사: 방향 폴백·전투 조명 4개, 두 공식 맵의 절벽 생성·위치·반복성 2개, 원본 가이저 본체 1개.
전체 46개 통과, 솔루션 빌드 성공, 두 맵의 MonoGame PNG 저장·종료 확인.
## 저장된 작은 받침 island·islandStalag 복원 (2026-09-28 후속)

`Islanddropper`의 `0046e6c0`은 작은 받침 하나에 `noIsland` 9개, `island` 1개,
`islandStalag` 1개가 있어야 한다고 검사한다. `0044bd20`의 소유자 변경 루프도 기준점
`(x,y)`에서 `(x-2,y-2)`까지의 3×3 칸을 처리한다. 기준점은 오른쪽 아래 칸이다.
`004421c0`은 윗면과 같은 좌표에 하단 바위를 만든다. 일반 절벽의 y+4칸 이동은 적용하지 않는다.

`FortIslandSupports.Find`는 저장된 `noIsland` 중 같은 소유자의 완전한 3×3 묶음만 복원한다.
`createsisland` 건물·가이저 기준점을 먼저 확인하여 서로 붙은 받침의 경계를 유지하고,
남은 완전한 묶음도 y·x 순서로 찾는다. 인식한 9칸에는 일반 `isle`·`fringe`를 그리지 않는다.
불완전하거나 소유자가 섞인 묶음은 기존 지면 미리보기에 남긴다. 본섬 마스크 `IslandCells`는 바뀌지 않는다.

색상 선택 함수 `004421a0`은 전투 중 소유자가 있으면 플레이어 색상 번호에서 1을 빼고,
그 밖에는 클러스터 8을 반환한다. `island.type`·`islandStalag.type`에는 P01~P09가 있다.
따라서 플레이어 번호 자체를 클러스터 번호로 사용하면 안 된다. 뷰어는 제공된 공식 미션 캡처에
맞춘 개발용 표(플레이어 1→색상 7 청록, 플레이어 2→색상 2 빨강)를 사용하며,
중립·미지정 색상은 테두리 없는 P09로 표시한다. 일반 플레이어 설정의 색상 복원은 후속 작업이다.

| 맵 | 복원한 받침 | 저장 noIsland 칸 |
|---|---|---|
| Save the Island! | 26 | 234 |
| The War Begins! | 13 | 117 |

두 맵에서 저장된 모든 `noIsland` 칸이 정확히 한 받침에 포함되고 소유자가 일치하는지 검사했다.
Save the Island!의 sunBlocker `(175,94,1)`과 중립 가이저 `(165,137,0)`도 확인했다.
붙은 받침·불완전한 묶음·색상 선택을 포함한 검사 8개를 추가해 전체 **54개 통과**,
솔루션 빌드 성공, MonoGame PNG 저장·자동 종료를 확인했다.
캡처는 `extracted/screens/fort-map-supports-savetheisland.png`, `fort-map-supports-thewarbegins.png`다.

이 구현은 저장된 논리 칸의 정적 복원이다. 원본 배치·드롭·연결 시 받침 생성과 소유자 전파,
깊이 정렬·그림자·일반 플레이어색은 아직 재현하지 않는다.
이 단계에서 흰 가장자리 장식은 `isle`·`fringe` 원본 프레임만으로 설명되지 않았다.
이전 조사에서 후보로 적은 `00486440`은 재확인 결과 `Make Local Geysers`를 출력하며
가이저를 배치하는 함수다. 지면 가장자리 장식의 출발점에서 제외한다.
`00498220`의 소유자 색상 변환 경로와 `isle.type`의 `rim` 클러스터를 계속 대조해야 한다.
타입·배치 규칙과 직접 연결한 근거는 아직 없다. 정적 프레임 확인 방법은
[스프라이트 탐색 뷰어](../sprite-browser.md)에 정리했다.

## 본섬 isle 소유자 색상 변환 (2026-09-28 후속)

`Renderer.cpp`의 `00498220`은 오브젝트 소유자가 0이 아니고 타입별 변환표가 있으면
`DAT_00531b08[소유자]`로 색상 번호를 구해 256바이트 표의 해당 행을 그리기에 전달한다.
`0043bc40`은 전투 표시 모드에서 `isle` 변환표를 생성하며, `0043b750`은
팔레트 인덱스 `0x2c~0x40` 및 별도 12개 인덱스의 HSL 명도에 색상별 보정값을 더한 뒤
각 색상 후보 8개 중 명도가 가장 가까운 인덱스를 선택한다. 같은 거리는 앞선 후보가 우선이다.
나머지 인덱스는 항등 변환이다. 이 표는 `!color.dat`의 고정 표와는 별도로 생성된다.

`IsleColorRemap`에 원본의 후보 표(VA `0x531a08`)와 명도 보정값을 옮겼다.
`FortTerrainPreview`는 영역 신전과 불완전한 받침의 소유자를 타일에 전달한다.
맵 뷰어는 공식 미션 캡처를 기준으로 한 개발용 플레이어 색상 번호 1→7, 2→2를 적용하고,
중립 타일은 색을 바꾸지 않는다. 텍스처 캐시도 프레임과 색상 번호를 함께 사용한다.

Save the Island! 뷰어 캡처 `extracted/terrain/player-color-map.png`를 수정 전
`current-map.png` 및 `screenShots/Save the Islands! - Started.png`와 육안 대조했다.
The War Begins!도 `extracted/terrain/player-color-thewarbegins.png`로 저장해 지면 표시를 확인했다.
본섬 윗면의 갈색 테두리가 청록색으로 바뀌며 원본의 푸른 테두리에 가까워졌다.
이 단계에서는 원본의 흰 돌출 장식이 나타나지 않았다. 아래 후속 조사에서
타입과 배치 경로를 확인했다. 일반 플레이어 설정의 색상 선택, 프레임 변형,
깊이 순서는 별도 조사가 필요하다.

## 흰 가장자리 장식 edgeFarm (2026-09-28 후속)

원본 캡처의 흰 돌출 모양은 `edgeFarm` 타입의 셰이프 프레임과 일치한다.
`edgeFarm.type`에도 `isle.type`과 같은 순서로 첫 172개 클러스터가 있으며,
`AB07` 같은 가장자리 프레임은 `isle`보다 세로로 20픽셀 이상 돌출한다.
원본 Save the Island! `.fort`에는 `edgeFarm` 오브젝트가 없으므로 저장된 오브젝트 표시만으로는
이 장식을 볼 수 없다.

`Islandbuilder.cpp`의 `0046da70`은 지면 생성 직후 영역별 `0040e560`을 호출한다.
이 함수는 영역 청크 수 × 20을 배치 목표로 `edgeFarm`을 시도한다.
`0040db90`은 `matchframe` 타입을 기존 `isle` 칸에 배치할 때 기존 프레임 번호를 가져와
그 칸을 `edgeFarm`으로 대체한다. 원본의 프레임 번호를 그대로 사용할 수 있는 이유는
타입 정의 주석의 프레임 순서 일치 규칙과 셰이프 데이터에서 확인했다.
`0043bbe0`은 `isle`과 `edgeFarm`에 동일한 방식의 소유자색 변환표를 만든다.

개발용 뷰어의 `FortEdgeFarmPreview`는 `rim` 플래그와 두 타입의 같은 번호·이름을 확인한 뒤
영역 청크당 20개를 목표로 칸을 고른다. 원본은 전역 난수와 실제 배치 가능 여부로 위치를 정하므로
현재 위치 선택은 좌표 기반의 재현 가능한 근사다. Save the Island!에서는 220개,
The War Begins!에서는 180개가 선택되며, 각 칸의 프레임·소유자 대응을 검사했다.
`extracted/screens/fort-map-edgefarm-savetheisland.png`와
`fort-map-edgefarm-thewarbegins.png`를 각각 원본 시작 캡처와 육안 비교해
흰 돌출 장식의 형태가 나타나는 것을 확인했다. 전체 검사 150개가 통과했다.
개별 배치 위치·겹침 순서·타일 변형의
픽셀 단위 일치는 검증하지 않았다.

## 안쪽 AA 지면의 3×3 그림 (2026-09-28 후속)

`isle.type`의 `JJ00` 자리표시자(클러스터 172) 뒤에는 `AA00`이 원소당 36개씩 있다.
각 원소에서 3×3 그림 네 변형이 연속으로 저장된다. 원소 순서는 해·천둥·바람·비다.
`Terrainbuilder.cpp`의 `004c04b0`은 지면 칸이 `x`이고 직선·대각선 이웃 방향이 모두 `A`일 때
이 그림을 사용한다. 원본의 프레임 번호 식은 다음과 같다.

```text
JJ00 번호 + 1 + 원소 번호 × 36 + 변형 번호 × 9 + (y % 3) × 3 + (x % 3)
```

변형 번호는 99개 값의 전역 난수표와 `(x / 3, y / 3)`에서 구하므로 같은 3×3 영역의
아홉 칸이 한 변형을 공유한다. `004c04b0`은 첫 호출에서 MSVC `_rand` 값을 99개 뽑고,
연속한 두 값의 하위 2비트가 같으면 뒤 값을 1 올린다. 이후 다음 식으로 변형 번호를 고른다.

```text
bx = x / 3, by = y / 3
변형 = (표[(표[by % 99] + 표[bx % 99]) % 99] + by) % 4
```

현재 `FortTerrainPreview`는 이 표 생성과 선택식을 재현한다. 미리보기의 결과를 일정하게
유지하기 위해 원본 `00455970`의 고정 시드 `0x38D535`와 시드 직후의 103회 `_rand`
호출을 적용한다. 실제 게임은 시간 시드 경로를 사용하거나 표 생성 전에 전역 난수를 더
소비할 수 있으므로 원본 캡처의 개별 변형 번호까지 일치한다고 보장할 수 없다.
작은 받침의 근사 지면에는 이 본섬 전용 규칙을 적용하지 않는다.

네 원소의 3×3 프레임 순서를 원본 타입 정의와 검사하고,
`extracted/screens/fort-map-core-savetheisland.png`와
`extracted/screens/fort-map-core-table-savetheisland.png`를 원본 시작 캡처와 육안 대조했다.
원본 변형 번호와 픽셀별 일치 여부는 아직 확인하지 않았다.

## 가장자리 타일의 원소별 변형 범위 (2026-09-28 후속)

`0049aa90`은 두 방향 문자가 맞는 클러스터를 타입 정의 순서로 모은다. 원소 번호가
0~3일 때 후보 수를 4로 나눈 값을 `q`라 하면 `[원소 번호 × q + 1, (원소 번호 + 1) × q)`
범위에서 변형을 뽑는다. 각 원소 묶음의 첫 프레임은 이 범위에 포함되지 않는다.
`004c04b0`의 최초 지면 생성은 원소 번호 0을 사용하고, `0046fe40`의 원소 갱신도
이 선택 함수를 원소 번호와 함께 호출한다. `isle.type`의 후보 순서는 해·천둥·바람·비다.

예를 들어 `AB01`~`AB08`은 원소별로 2개씩 있어 유효 후보가 `AB02`·`AB04`·`AB06`·`AB08`
하나씩이다. `BF01`~`BF20`은 원소별 5개씩이며 두 번째부터 다섯 번째까지 고른다.
미리보기는 이 유효 후보 집합을 사용한다. 개별 변형은 좌표로 고정하므로 원본의 전역 난수
소비 순서에 따른 선택과 일치한다고 보장하지 않는다. 불완전한 작은 받침의 일반 `AA`
폴백에서는 본섬 전용 `AA00` 3×3 조각을 후보에서 제외했다.

네 원소의 `AB` 단일 유효 프레임과 `BF` 후보 범위, 작은 받침의 `AA00` 제외를 검사했다.
전체 168개 검사가 통과했으며 Save the Island!·The War Begins! 뷰어 화면을
`extracted/screens/fort-map-edge-variants-*.png`에 저장해 육안 확인했다.
