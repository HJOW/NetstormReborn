# 후순위 계획: 60/120프레임 지원과 CD 10.72 복원·호환성 (2026-11-11)

마지막 디컴파일 PC 호스트명: HJOW-Athlon(변경 없음). LEFT_JOBS의 "1~11차 뒤 60/120프레임, CD 10.72 전체 복원·호환성의 계획을 정한다"에 대한 **계획 문서**다(구현은 하지 않았다). 근거는 현행 소스와 AGENTS.md의 요구다.

## 1. 60/120프레임

### 1.1 현행 사실

- **원본 프레임 상한은 75다.** `ClientMain.cpp`의 원문 주석에 `DAT_005318d8 = 0x4b; maxFPS`가 있고 `configuration_.ReadInt("maxFPS", maxFps_)`가 설정 파일의 `maxFPS`로 바꾼다(`frameInterval_ = 1/maxFps`).
- **제한 방식:** `Client::Frame()`이 직전 그리기 뒤 `1/maxFPS`초가 지날 때까지 벽시계를 바쁘게 기다린 뒤 `PresentScene`을 부른다. 옵션 `sleepPerLoop`(원문 `DAT_0054db0c`)이 있으면 루프마다 `Sleep`한다.
- **게임 논리는 프레임 수가 아니라 게임 시계(`Now()`, 초)로 진행한다.** Kernel은 매 루프 `RunFrame()`으로 모든 프로세스를 한 번씩 돌리고, 프로세스는 자기 시각(예: 걷기 애니메이션 12Hz, 성장 40초 주기)을 보고 움직인다.
- 따라서 상한만 올리면(60/120) **논리 상태가 같은 화면을 더 자주 다시 그릴 뿐**, 걷는 유닛/카메라의 움직임이 부드러워지지는 않는다(원문 75Hz에서도 논리 갱신 간격은 프로세스별 시각이다).

### 1.2 계획

| 단계 | 내용 | 검증 |
| --- | --- | --- |
| F1 | 옵션 메뉴에 `Frame rate`(원본 75 / 60 / 120) 하위 메뉴를 추가하고 `maxFPS` 설정에 저장한다(11차 난이도와 같은 방식: `RawGameMenus` 하위 메뉴 + Tell 구간). 기본은 **원본 75**. | 단위 + 옵션 화면 + `--render-stats`의 실측 프레임 수 |
| F2 | 상한 정확도: 바쁜 대기 대신 `timeBeginPeriod(1)`+고정밀 대기(또는 vsync Present)로 CPU 점유를 줄이고 120Hz에서 프레임 간격 오차를 측정한다. | 120/60초 실측 프레임 수 ±1% |
| F3 | 부드러움: 이동하는 객체(걷기/비행/투사체)와 카메라 스크롤의 **표시 위치를 직전·현재 논리 위치 사이에서 보간**한다(논리 갱신은 그대로 유지해 원문과 동일성을 지킨다). 객체 종류별 애니메이션 프레임률(원본 요소마다 다름)은 원본 수준으로 먼저 맞추고 그 뒤 보간을 켠다. | 같은 시드의 `--fixed-frame-ms` 결정론 비교로 논리 불변 확인, 영상 비교 |
| F4 | 소리·간격 분리: 소리 재생/동기화가 프레임 간격에 묶여 있지 않은지(`sleepPerLoop`/Kernel 뒤 갱신) 확인한다. | 소리 보고서(`--audio-report`) |
| F5 | 전체화면/와이드 해상도 조합과 FSR 후처리에서 120Hz 부하를 측정한다. | 성능 측정 |

**F1 구현 완료(제품 1297):** 옵션 메뉴에 `Frame Rate >`(60 FPS / 75 FPS (Original) / 120 FPS) 하위 메뉴를 추가했다(영·한·일 제목: `프레임 속도`/`フレームレート`). 선택은 `maxFPS` 설정에 저장하고 `Client::ApplyPresentationOptions`가 즉시 프레임 상한(`frameInterval_`)에 반영한다. 기본(설정 없음)은 원본 75다. 단위 `FrameRateOption_ParseAndNormalize`, 실제 옵션 화면에서 `60 FPS` 선택 뒤 다시 열면 60에 체크(`extracted/cpp-resume-1278/fps-en/`), 300프레임 실측: 상한 60→75→120에서 소요 시간 차이가 각각 약 1.0초·1.5초로 이론값(5.0/4.0/2.5초)과 일치했다. **F2~F5(고정밀 대기·보간·소리 분리·부하 측정)와 CD 10.72(C1~C5)는 미착수다.**

위험: 바쁜 대기를 쓰는 현행 루프는 120Hz에서도 CPU 한 코어를 점유한다(F2에서 해결). 보간은 표시 전용이므로 MP 동기화 영향이 없다.

## 2. CD 10.72 복원·호환성

### 2.1 현행 사실

- `OriginalEdition::Cd1072`는 데이터/자산 계층의 상당 부분에 이미 구분 분기가 있다(소스 40개 파일 55곳). 반면 `Patch1078` 전용 가정은 client 소스 132개 파일에 있고, 일부 몸체는 CD 판본을 명시적으로 거부한다(예: `RawCarrierPickup`/`RawAiCreate`는 `Patch1078`만 허용).
- 디컴파일: 10.72 CD판은 5,823함수(성공 5,822, 실패 1), 10.78과의 함수 대응 2,496쌍(강 1,738)이 있다([마지막 디컴파일](cpp-decompilation-20261103.md)). 원문 비교 주석(`↔ CD 004a9460` 등)이 소스 곳곳에 이미 있다.
- 설치 CD 자료는 `originalCD`에 있고 인트로 영상은 이미 배포 ZIP이 `game/`에 넣는다.

### 2.2 계획

| 단계 | 내용 |
| --- | --- |
| C1 | **구동 불가 원인 문서화:** 10.72 원본이 Windows 10에서 아예 구동되지 않는 이유(DirectDraw 열거/전체화면 모드 설정, 설치 CD 확인 `CD.NETSTORM.TITANIC.ACTIVISION`·Autorun/DSETUP 의존, 구형 `3DCARD.DLL`, 16비트 설치 흔적 등)를 **정적 분석으로** 확정해 해결 방안(10.78이 쓴 창 모드 DIB 호환 장치 재사용, CD 확인 우회를 클론 설정으로 대체, 16/256색 팔레트)을 문서화한다. 원본 실행은 AGENTS 규칙(허용 호스트 예외·사용자 확인)을 따른다. |
| C2 | **판본 게이트 목록화:** `Patch1078`만 허용하는 몸체/`Cd1072`를 명시 거부하는 위치를 표로 만들고 각 몸체의 10.72 대응 주소(주석의 `↔ CD ...`)를 연결한다. |
| C3 | **우선순위별 복원:** ① 자산·타입 표·폰트 경로(이미 일부 구분) → ② 미션/튜토리얼 시작·HUD → ③ 전투(Gun/Carrier/Ai) 순으로 CD 분기를 채우고 각 단계는 원문 fixture(10.72 기계어 오라클)로 대조한다. |
| C4 | **MP:** 10.72와 10.78의 네트워크 버전 차이(R10.71 3BYTE 존/Client 10.78 47BYTE 존의 compact 호환 범위)를 정리하고 LAN 호환 범위를 정한다. |
| C5 | **검증:** CD 자료(`originalCD`)로 클론을 `--cd`로 실행해 메인 메뉴·튜토리얼 진입을 확인한다(외부 접속·유효성 검증은 10.78과 같이 비활성). |

위험/결정: 10.72 전체 복원은 10.78 복원에 맞먹는 규모다. 우선순위(어느 모드까지)와 CD 확인 우회 정책은 사용자 결정이 필요하다.

## 3. 사용자 결정 필요

1. 60/120프레임의 범위: 상한 옵션만(F1~F2)인지 보간(F3)까지인지.
2. CD 10.72 복원의 목표 범위(C3 어디까지)와 설치 CD 확인 처리 정책.
