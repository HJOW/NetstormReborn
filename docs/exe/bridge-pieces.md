## 2. 모양 표 (VA 0x52f998)

26개 항목 × 72바이트: `가중치, 폭, 높이, 칸 15개(행 우선 y × 폭 + x)`. 방향 글자는 지면과 같은 연결 표(VA 0x52f910: 북 1, 동 2, 남 4, 서 8)를 쓴다 — A 네 방향, B 북·동·남, C 동·남·서, D 북·남·서, E 북·동·서, F 동·남, G 남·서, H 북·서, I 북·동, J 남북, K 동서, L 남, M 서, N 북, O 동, P 없음. 변형 번호는 bridge.type 클러스터 번호다(J1 → `J01`, B2 → `B02`).

## 3. 추첨 (FUN_004257c0)

```text
r = 난수 % 287
누적 = 0
표 순서로: 누적 += 가중치; r <= 누적 이면 그 모양
```

비교가 "이하"라서 **r = 0이면 가중치 0인 0번(한 칸)** 이 뽑힌다. 가중치 0인 11·12·24번은 누적값이 앞 모양과 같아 사실상 뽑히지 않는다(11·12번은 앞의 10번, 24번은 앞의 23번이 먼저 걸린다). 난수는 `FUN_004558c0(10000)` 또는 `FUN_004558f0(0, 10000)`이다.

게임 전역 난수(`DAT_00532710`): `상태 = (상태 == 0 ? 0x0BAD0BAD : 상태) × 0x10003 + 3`, 결과 `(상태 >> 16) % 상한`. 지형 생성의 `004bca20`과 같은 식이다.

## 4. 회전

`FUN_00425c20`의 회전 번호 0~3은 `param_4 / 2`다. 회전 1은 **연결을 시계 방향으로 90°** 돌린다. 방향 글자 표 VA 0x531590(회전 번호 × 16 + 글자, 32비트 글자 코드):

| 회전 | A B C D E F G H I J K L M N O P → |
|---:|---|
| 0 | A B C D E F G H I J K L M N O P |
| 1 | A C D E B G H I F K J M N O L P |
| 2 | A D E B C H I F G J K N O L M P |
| 3 | A E B C D I F G H K J O L M N P |

칸 위치는 시작 칸 표(0x531570 `{0,0,1,1}`·0x531580 `{0,1,1,0}`)와 이동 표(0x531550 `{1,0,−1,0}`·0x531560 `{0,−1,0,1}`)로 순회하며, 결과는 다음 식과 같다(폭 w, 높이 h, 원래 칸 (x, y)).

| 회전 | 회전 뒤 칸 | 회전 뒤 크기 |
|---:|---|---|
| 0 | (x, y) | w × h |
| 1 | (h − 1 − y, x) | h × w |
| 2 | (w − 1 − x, h − 1 − y) | w × h |
| 3 | (y, w − 1 − x) | h × w |

회전 뒤 칸의 월드 위치는 조각 원점(`param_5`, `param_6`) + (열, 행)이다.

### 원본 실행으로 확인한 조작 (2026-09-29)

- **조각을 든 채 오른쪽 클릭 → 90° 회전.** 기본은 **시계 방향**(회전 번호 +1)이다.
- **C 키는 조각을 돌리지 않고 "반대 회전"(옵션 Counterclockwise Piece Rotation, 설정 `rotmode`)을 켜고 끈다.** 켜진 동안 오른쪽 클릭은 반시계 방향(−1)이다.
  - `help.english`: "To rotate a bridge 90 degrees simply right-click with the mouse and to activate reverse bridge rotation, press the C key."
  - 튜토리얼 `tutorial1.english`의 "Rotating Bridges"도 오른쪽 클릭 회전을 안내한다.
- 확인 경과: 원본에서 든 조각은 5번(`J1`/`B1 K1`/`J1`/`J1`)이었다.
  - C를 켠 뒤 오른쪽 클릭 → 가로 4칸 위로 가지(회전 3)
  - C를 끈 뒤 오른쪽 클릭 → 원래 모양(회전 0)
  - 한 번 더 → 가로 4칸 아래로 가지(회전 1)
  - 모두 위 표의 회전 식과 같다.
- **들고 있는 조각의 위치:** 조각의 **왼쪽 위 칸이 커서로만 정해지고**, 조각 크기·회전과 관계없다(2×4 ↔ 4×2 회전 전후와 커서 이동에서 왼쪽 위 기준점이 같았다).
  - 칸 (cx, cy)의 기준점(스프라이트 오른쪽 아래 끝)을 월드 픽셀 (16·cx, 11·cy)로 두면, 커서가 x 기준점 −7 ~ +8, y 기준점 ~ +10 범위에 있을 때 그 칸이 왼쪽 위가 된다.
  - 1픽셀 단위 측정: x 793~808 → 기준점 800, 792 → 784, 809 → 816. y 151~161 → 기준점 151, 150 → 140, 162 → 162.
  - 클론: `BridgeCursor.TopLeftCell` = (⌊(x + 7) / 16⌋, ⌊y / 11⌋).
- 붙일 수 없는 곳에서는 조각 전체가 **순수 빨강**으로 칠해진다. 구름 위와 초목이 늘어진 섬 왼쪽 가장자리 옆에서 확인했다.
- 튜토리얼 "Bridges" 안내: 다리는 **섬 가장자리** 또는 **다른 다리의 열린 끝**에 붙여야 하고, 붙지 않았거나 아래에 무언가가 막고 있으면 전체가 빨강이다. **초목이 가장자리 밖으로 늘어진 곳에는 붙일 수 없다.** 배치 판정 분석(8절)의 기준으로 쓴다.
- 원본 사이드바는 칸의 조각을 **절반 크기**(칸당 약 8×5.5px)로 그린다.

## 6. 생산 창 다리 칸 채우기 (플레이어)

`Combatgump.cpp`가 매 프레임 다음 순서로 처리한다.

1. 생산 칸의 다리 조각 수(`iVar13`)와 그중 한 칸 조각 수(`iVar9`)를 센다.
2. **템플이 사라진 순간**(직전 +0xdc ≠ 0, 지금 플레이어 +0x7c = 0, 편집기 아님) 칸의 다리 조각을 모두 없앤다. 사용자 확인 규칙 "템플이 파괴되면 다리 조각이 덱에서 사라진다"와 일치한다([workshop-deck.md](../gameplay/workshop-deck.md)).
3. 다음 조건이 모두 참이면 새 조각을 검토한다.
   - 플레이어 +0xb0 = 0 (의미 미확인)
   - 편집기이거나 템플이 있다
   - 간격 시각이 지났다(`generatortimer` 콘솔 명령으로 끄면 매 프레임)
4. 조건이 참이면 **다음 시각 = 지금 + 1초**로 예약하고(`_DAT_00531b2c = 1`), 칸 수가 상한(전투 옵션 Bridge Slots 2/4/6) 미만이면 새 조각을 만든다.
   - 칸이 가득 차 있어도 시각은 다시 예약하므로, 칸이 비면 최대 1초 뒤에 채워진다.
5. 새 조각의 모양은 `FUN_004257c0(FUN_004558c0(10000))`로 고른다.
   - 전역 카운터 `DAT_00557dac`의 증가 전 값이 5의 배수(0, 5, 10…)이고 칸에 한 칸 조각이 없으면 **0번(한 칸)** 으로 바꾼다.
   - 이 카운터는 프로세스 전역이며 미션이 바뀌어도 초기화하지 않는다.
   - 디버그 값 `DAT_0054db7c`가 0이 아니면 그 번호로 고정한다.
6. `FUN_004afa70(bridge, 모양, 0x40, 0x10, 0)`으로 생산 칸 조각 오브젝트를 만든다. 회전은 0이다.

AI(`FUN_0040fb30`)는 자체 간격(`+0x10` + `_DAT_0055b4d0`)으로 추첨하고, **0·4·8…번째 추첨을 한 칸 조각으로 강제**한다(`카운터 % 4 == 0`). 칸에 한 칸 조각이 있는지는 보지 않는다.

### 8.3 원본 관찰과의 차이 (남은 확인)

- 모델에서 한쪽만 붙은 단일 칸은 **첫 갱신 7 → 6 → 5 → 4(금 감) → … → 0**이다.
  - 첫 갱신 뒤 약 30초 동안 보통 그림, 약 40초 동안 금 간 그림을 거쳐 약 70~80초 만에 사라진다.
  - 원본 관찰(4절)의 **금 간 기간 약 40초는 같지만**, 보통 그림이 약 120초 유지된 뒤 금이 갔다.
  - 붕괴가 시작되기 전의 대기 조건(`FUN_004218b0`의 `DAT_005453a0`·`DAT_005453a4`, 이웃 수 < 2·< 3 조건)을 더 풀어야 한다.
  - **2026-09-30 재분석 결과:** 8.1 의 세부 조건대로 따라가면 섬에 한쪽만 붙은 보통 품질 가로 한 칸은 첫 갱신에서 7, 넷째 갱신에서 4(금 감)가 되어 **30~40초** 에 금이 가야 한다. 10초 주기(프레임 시간 ÷ 10초 × 번호 범위만큼 나누어 처리, `0x422c31` 부근), 일시정지(`FUN_00460de0` = 일시정지 카운터 `DAT_0055b4b0` > 0)도 확인했지만 120초를 설명하는 조건은 찾지 못했다.
  - 같은 측정의 **서쪽 칸**(칸에 7분, 즉 보통 품질)은 놓은 뒤 51초 캡처에서 이미 금이 가 있어 모델(30~40초)과 맞는다. 동쪽 칸(칸에 48초)도 보통 품질이다. 서쪽 칸이 동쪽 칸보다 늦게 사라진 것은, 끝 칸이 무너지면 이웃 판자가 끝 칸(L~O)·수명 4 로 바뀌는 처리(`FUN_004215d0` 계열)와 맞는 방향이다(다만 이 변환의 호출 경로는 폭발 쪽에서만 확인).

### 8.4 초목 가장자리 판별 (2026-09-30 exe 확인 + 구현)

- 섬 가장자리의 초목은 지면 생성 뒤 `Islandbuilder.cpp` `0040e560`이 영역 청크당 20개를 목표로 놓는 **`edgeFarm`** 오브젝트다(이전 문서의 "흰 가장자리 장식"과 같은 것). `edgefarm.type`: `typeflags edgefarm matchframe dropBlocking walkBlocking mayDropOnRim`.
- 오브젝트를 월드에 놓을 때 `Squid.cpp` `FUN_004b02d0`이 발자국 칸마다 `FUN_004afd30`(= 타입 플래그2 `+0xec`의 하위 비트, 안쪽 칸이면 0x8 추가)을 **스폿 지도**(`Spot.cpp`, `DAT_005c7c44`, 256×256 바이트)에 OR 한다. 비트: 0x2 island, 0x4 bridge, 0x8 발자국 안쪽, **0x10 dropBlocking**, 0x20 shotBlocking.
- 배치 판정 `Rifttype.cpp` `FUN_0049b510`은 조각 주변 칸을 살필 때 스폿 비트 0x10이 있는 칸을 이어 붙일 섬 칸으로 쓰지 않는다. 그래서 **초목(edgeFarm) 칸 옆에서는 다리를 시작할 수 없다** — 사용자 확인 규칙과 같다.
- dropBlocking 을 가진 타입: `edgeFarm`, 세 신전·firevortex, 네 워크샵, outpost, residence, monument·ruin·treetwo·treethree, geyser·emptygeyser. 이 오브젝트가 선 섬 칸에서도 다리를 시작할 수 없다.
- 클론: `TypeFlagBits.DropBlocking`(0x10), `Bridges/BridgeAnchors.DropBlockingCells`(dropBlocking 오브젝트 발자국 + edgeFarm 칸) → `BridgeAnchors.CanAttach` 를 `BridgeGrid` 의 `canAttachToIsland`로 넘긴다. 테스트 `BridgeAnchorTests`: 원본 타입 플래그, 초목 칸 옆 불가·초목 없는 칸 옆 가능, 원본 Bridge the Gap! 맵의 모든 가장자리 칸 검사.

### 8.5 건물형 유닛이 없어질 때 주변 다리 약화 (2026-09-30 사용자 확인 + exe 확인 + 구현)

- **규칙(사용자 확인, 2026-09-30): 다리 붕괴 조건은 시간만이 아니다. 건물형 유닛이 파괴될 때 바로 옆에 인접한 다리도 1단계 약화되고, 이로 인해 붕괴될 수 있다.**
- exe: 전투 오브젝트 공통 vtable(예: 0x503d80, 30여 개 클래스)의 슬롯 0x18 `FUN_0044b9e0` — 오브젝트가 월드에서 빠질 때 부르는 처리(끝에 기본 처리 `FUN_004b0840`). 다리 약화 부분은 다음 조건에서 실행된다.
  - `inBattleMode`(`DAT_00594fbc`) 이고, 없어지는 오브젝트의 `+0x28 & 9` 가 0
  - `FUN_004adc60` 이 참: 타입 플래그1 0x10 — **`.type`에 `maxHitPoints`가 있으면 켜지는 비트**(typeflags 해석 `0x49d104`). 단 플래그2 `dais`(0x400000) 타입은 `+0x28` 비트 1 을 대신 보는데 앞 조건과 겹쳐 사실상 제외된다.
  - 플래그2 & 0x130000 = 0: walker·balloon·flyer(이동체)가 아니다 → **건물형 유닛·건물**만 해당
- 범위: 발자국 중심(`FUN_004adea0` = 위치 − foot × 0.5)을 소수점 버림한 칸에서 가로·세로 ±2 칸(`FUN_00422230(중심, 2, 2, 0)` → `FUN_004b16d0`).
- 칸마다(다리 타입만):
  - 금 간 칸(`FUN_004224c0`, 프레임 플래그 0x20)이고 늦춰진 낙하 예약(이벤트 0x2692, `FUN_00421fe0`)이 없으면 → **제거**
  - 그 밖에 단단하지 않으면(`FUN_00422560`, 0x40) → **금 감·수명 4** (`FUN_00421db0`)
  - 단단한 칸 → 그대로
- 이 분기는 제거 이유 플래그(`param_2`)를 보지 않는다. 회수(`FUN_0044c420`)는 `FUN_004437c0(번호, 0x200000)`으로 제거 메시지(9번)를 보내므로 **회수도 같은 처리를 거친다고 추정**한다(수신 쪽 호출 경로는 미확인, 원본 화면 미확인).
- 클론: `BridgeGrid.WeakenAround(중심x, 중심y)`, `BattleSession`이 회수 뒤 `WeakenBridgesAround`로 호출하고 `BridgeCracked`·`BridgeCollapsed` 이벤트를 낸다. 중심은 `Footprint.CenterX/Y`(홀수 크기는 가운데 칸)를 버림한다. 원본 위치 실수값(+0xe)의 칸 규약에 따라 **짝수 크기 발자국은 한 칸 어긋날 수 있다**(근사). 전투 파괴가 구현되면 같은 함수를 부른다.
- 결과: 3×3 발자국이면 둘레 한 칸, 5×5 이면 발자국 안만 범위가 된다(원본 식 그대로라면). 5×5 건물 옆 다리가 약해지는지는 원본 확인이 필요하다.
