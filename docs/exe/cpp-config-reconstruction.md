# cpppj 설정 계층 복원 (Config·ConfigInterface)

> 2026-10-05. 기준은 패치판 `originals/Netstorm.exe`(10.78), 대조는 CD판 `originalCD/NETSTORM.EXE`(10.72).
> 원본 게임 프로세스는 실행하지 않았다. 처음 복원할 때 원본 파일은 읽기만 했고, 이후 [옵션 저장 복원](cpp-options-reconstruction.md)의 검사는 허용된 설정 파일만 임시 변경 후 복구했다. [후속 계획](../cpp-roadmap.md)의 1단계에 해당한다.

원본 `Config.cpp`·`Configinterface.cpp`의 설정 객체 층, 조회·치환, 값 쓰기, 섹션, 시작 순서, 경로 지정값을 C++로 옮겼다. 조회·치환·줄 삭제·값 쓰기 대상 선택·섹션 검색은 두 판본의 x86 기계어를 격리 실행한 결과와 대조했다. 형식 규칙은 [설정 파일 문서](../formats/config.md)에 있다.

## 이번에 확인한 원본 동작

기존 문서와 달랐거나 문서에 없던 것들이다. 모두 역어셈블 또는 x86 실행으로 확인했다.

1. **찾지 못한 키는 `{Not Found:키}`가 아니라 `{키}`로 남는다.** `00440760`은 `{` 뒤에 `Not Found:`를 쓰지만 쓰는 위치를 옮기지 않고 같은 자리에 키를 복사해 덮어쓴다. 두 판본이 같다. 키는 괄호 해석에서 대문자가 됐으므로 `{c}` → `{C}`다. 최상위 조회(`Get`)는 빈 문자열이다.
2. **인코딩된 설정 파일의 첫 줄은 조회되지 않는다.** `00440380`은 복호화한 내용을 서명 `mQdsT`째로 버퍼에 붙인다. `options.cfg`는 `mQdsTInstallDir = "…"`로 시작하므로 이 줄은 `InstallDir` 키로 인식되지 않는다(시작 순서가 `InstallDir`을 따로 쓴다). `setup.cfg`는 서명 뒤가 줄바꿈이라 영향이 없다.
3. **등록 순서.** 정적 초기화 표(패치 `005280ac`, `005280b0`)에서 언어 용어표(`004fc8c0`)가 전역 설정(`004fc8e0`)보다 먼저 만들어진다. 조회는 마지막에 등록한 것부터이므로 전역 설정이 용어표보다 우선한다. 그 위에 `local`·`mission` 같은 임시 객체가 쌓인다.
4. **조회는 `this`의 버퍼가 아니라 등록된 모든 객체를 본다.** `this`는 환경 변수 허용 여부와 "버퍼가 있는가" 검사에만 쓰인다.
5. **값 쓰기의 대상 선택.** 키에 `.`이 있으면 마지막에 등록한 객체부터 `strnicmp(키, 객체 접두어, 접두어 길이)`가 0인 첫 객체에 쓰고, 키는 첫 `.` 뒤로 바꾼다. 이름 없는 객체는 길이 0 비교라 항상 맞는다. 그래서 전역 설정이 맨 위에 있을 때 `Set("a.b", v)`는 전역 설정에 `b`를 쓴다.
6. **값 쓰기는 버퍼 전체에서 같은 키를 지운다.** 삭제 범위는 키 위치부터 다음 줄 첫 글자 앞까지이며, 줄 뒤의 빈 줄과 다음 줄의 들여쓰기도 함께 지워진다. 새 값은 버퍼 끝(`[END]` 섹션)에 붙는다.
7. **저장 내용.** `00440f30`은 `[파일이름]` 섹션 본문과 `[END]` 섹션 본문을 이어 쓴다. 파일 이름 본문이 있고 서명으로 시작하지 않으면 서명을 먼저 쓴다. 파일 이름 본문이 없으면 `[END]`만 XOR하며 서명을 추가하지 않는다. 실행 중에 쓴 값은 `options.cfg`로 간다. 시작·변경 후 저장은 [후속 복원](cpp-options-reconstruction.md)에서 연결했다.
8. **명령줄 글 안의 `@낱말`.** `00440410`은 `@`로 시작하는 낱말을 파일 이름으로 보는데 `@`를 뗀 이름이 아니라 **`@`가 붙은 이름 그대로** 파일을 찾는다(`push ebp`가 `@` 위치를 가리킨다). 낱말이 글의 끝이면 원본은 문자열 끝 너머를 읽는다.
9. **`IntEquals`(`00441470`)는 0과의 비교가 항상 거짓이다.** 지역 변수 0에서 시작해 `ReadInt`가 "값이 바뀌었다"고 한 경우에만 비교하기 때문이다.
10. **섹션 검색.** 줄의 첫 글자가 `[`인 줄에서만, 그 줄 안의 모든 `[` 위치를 머리글과 비교한다. 본문이 비어 버퍼 끝이면 호출자들은 찾지 못한 것으로 다룬다.

## 새 구현이 원본과 다른 점

* **자기 참조 값.** `A = "{A}"`는 원본에서 스택이 넘친다. cpppj는 치환 깊이 32에서 그 조회를 "찾지 못함"으로 처리한다.
* **버퍼 한도.** 원본의 8KB 값 버퍼, 256바이트 서식 버퍼(`004402f0`), 1000개 객체 한도 뒤의 배열 밖 쓰기는 옮기지 않았다. 객체 수 한도는 예외로 멈춘다.
* **문자 인코딩.** 버퍼는 UTF-8이고 원본 Windows-1252는 읽을 때 변환한다. **후속 복원에서 저장의 UTF-8 BOM 확장을 제거했다.** 저장할 때 Windows-1252로 되돌려 원본과 같은 바이트를 쓴다. 원본에 없는 문자는 파일 쓰기 전에 거부한다. 이전 BOM 파일의 읽기 호환은 유지한다.
* **끝 너머 읽기.** `@낱말`이 글의 끝인 경우, `]` 없는 섹션 머리글의 이름 복사는 버퍼 끝에서 멈춘다.
* **옮기지 않은 것.** 설정 파일 위치 탐색(6개 후보 경로), 작업 폴더 변경, CD 찾기, `*.tarc` 자동 등록, 로그 출력, 레지스트리 읽기(함수가 없으면 찾지 못한 것으로 처리).

## x86 대조

```powershell
python tools/decomp_config_oracle.py     # 약 2분. extracted/oracle-python 의 Unicorn 필요
```

`tools/decomp_config_oracle.py`는 설정 객체 배열을 가상 메모리에 만들고 원본 함수를 실행한다. 두 판본의 결과가 같은 입력만 `cpppj/tests/fixtures/config-x86.tsv`에 적고, 실행 근거를 `cpppj/recovery-config-evidence.json`에 남긴다. C++ 검사 `ConfigObjectLayer_MatchesBothOriginalX86Editions`가 그 기대값을 읽는다.

| 종류 | 입력 수 | 실행한 원본 함수 |
|---|---|---|
| `Subst` 치환 | 495 | `00440b60` → `00440a00` → `00440760` → `00440150`·`0043fd70` |
| `Get` 최상위 조회 | 77 | `004409d0` (실제 설정의 경로 지정값 포함) |
| `Remove` 줄 삭제 | 272 | `00440240` |
| `Set` 값 쓰기 | 143 | `004404e0` (대상 객체, 키, 삭제 뒤 버퍼) |
| `FindSection` | 1,045 | `0043fe60` |
| `Section` | 408 | `00440570` |
| **합계** | **2,440** | |

* 입력은 규칙별 경계 사례와 시드 고정 임의 입력(치환 420개), 그리고 **실제 설정 버퍼**다. 실제 설정 버퍼는 두 판본의 `options.cfg`·`setup.cfg`를 시작 순서대로 이은 것이며, 값에 괄호가 있는 모든 키를 `local.1`~`local.3`과 함께 조회했다(`missionSpec`·`fortSpec`·`battleFortSpec`·`languageSpec`·`GamePalSpec` 등).
* 대체한 것: ASCII `toupper`·`strnicmp`·`strchr`, `getenv`(고정 표), `sprintf`(`%c%s%c`, `%c%s`), assert 보고, 값 쓰기의 서식·이어 붙이기(`004402f0` ↔ `0042acd0` — 인자만 기록). 스택 확보 함수(`__chkstk`)는 원본 코드를 그대로 실행한다.
* 제외한 입력: 파일·레지스트리를 읽는 경로로 들어간 것 2개, `]` 없는 머리글 등 원본이 버퍼 밖을 읽은 것 43개. `{@미션.키}`는 x86으로 실행하지 않았고 단위 검사로만 확인했다.
* 원본 assert가 불린 입력(머리글 줄이 줄바꿈 없이 끝나는 경우 등)은 판본마다 31번이었고 결과는 C++과 같다.

## 실제 파일 검사

```powershell
python tools/cpp_config_smoke.py
```

두 판본에서 다음을 확인한다. 결과는 `extracted/cpp-config-smoke/report.json`에 남는다.

* `--config-dump`의 설정 버퍼가 Python이 원본 파일에서 직접 구성한 버퍼와 바이트 단위로 같다(패치 18,355바이트·CD 15,536바이트 — `InstallDir` 값에 저장소 경로가 들어가므로 길이는 PC마다 다르다).
* `missionSpec`·`fortSpec`·`languageSpec`·`GamePalSpec` 경로가 기대값과 같고 그 경로의 파일이 VFS에서 읽힌다(TEST01, 캠페인 1-1 `thewarbegins`).
* `--config-save`로 값을 쓰고 저장한 파일을 기존 `tools/nscfg.py`로 복호화하면 새 값이 한 번씩만 나온다.
* 사용자 결정에 따라 원본 폴더의 `d/options.cfg`에도 저장한다. 다른 이름의 원본 폴더 출력은 대소문자·`..` 표기까지 거부한다. 스모크는 설정을 보관하고 성공·실패 모두 복구하므로 원본 파일의 SHA-256과 존재 상태가 유지된다.
* 저장의 원본 기계어 대조는 별도 [옵션 저장 복원](cpp-options-reconstruction.md)에 있다. 16개 입력 및 실제 두 판본 설정 버퍼의 최종 XOR 바이트가 일치했다.

검사 명령:

```powershell
cpppj/build/bin/Release/NetstormCpp.exe --config-dump originals
cpppj/build/bin/Release/NetstormCpp.exe --config-get originals currentLanguage
cpppj/build/bin/Release/NetstormCpp.exe --config-spec originals missionSpec TEST01
cpppj/build/bin/Release/NetstormCpp.exe --config-save originals extracted/options.cfg SCREENW=800
```

자산 검사 명령(`--inspect-assets` 등)은 이제 팔레트 경로를 설정에서 계산한다(`GamePalSpec`에 `battlePal`을 넣은 값).

## 한계

* 시작 순서와 접근 함수(`ConfigInterface`)는 정적 대조와 단위 검사다. x86 기대값은 조회·치환·삭제·대상 선택·섹션 검색 2,440개와 후속 저장·XOR 쓰기 16개다.
* CRT는 ASCII 로케일로만 검증했다.
* 설정 값의 **의미**(각 키가 게임에서 하는 일)는 이 작업의 범위가 아니다. 화면 모드·전체화면 재실행 문제는 화면 장치를 옮길 때 다룬다.
* dotnetpj의 `ConfigStore`는 찾지 못한 키를 `{Not Found:키}`로 남긴다. 위 1번과 다르다. 이번 작업에서 C# 소스는 고치지 않았다.
