# 기본/Factory 레벨 진단의 실제 Client 연결

단위 813은 실제 Session의 기본 레벨 처리기와 Factory 상태 변경 처리기에 현재 Client 진단을 연결했다. 기존 `RawSquidLevel`은 진단 복귀 뒤 현재 상태 BYTE를 다시 읽어 저장하지만 두 실제 연결점은 `SessionMissing`으로 항상 중단하고 있었다. `MakeSquidLevelAssertion`이 원문 식·파일·행을 전달하고 Session은 진단을 선택한 순간의 `services.ai.assertion`을 읽는다. 정상 0..7은 진단 장치를 요구하지 않으며 선택된 장치가 없을 때만 예외다.

10.78 `004ad110`의 범위 진단은 `0 <= n && n < 8`, `\Ns\O\Squid.cpp`, 0x579다. 10.72 `004ace20`은 같은 식, `\ns\o\Squid.cpp`, 0x562다. CD 문자열의 대소문자는 보호 PE의 실제 주소 00539f48/00539f58에서 읽어 확인했다. 원문의 항상 참인 hasLevel OR 조건, signed 범위 판정, 진단 뒤 하위5비트 재조회와 상위3비트 저장을 바꾸지 않았다. Factory의 `00475290`/CD `0042b230`은 같은 풀의 setter 복귀 뒤 기존 가상88 표시 갱신을 계속한다. Factory 모듈과 입력/업그레이드의 상태 변경 경로는 그대로다.

집중 **4개(새1개), 최종 실패0**이다. 기존 독립 원문 [레벨 관측](../../cpppj/squid-level.json)의 양판본 96행을 실제 진단 어댑터로 재생해 전체 슬롯·반환값·진단 횟수를 비교하고 식/파일/행도 확인했다. 기존 정상/범위 밖 하위비트 보존과 실제 프레임 효과 검사도 통과했다. 새 검사는 일반 Factory만 사용해 현재 서비스 교체, 진단 중 슬롯 변경, 저장→표시 순서, 선택한 장치 누락 시 쓰기/표시 전 중단, 정상 입력의 장치 불필요를 확인했다. 아웃포스트/MP 경로는 실행하지 않았다.

최초 새 검사는 콜백 입력 0x0b에 해제 비트가 포함되어 기존 할당 슬롯 쓰기 경계에서 실패했다. 제품은 수정하지 않고 유효한 0x0a로 입력과 BYTE 산술값을 교정했다. 최초 실패 로그를 보존했으며 원문 fixture는 변경하지 않았다. Release 빌드3회(게임/집중 빌드, 게임 재링크, 검사 교정 재빌드)는 모두 종료0·경고/오류0이다. 첫 빌드 중 줄바꿈을 HEAD 규약으로 정리하면서 라이브러리가 다시 컴파일되어 게임을 마지막 라이브러리로 재링크했다.

실제 Client 연결은 소스/빌드 근거이며 검사의 외부 진단과 표시는 명시 장치다. 실제 게임/GUI·사제 포획/희생·공격/승리·공중3종 전용·MP/통신·물리/PCM·전체 CTest/71대상·34경로·ZIP은 실행하지 않았다. 전체 메뉴 상태/수명이나 동일성 완료로 확대하지 않는다. 이번 범위는 checking과 무관하여 잔여30(부모21·부분6·MP3)을 유지한다.
