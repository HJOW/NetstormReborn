# 테스트용 우리 편 AI·행동 빈도·스톰파워 지원 가능성 검토

작성일: 2026-10-21. 검토 기준은 `9f70eeb3`의 cpppj 코드와 같은 PC의 기존 정밀 디컴파일 소스다. 현재/마지막 전체 정밀 디컴파일 PC는 **VM-W11-CODEX / 2026-10-21**로 같다. 사용자가 요청한 **가능성 검토와 문서화만** 수행했다. 게임·검사·빌드는 실행하지 않았고 게임 코드/설정/보호 원본도 변경하지 않았다. 아래 옵션명·수치·운영 방식은 **미구현 제안**이다.

> 후속 일반 복원: [실제 AI 지갑 가산 연결](cpp-ai-wallet-current-20261021.md)에서 보상·차감의 지갑 쓰기를 같은 Player/brain에 연결했다. 아래 “현재 분리된 지갑” 설명은 이 검토 작성 시점의 상태다. 전체 전략/초기 SP 조정/생성·삭제 목록 통지와 테스트 AI/SP 옵션은 계속 후속이며 구동 테스트를 재개한 것은 아니다.

## 판단

제안한 세 기능은 구현할 수 있다. 다만 **우리 편 AI 생성은 가능하지만, 현재 구현에서 활성화와 속도 설정만 추가해 자동 건설·클리어까지 진행할 수는 없다.** 스톰파워 지원을 먼저 준비하고, 자동 플레이는 원본 전략 AI 복원 또는 별도의 테스트용 상황 판단기를 통해 진행하는 순서가 현실적이다. 추가로 요청한 **캠페인1-1은 포획·희생의 통합 테스트 후보로 적합하다.** 같은 전략 AI 미복원 문제는 남지만, Early5의 전투/안내 진행을 반복하지 않고 신전 파괴→포획→희생 경로를 확인할 수 있다.

| 제안 | 현재 준비된 부분 | 추가로 필요한 부분 | 판단 |
| --- | --- | --- | --- |
| 데모처럼 우리 편 AI 활성화 | 같은 Session의 `CreateAi`, 생성·부착·초기 갱신·피해 반응·해제 | 전략 프레임과 다리/배치/경제 명령, 현재 지갑·생성/삭제 통지 연결 | 생성 자체는 가능. 자동 플레이 준비에는 큰 작업이 남음 |
| 우리 편 행동 빈도를 적보다 높이기 | owner별 AI 설정과 다리 공급/이동 간격 관련 원본 필드 | 실제 설정 소비자 복원, 우리 편만의 판단 주기 조정과 행동 계측 | 구현 가능. 현재 설정값만 바꾸어 효과를 낼 수는 없음 |
| 테스트에서 플레이어에게 많은 SP 지급 | `myStartMoney`, 실제 분산 SP 저장소, `SetSp`와 `AddSp` | 테스트 옵션·적용 시점·보고, AI 동시 사용 시 지갑 연결 | 세 항목 중 먼저 진행하기 적합 |

스톰파워와 행동 횟수가 많아져도 사거리·사선·유닛 대응·건설 공간이 잘못되면 패배할 수 있다. 직전 Early5의 스톤 타워 붕괴 후 썬 캐논이 먼저 파괴될 수 있는 상황은 배치/방어 판단 문제도 포함한다. 제안한 지원을 클리어 보장으로 해석하지 않는다.

## 현재 구현에서 확인한 근거

### AI 생성과 자동 플레이는 별개

[`RawMissionStart::Start`](../../cpppj/src/o/RawMissionStart.cpp)는 사제가 존재하는 owner1..8을 순회한다. 일반 미션에서는 로컬 owner를 제외하고, `demo!=0`이면 로컬 owner도 AI 생성 대상에 포함한다. [`RawCampaignMissionStartBindings::CreateAi`](../../cpppj/src/client/RawCampaignMissionStartBindings.cpp)는 기본값→공통 설정→owner 설정으로600BYTE를 준비한 뒤 같은 Session에 생성 요청을 전달한다.

[`RawAiCreate::Create`](../../cpppj/src/o/RawAiCreate.cpp)는 색 변경→기존 brain 확인→NoTemple 처리→생성→Player 부착→초기 갱신 순서다. 기존 brain이 있으면 설정을 새로 적용하지 않고 반환한다. 따라서 생성 후 속도 옵션만 바꾸거나 `CreateAi`를 다시 호출하는 방식으로 갱신된다고 가정할 수 없다. `ai<owner>NoTemple`은 신전 제거 경로를 선택할 수 있으므로 테스트 활성화 스위치로 사용하면 안 된다.

현재 [`RawCampaignSession`](../../cpppj/src/client/RawCampaignSession.cpp)은 생성자/초기 갱신, `RawAiDamage`의 피해 반응과 간헐천 등록을 연결한다. 그러나 `RunFrame`에는 전략 AI 순회가 없다. 원본의 **00417de0→00417d30→00414af0/00416eb0/004139f0/00417c70**에 해당하는 전략 순회와 후속 배치 판단은 아직 연결되지 않았다. 기존 적 썬더 캐논/훨리베이스가 공격하는 것은 이미 배치된 객체의 동작 경로이며, 적의 자동 건설 전략이 완성됐다는 증거가 아니다.

또한 `RawPlayerParticipation::AttachBrain`은 실제 Player+b0/flags20을 쓰지만, [`SquidPostPopState::aiAttached`](../../cpppj/src/o/SquidPostPop.h) 및 보상의 `aiWallet` 배열과 자동으로 같은 저장소가 되지 않는다. [`SquidPostPop`](../../cpppj/src/o/SquidPostPop.cpp)과 [`SquidDestroyLifecycle`](../../cpppj/src/o/SquidDestroyLifecycle.cpp)은 기존 `aiAttached`가 참인 해당 분기에서 AI 생성/삭제 통지 미복원을 명시 거부한다. 단순히 이 표를 true로 맞추면 새 건설/파괴 때 오류가 생길 수 있다. 미연결 통지를 빈 함수로 넘기거나 거부 조건을 지워 활성화해서는 안 된다.

따라서 원본 AI로 진행하려면 판단 루프뿐 아니라 지갑, 목록 갱신, 생성/삭제 사건과 실제 명령의 연결까지 복원해야 한다.

### 전체 데모 모드 전환은 피한다

로컬 AI 생성 분기를 재사용하더라도 `gate.demo=1`로 일반 미션 전체를 데모로 바꾸는 방식은 권하지 않는다.

- [`RawMissionFrameGate::RunFrame`](../../cpppj/src/o/RawMissionFrameGate.cpp)은 demo일 때 Early Missions1~6의 일반 튜토리얼 처리 호출을 생략한다.
- [`RawMissionOutcome::Event`](../../cpppj/src/o/RawMissionOutcome.cpp)는 demo일 때 사건 이름에 `Demo` 접두어를 붙인다.
- 데모 종료 타이머와 브리핑의 Demo 절도 별도 동작한다.

이 상태에서 희생까지 갔다고 해도 원래 Early5 단계의 자연 진행을 확인한 것이 아닐 수 있다. **일반 미션/demo0을 유지하고 로컬 owner를 추가 생성하는 테스트 경계**를 두는 편이 적합하다. 로컬 번호를1로 고정하지 않고 현재 `LocalOwner()`를 읽어야 한다.

### 행동 빈도 관련 설정

[`RawMissionAiSettings`](../../cpppj/src/o/RawMissionAiSettings.cpp)는 다음 값을 공통 `ai...`와 owner별 `ai<owner>...` 키로 읽는다.

| 설정 뒤 이름 | 설정 offset / 기본값 | 확인 범위 |
| --- | --- | --- |
| `BridgeDrawRate` | +0x220 / 6.0 | 원본00416eb0이 내부 다리 재고 객체+0x10으로 전달한다.0040fb30/0040fd30은 이 값을 현재 게임 시각에 더해 다음 공급 기한을 만든다. 일반적인 간격 축소는 공급을 빠르게 하지만 재고 상한·신전·로컬 특수 분기도 있음 |
| `StuffRefreshRate` | +0x224 / 3.0 | 파서와 본체 복사는 확인. 이번 검토에서 전체 실제 소비/상한/시간 단위는 확정하지 않음 |
| `TimeBetweenMoves` | +0x228 / 3.0 | 원본00416eb0의 조건부 `현재 시각+설정값` 쓰기와 여러 전략 함수의 +0x5a8 기한 검사를 확인. 이 값 하나가 모든 행동의 공통 주기를 뜻하는 것은 아님 |
| `StartMoney` | +0x22c / 기본 startingSp2500+4000 | 실제 brain+0x2d8의 정수 지갑 초기값 |
| `Off` / `Ability` / `Tech` | +0x254 / +0x248 / +0x1e | 활성 상태·행동 능력·기술 준비. 능력 이름이 존재해도 대응 전략 함수의 구현을 뜻하지 않음 |

현재 cpppj는 이 설정을 준비·복사하지만 해당 전략 프레임 소비자가 없으므로, `ai1TimeBetweenMoves` 등을 바꾸는 것만으로 다리/건설 빈도가 높아지지 않는다. 수치를 무조건 크게 하면 빨라지는 것도 아니다. **공급 간격, 판단 주기, 실제 명령 성공 횟수**를 각각 구분해 구현·관측해야 한다.

추후 속도 비교는 게임 시각 기준으로 우리 편/적의 판단 횟수, 다리/건설 요청 횟수와 성공 횟수를 별도로 기록한다. 우리 편 판단 주기를 우선2~4배로 조정해 볼 수 있지만 이는 테스트 제안이며 원본 값/검증 결과가 아니다. 비용·공간·공급 제한으로 실제 성공 횟수의 비율은 다를 수 있다. 전체 `World`/`Kernel`을 여러 번 호출하거나 게임 시계를 빠르게 돌리는 방법은 적의 공격·건설 시간도 함께 바꾸므로 사용하지 않는다.

### SP 지급과 AI 지갑

[`RawMissionStart::Start`](../../cpppj/src/o/RawMissionStart.cpp)는 시작 시 `myStartMoney`를 읽고 현재 로컬 플레이어의 SP를 지정한다. [`RawCampaignSession::SetSp`](../../cpppj/src/client/RawCampaignSession.cpp)는 같은 분산 저장소의 float 비트만 쓰며, [`SquidReward::AddSp`](../../cpppj/src/o/SquidReward.cpp)는 지급/차감에 더해 별도 AI 지갑과 화면 갱신도 처리한다. 에디터/고정 SP 전역은 다른 게임 규칙도 선택하므로 테스트 지급을 위해 재사용하지 않는다.

AI 본체의 지갑은 +2d8, 초기값은 `ai<owner>StartMoney`다. 현재 보상 쪽 `aiWallet`은 별도 배열이며 실제 brain 바이트에 직접 연결되어 있지 않다. 원본00416eb0에는 로컬 AI 지갑과 실제 SP가 다르면 금액을 맞추는 분기가 있고,00417c70에는 두 금액의 일치 진단도 있다. 따라서 AI를 함께 쓸 때 실제 SP만 크게 쓰면 복원된 후속 AI가 이를 되돌리거나 지갑과 어긋날 수 있다.

권장 지급 방식은 다음과 같다.

1. **AI 없이 진행하는 첫 단계:** 미션 파일을 읽은 뒤 Stage3의 시작 SP 지정 전에 메모리의 `myStartMoney`를 테스트 값으로 덮어쓴다. `MissionScript::Set`이 기존 연결점이다. 예를 들어 시작 잔액을 최소50,000 SP로 정하되 더 높은 원래 잔액을 낮추지 않는다. 로그인/요새 Money 로드 전에 지급하면 이후 로드/Start가 덮어쓸 수 있다.
2. **로컬 AI도 켜는 단계:** 위 시작 금액과 로컬 `ai<owner>StartMoney`를 함께 정하고, 실제 brain/보상 지갑 연결을 먼저 복원한다. 적의 StartMoney/속도/능력은 테스트 덮어쓰기 대상에서 제외한다.
3. **진행 중 추가 지급이 필요할 때:** 현재 owner에 대한 한 번의 지급 이벤트로 처리한다. `AddSp` 경로와 실제 brain 지갑이 연결됐는지 확인한 뒤 적용하며 지급액/전후 잔액을 기록한다. 매 프레임 `SetSp(50000)`으로 잔액을 고정하는 방식은 건설/주문/희생 보상 변화까지 가린다.

금액은 유한한 양수 정수로 제한하고 초기 시험 상한을1,000,000 SP 정도로 두는 방안을 제안한다. 이 범위는 테스트 설계값이며 원본 게임의 한도로 확인한 것이 아니다. 무한대/NaN/정수 범위 초과는 허용하지 않는다.

SP 저장의 `Set`은 이미 초기화된 경우 한 번에32비트×잡음5회의 **공유 게임 난수160회**를 소비한다. 초기화 전에는 재시드/순열 처리도 추가된다. 원래 Start의 지급값을 바꾸면 해당 기존 쓰기를 이용할 수 있지만, 별도 추가 지급은 난수 소비도 추가한다. 로컬 AI의 판단/다리 생성 역시 공유 난수 흐름에 영향을 줄 수 있다. 같은 시드를 쓰더라도 일반 실행과 테스트 지원 실행의 적 행동이 비트 단위로 같다고 주장하지 않는다. 적의 설정/시계는 그대로 유지하되 이러한 간접 차이는 기록한다.

## 캠페인1-1에서의 포획·희생 테스트 검토

### 실제 스크립트와 Early5의 차이

보호 아카이브 `originals/netstorm.tarc`의 `\d\thewarbegins.english`를 메모리에서 읽어 확인했다. 스크립트는1761BYTE이며 SHA256은 `db4fb183bc12c3b3f2f20e7a6c1ffb9d9ed0aac5401e6001372464c897ae9b96`다. 아카이브 SHA256은 `f2cafc1a0242ffe59b9b2fbfd6555907a03585cd6053d4bb4b0599a2445ea2e6`다. 게임 실행이나 파일 추출/수정은 하지 않았다.

| 항목 | 캠페인1-1의 실제 설정/조건 |
| --- | --- |
| 미션 키/제목 | `TheWarBegins` / `The War Begins!` |
| 종류/번호 | `missionType=Tutorial`, `missionNumber=1`이지만 **tutorialNumber는 없음** |
| 초기 우리 편 SP/기술 | 3000 / `sunWalker;rainBattery;sunAviary;sunCannon` |
| 공통 AI 이름/자원/기술 | `The Jailer` / `aiStartMoney=0` / `sunWalker;windBattery;sunArcher` |
| 공통 AI 행동 설정 | `aiTimeBetweenMoves=6`, 콜렉터1, 간헐천 부착1, `ENCIRCLE_ENEMY_ISLAND`·`USE_PRIEST_TO_COLLECT` 비활성 |
| 시작/성공 절 | `[A.]`의 지식 보기·미션 시작 버튼 / `[Succeeded][BadTeamDead]`의 성공 안내와 다음 미션 |

반면 실제 `tutorial5.english`는 `loadFort=SubtleDefense`, `tutorialNumber=5`, `myStartMoney=4000`, `aiOff=1`이다. 이 차이는 중요하다. **캠페인1-1은 원본의 하드코딩 튜토리얼1이 아니며 Early5의 A→B→… 안내 조건을 재사용하면 안 된다.**

사용자가 설명한 채취→방어 발사기 파괴→신전 공격→포획→희생은 실제 플레이에서 필요한 전술/경제 과정이다. 1-1 스크립트가 각각을 순서대로 강제하는 단계 목록은 아니다. 따라서 많은 시작 SP로 채취를 생략할 수는 있지만, 그 실행은 채취 기능 검증을 포함하지 않는다. 채취도 보려면 골렘의 첫 채취·귀환·SP 증가를 별도 확인한 뒤 자원 지원을 하거나 지원 금액을 조절하는 시나리오로 나눈다.

기존 [cpppj 초기 자료 감사](cpp-campaign-1-1-runtime-audit.md)는 적의 썬 디스크 발사기9·썬 바리케이드8과 양측 신전/사제를 기록한다. 기존 [원본 플레이 녹화 판독](../videos/the-war-begins-record-play-20260930.md)은 신전 파괴 후 적 사제 보호막, 골렘 운반, 제단 도착, 다섯 룬과 희생, 성공 안내까지 관측했다. 이는 이 경로가 원본1-1에 있다는 근거이며 **현재 cpppj가 그 전 과정을 GUI로 통과했다는 증거는 아니다.** 오래된 `docs/gameplay/campaign-one.md`의 임시 AI 설명은 dotnetpj 대상이므로 cpppj 전략 구현 근거로 사용하지 않는다.

### 우리 편만 켤 때 꼭 분리할 설정

`RawMissionAiSettings::Prepare`는 공통 `ai...`를 먼저 적용한다. 1-1에서 로컬 AI를 생성만 하면 공통의 **자금0·적 이름·적 기술·6초 설정·능력 금지**를 로컬도 상속할 수 있다. `RawAiBrainInitialUpdate`는 `Tech`를 실제 기술 목록에 추가하므로 원래 우리 편에 없던 `windBattery;sunArcher`까지 추가될 수 있다. 단순 활성화가 원래 우리 편의 조건을 그대로 쓰는 것은 아니다.

테스트 로컬 owner용 설정은 공통/적 설정을 수정하지 않고 별도로 준비해야 한다.

- `Tech`는 원래 우리 편의 현재 허용/생산 기술을 기준으로 한다. 공격/포획/의식에 필요한 기술이 정상 워크샾/생산 경로로 사용 가능한지 확인한다. 이름에 `dais`를 추가하는 것만으로 의식 준비가 끝났다고 판정하지 않는다.
- `StartMoney`는 테스트 SP 지급과 맞추고 이름/Off/NoTemple/동맹/능력도 로컬용으로 명시한다. 공통 `aiStartMoney`나 `aiOff`를 바꾸어 적까지 변경하지 않는다. 특히 Early5에서 같은 기능을 재사용할 때는 공통 `aiOff=1`의 상속도 주의해야 한다.
- 빠른 판단/다리 공급은 우리 편에만 적용한다. 적은 기존 값과 동작 경로를 유지하며 공유 난수에 따른 간접 차이는 보고한다.
- 원본 AI를 쓰는 방식이면 앞 절의 전략·지갑·목록/사건 연결이 선행돼야 한다. 테스트 상황 판단기 방식이면 원본 brain을 붙였다고 표시하지 않고 별도 모드로 기록한다.

### 권장 시나리오와 확인 지점

**1-1을 포획·희생 통합 테스트의 우선 후보로 추가하는 것을 권한다.** 실제 미션/demo0과 원래 승패 사건을 유지하고, 테스트 조작기가 정상 명령을 보내는 방식이다. 다음 확인 지점은 원본에 새 단계 게이트를 추가하자는 뜻이 아니라 테스트 관측 기준이다.

| 관측 구간 | 확인할 실제 상태/명령 | 실패 시 구분할 문제 |
| --- | --- | --- |
| 시작·경제 | 로컬 SP 지원 기록, 워크샾/생산·골렘 채취·신전 귀환 | 초기화 덮어쓰기, 기술/생산/경로/경제 |
| 진격·방어 제거 | 다리 연결, 제네레이터 공급, 발사기/썬 바리케이드 대응, 정상 사거리·사선의 공격 | 다리/배치 공간/목표 선택/공격 계산 |
| 적 신전 파괴 | 실제 공격으로 HP 감소→파괴, 적 사제 보호막·포획 가능 상태 | 파괴 후처리/사제 상태 전환 |
| 포획·귀환 | 운반 가능한 골렘과 실제 대상 명령, 포로 내용물/원소유자, 안전한 귀환 경로 | 포획 권한·내용물·이동 |
| 제단·의식 | 정상 건설/전달/우리 사제 참여, 다섯 룬 진행과 완료 | 다이스·배달·의식 예약/후처리 |
| 종료 | 적 사제 사망/참여 갱신, BadTeamDead, 성공 안내 | 의식 완료/승패 사건/안내 연결 |

실행 시간을 줄이려면 우리 편의 시작 SP를 지원하고 전투·다리·공급 판단을 자동화한 뒤, 포획 직전부터 사용자가 직접 조작하는 인계 방식도 가능하다. 자동 의식 확인과 사용자 조작 확인은 실행 기록에서 구분한다. 포획 직전 상태를 저장/복원해 재사용하는 기능은 별도 수명/재현성 검토가 필요하며 현재 가능하다고 전제하지 않는다.

신전 파괴로 적 사제가 포획 가능한 상태가 되는 경로와 **Devastation 주문으로 포획 가능 상태를 만드는 경로는 별도**다. 1-1의 포획·희생 성공만으로 Devastation의 시전/비용/반경/대상 효과 검증까지 완료했다고 처리하지 않는다. 주문 확인은 후속 별도 시나리오에 남긴다.

이 검토에서도 실제1-1 게임/검사 실행과 로컬 AI/SP 옵션 구현은 하지 않았다. 1-1이 Early5보다 안정적/빠르게 끝난다는 실행 결과도 아직 없다.

## 구현 방향 제안

**우선순위1은 일회성 시작 SP 지원**, 그다음은 필요한 테스트를 진행할 자동 조작 방식의 선택이다.

| 자동 조작 방식 | 장점 | 선행 작업과 한계 |
| --- | --- | --- |
| 원본 AI를 복원한 뒤 로컬만 활성화/가속 | 데모·적 AI·일반 게임 복원에 공통으로 도움이 됨 | 전략·경제·목록·생성/삭제 통지·지갑 연결까지 필요. 단순 테스트 옵션 추가보다 큰 작업 |
| 별도의 테스트용 상황 판단기 | 직전 실패를 직접 다룰 수 있음. 타워 위험도·공격 사선·다리/캐논 공간 확보를 우선 판단하도록 구성 가능 | 원본 AI 분석 결과가 아님을 명시해야 함. 별도 전략 작성과 종료 조건 필요. 정상 배치/명령 경로로만 조작하며 단계·HP·적 좌표를 직접 쓰지 않음 |

희생 관련 GUI 검증을 먼저 목표로 삼는다면 두 번째 방식에 SP 지원을 결합하는 편이 범위를 좁히기 쉽다. 예를 들어 타워 교전 상태 확인→방어 재건 가능성 판단→캐논 공격 위치/3×3 공간 보존→다리 연결→주문/포획/제단 전달 순으로 현재 상태를 읽어 명령을 선택한다. 이 절차도 아직 구현·성공 확인한 것이 아니다. 실패한 고정 좌표 입력을 빨리 반복하는 방식으로는 해결되지 않는다.

원본 AI와 테스트 판단기가 같은 owner에 동시에 명령을 보내지 않도록 한쪽만 선택한다. 사용자 입력과 함께 사용할 경우에는 개입 후 잠시 자동 조작을 쉬거나 명시 수동 전환을 제공한다. 일시정지/브리핑/단계 안내 중에는 새 명령을 보내지 않는다.

향후 인터페이스는 다음과 같이 분리할 수 있다. **아래는 제안이며 현재 CLI에는 없는 옵션이다.**

| 제안 옵션 | 의미 |
| --- | --- |
| `--test-local-ai original` 또는 `scenario` | 복원된 원본 AI 또는 테스트 상황 판단기 중 하나를 현재 로컬 owner에 적용 |
| `--test-local-ai-speed 3` | 해당 테스트 조작기의 판단 주기를 조정. 실효 행동3배를 보장하는 의미는 아님 |
| `--test-local-sp 50000` | 미션 시작 시 로컬 잔액의 하한을 일회성으로 지정 |

기본값은 모두 비활성으로 두고 일반 실행의 원본 규칙을 유지한다. 원본 파일/일반 옵션 파일/캠페인 진척에 테스트 지원 상태를 저장하지 않는다. 미션 재시작/다음 미션에서는 새 미션·새 로컬 owner·적용 횟수를 명시적으로 처리한다. 코드와 로그에는 **“테스트 전용 임시 조작이며 원본 게임 분석 결과가 아님”**을 표시한다.

기존 `--test-bridge-patterns`는 현재 로컬 생산 UI의 공급 경로에 적용한다. 원본 AI에는 별도 다리 재고/공급 코드가 있으므로 로컬 AI를 붙인다고 이 옵션이 모든 AI 공급에도 적용된다고 가정하지 않는다. 필요하다면 해당 경로도 별도 테스트 경계로 연결한다. `ㅏ`자 반복 공급을 쓰더라도 과도하게 놓아 캐논 공간을 채우지 않도록 판단기가 설치 금지/예약 영역을 관리해야 한다.

## 후속 구현의 확인 항목

- 옵션 미지정 실행은 기존 AI/SP 경로를 유지하고, 활성 실행만 테스트 지원을 보고한다.
- 로컬 owner만 지원하고 적의 설정값은 유지한다. 로컬이1이 아닌 입력, 재시작, AI 해제, 이미 존재하는 brain도 확인한다.
- 일반 미션의 demo0·튜토리얼 단계·승패 절·사제 참여와 희생 보상을 유지한다.
- 생성/삭제/보상 뒤 실제 SP·AI 지갑·목록이 일치하며 선택된 미복원 경계를 숨기지 않는다.
- 같은 게임 시각 구간의 우리 편/적 요청·성공 횟수와 거부 이유, 지급 기록, 실제 HP/SP/미션 단계, 원본/바이너리/입력 식별 정보를 남긴다. 사용자 포획/희생의 최종 상태를 직접 만들어 통과로 표시하지 않는다.
- 지원 실행의 성공은 해당 조건에서의 동작 확인으로 기록한다. 기본 자원/기본 AI 속도의 클리어 가능성이나 원본 밸런스 동일성은 별도 검증으로 남긴다.

이번 요청은 검토/문서화이므로 옵션 구현과 실제 테스트는 진행하지 않았다. 앞서 중단한 Early5 구동/희생 테스트도 계속 보류한다. 본 문서는 실행 재개 또는 자동 클리어 성공의 기록이 아니다.
