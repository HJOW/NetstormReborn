# cpppj 다리 이벤트 처리기와 끝 칸 변환

2026-10-07. **1차 기준은 10.78**이다. [객체 부착 프로세스](cpp-process-reconstruction.md)가 남겨 둔 "다리 이벤트 `0x2692`의 처리기 몸체"를 복원했다. 다리 객체의 이벤트 처리기(vtable +0x5c)와, 그 안에서 불리는 **끝 칸 변환**(패치 `004215d0`)을 raw SID 풀 위에서 구현하고 세 실제 PE의 제한 x86 기대값으로 검사한다.

소스: [RawBridgeEvents.h](../../cpppj/src/o/RawBridgeEvents.h), [RawBridgeEvents.cpp](../../cpppj/src/o/RawBridgeEvents.cpp), 글자별 프레임 구간은 [RiftType.h](../../cpppj/src/o/RiftType.h)의 `RiftTypeFrames::Run`. 검사: [BridgeEventTests.cpp](../../cpppj/tests/BridgeEventTests.cpp). 독립 결과: [bridgeevent-x86.tsv](../../cpppj/tests/fixtures/bridgeevent-x86.tsv), [감사 기록](../../cpppj/recovery-bridgeevent-evidence.json), [실행 도구](../../tools/decomp_bridgeevent_oracle.py), [내보낸 함수 목록](../../tools/ghidra/bridgeevent-functions.json).

**실제 다리 변환/낙하의 완료를 뜻하지 않는다.** 이웃 탐색기·표면 알림·새 객체 생성·가상 destroy·소유자 지정·Pop은 호출자가 연결하는 외부 효과이며, 이 어댑터는 그것들을 원본과 같은 순서·인자로 부를 뿐이다. Kernel 프레임을 게임 루프에 잇는 일과 raw GameWorld 연결은 남아 있어 미션에서 다리가 실제로 떨어지지는 않는다.

## 이벤트 처리기

호출 규약은 `thiscall(이벤트, 횟수, payload)`이며 반환은 x87 `ST0`의 float이다. 횟수는 읽지 않는다.

| 이벤트 | 권한 있음 | 권한 없음 |
|---|---|---|
| `0x2691` | 자기 destroy(vtable +0x10, 인자 0), **-1.0** 반환 | 0.0 반환 |
| `0x2692` | payload를 `_ftol`해 `x = 하위 8비트`, `y = 부호 있는 >> 8`로 풀고 끝 칸 변환, **-1.0** 반환 | 0.0 반환 |
| 그 밖 | payload를 그대로 반환 | payload를 그대로 반환 |

반환 -1.0은 Regular 프로세스 계약에서 "그대로 둔다"이고 0.0은 "종료"다. 즉 권한이 없는 쪽에서는 낙하 예약이 사라진다. 상수는 `00502350`/`005019dc`(-1.0)와 `00500fc4`/`005019e0`(0.0)다. payload는 [지연 낙하 예약](cpp-bridgeeffects-reconstruction.md)이 `(x & 255) | (y << 8)`을 float로 바꾼 값이며, 처리기는 그것을 `fild`/`fstp`로 다시 float 두 개로 푼다. `_ftol` 하위 DWORD이므로 비유한 값·64비트 밖의 값은 하위 0이 되어 (0, 0)이다.

## 끝 칸 변환 (`004215d0`)

`(x, y)`는 낙하 예약이 가리키던 칸 좌표다. 순서는 다음과 같다.

1. 디버그 유지(`0054db80` / CD `0052e928`)가 켜져 있거나 권한(`00540bc4` / CD `00540a2c`)이 없으면 아무것도 하지 않는다.
2. **방향 글자**는 현재 프레임 코드의 첫 바이트다. `J`이면 객체의 y를 인자 y와, `K`이면 객체의 x를 인자 x와 비교한다. `J`: `objY < y`이면 **N**, 아니면(같거나 NaN 포함) **L**. `K`: `objX < x`이면 **M**, 아니면 **O**. 다른 글자는 아무것도 하지 않는다. 패치판은 `fcomp` 뒤 `test ah,5`/`jp`, CD판은 피연산자를 바꿔 `test ah,0x41`을 쓰지만 같은 판정이다(NaN은 모두 L/O 쪽).
3. 타입의 **글자별 첫 프레임 표**(`type + 0x2c + 글자*4`)에서 바꿀 프레임 번호를 읽는다. 아래 절 참조. 이 프레임을 임시로 객체에 쓴다(패치 +0x24 DWORD, CD +0x22 바이트).
4. 이 상태에서 flag 8 **표면 이웃 탐색기**(`004b23e0`)를 만들고 첫 이웃 번호(탐색기 +0x34)를 읽은 뒤 **곧바로 원래 프레임을 되돌린다.** 이웃이 없으면 가상 destroy(0)를 부르고 끝낸다.
5. 수명 단어(+0xc)의 3~6비트를 `(금 간 수명 - 1)`로 쓴다. 금 간 수명(`0052f960`/CD `0051f05c`)이 5이므로 **4**다. 이어 표면 알림을 부른다.
6. **단단한 프레임 검사:** 프레임 코드 플래그 0x40이 켜져 있으면 여기서 끝난다(객체를 교체하지 않는다). **검사 대상은 새 끝 프레임이 아니라 되돌려 놓은 옛 프레임이다.** 기계어가 `mov ecx,[esi+0x24]`를 되돌린 뒤에 읽는다.
7. 아니면 같은 타입의 새 객체를 만들어(`004af530(타입, 0)`) 끝 프레임을 쓰고, 옛 객체의 소유자 바이트로 가상 소유자 지정(+0x74)을 부르고, 옛 수명 단어를 단어 쓰기로 옮긴다(새 객체의 타입이 다리 타입이면 표면 알림). 부모 단어(+8)를 복사하고 플래그의 0x10 비트만 옮긴다. 옛 위치 float을 읽어 옛 객체를 destroy(0)한 뒤 새 객체를 같은 위치에 Pop(+0x90, flags 0)한다.

소유자·플래그 필드의 위치는 판본마다 다르다: 패치는 소유자 +0x22·프레임 +0x24(DWORD)·플래그 +0x28, CD/10.37은 소유자 +0x20·프레임 +0x22(바이트)·플래그 +0x23이다. 위치 float은 둘 다 +0xe/+0x12다.

## 글자별 프레임 구간 표 (`0049b060` ↔ CD `00444da0`)

타입 구조체에는 방향 글자 `A`~`P` 16개마다 **첫 프레임 번호**(+0x130, 없으면 -1)와 **프레임 개수**(+0x170), 그리고 구간이 있는 글자 수(+0x12c)가 있다. 프레임 코드 배열을 앞에서부터 훑어 만든다. `RiftTypeFrames::Run(글자)`·`LetterKinds()`가 같은 값을 돌려준다. 끝 칸 변환이 읽는 `type + 0x2c + 글자*4`는 같은 표이며 `L`~`O`는 `+0x15c`~`+0x168`이다.

타입 로더가 이 함수를 부르는 위치와 실제 `bridge.type`의 표 값은 아직 대조하지 않았다. 지금은 프레임 코드 배열에서의 계산만 원본 기계어와 같음을 확인했다.

## x86 대조 결과

새 도구 [decomp_bridgeevent_oracle.py](../../tools/decomp_bridgeevent_oracle.py)가 세 실제 PE에서 Unicorn으로 실행한다. 처리기 몸체·끝 칸 변환·방향 글자·타입 조회·단어 쓰기·`_ftol`·글자 표 생성은 **실제 명령**이다. 이웃 탐색기 생성(첫 이웃 번호는 입력)·표면 알림·새 객체 생성(타입/가상 표 헤더만 기록)·가상 destroy/소유자/Pop은 호출 사실과 인자만 기록하는 대체다. 타입 표와 프레임 코드는 합성이며 다리 타입 번호는 실제 초기값 82다.

| 입력 종류 | 개수 |
|---|---:|
| 이벤트 처리기(세 PE × 1,207) | 3,621 |
| 끝 칸 변환 직접 호출(패치만) | 726 |
| 글자 표(세 PE·두 정밀도에서 같아 한 번만 저장) | 306 |
| 합계 | **4,653** |

처리기 입력은 현재 프레임 글자(J/K/A/L)×위치 5개×payload 22개의 판단 격자, 프레임 변형 3종(교체 금지 프레임 배치)·현재 프레임·이웃 유무·다리 타입 전역·수명 단어·소유자·부모 단어·플래그의 효과 표본, 권한/디버그/이벤트 번호(0x2691·0x2692·인접 번호·0·0xffffffff 등) 가드 격자다. 끝 칸 변환 직접 호출은 객체 위치 2개×인자 좌표 11개²(경계·NaN·±무한대 포함)×프레임 3개다. 두 x87 정밀도(53/64비트)의 관찰이 모든 입력에서 같았다. 모든 호출의 정상 반환·스택 복구·x87 TOP/제어 워드를 확인했고 원본 assert 도달은 0이다. 슬롯 쓰기는 다리의 수명 단어·프레임과 새 객체의 프레임·단어·+8·플래그 외에는 거부한다. 이웃 탐색기에 임시 프레임이 쓰인 상태에서 호출되는지도 사건에 프레임 값을 기록해 대조한다.

**제한:** CD/10.37은 끝 칸 변환이 처리기에 인라인되어 직접 호출 행이 없다. 그 판본은 정수 좌표 payload가 닿는 범위만 대조한다(NaN 같은 경계는 패치판 직접 호출로만 확인). 이웃 탐색기의 실제 결과·새 객체의 실제 생성/Pop/소유자 등록·표면 알림의 실제 효과는 이 단계의 범위가 아니다.

```powershell
# 1) 읽기 전용 Ghidra 내보내기 (프로젝트 변경은 저장하지 않는다). 결과: extracted/bridgeevent/<판본>/
powershell -ExecutionPolicy Bypass -File tools/ghidra/export_functions.ps1 -Name bridgeevent
# 2) 기대값 생성(약 3분) / 저장된 기록 확인
```

## 최종 검증

x64 Release 경고/오류 0, 콘솔 CTest 실행 파일 1개 안의 내부 **205개·실패 0**(104.23초; 이전 200개 + 이 단계의 새 검사 4개 + 프로세스 단위 테스트 1개), 누적 제한 x86은 **106,786개**(보강 재생성한 프로세스 5,893을 반영한 앞 합계 102,133 + 4,653)다. 새 검사 4개는 세 PE 처리기/끝 칸 변환 fixture 재생과 글자별 구간 표 재생이다. 새 도구의 `--verify`(도구·fixture·내보내기·원본 SHA와 행 수) 통과, 원본 assert 도달 0, 두 x87 정밀도 관찰 불일치 0이다.

**변이 확인**([도구](../../tools/cpp_mutation_check.py)): 이 단계의 구현을 일부러 한 군데씩 틀리게 바꿔 검사가 잡는지 확인했다. 6개 모두 검출됐다 — 단단한 프레임 검사를 새 프레임의 플래그로 함(3개 판본 fixture 검출), J 칸 방향 판정에서 NaN을 N으로 취급(패치 직접 호출 행만 검출, CD/10.37은 정수 payload라 닿지 않음), 수명 비트를 금 간 수명으로 씀, 플래그 비트 복사 생략, 권한 없을 때 유지(-1) 반환, 글자 구간의 첫 프레임 대신 마지막 프레임 기록.

## 2026-10-08 후속: 처리기 연결·실제 프레임 확인

- **처리기 분배:** `MakeBridgeRegularHandler`가 `SquidProcessHost`의 부모 이벤트 처리기를 **객체의 가상 표 기록값**으로 분배한다(원본의 가상 호출과 같은 기준). 슬롯 +0의 DWORD가 다리 클래스(`005034c8`/CD `00501ab0`)이면 다리 처리기를, 아니면 넘겨받은 처리기나 base(payload 반환)를 부른다. 지연 낙하 예약 → Kernel 프레임 → 분배 → 끝 칸 변환 → 권한이 없을 때의 예약 종료까지를 단위 검사 한 개로 확인했다(외부 효과 훅은 기록만 하고 소유자 지정만 실제 함수에 이었다).
- **"표면 알림"의 정체:** 패치판 `004214a0`은 상태를 바꾸지 않는 **디버그 검사**다. 객체가 다리 타입(`005411a0`)이고 buried가 아니며 assert가 켜져 있을 때(`005e4794`) 수명 비트(+0xc의 3~6비트)가 7을 넘으면 `num >= 0 && num <= 7`(Bridge.cpp 255행) assert를 보고할 뿐이다. CD판 `00448c10`은 슬롯 주소만 돌려준다. 따라서 이 훅은 연결하지 않아도 게임 상태가 같다(호출 순서 대조를 위해 훅은 남겨 둔다).
- **글자 표를 만드는 시점:** `0049b060`은 타입 후처리 `0049b0d0`가 모든 타입에 대해 부른다(호출 위치 `0049b4b8`, CD는 `0044519d`). 발자국 y 6→8 보정 바로 앞이다.
- **실제 `bridge.type`:** 프레임 60개, 글자 16종. J는 35번부터 6개·K는 41번부터 6개이고, 끝 글자의 첫 프레임은 **L 47·M 50·N 53·O 56**(각 3개: 보통 1·금 간 11·단단한 20)이다. 첫 프레임은 모두 보통 프레임이므로 끝 칸 변환은 보통 끝 프레임으로 바꾼다. J·K에서 교체가 막히는 것은 번호 20(플래그 0x40) 프레임 둘뿐이다. 값은 [다리 붕괴 기대값](../../cpppj/tests/fixtures/bridgedecay-x86.tsv)의 `Frames 0` 행(원본 자산에서 읽은 프레임 코드)으로 검사한다.

원본/복사본 실행과 창 검사는 이 작업에서 하지 않았다.
