# Edit Template 저장·삭제의 공유 경로 고리 (단위740)

2026-11-02 / HJOW-Athlon / Windows10. 마지막 전체 정밀 디컴파일은 **HJOW-Athlon / 2026-10-23**이며 새 디컴파일은 없다.739의 게임/테스트/전체 선택 빌드 우선 요청을 완료한 뒤 기존1~2차 파일 수명을 이어 진행했다. 현재 실행 제품은 **740 / 표시11.01**이다.

## 원본과 연결

738은 실제 Edit의 조회/읽기에 Client의 같은 경로 소유자를 연결했지만, Template 저장과 삭제는 직접 CRT로 넘어가 원문 경로 버퍼 사용을 건너뛰었다. 기존 뷰를 다른 소비자가 빌린 상태에서 저장/삭제를 실행하면 열 칸 고리의 번호와 뷰가 덮어써지는 시점이 달라졌다.

이번에는 원본10.78 PE의 여섯 함수와 현행 전체 디컴파일을 정적으로 대조했다. 실제 Template 저장 `0044d8d0 → 0041bb90 → 0041b4c0`은 절대 장치 판정 `00459900`을 한 번 실행한다. `0041a5b0`의 r+b 실패 뒤 w+b 생성은 같은 상위 판정을 반복하지 않는다. 삭제 `0041aef0`도 절대 경로의 성공/실패와 무관하게 먼저 같은 getter를 한 번 호출한다.

반면 저장 부모의 `004f868b` chmod는 현재 파일명으로 CRT를 직접 호출하므로 경로 getter를 사용하지 않는다. chmod에 불필요한 예약을 추가하지 않았다. 호스트 전용 작업본 준비/일반 잘라쓰기에도 새 원문 호출을 합성하지 않는다.

`EditorFiles::WriteTemplate`과 `Delete`에서 기존 보호 경로 검사 뒤 `ReadBaseFileDevice`에 같은 `fileNames_`를 전달했다. 읽기와 같은 실제 Client 주소/번호를 사용하며 새 소유자를 만들지 않는다. 기존 r+b/tail 보존/쓰기·닫기 반환 정책, 삭제 실패 무시, 원본/CD 보호, UTF-8/W CRT 호환 처리는 유지한다. Windows10/11의 Unicode 파일 경로에 원본 ANSI 대신 W CRT를 쓴다는 기존 주석도 유지했다. 원문 FILE 예외 객체의 전체 ABI나 다른 쓰기 부모를 새로 복원한 것으로 확대하지 않는다.

연결한 getter는 기존 RawFileName의256BYTE 물리 범위 밖 입력 거부 정책을 그대로 사용한다. 긴 절대 경로 전체의 호환성을 새로 확인한 작업은 아니며 해당 범위까지의 원본 동작 일치를 주장하지 않는다.
