# C++ 다리 복원: 판본 차이·기계어 검증·후속 작업

2026-10-05. AGENTS.md·LEFT_JOBS.md와 현재 소스를 확인한 뒤, 다음 복원 대상인 다리의 계산 부분을 원본 패치판 10.78·설치 CD판 10.72와 대조했다. 원본 게임은 실행하지 않았다. PE 파일의 선택 함수만 Unicorn x86 환경에서 실행하고 실제 자산을 읽었다. AGENTS.md·원본 자료·C# 소스는 수정하지 않았다.

현재 cpppj는 메뉴→캠페인→브리핑→기본 지형/객체·선택/사제 이동·카메라·정지/복귀까지 연결되어 있다. 이번에는 다리 모양·추첨·회전/프레임 반복·열린 방향·수명 비트 갱신의 일부를 C++로 복원했다. **다리 배치 UI와 동적 표면 그래프, 전체 붕괴는 아직 GameWorld에 연결하지 않았다. 건설·경제·전투·AI·승패가 없어 미션 완주는 여전히 불가능하다.**

### CD판을 대조해 발견한 데이터 차이

다리 표는 패치판 `0052f998`, CD판 `00514a80`의 26개×72바이트다. 폭·높이·15개 셀의 모양과 회전 표는 같지만 **가중치는 같지 않다.** 0부터 센 조각 번호의 차이는 다음과 같다.

| 조각 번호 | 패치판 가중치 | CD판 가중치 |
|---|---:|---:|
| 22 | 1 | 10 |
| 23 | 1 | 10 |
| 24 | 0 | 1 |
| 합계 | **287** | **306** |

따라서 판본별 표를 따로 생성했다. 기본 게임 기준은 패치판이다. 실제 추첨의 `나머지 <= 누적 가중치` 비교를 보존하므로, 입력 0은 가중치 0인 첫 조각을 고른다. 음수 나머지도 원본의 부호 있는 연산대로 처리한다. 같은 입력 10,005개 중 두 판본의 결과 8,733개가 다른 것은 이 데이터 차이에 따른 결과다.

### 잘못 연결된 함수 대응을 수정

기존 자동 대응 `004217f0`↔CD `00449e30`은 전체 열린 끝 탐색(`ret 4`)을 한 방향 검사(`ret 8`)에 연결한 오대응이었다. 실제 짝은 `00421770`↔CD `00449e30`이다. CD판의 전체 판단은 `00449250`에 인라인되어 별도 함수 짝을 만들 수 없다.

[기계어 검증 기록](../../cpppj/recovery-bridge-evidence.json)의 7개 완전 함수 대응을 검토 앵커로 추가하고 오대응을 금지했다. [decomp_refine.py](../../tools/decomp_refine.py)는 원본/생성 도구/기대값 SHA-256과 호출 규약·`ret N`을 확인한 뒤 적용한다. 접두 구간만 검사한 수명 함수는 검토 앵커에서 제외했다. 재생성한 대응은 **2,494쌍, 검토 앵커 12쌍**이다. strong 1,733·medium 710·weak 51, 호출 규약 일치 2,311/2,377, `ret N` 일치 2,338/2,387이다. 대응 수 감소는 잘못된 짝을 제거한 결과이며 복원 후퇴를 뜻하지 않는다.

### 디컴파일 C에서 빠진 실수 연산

표면 조회 `0040eaf0`는 실제로 float 좌표 두 개를 받아, 패치판 `00500edc`의 단정도 상수 **0.9999f**를 더하고 `_ftol`로 0 방향으로 잘라 칸을 고른다. 비트는 `3f7ff972`, 정확한 값은 `0.9998999834060669`다. 일반적인 반올림으로 바꾸면 경계 입력의 표면 번호가 달라진다.

좌표에 이웃 이동량을 더한 결과는 float지만 상수를 더한 x87 중간값을 다시 float로 좁히면 안 된다. 새 C++는 이 중간 합을 double로 보존하고 정수로 변환한다. 0/256 경계, 음수, 편향 합이 정수 바로 아래인 입력을 원본 기계어로 대조했다.

## 2. 검증 결과와 제한

[decomp_bridge_oracle.py](../../tools/decomp_bridge_oracle.py)가 원본 기계어의 기대값을 [bridge-x86.tsv](../../cpppj/tests/fixtures/bridge-x86.tsv)에 생성한다. C++ [BridgeTests.cpp](../../cpppj/tests/BridgeTests.cpp)는 생성 도구의 계산을 정답으로 삼지 않고, 원본이 남긴 반환값·난수 상태·프레임/좌표 비트·수명 단어/제거 인자를 비교한다.

| 사례 | 입력 수 | 대조 범위 |
|---|---:|---|
| 가중 추첨 | 10,005 | 두 판본 각각의 실제 결과, 극단/음수 포함 |
| 난수 | 1,056 | 132개 상태×8개 제한, 다음 상태와 결과 |
| CanonDecoder | 752 | 다리 26+영역 68개×4회전×2프레임 구성, 전체 출력 순서 |
| 열린 방향 | 5,760 | A~P×8방향×9좌표×5지도/이웃 구성(균일 4·비균일 1), 전체 방향은 패치판만 |
| 수명 접두 구간 | 480 | 이전 수명·목표 수명·Battle 여부·J/K/B, 비트/제거 플래그 |
| 합계 | **18,053** | 전체 게임이나 전체 붕괴의 검사 수가 아니다 |

정상 함수는 허용한 함수 몸체 안에서만 실행하고, 명령 수 200,000 제한·복귀 EIP·ESP/`ret N`을 검사한다. 네이티브 메모리 쓰기는 시험 객체·시험 스택·추첨 캐시·난수 상태로 한정한다. 서로 다른 쓰기 대상의 주소/크기 조합은 패치판 51개·CD판 53개였다(기록의 `native_write_sites` 값이며 명령어 위치 수가 아니다). OS 함수와 게임 프로세스는 실행하지 않는다. `_ftol`은 실제 CRT 기계어로 실행했다. 일부 프레임을 의도적으로 제거한 사례의 assert 보고만 대체했다(각 판본 111회). 이 보고 함수의 구현까지 검증한 것은 아니다.

열린 방향 입력의 다섯 번째 지도는 각 칸 번호가 `0/7/8/9[(x+3*y)%4]`인 비균일 지도다. 기대값 TSV의 지도 값 `65536`은 이 입력을 선택하는 표시이며 실제 표면 번호가 아니다. 균일 지도만으로 놓칠 수 있는 내부 칸 주소 계산 차이를 원본 반환값으로 검사한다.

수명 함수는 패치판 `00421c7b`/`00421cb6`, CD판 `0044a210`/`0044a241`에서 첫 외부 효과 전에 중지한다. 정상 복귀까지 실행하지 않는다. Battle 모드에서 수명 0이면 이전 상태 단어를 보존하고 제거 호출을 예약하며, J/K 판자는 `02000000` 플래그를 넘긴다. 다른 경우에는 `0x78` 수명 비트만 갱신한다. 금 간 프레임·화면 갱신·탑승 객체 낙하·실제 삭제·재귀 붕괴는 후속이다.

현재 Release 빌드는 경고·오류 0, **CTest 1개 실행 파일의 내부 검사 75개**가 통과했다. 기존 x86 기대값 5,365개에 이번 18,053개를 더해 **23,418개 입력 사례**다. 이 중 수명 480개는 접두 구간 검사이며 전체 함수 검사로 세지 않는다.

[cpp_bridge_smoke.py](../../tools/cpp_bridge_smoke.py)는 `--inspect-bridges` 출력과 실제 PE 표/타입 자산을 독립 Python 판독기로 비교한다. 두 판본 각각 **26모양·104회전·468셀**, 합계 936셀의 프레임·좌표·방향·번호가 일치했다. 검사 전후 원본 두 폴더 **1,819개 파일**의 해시와 존재 상태가 같았다. 영역 반복자 회귀를 포함한 `cpp_fort_smoke.py`도 두 판본 **488요새·320,634객체·326,169비교 행**을 통과했다.

## 3. 신뢰도를 더 높이는 방법과 이번 적용

1. **원형과 구조체를 확인한 함수에만 적용한다.** ECX·스택 인자·반환형·오프셋·`ret N`을 어셈블리/두 판본/실제 입력으로 확인한다. [Ghidra 공식 안내](https://ghidra.re/ghidra_docs/GhidraClass/Beginner/Introduction_to_Ghidra_Student_Guide.html)는 자료형·함수 원형 수정이 디컴파일과 호출자 해석에 전파됨을 설명하며, Parameter ID가 추정 원형을 잠그므로 충분한 자료형 정보가 있을 때 사용하도록 안내한다. 전체 함수의 추정을 일괄 확정하지 않는다.
2. **출력 C의 의미를 실제 명령으로 재검증한다.** signed remainder·char 확장·16비트 마스크·x87 `_ftol`처럼 의미가 쉽게 달라지는 부분에 경계 입력을 넣고 반환/출력 메모리를 비교한다. [Unicorn 공식 문서](https://www.unicorn-engine.org/docs/beyond_qemu.html)의 실행 계측 기능을 이용해 이번에는 코드 범위뿐 아니라 메모리 쓰기도 제한했다. 실행 제한의 사용법은 [공식 예제](https://www.unicorn-engine.org/docs/tutorial.html)를 참고했다.
3. **CD판의 구조와 데이터 차이를 분리해 기록한다.** 인라인 함수는 억지로 짝짓지 않고 호출자 안에서 확인한다. 테이블 차이는 별도 판본 데이터로 보존한다. 영상/스크린샷은 이후 실제 동작·시각·소리의 증거로 보완한다.
4. **근거를 다시 만들 수 있게 보관한다.** 바이너리·생성 도구·기대값 해시, 검토/거부한 짝, 호출 규약, 중지 주소, 대체 함수와 미검증 범위를 함께 기록한다. 같은 코드에서 만든 계산식만 서로 비교하면 독립 검증으로 취급하지 않는다.

[ApplyBridgeTypes.java](../../tools/ghidra/ApplyBridgeTypes.java)는 `CanonCell32`·72바이트 패턴·0x54 CanonDecoder·판본별 타입/다리 객체·표면 번호 목록과 원형을 적용한다. [recover_bridge_types.ps1](../../tools/ghidra/recover_bridge_types.ps1)로 읽기 전용 정밀 프로젝트에서 패치판 9개·CD판 8개 함수의 `typed-bridge.c`를 생성했다. 기존 프로젝트의 변경은 저장하지 않았다.

**자료형 적용 뒤에도 `SurfaceAtRoundedPosition` 출력에는 x87의 편향 덧셈이 빠진다.** `_ftol`의 ST0 입력이 아직 표현되지 않기 때문이다. 원형 적용 성공이나 디컴파일 성공 표시만으로 식의 완전성을 판단하지 않는다. 후속으로 ST0 입력/EDX:EAX 반환 저장 규약을 개별 복구하고 호출자 식이 실제 명령과 맞는지 다시 확인한다. 현재 C++ 식의 근거는 어셈블리와 실제 기계어 입력 대조다.

재현 명령은 저장소 루트에서 실행한다. 기대값 재생성에는 Python·Unicorn·PE 판독 환경이, 자료형 디컴파일에는 기존 정밀 프로젝트·Ghidra·Java가 필요하다. C++ 빌드/CTest는 저장된 기대값을 사용하므로 이 분석 도구가 필요 없다.

```powershell
python tools/cpp_canon_tables.py
python tools/decomp_bridge_oracle.py
python tools/decomp_refine.py
powershell -ExecutionPolicy Bypass -File tools/ghidra/recover_bridge_types.ps1
cmake --build cpppj/build --config Release
ctest --test-dir cpppj/build -C Release --output-on-failure
cpppj/build/bin/Release/NetstormCpp.exe --inspect-bridges originals
cpppj/build/bin/Release/NetstormCpp.exe --inspect-bridges originalCD --cd
python tools/cpp_bridge_smoke.py
python tools/cpp_fort_smoke.py
```
