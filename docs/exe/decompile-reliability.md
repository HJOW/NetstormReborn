## 2. 최종 C 파일 읽는 법

`extracted/refined/originals/Netstorm.c`(패치판)와 `extracted/refined/originalCD/NETSTORM.c`(CD판)는 함수마다 머리줄 아래에 근거 주석이 붙는다. 머리줄(`// ==== 이름 @ 주소`) 형식은 기본 디컴파일과 같다.

```c
// ==== FUN_0040a5e0 @ 0040a5e0
// [신뢰도 A] · 호출자 2 · 포인터 0 · CD판 FUN_0040a080@0040a080 (callers/medium 0.981)
// 호출 규약 __thiscall (근거 ecx-both-sides: 호출 지점 2곳 중 2곳 ECX 설정, ECX 먼저 읽음 1, ret 0)

void * __thiscall FUN_0040a5e0(void *this)
```

```c
// ==== FUN_004b1e80 @ 004b1e80
// [신뢰도 B] · 호출자 0 · 포인터 1 · 복구 출처 adjacent · CD판 대응 없음
// 호출 규약 __thiscall (근거 ecx-callee+pointer: 호출 지점 0곳 중 0곳 ECX 설정, ECX 먼저 읽음 1, ret 4)
// 함수 포인터 표: 00513098[0]
```

* **호출자 / 포인터**: 직접 `call` 로 부르는 곳의 수, 데이터 구역에서 이 함수 주소를 가리키는 곳의 수.
* **복구 출처**: 자동 분석이 못 찾아 따로 복구한 함수에만 붙는다 (4.2절).
* **CD판 …@주소 (방법/수준 유사도)**: 상대 판본의 짝. 수준은 `strong` > `medium` > `weak` (4.4절).
* **호출 규약 … (근거 …)**: 4.3절의 판정 근거. `CD판과 규약 다름`·`ret N 다름`이 붙으면 그 함수의 원형이나 대응을 의심한다.
* **함수 포인터 표: 주소[슬롯]**: 가상 함수 표나 콜백 표에 실린 위치. `(**(code **)(*param_1 + 8))()` 같은 간접 호출을 풀 때, 표 주소를 `vtables.tsv`에서 찾아 슬롯 2(=+8)의 함수를 보면 된다.
* **미추정 레지스터 N종**: 표준 호출 규약으로 설명되지 않는 레지스터 입출력(`in_EAX`, `unaff_ESI`, `extraout_ECX` 등)의 종류 수. 0 이 아니면 인자·반환값 해석에 주의한다.
* **CD판 쪽이 더 깨끗함**: 짝의 미추정 레지스터가 더 적거나 조각 징후가 없을 때 붙는다. **이 표시가 있으면 CD판 함수를 같이 읽는다.**
* **예외 처리 funclet**: `Unwind@…`·`Catch@…`. 부모 함수의 `EBP` 를 그대로 쓰는 것이 정상이며(`unaff_EBP + -0x28` 은 부모의 지역 객체), 조각이 아니다.

주소는 함수 진입 주소가 아니어도 된다(그 주소 앞에서 시작하는 가장 가까운 함수를 고른다). 같은 소스가 다른 컴파일러로 빌드된 것이라 **한쪽이 모호하면 다른 쪽이 답을 주는 경우가 많다** — 레지스터 배정, 인라인 여부, 지역 변수 배치가 달라서 같은 로직이 다른 모양으로 나온다.

예: 메인 프레임 함수는 패치판 `FUN_004d62b0`(16,945바이트) ↔ CD판 `FUN_0041ae80`(14,706바이트)로 짝지어진다(`string/strong`, 짝지어진 이웃 196개 중 160개가 겹침).

## 4. 방법

`refine_all.ps1` 이 아래 순서로 실행한다. 1단계와 2단계는 `refine_decomp.ps1` 이고, 판본 간 대응·힌트·등급은 `tools/decomp_refine.py` 다.

```
판본별 1단계: 임포트·자동 분석 → FixSwitches → RecoverMissing(commit) → FixSwitches → ApplyConventions → ExportDecomp → DumpFunctions
decomp_refine.py --hints   : 판본 간 대응 → 호출 규약 힌트
판본별 2단계: ApplyConventions(힌트 적용) → ExportDecomp → DumpFunctions
decomp_refine.py           : 판본 간 대응 → 대응표·함수 포인터 표·등급·최종 C 파일
```

### 4.1 `switch` 몸체 보정 (`FixSwitches.java`)

`jmp dword ptr [reg*4 + 표]` 형태의 간접 점프마다 exe 바이트에서 표를 직접 읽어, 분기 대상이 그 함수의 몸체에 들어 있는지 확인한다. 빠져 있으면 점프 참조를 추가하고 함수 몸체를 다시 계산한다. 표의 항목 수는 점프 앞의 범위 검사(`cmp reg, N`)와 2단 `switch` 의 색인 표에서 구하고, 다른 표의 시작이나 코드가 아닌 값에서 멈춘다.

* 패치판에서 고친 곳은 메인 프레임 함수 `FUN_004d62b0` 의 `switch` 3개(`0x4d8cc3` 20분기, `0x4d96f3` 17분기, `0x4d985b` 9분기)와 복구한 함수 안의 2개다. CD판은 고칠 것이 없었다.
* **디컴파일 결과 자체는 바뀌지 않는다.** 디컴파일러는 점프 테이블을 스스로 복구하므로 `FUN_004d62b0` 의 디컴파일에는 처음부터 `switch` 3개와 `case` 48개가 들어 있었다. 빠져 있던 것은 Ghidra 리스팅의 함수 몸체뿐이고, 그 탓에 분기 블록이 "함수 밖 코드"로 남아 가짜 함수로 복구되었다. 이 단계의 목적은 그것을 막는 것이다.

### 4.2 누락 함수 복구 (`RecoverMissing.java`)

자동 분석이 함수로 인식하지 못한 코드를 찾아 함수로 만든다. 새 함수를 만들 때마다 Ghidra 분석기를 다시 돌리고(스택·참조 분석), 후보가 더 나오지 않을 때까지 반복한다.

| 출처 | 규칙 | 패치판 | CD판 |
|---|---|---|---|
| `call` | 직접 `call` 의 대상인데 함수가 없는 주소 | (분석기가 먼저 처리) | (분석기가 먼저 처리) |
| `prologue` | 바로 앞이 패딩이고 흔한 함수 프롤로그로 시작 | 253 | 795 |
| `prologue+pointer` | 위와 같고 데이터 구역에 그 주소가 저장됨 (가상 함수 표·콜백 표) | 361 | 681 |
| `adjacent` | 기존 함수의 끝 바로 다음에 패딩 없이 이어지는 프롤로그 (앞 함수가 `throw`·`jmp` 로 끝나는 경우) | 363 | 498 |
| `afterret` | 함수 밖에서 `ret`/`ret N`/`jmp` 바로 뒤에 패딩 없이 이어지는 프롤로그 | 38 | 64 |
| 그 밖의 조합 | `adjacent+pointer`, `afterret+pointer` 등 | 16 | 27 |

* **패딩**: `CC`(INT3), `90`(NOP), `8B FF`(`mov edi, edi`), `lea reg, [reg+0]` 형태(`8D 49 00`, `8D 64 24 00`, `8D 9B 00000000`, `8D A4 24 00000000`). 패치판은 함수 사이를 `CC` 로, CD판은 뒤의 여러 NOP 을 이어 붙여 채운다. **패딩 명령어 자체는 함수 시작으로 보지 않는다** — 그렇게 하지 않으면 CD판에서 451개 함수가 진짜 진입점보다 앞(패딩 시작)에서 만들어지고, 패치판에서는 `8B FF` 로 정렬한 점프 테이블이 함수로 잘못 만들어진다.
* `adjacent`·`afterret` 로만 복구되고 호출자·포인터·판본 간 짝이 없는 함수는 다른 함수의 꼬리 조각일 수 있어 D 등급이 된다.

### 4.3 근거 기반 호출 규약 (`ApplyConventions.java`)

기본 자동 분석은 패치판 함수 4,506개 가운데 4,211개의 호출 규약을 `unknown` 으로 남긴다. 그러면 디컴파일러가 호출 지점에서 `this`(ECX)를 인자로 보지 않아 `FUN_004b2270(param_2)` 처럼 **객체가 빠진 호출**이 나온다. 이 단계는 **기계어에서 직접 확인되는 근거만으로** 규약을 지정한다. 인자 목록은 잠그지 않는다(디컴파일러가 규약을 바탕으로 계속 추정한다).

| 판정 | 조건 | 패치판 | CD판 |
|---|---|---|---|
| `__thiscall` (`ecx-both-sides`) | 함수가 ECX 를 쓰기 전에 읽고, 직접 호출 지점의 80% 이상이 호출 직전에 ECX 를 넘긴다 | 1,491 | 1,342 |
| `__thiscall` (`ecx-pass-through`) | 진입부터 ECX 를 건드리지 않고 ECX 를 읽는 다른 함수를 부른다 (`this` 를 그대로 넘기는 멤버 함수) | 21 | 36 |
| `__thiscall` (`ecx-callee+pointer`) | 직접 호출자가 없고 데이터 포인터 참조가 있으며(가상 함수 표로만 호출) ECX 를 먼저 읽는다 | 574 | 622 |
| `__thiscall` (`hint`) | 근거가 엇갈리지만 상대 판본의 짝이 양쪽 근거로 `__thiscall` 이다 (4.5절) | 8 | 9 |
| `__fastcall` | ECX 와 EDX 모두 양쪽 근거가 있다 | 4 | 0 |
| 지정 안 함 (`ambiguous-ecx`) | ECX 를 먼저 읽지만 호출 쪽 근거가 엇갈린다. 디컴파일러의 자체 추정에 맡긴다 | 46 | 201 |
| `__stdcall` (`ret-n`) | ECX 를 먼저 읽지 않고 `ret N` (N>0) 이다 | 181 | 256 |
| `__cdecl` | 그 밖 | 2,922 | 3,080 |

판정 세부:

* **"ECX 를 쓰기 전에 읽는다"**는 진입부 직선 스캔과 기본 블록 경로 추적 두 가지로 확인한다(분기 뒤에서만 읽는 함수 포함). `push ecx` 는 MSVC 가 지역 변수 4바이트를 잡는 데도 쓰므로 읽기로 치지 않고, `xor ecx, ecx` 는 쓰기로 친다.
* **스택 프로브 호출은 투명하게 지나간다.** 지역 변수가 큰 함수는 `mov eax, 크기; call __chkstk` 로 시작하는데 이 함수는 ECX·EDX 를 보존한다. 두 판본의 `__chkstk` 는 모양이 달라(패치판 `0x4e4a40`, CD판 `0x4f1bd0`은 이름도 없다) 시작 바이트로 식별한다.
* **호출 쪽**은 호출 명령어에서 거슬러 올라가 바로 앞 호출 이후에 ECX 를 쓰는지 본다. 호출자의 진입부터 ECX 를 건드리지 않고 온 경우(통과 호출)도 넘긴 것으로 친다.
* `__fastcall` 은 ECX·EDX 양쪽 근거가 다 있을 때만 준다. MSVC C++ 코드에서 `__fastcall` 은 드물다.

### 4.4 판본 간 함수 대응 (`tools/decomp_refine.py`)

두 판본은 같은 소스를 다른 컴파일러로 빌드한 것이라 기계어가 같지 않다. 그래서 바이트 비교가 아니라 **컴파일러와 무관한 특징**으로 짝짓는다. 근거가 강한 순서로 확정한다.

1. **이름** (197쌍): Ghidra 가 라이브러리 함수로 식별해 같은 이름을 붙인 함수.
2. **유일 문자열** (595쌍): 양쪽 판본에서 각각 한 함수만 참조하는 문자열(로그·오류 메시지 등).
3. **호출 순서 전파** (`callseq` 878쌍): 이미 짝지은 함수 쌍의 호출 순서를 맞대어, 같은 자리에 있는 미확정 피호출 함수끼리 짝짓는다.
4. **호출자 전파** (`callers` 635쌍): 짝지어진 호출자를 공유하는 미확정 함수끼리 짝짓는다.
5. **국소 구간** (`gapfill` 106쌍, `neighbor` 82쌍): 주소 순으로 이웃한 두 확정 쌍이 상대 판본에서도 가까이 순서대로 놓여 있으면, 그 사이의 미확정 함수끼리 짝짓는다.
6. **문맥 검증**: 짝지어진 호출자·피호출 함수가 3개 이상인데 겹치는 비율이 34% 미만이면 대응을 취소하고 다시 확정하지 않는다.

확정한 쌍의 수준: `strong`(이름·문자열 근거, 또는 겹치는 이웃이 3개 이상이고 60% 이상) 1,729쌍, `medium` 712쌍, `weak` 52쌍. `weak` 는 등급 계산에서 짝으로 치지 않는다.

**링크 순서**: 두 판본은 오브젝트 파일(모듈)의 링크 순서가 다르다. 전체 주소 순서는 유지되지 않지만(최장 증가 부분 수열이 앵커의 18%뿐), **한 모듈 안의 함수 순서는 유지된다**(이웃한 쌍의 82.8%가 CD판에서도 같은 순서). 그래서 5번은 전체가 아니라 국소 구간에만 적용한다.

**유사도**(니모닉 분포, 명령어 수, 호출 수, 문자열·API·상수 집합)는 후보를 가르는 보조 수단으로만 쓴다. 진짜 짝의 중앙값이 0.77 인데 크기가 비슷한 무작위 쌍도 상위 10% 가 0.72 를 넘어, 유사도만으로는 확정할 수 없다.

### 4.5 상대 판본의 근거로 보완 (호출 규약 힌트)

같은 소스에서 나온 함수는 두 판본에서 호출 규약이 같아야 한다. 한쪽은 양쪽 근거로 `__thiscall` 인데 다른 쪽은 ECX 를 먼저 읽지만 호출 쪽 근거가 엇갈려 규약을 못 정한 경우(`ambiguous-ecx`), 확실한 쪽의 판정을 가져온다. 호출 지점이 있는데 절반도 ECX 를 넘기지 않으면 상충하는 근거로 보고 보완하지 않는다. 보완한 함수는 패치판 8개, CD판 9개로 적다 — 대부분은 자기 판본의 근거만으로 정해진다.

## 6. 시도했다가 버린 방법

**Decompiler Parameter ID 로 원형 일괄 확정.** Ghidra 의 `DecompilerParameterIdCmd` 는 디컴파일러가 추정한 인자·반환형·호출 규약을 프로젝트에 확정한다. 호출 지점의 인자 수가 피호출 함수의 원형과 일치하게 되지만, **추측이 틀린 채로 굳어 호출자에게 전파된다.** (패치판에서 실제로 돌려 본 결과다.)

* `__fastcall` 이 901개 나왔다(근거 기반 판정으로는 4~5개). `FUN_00406903` 은 인자 6개짜리 깔끔한 함수였는데, 피호출 함수가 `__fastcall` 로 잘못 추정되면서 가짜 레지스터 인자 2개와 `extraout_ECX` 가 생겼다.
* 가변 인자 로그 함수 `FUN_004c2630(9, "…battle %d…", uVar1)` 의 원형이 인자 2개로 굳어 세 번째 인자가 사라졌다.
* `extraout_…` 가 있는 함수 38 → 311, `in_stack_…` 가 있는 함수 41 → 66, `unaff_…` 가 있는 함수 577 → 859.

그래서 쓰지 않는다. 인자 목록을 잠그지 않고 호출 규약만 근거로 지정하는 4.3절의 방법이 이를 대신한다.

**점프 테이블 재정의(`JumpTable.writeOverride`).** `switch` 의 분기 대상을 디컴파일러에 강제로 알려 주는 Ghidra 기능이다. 쓰면 `case` 값이 실제 값이 아니라 0부터 매겨지고(`switch(uVar7 - 1)`), 같은 대상의 `case` 가 합쳐져 48개가 44개로 줄었다. 디컴파일러는 표를 스스로 복구하므로 필요 없다. 4.1절은 점프 참조와 몸체 재계산만 한다.

**전체 주소 순서로 짝짓기.** 링크 순서가 판본마다 다르므로 틀린 가정이다(4.4절).

**`mov edi, edi` 를 함수 프롤로그로 취급.** 이 실행 파일들에서는 2바이트 정렬 패딩이다(4.2절).

## 7. 한계와 남은 일

* **대응률은 45% 안팎이다.** 짝이 없는 함수는 판본 사이에 바뀌었거나, 인라인 여부가 다르거나, 문자열·호출 관계 같은 단서가 없는 작은 함수다. 짝이 없다고 가짜 함수라는 뜻은 아니다. 예: 프레임 제한·그리기 함수는 패치판 `FUN_00436450` ↔ CD판 `FUN_00486df0`으로 내용이 같지만 자동으로는 짝지어지지 않았다. 이런 경우 짝지어진 호출자(여기서는 `WinMain`)의 **같은 자리에 있는 호출**로 사람이 맞춘다 — [main-loop.md](main-loop.md) 2절의 표가 그렇게 만든 것이다.
* **인자 목록은 추정이다.** 호출 규약은 근거로 지정하지만 인자 개수·자료형은 디컴파일러가 추정한다. 일부 호출 지점은 `this` 가 여전히 빠진다(예: `FUN_0040e800` 은 40곳 중 1곳).
* **비표준 레지스터 인자**(`in_EAX`, `unaff_ESI` 등)를 쓰는 함수는 표준 호출 규약으로 표현되지 않는다. 패치판에 898개, CD판에 479개 함수가 이런 징후를 하나 이상 가진다(예외 처리 funclet 포함). 패치판이 더 많은 것은 최적화가 더 공격적인 컴파일러로 빌드되었기 때문으로 보인다 — 이런 함수는 CD판의 짝이 더 읽기 쉬운 경우가 많다.
* **자료형·구조체·이름은 복구하지 않았다.** RTTI 는 예외 클래스 몇 개뿐이고 심볼 파일은 없다. 클래스 구조는 `vtables.tsv` 와 assert 문자열의 소스 파일 이름([modules.md](modules.md))으로 사람이 추적해야 한다.
* **CD판 C·D 등급이 569개**로 패치판(71개)보다 많다. CD판은 함수 사이 패딩이 불규칙해 복구 함수가 많고(2,065개) 그중 근거가 약한 것이 섞여 있다.
* Linux 용 실행 스크립트는 없다(`refine_all.ps1`·`refine_decomp.ps1`·`run_script.ps1` 은 PowerShell 전용). Ghidra 스크립트(`*.java`)와 `decomp_refine.py` 는 운영체제와 무관하므로 `analyzeHeadless` 호출만 셸 스크립트로 옮기면 된다.

## 9. 자료형과 동작 의미 검증 (2026-10-05 후속)

`cpppj/recovery-manifest.json`의 검토 대응은 x86 에뮬레이션을 통과한 뒤 자동 매칭에 우선 적용한다. `0049a9e0`↔CD `00444350` 오대응을 금지하고, 실제 같은 마스크 검색인 CD `00444410`을 연결했다. 인자 개수·`ret N`·부호 확장까지 확인해야 C++로 옮길 수 있다는 실제 사례다.

`tools/ghidra/recover_types.ps1`은 두 판본 각 5개 함수에 확인한 구조체·ECX/ESP 인자·반환형을 적용해 `typed-core.c`를 만든다. 정밀 프로젝트를 읽기 전용으로 열어 기존 분석은 저장하지 않는다. `tools/decomp_oracle.py`는 원본 게임 없이 선택 함수의 기계어 결과를 만들고 C++ 단위 검사가 이를 대조한다. 재현 명령·범위·원본 자산 검증은 [후속 문서](cpp-reconstruction.md)에 있다.

## 10. 다리 계산에서 확인한 오류와 보강 (2026-10-05)

자동 대응 `004217f0`↔CD `00449e30`은 `ret 4` 전체 방향 탐색을 `ret 8` 한 방향 검사에 잘못 연결했다. 실제 짝 `00421770`↔CD `00449e30`으로 수정했으며, 전체 CD 판단은 `00449250`에 인라인이다. 새 7개 완전 함수 대응을 바이너리/생성 도구/기대값 해시로 확인해 검토 앵커로 추가했다. 재생성 결과는 **2,494쌍(strong 1,733·medium 710·weak 51), 검토 12쌍**, 호출 규약 2,311/2,377·`ret N` 2,338/2,387 일치다.

두 판본의 26개 다리 모양은 같아도 추첨 가중치 합계는 287/306이다. 패치판 `0040eaf0`의 출력 C에는 실제 x87의 `0.9999f` 덧셈이 빠져 있었다. 인자/구조체 적용 후에도 `_ftol`의 ST0 입력을 아직 복구하지 못해 이 식은 누락된다. 디컴파일 성공이나 좋은 함수 경계 등급은 의미가 완전하게 복원됐다는 증거가 아니다.

`recover_bridge_types.ps1`로 패치 9개·CD 8개 함수의 원형/구조체를 개별 적용하고, `decomp_bridge_oracle.py`로 정상 함수의 코드/메모리 쓰기·명령 수·복귀 스택을 제한해 18,053개 기대값을 만들었다. 수명 480개는 첫 외부 효과 전까지만 검증했고 검토 앵커에서 제외했다. 원본 기계어와 실제 PE 표/자산의 독립 판독을 C++와 대조했다. [근거·공식 Ghidra/Unicorn 자료·재현 명령·남은 범위](cpp-bridge-reconstruction.md)에 자세히 기록했다.
