## 소리 프로세스

객체는 0x28바이트다: `+4` form SID, `+8` 부모 SID, `+0xc` 재생 중인 소리 항목, `+0x10` 소리, `+0x14` 대체 소리, `+0x18` flags, `+0x20` 시작 시각(double). 생성자는 재생 중인 소리 0·시작 시각 0.0을 쓰고 **현재 타입 전역**을 읽어 `BaseProcess 부착(타입, 부모, 0, 0x10)`을 부른다. `+0x1c`는 쓰지 않는다. C++의 `SoundProcessSystem::Add`가 같은 순서로 실제 `SquidProcessHost::Attach`(form은 client 번호)를 호출한다. 원본 호출자 가운데 지연 재생은 생성 직후 `+0x20`에 "현재 벽시계 + 지연"을 적는다(`SetStartTime`).

flags는 낮은 네 비트만 쓰인다.

| 비트 | 이름(원본 assert 문자열) | 뜻 |
|---|---|---|
| 1 | `playAt` | 부모의 현재 좌표에서 재생한다. 없으면 전역 재생이다 |
| 2 | (이름 없음) | 부모의 상태 단어(raw `+0xc` WORD)가 0이 아니면 대체 소리를 쓴다 |
| 4 | `playOnce` | 한 번 요청한 뒤 프로세스를 끝낸다. 없으면 반복 재생이다 |
| 8 | `playPriority` | 재생 함수에 값 8을 그대로 넘긴다 |

실행 몸체의 순서는 다음과 같다. 소리 선택(상태 단어) → **벽시계** 조회 → 시작 시각 비교 → flags → 부모 타입의 마지막 소리 프레임이 현재 프레임 카운터와 같은지(`played`) → 좌표 → 재생.

- **위치 + 반복**(`playAt`, `playOnce` 없음 — 보호막이 쓰는 조합): 재생 중인 항목이 있거나 `played`가 아니면 `위치 반복 재생(x, y, 재생 중인 항목, 소리)`을 부르고 반환값을 `+0xc`에 저장한다. 그래서 **재생 중에는 같은 프레임 번호여도 매 프레임 다시 불러** 위치를 갱신한다. 저장한 값이 0이 아니면 타입의 마지막 소리 프레임을 현재 프레임으로 적는다.
- **위치 + 한 번**: `played`가 아니면 `위치 한 번 재생(x, y, 소리, flags & 8, 0)`을 부르고(반환값은 저장하지 않는다) 프레임을 적는다. **`played`여서 재생하지 못해도 프로세스는 끝낸다.**
- **전역**: 재생 중인 항목이 없고 `played`가 아니면 `전역 재생(소리, playOnce가 아니면 1, 0, 0, flags & 8, 0)`을 부르고 반환값을 저장한 뒤 프레임을 적는다(반환이 0이어도 적는다). `playOnce`이면 프로세스를 끝낸다.

"같은 프레임에 같은 타입의 소리는 한 번만 시작한다"는 제한은 타입 레코드의 한 필드를 여러 소리 요청 함수가 함께 쓰는 원본 구조다(`00426290`·`0045e8b0` 등도 같은 필드를 쓴다). C++은 `SoundProcessState::typeFrames`(타입 번호 색인)에 둔다. 재생 함수가 돌아온 뒤 부모 타입과 프레임 번호를 **다시 읽어** 적는 것도 원본과 같다. 좌표는 산술 변환 없이 비트 그대로 넘긴다.

재생 함수 인자의 뜻은 이번에 확정하지 않았다. 소리 프로세스는 값을 위 순서 그대로 넘길 뿐이다. 정적 판독으로는 전역 재생 `004a9550`의 다섯째 인자가 0이면 동시 재생 수 한도를 넘을 때 재생하지 않고, 위치 한 번 재생 `004a9c30`은 자신의 넷째·다섯째 인자를 `004a9550`의 둘째·다섯째로 넘긴다. 그래서 `flags & 8`은 전역 재생에서는 다섯째, 위치 한 번 재생에서는 둘째 인자 자리에 도착한다. 둘째 인자가 반복 재생 여부라는 것은 추정이며, 두 함수의 디컴파일에는 미추정 레지스터가 있어 재생 계층을 옮길 때 기계어로 확인해야 한다.

form 삭제 통지는 재생 중인 항목이 있고 `playOnce`가 아닐 때만 `정지`를 부르고, 이어 `재생 여부`가 0이 아니면 `!isSoundPlaying( currentSound )`(줄 21)를 보고한다. 통지의 flags 인자는 읽지 않는다. 한 번 재생 소리는 프로세스가 끝나도 끝까지 들린다.

### 판본 차이

- **NaN 시각.** 패치판은 `fld 현재; fcomp 시작; test ah,1`로 "현재 < 시작"이거나 **비교 불가(NaN)**이면 돌아간다. CD판은 `fld 시작; fcomp 현재; test ah,0x41`로 "시작 > 현재"일 때만 돌아가 **NaN이면 실행한다.** C++은 판본에 따라 `!(now >= start)` / `start > now`로 나눴다.
- **패치 debug.** 패치판만 debug 전역이 켜져 있으면 `isRobust( 1 )`(form/부모 SID 범위 검사, 항상 참)과 `playOnce || !playPriority`(줄 53)·`playOnce || playAt`(줄 54)를 보고한다. 보고 뒤의 흐름은 debug가 꺼진 때와 같다. C++은 `SoundProcessHooks::report`로 전달하고 연결하지 않으면 건너뛴다(원본 assert 보고는 돌아온 뒤 실행을 계속한다).

## 소리 이름 표

표는 `new(0x8000)`으로 확보해 0으로 채운 버퍼이고 항목이 빈틈없이 이어진다. 항목은 0x1c바이트 머리 뒤에 NUL로 끝나는 이름이 온다: `+0` 장치 버퍼, `+4` 자기 자신(원본 항목), `+8` 복제 항목 연결, `+0xc`/`+0x14`/`+0x18` 재생 상태, `+0x1c` 이름. 새 항목은 `+0x10`을 쓰지 않는다. 이름이 빈 항목이 표의 끝이다.

조회는 첫 항목부터 **C 로캘 `_stricmp`**(ASCII `A`~`Z`만 접는다)로 비교해 처음 같은 항목을 돌려주고, 없으면 끝에 추가한다. 순회가 끝난 오프셋이 **0x7fb0 이상이면 추가하지 않고 대체 소리**(초기화가 처음 넣는 `nonexistant.wav`, 원본 철자 그대로)를 돌려준다. wav 파일 읽기는 조회가 아니라 첫 재생 때 일어난다(재생 계층, 미복원).

기계어에서 확인한 세부:

- **null 이름 → 0.** `SoundList::Lookup(const char*)`이 같은 동작을 한다.
- **표 안을 가리키는 포인터 → 포인터 − 0x1f.** 표를 읽지 않는다. 머리 크기 0x1c가 아니라 0x1f이며 두 판본이 같다. 뜻은 확인하지 못했고 `LookupPointer`로 값만 재현한다(추정하지 않는다).
- **CD판의 항목 검사.** CD판은 순회하는 기존 항목 이름의 마지막 글자가 `v`가 아니면 `s->isRobust()`(줄 438)를 보고한 뒤 비교를 계속한다. 대문자 `.WAV`로 등록된 이름도 해당한다. 패치판에는 없다.
- 표가 가득 찼어도 이미 있는 이름은 찾는다. 대체 소리 이름의 조회도 같은 항목을 돌려준다.

C++의 `SoundHandle`은 `kSoundListBase(0x15000000) + 표 안 오프셋`이다. 원본은 32비트 포인터를 쓰므로, 자기 참조 필드와 `− 0x1f` 경로를 같은 숫자로 재현하려고 고정 기준값을 더했다(호스트 주소가 아니다). 대조 도구가 표를 같은 가상 주소에 올리므로 **표 전체 0x8000바이트의 Adler-32를 원본 관찰과 그대로 비교**한다.

원본과 다르게 둔 것: 빈 이름·NUL을 포함한 이름은 거부한다(원본은 빈 이름을 넣으면 표의 끝 표시와 구별되지 않는다). 추가할 이름이 표 끝을 넘으면 `std::length_error`를 던진다(원본은 검사 없이 버퍼 밖에 쓴다). 표 밖을 읽게 되는 끝 위치는 빈 이름으로 취급한다.

- **패치 CRT의 로캘 선택.** 패치판 `_stricmp`(`004e65ed`)는 스레드별 로캘을 OS에서 얻는다(`_getptd`). 진입에서 C 로캘의 본문 `__ascii_stricmp`(`004ef510`)로 넘겨 **비교 본문은 실제 명령으로 실행**했다(2,912회). CD판 `_stricmp`(`004f2980`)는 전역 로캘 값이 0인 채 전체를 실제 실행한다.
- **표 초기화.** 소리 장치 초기화 함수(`004aa600` / CD `00437820`)는 DirectSound를 부르므로 실행하지 않았다. 표의 확보·0 채움·대체 소리 전역 대입은 Python이 하고, 첫 `nonexistant.wav` 조회는 실제 명령이다.

한계: 프로세스 객체·부모 raw·타입 레코드는 합성 입력이다. 빈 이름, 표 끝을 넘는 이름, 손상된 표는 입력에서 뺐다. 소리 장치와 실제 재생/정지·wav 읽기, 전체 게임 루프에서의 실행은 대조하지 않았다.

## C++ 검사

[`SoundProcessTests.cpp`](../../cpppj/tests/SoundProcessTests.cpp)의 새 검사 5개.

1. **세 PE 관찰 재생(3개).** 실행/통지 행은 실제 `SquidProcessHost`·`Kernel`·공통 삭제 위에 프로세스를 붙여 실행하고 사건 문자열·객체 필드·타입 프레임을 비교한다. 이름 표 행은 같은 연산을 실제 `SoundList`에 적용해 반환·보고·빈 위치·표 전체 Adler-32를 비교한다. 생성자 행은 실제 부착 결과(form의 타입 번호, 부모, client 번호 여부)를 원본의 부착 인자와 비교한다.
   - 원본의 `Kill(0)` 호출은 C++에서 실제 form 삭제로 관찰한다(프로세스가 Kernel에서 사라지면 사건 `K:0`으로 센다). Kill의 flags 값 0 자체와, 삭제된 객체에 남는 필드는 C++ 재생에서 따로 확인하지 않는다(원본 관찰과 소스에만 있다).
2. **보호막 수명 연결.** 두 raw 배치에서 실제 보호막 생성자/소유자/Pop/예약([앞 단계 장면](cpp-forcefield-lifecycle-reconstruction.md)) 위에 실제 이름 표와 소리 프로세스를 연결했다. 생성 wrapper가 `priestForceField.wav`를 조회해(대체 소리 다음 항목, 오프셋 44) **사제가 아니라 새 보호막에** 소리 프로세스를 붙인다 → 첫 프레임에 위치 반복 재생 요청과 타입 프레임 기록 → 재생 중에는 매 프레임 재요청 → 사제가 사라져 보호막이 자기 삭제할 때 종속 form 정리에서 `정지`·`재생 여부` 순서 → SID/Kernel 전부 반납. 소리 프로세스 확보 실패(new 실패)면 조회/부착 없이 보호막만 만든다.
3. **시작 조건과 거부.** 지연 시작, 대체 소리, 같은 프레임의 타입 제한과 다음 프레임 시작, 한 번 재생의 종료(소리는 멈추지 않음), 반복 프로세스 Kill 때의 정지, 패치판의 dead 부모 부착 생략, 잘못된 타입 번호·빠진 효과·다른 풀·잘못된 이름/포인터의 거부.

변이 확인([`cpp_mutation_check.py`](../../tools/cpp_mutation_check.py), 저장소 밖 사본에서 실행): 새 변이 **10개**(NaN 시각 규칙, 타입 프레임 제한 무시, 조용할 때 프레임 기록, 재생 못 한 한 번 재생 유지, 전역 반복 인자, 한 번 재생의 삭제 때 정지, 상태 단어 하위 바이트만, 한도 비교, 대소문자 접기 범위, CD 전용 보고) — 10개 모두 검출됐다(아래 "최종 검증").
