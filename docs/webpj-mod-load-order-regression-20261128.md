# WB04-E1481 모드 초기 적재의 기존 오류/취소 순서 복구

E1480 뒤 Node26 전체는7,019/7,021·실패2·취소/건너뜀/todo0이었다(580.754초). 같은12,385개 원시 입력은 종료 때 모두 그대로였다. 실패는 기존`error-reporting.test.mjs`의 현재 세대 준비 실패 보고와 이전 세대 취소이며, 처음7019통과를 전체 통과로 세지 않는다. 작성 입력 고정은 실행기 종료/해시 확인 뒤 해제했다.

E1480에서`await this._mods?.load()`를 무조건 수행하고 뒤에 루트 존재 검사도 붙였다. 모드 관리자가 없는 경로에도 불필요한 microtask를 추가해 기존 준비 훅의 즉시 호출 순서를 바꿨으며, DOM 없이 준비 훅만 사용하는 정상 검사 경로는 오류 보고 전에 돌아왔다. 그 결과 첫 검사는`loading !== error`, 둘째는`rejectPreparation is not a function`으로 실패했다.

실제 모드 관리자가 있을 때만 load를 기다리고, 그 뒤에는 원래 적재 세대 번호로 취소를 판정하도록 고쳤다. destroy는 원래 이 세대 번호를 올리므로 추가 루트 판정은 필요 없다. 기존 두 검사와 모든 원본 fixture/단언을 유지했고, 실제 비동기 모드 적재 대기 후 준비 실패의 원인/문맥과 이전 세대 완료 무시2건을 보강했다. 실제 앱의 모드 저장 검증 순서/강제 꺼짐·Worker 장벽은 유지한다.

Node26/22 집중 각27/27(기존오류/새비동기2·Client프레임·관리자), 선행전체ESLint/운영빌드 종료0(69.694초)·단일JS5,845,774바이트다. 실제 아군AI1-1/고정모드 Chromium2/2도통과했다(26.0초). 최초 전체 원문/해시는[증빙](webpj-e1481-evidence/provenance.json)에 기록한다. 수정 완료 뒤 주기는v26=5/4·v22=5/8이며 실패 전체로 주기를 리셋하지 않는다. E1482에서 현재 입력을 다시 고정해 Node26 전체7,023예상을 즉시 실행한다. 새 전체가 통과하기 전까지 전체 회귀 완료로 표기하지 않는다. Node22 전체는 주기8/8에 아직 이르지 않았으며 이번에는 변경의 집중 검사를 수행한다.
