# webpj 검사 전용 고정 시각 모드와 cpppj 타임라인 대조 (WB04-E1271, 2026-11-23)

4D-10b(L2 판정)의 남은 일 "고정 시각 실행 모드로 행 전체 일치 판정"의 첫 단계다. 앱에 cpppj `--fixed-frame-ms` 와 같은 고정 프레임 시각 모드를 더하고, 같은 조건의 cpppj 실행(Tutorial1, 1024×768, 25ms)과 Session 덤프를 행 단위로 대조해 남은 차이를 좁혔다.

## 고정 시각 모드

- 주소 `?fixed=25`(또는 옵션 `fixedFrameMs`)로 켠다. 1~60000 정수만 받고 그 밖은 꺼짐이다.
- `ClientTimeSource.enableFixed({ frameMilliseconds })` 를 `_initializeClientRuntime` 에서 켜 시계와 난수 초기화의 유닉스 초가 같은 값에서 시작한다.
- 프레임은 requestAnimationFrame 이 아니라 `await app.stepFixedFrames(n)` 로만 진행한다(가상 시각이 프레임마다 25ms 씩 전진). 프레임 사이에 이벤트 루프를 한 번 넘기지만 아직 준비되지 않은 자산을 기다려 주지는 않으므로, 호출하는 쪽이 `_prepareCampaignAudio()` 로 효과음 준비를 먼저 마친다.
- 시작 그림(세 장 × 3초)은 시각만 흐르고 프레임(번호·시간차)으로는 세지 않는다. 그림 시작 시각을 진입 순간으로 잡아 정확히 360프레임·게임 시각 9.0초가 된다(`ClientFrameClock.advanceWithoutCapture`).
- 일반 모드(고정 시각이 꺼진 상태)는 바뀌지 않는다(title·첫 실행·Frame Rate e2e 통과).

## 결정론

새 e2e `e2e/fixed-time.spec.js`: 시작 그림 360프레임·게임 시각 9초·주 루프 프레임 번호 90, 같은 입력의 두 실행(별도 브라우저 문맥)이 **문자 단위로 같은 Session 덤프**를 낸다. 고정 시각이 꺼져 있으면 `stepFixedFrames` 가 오류다.

### 원인 후보(다음 단계)

1. **Start 시점 차이**: cpppj 는 월드가 연결되는 f4 에 첫 창이 열리고 정지하므로 관문이 그보다 앞서(f4 의 `lockFrames` 가 0 이 되도록 f0 근처) 시작된 것으로 보인다. 웹은 `completeLocalConnection` 과 Start 를 같은 프레임(F4)에서 하고 관문이 거기서부터 센다. cpppj 의 State8/Start 와 월드 연결 완료의 프레임 순서를 `UberGump.cpp`·`RawCampaignSession::Start` 에서 확인해 맞춘다.
2. **초기 시계 0.125**: cpppj 는 첫 주 루프 프레임 전에 시계가 5프레임분 흐른다(웹은 0). 시작 그림 구간 뒤 시각을 직접 비교하면 정지 시각(9.2)은 우연히 같다.
3. **난수(시작 그림 구간)**: 웹은 그림 구간 360프레임 동안에도 주변음·바람이 Game 난수를 썼으나 cpppj 의 그림 구간은 주 루프가 아니다. **E1272 에서 그림 구간의 주 루프 갱신을 건너뛰게 했다**(시각만 흐르고 그림만 그림): 행 전체 일치 1,773 → 1,787/1,964, 남은 불일치 `random` 1·`regular` 6·`pool` 1·`slot` 85·`object` 74·`player` 9·`sp` 1.
4. 풀 해시·SP 소유자 0(원본도 실행마다 다른 미초기화 값)·Player 앞 4바이트는 비교에서 따로 다룬다(E869, E1129).

## 게임 난수 소비 대조 (E1272)

Game 난수는 `상태 = 상태 × 0x10003 + 3`(하위 32비트)이라 두 덤프의 `random` 첫 값 사이에 몇 번 뽑았는지 역산할 수 있다. cpppj 프레임별(25ms, Tutorial1) 뽑은 횟수와 웹(`begin` 뒤 F1~F5, 호출 스택별 계측)을 나란히 둔다.

| 프레임 | cpppj | 웹 | 웹의 내역 |
| --- | --- | --- | --- |
| 1 | (기준 없음) | 3 | 주변음 2·주변 바람 1 |
| 2 | 1 | 1 | 주변 바람 |
| 3 | 1 | **804** | 장면 음악 1·구름 생성(Kencloud) 801·바람 2 |
| 4 | **1,282** | **2,410** | 지형 도장 ≈209(`frameAt` 150·`create` 59)·농장 군집 304·영역 칠하기 450·Fort 객체 무작위 프레임 1·SP 수신 1,280·시작 SP 160·그 밖 ≈6 |
| 5 | **2,106** | 1 | |
| 6~16 | 프레임당 1(f6→f8 2, f8→f12 4, f12→f16 5) | 프레임당 1~2 | |

- cpppj 의 4→5 프레임 2,106 은 웹 F4 2,410 에서 농장 군집 304 를 뺀 값과 같다(구름 800 + 농장 304 가 cpppj 3→4 프레임 1,282 안에 있다고 보면 1,282−1,104=178 이 남음). 즉 **월드 생성 순서가 한 프레임씩 어긋나 있고(웹이 한 프레임 이르다) 생성 중 난수 소비 총량이 웹이 약 175회 적다.** 90프레임 시점 `random` 행은 웹에서 cpppj 로 3,843회 더 뽑아야 도달한다.
- 90→130 프레임 사이 소비는 cpppj 43회·웹 47회(프레임당 1 + 추가 3·7)로 추가 소비 위치도 다르다.

## 90프레임 논리 화면 대 `load.png` (E1278)

`e2e/fixed-time.spec.js` 가 고정 시각 모드로 Tutorial1 을 90프레임 진행한 웹 논리 화면(`_surface` 색 번호 + `_clientPaletteScreen.palette()`)을 RGB 로 바꿔 cpppj 오라클 `tutorial1/oracle/tutorial1/load.png`(1024×768)와 `compareImages` 로 대조한다. 같은 입력의 두 실행은 화면도 같다.

- 다른 픽셀은 **7,195개(0.91%)** 이고 모두 가장자리 상자 [5,32,697,566] 안에 있다. 안내 창("NetStorm!") 글자·단추·창 틀과 그 오른쪽 영역, HUD 의 나머지(미니맵 표시 구역 밖)는 **완전히 같다**(영역별: 미니맵 구역 992·안내 창 안 118(창 왼쪽 가장자리의 섬 아랫면)·창 위 966·창 아래 2,301·창 왼쪽 2,818·창 오른쪽 0).
- 차이의 정체: ① **섬 아랫면**(바위 뿌리 모양)이 서로 다르다 — 지형 도장의 무작위 프레임이 웹과 cpppj 에서 다른 난수 상태로 뽑혀 모양이 갈린다(위 난수 소비 대조의 약 3.5천 회 차이와 월드 생성 순서 어긋남이 이 차이의 원인으로 보인다). ② 왼쪽 HUD **미니맵 표시**의 작은 섬 조각 배치가 일부 다르다(992픽셀). ③ 섬 아래쪽 건물 하나(≈(257~275, 510~520))의 모양이 다르다(cpppj 는 창이 있는 직사각형, 웹은 둥근 탑 — 난수 프레임 또는 애니메이션 위상 후보).
