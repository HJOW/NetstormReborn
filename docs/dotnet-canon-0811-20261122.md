# dotnetpj 0.811 — 실제 파편 장치와35h 섬 정리 수신

## 변경

0.809의 `ShrapnelVisualSystem`을 실제 `HostSession`의 같은 WorldRendering·공장·Pop·DependFormHost·Game/CRT·Kernel에 연결했다. Game 장치는 기존 실제 캡처와 dirty/clip/pitch/8비트 픽셀을 사용한다. 프레임 준비와 카메라 설정에서 같은 파편 상태를 갱신하며, Add 자체는 별도 시각/카메라 조회를 하지 않는다. 원문의 실제 확보 실패만 null로 바꾸고, 뷰 미설치와 다른 장치 오류는 도달 위치에서 실패한다. 같은 Host가 남아 있을 때 파편을 먼저 반납한다.

35h의 고정 entry `46e940`은 원문 순서로 signed X·owner·flags·Y를 읽고16.16→double→float 변환, 현재 건설 시각/소유자/동맹 준비를 거쳐 기존 실제 `RawConstructionEffects.DropIsland`를 호출한다. 장기 `IslandDropBlocked`(BSS0)·`IslandStumpType`(초기96), 현재 Authority/BridgeState, 실제 Variant2/위치 낙하음/전체 가상 삭제/FallWalker/기존20BYTE 작성·원격 전용 방송과 원문9/1/1 진단을 연결했다. Displace 전용 private 본체는 이 수신에 사용하지 않는다. **Host API의 실제 고정 본문은18/26**이며 전체 등록/Root 설치와 나머지8본문은 남았다.

`BindWorldDeletion`은 기존 `RawSquidFormDispatch`를 새 공통 삭제로 복제하지 않고 같은 현재 Host의 삭제 본체/깊이인지 확인해 State와 Runtime.Asset에 함께 연결한다. 실제 감시 쌍의 가상 삭제도 같은 분배기를 사용한다. 파편 더미110의 통지는 일반 Pre/Post 완료 대신 전체 world 삭제를 실행한다. 첫 통합 검사에서 Runtime.Asset 미설치로 소진/캡처 실패 정리가 막힌 문제를 이 연결로 교정했다.

## 확인한 범위와 한계

창 없는 제품 검사는 실제 Game 생성자/보호SHP/Screen/음향 몸체와 같은 Host를 사용한다. 검사의 삭제 조립은 기존 공통 수명/표면 수명/ProcessForm/DependForm 분배를 같은 삭제 본체에 연결하고, 명시한 표면·더미5클래스만 허용한다. 다른 파생은 진단으로 실패한다. 이는 일반 Pre/Post 완료를 전체 삭제로 위장한 경로가 아니다.

**일반 제품 Root의 전체 Native 삭제 설치가 완료된 것은 아니다.** 현재 Root의 일반 typed Host는 별도 현재 RawSquidDestroy를 빌리고 Storage의 Native 기본 삭제는 Native 전송/진단 계약을 요구한다. 두 본체를 같은 깊이로 간주해 섞지 않았다. 검사의 제한된 클래스 조립을 제품 전체 서비스로 복사하지 않았다. Root의 전체 `DestroyAsset/ProcessFormDispatch/CommonDeletion`·실제 파생·UI/AI·송수신·진단 정상 복귀 장치 설치가 계속 필요하다. 현재 Game의 단독 일반 미션은 실제 NULL9 원격 표를 사용하며 MP 표 미설치는 전파 위치에서 실패한다. 전용 Flyer/Bridge/Bomb 등의 나머지 캡처와 R5 월드 뷰도 남아 있다.
