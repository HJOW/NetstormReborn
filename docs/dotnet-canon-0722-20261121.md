# 0.722 실제 Client Frame과 게임 시각 공유

Client의 같은 FrameTime.game을 양방향으로 빌리는 안정된 DoubleBox를 추가하고, 실제 HostSession의 ProcessTime에 그 상자를 넘겼다. 세션 생성은 현재 시각을 초기화하지 않는다. HostFrameDriver는 고정 시각 전진 뒤·스크립트 입력 전에 Client Clock을 한 번 캡처한다. 제품 Kernel은 별도 dt를 더하지 않고 그 시각을 그대로 읽는다. 기존 독립 세션의 AdvanceMissionFrame은 명시 전진 계약을 유지한다.

미션 음향/주변음의 벽시각은 같은 GameClock.WallSeconds를 조회하며, 음향과 burning 준비는 같은 Frame의 번호/게임 시각을 사용한다. UI의 OS 시각 공급과 합치지 않았다. 이번 단위에서는 기존 주변음/바람/입력/Kernel의 상대 순서를 유지했다. 원문 ClientMain의 실제 순서 연결은 0.723에서 진행한다. 장기 ProcessHostStorage와 Native WorldRuntime 장치 일원화도 후속이다.

집중 Client 95건이 모두 통과했다(신규 5건). 같은 Frame 주소의 양방향 변경, Clock 내부 프레임과 외부 Frame의 구분, 같은 Kernel의 현재 시각 소비, 생성 시 보존, 독립 명시 전진, 고정 시각 전진→캡처→입력 및 캡처 예외의 부분 효과를 확인했다. 근거는 extracted/dotnet-0722/client-initial.log와 client-shared-frame-initial.trx다. cpp_sync 종료 0이며 연결된 fixture 360개는 불변이다. PORT_MAP에 실제 프레임 orchestration의 ClientMain.cpp/.h→HostFrameDriver 두 행을 추가했다.

실제 thewarbegins/tutorial1/surrounded 세 시작이 모두 종료 0이었다. 조건은 시드 1760000000·25ms/90프레임·영어 1024×768 창/음소거이며 사용자 제외 항목(포획/희생·특정 적 공격·승리)은 재현하지 않았다. 원본 1392개 파일 SHA가 모두 불변이다. 근거는 extracted/dotnet-0722/capture.py, capture.log, capture-summary.json, capture-originals-audit.json 및 capture/<mission>/dn/run.json·f090.tsv다.

0.721과의 변경 태그는 thewarbegins의 frame 1/regular 20/pool 1/slot 1, tutorial1의 frame 1/regular 3/pool 1/slot 1, surrounded의 frame 1/random 1/regular 59/pool 1/slot 6이다. 90프레임 게임 시각은 반복 덧셈 2.249999999999996에서 원문 밀리초 나눗셈/나머지 계산 2.25로 바뀌었다. surrounded의 여섯 slot은 모두 offset 36의 프레임 바이트만 달라졌다. regular PID4의 다음 시각도 3.0499999999999967→3.025다. 이 시간 경계 차이가 정기 실행/난수 소비 변화와 관련된 것으로 추정하나, CPP와의 전체 일치로 판정하지 않는다.

thewarbegins/tutorial1의 기존 CPP 비교 지표는 모두 같다. surrounded는 frame_equal 5690→5689, slot_equal 5371→5370이고 게임 난수 672338744→2339453355다. type/owner/graph/슬롯 개수와 CRT 난수는 같다. CPP surrounded의 시각은 10.6초로 시작 상태/시간 전이 차이가 여전히 남는다. M1은 0/34이며 이번 시각 변경과 다음 순서 변경은 0.724의 전체 회귀에서 구분해 감사한다.
