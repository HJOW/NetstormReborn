# 0.615 지면 프레임 CRT·J 경로 고정 (원인 좁히기)

- 일시: 2026-11-18, HJOW-Athlon
- 범위: R4-2 지면 프레임 불일치(타입·소유자 100%, 프레임 0/1353)의 원인 좁히기. `RawTerrainStamp` CRT·J-case 경로를 실제 미션 상수로 고정하는 진단 단위이며 제품 코드 변경은 없다.
- 목표: 0.614에서 남은 프레임 0/152가 농지 전용이 아니라 지면 스탬프 전체의 문제임을 확정하고, 다음 원인 후보를 좁힌다.

## 원인

- 0.614 L2에서 지면(97) 1353셀의 좌표 집합이 cpp/dn 완전히 일치하고, 농지 152셀의 타입·소유자도 100% 일치하는데 프레임만 0% 일치했다.
- 정적 대조 결과 `TerrainBuilder`(이웃·연결·방향·정규화), `RawFrameChoose`, `RawTerrainStamp`(FrameAt/Stamp/Create/Initialize), `RawTerrainContext`(MarkEdges/Normalize), `RiftTypeFrames.Run/FrameTable`, `GameRandom`·CRT LCG는 모두 cpp와 일치한다. 포트는 충실하므로 런타임 입력(지도 코드·지역, 난수 스트림) 또는 후처리 덮어쓰기가 남는다.

## 좁히기 (증거)

- 잔차 분석: `(프레임-1-x%3-(y%3)*3) mod 9`를 전 지면 셀에 계산하면 dn·cpp 모두 약 80%가 같은 잔차 1에 모인다. J-case 분류(`code=='x'`·A/A)는 양쪽이 일치하고, JFirst mod 9도 같다. 차이는 J-case 내부 `chosen`과 non-J 선택에 있다.
- CRT 상수 추적: 덤프 CRT 행은 6개 덤프 모두 `296677442`다. 호스트 reseed(고정 시각 1760000000, 모드 1) 뒤 상자가 `511160713`이며, 여기서 정확히 99회 draws 뒤 `296677442`가 된다. 즉 CRT 시작값과 소비 횟수는 cpp와 같은 설계대로 동작한다.
- CRT 경로는 아래 L1 3건으로 고정했다. 남은 후보는 셀별 코드·지역 입력 차이와 스탬프 뒤 postPop 프레임 덮어쓰기다(0.616에서 성장 지도·postPop Prefix 대조).

## 수정

- 제품 코드 변경 없음.
- `dotnetpj/tests/Netstorm.Core.Tests/TerrainStampFrameTests.cs`: 신규 L1 3건(합성 지도, 외부 자료 불필요).
  - `InitializeConsumes99CrtDraws`: 실제 미션 상자 `511160713`에서 FrameAt 1회 뒤 상자가 덤프 상수 `296677442`와 같아진다.
  - `JCaseFrameMatchesDocumentedFormula`: 합성 J-clock 지도 중심(5,5)에서 프레임이 수동 계산값 `9`와 같다(V0=41, V1=18467, 합=7, V[7]=29359(bump), 선택=0).
  - `SameInputsGiveSameFrameWithoutGameRandom`: 같은 입력은 같은 프레임을 주고 J-case는 게임 난수 시드가 달라도 바뀌지 않는다.

## 검증 (증거)

- Release 빌드 0경고·0오류(기존 xUnit2020 안내 2건 유지).

## 남은 작업 (0.616 이후)

- 셀별 코드·지역 입력 대조: 같은 좌표 집합인데도 J-chosen/non-J 선택이 어긋나므로 성장 출력의 셀별 코드·`Regions`와 `MarkEdges` 후 코드를 덤프와 대조한다.
- 스탬프 뒤 postPop 프레임 덮어쓰기 대조: `IslandPostPop.Prefix`·`SquidFrame`의 깊이·프레임 선택이 스탬프 프레임을 바꾸는지 확인한다(0.604 적재 깊이 단위와 연결).
- 위 둘이 닫히면 L2 3경로 재수집으로 프레임 일치율을 확인하고 R4-2 잔여(그래프 번호·장부·첫 지역·AI·정기 처리)와 R4-3~R4-8을 계속한다.
