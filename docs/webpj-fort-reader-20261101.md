2026-11-01, **HJOW-Athlon**(마지막 전체 정밀 디컴파일 호스트 HJOW-Athlon/2026-10-23 과 같은 PC 이지만 이번 단위는 디컴파일 소스를 읽지 않았다. 근거는 cpppj 의 복원 소스 `o/Template.cpp`·`o/RiftTypeTable.cpp`·`o/RiftType.h`·`o/RawFortObjectLoad.cpp`(읽기만)와 그 근거 문서 [cpppj 타입 표와 요새 파일 읽기 복원](exe/cpp-fort-reconstruction.md)·[.fort 형식](formats/fort.md)이다). 사용자 요청("AGENTS.md, LEFT_JOBS.webpj.md 를 읽고 webpj 다음 작업 진행")으로 [인계](../LEFT_JOBS.webpj.md)의 '다음'에 남은 항목 중 원본 실행이 필요 없고 미션 구현보다 앞서는 **정적 맵 화면(M2)의 첫 단계**를 했다. ## 1. 범위와 결과

`.fort` 오브젝트 레코드는 타입마다 저장하는 필드가 다르고(프레임·수량·다리 번호·작업장 상태·소유자·내용물), 파일 속 타입 번호는 저장한 실행 파일의 번호라 `TypeNames` 해시로 현재 번호로 바꿔야 한다. 그래서 먼저 **타입 188개의 이름·플래그**가 필요하다. 지금까지 웹 타입 표(`type-table.js`)는 그림 규칙(프레임·글자 구간·기준점)만 가졌다.

| 대상 | 결과 |
|---|---|
| 타입 레코드 | 번호 0~187 전부(내장 5·프로세스 53·자산 116·빈 타입)의 이름·플래그 1/2·그릇/내용물 목록 플래그·그룹·발자국. 다리 82·섬 94 |
| `.fort` 읽기 | 섹션 35개(구독자·Money·Territory 원시·TypeNames 변환표·Technology·Deck·Chaff·Terr00~19)와 오브젝트 레코드 전체 |
| 원본 맵 | `assets/game-data` 의 느슨한 파일 433개 + `netstorm.tarc` 안 32개 = **465개 모두** 읽혔고, 독립 구현(`tools/fort.py`)의 기대값과 줄 단위로 같다. 오브젝트 레코드 합계 **313,712개**(cpppj 문서의 수와 같음) |

화면에 보이는 변화는 없다(판독기만). 웹 공개 데이터(`www/data`)도 늘리지 않았다 — 웹에 실리는 맵은 이미 있는 `netstorm.tarc` 안의 공식 맵 32개이고, 느슨한 맵 433개는 검사에서만 저장소 자산으로 읽는다.

## 2. 원본 규칙(cpppj 근거)

* **파일:** 매직 `0x46` + 플래그 1바이트 + 길이 접두 섹션(길이 u16, 길이 필드 포함). 이름 순서의 35개만 읽고 뒤의 섹션은 무시한다(꼬리 바이트로 센다). 길이가 2 미만이거나 `0x7fff` 초과이거나 파일 밖이면 거기서 멈춘다.
* **청크 섹션**(`Chaff`·`TerrNN`): 버전 u8 + 청크 레코드(표지 `c`=99, 오브젝트 수 u16, 오브젝트들). 빈 레코드(타입 0)도 개수에 들어 있어 보존한다.
* **오브젝트 레코드**(원본 004bdc60): 위치(상위 4비트 x·하위 4비트 y), 타입 바이트(`< 0xf6` 이면 `TypeNames` 로 변환, 이상이면 다리 약식 표기 — 타입은 다리, 소유자는 `0xff − 값`). 변환한 타입이 0 이면 뒤 1바이트(0 이어야 함)만 읽고 끝, 섬 타입이면 뒤 1바이트만 건너뛴다. 그 밖은 타입 플래그에 따라 `saveFrame` → `saveQA` → `saveQB`(부호 있는 16비트) → 다리 번호 → (버전 0이면 모든 타입에 상태 1바이트) → (버전 2 이상이고 작업장이면 상태 1바이트) → (버전 1 이상이고 소유자 마스크 `0x5d77cf00` 타입이면 소유자 1바이트) → `container` 이면 내용물 목록.
* **내용물 목록**(원본 004bd130): 개수 u8, 항목마다 타입(변환), QA/QB 수량, 목록 플래그(`타입의 +0x100` → `그릇 타입의 +0xfc` → 둘 다 0 이면 파일 1바이트), 그릇이면 중첩 목록. 변환한 타입이 0 이면 읽기를 그만두고 `complete` 가 거짓이며, 중첩이 끊기면 바깥도 끊긴다. `Technology` 는 플레이어(`PlayerSquid`, 그릇 플래그 0)를 그릇으로 한 목록이라 항목마다 목록 플래그 1바이트가 있고 폭탄 항목에는 없다.
* **`TypeNames`**(원본 004bd800): 현재 타입 188개를 번호순으로 훑어 이름 해시(글자를 부호 있는 8비트로 읽어 `(위치 % 4) × 8` 비트 밀어 32비트로 감아 더함)가 같은 **첫 파일 번호**에 자기 번호를 적는다. 같은 해시의 현재 타입이 여럿이면 번호가 큰 것이 남아, 해시 0(이름 없는 타입)의 첫 파일 번호(보통 0번)는 187 이 된다. 이름은 20글자에서 자르지 않는다 — 이름이 20글자 이상인 `fakeThreeByThreeSurface` 는 이름 앞 20글자 뒤에 설명 필드(`fake3x3Surface`)가 이어 읽혀 해시 `0534a54b` 가 된다. 프로세스 타입 이름은 20글자까지만 들어간다.
* **타입 플래그**(원본 0049c3b0 · 후처리 0049b0d0): `typeflags` 단어 48개가 플래그 1·2 의 비트를 켜고(대소문자 무시, 표에 없는 단어는 무시), `group` 속성(archer 0 … misc 9, 없으면 10)이 battery → `0x800`, archer·cannon → `0x8000000`, blocker → `0x4000000` 을 켜며, 후처리가 vortex·factory·walker·balloon → `container` + 그릇 목록 플래그(운반체 `0x20`, 아니면 `0x10`), bomb → 내용물 목록 플래그 1, buried → `saveQA` 를 파생한다.

## 4. 원본과 다르게 둔 점·가정

1. **판본:** 10.78 패치판 타입 표(188개) 하나만 쓴다. 파일이 CD판(171개) 번호 체계로 저장되어 있어도 해시 변환이 현재 번호로 바꾼다(느슨한 파일 대부분이 그렇다).
2. **소유자 바이트는 저장 값 그대로 보존**한다. 0 이거나 8 초과를 1 로 바꾸는 것(`normalizedOwner`)과, 실제로 쓰는지(`special`·`mission` 상태)·간헐천/묻힌 것의 소유자를 0 으로 만드는 것은 월드에 놓는 단계의 일이라 이 판독기는 하지 않는다. 간헐천도 소유자 바이트를 저장한다(값 0).
3. **모르는 타입 번호:** 변환한 타입이 0 이면 원본처럼 오브젝트에서는 뒤 1바이트가 0 이어야 한다고 보고(아니면 오류), 내용물 목록에서는 거기서 읽기를 끊는다. 465개 원본 파일에서는 일어나지 않는다.
4. 섹션 길이는 부호 있는 16비트 범위(`≤ 0x7fff`)만 받아들인다. 원본 파일에는 이를 넘는 섹션이 없다.
5. 이 단위의 검사는 **독립 구현(Python 판독기)과의 일치**와 cpppj 문서의 수치(313,712개·29개 파일)가 근거이다. 원본 실행 중 메모리나 원본 화면과 대조한 것이 아니다. Python 판독기와 cpppj 판독기는 이미 같은 465개에서 서로 일치함이 확인되어 있다([cpppj 문서](exe/cpp-fort-reconstruction.md) 검증 절).

## 6. 다음
