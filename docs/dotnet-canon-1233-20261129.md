# DN 1.233 — 실제 Fort 저장 가상 조회와 내용물 stream 연결

H-1 저장의 선행 자식인 `NativeFortSaveVirtual`과 `NativeFortContentSave`를 같은 장기 Surface/Template에 연결했다. 기존 `SceneMusicVirtualCount`의 제단/Dais/base 레벨 조회와 Core의 `RawContainedFinder`·`RawFortContentSave`를 재사용한다. 별도 World·Session·Player·난수·시각·loaded 값을 만들지 않는다. 전체 Fort/Battle snapshot과 State의 원래 호출 위치는 아직 연결하지 않았으며 H-1은 미완료다.

`NativeFortSaveVirtual`은 현재 raw 가상표로 ObjectRobust를 분배한다. 고정 거부9종은 TYPE를 읽기 전에0으로 돌아가고, 벌룬2종은 signed frame과 현재 TYPE의 실제 코드 개수를 비교한다. 그 밖의 현재 생성 가상표는 현재 flags1의 `0x20000000`을 판정한다. 내용물 Robust는 하위 flags BYTE만 읽으며 world 진단이 정상 복귀하면 같은 현재 BYTE를 다시 읽는다. HasLevel은 기존 원본 OR 조건을 유지하는 base 몸체, Level은 이미 사용 중인 공통 가상80을 사용한다.

`NativeFortContentSave.Save`는 실제 Create/Select가 반환한 `TemplateWriteStream`의 manager/노드/생성 수명을 고정한다. 기존 전체 내용물 작성자에 실제 Pool·현재 TYPE·중앙 진단·그 stream의16BYTE/버퍼를 빌린다. 각 재귀 목록에는 독립 `RawContainedFinder`를 만들고 checking·boss·ContentType은 현재 장기 owner에서 읽는다. 원본처럼 진단 뒤 head와 후보 필드를 재조회하며, 반환 전에 보관한 next로 계속한다. 현재 manager.current가 달라져도 원래 stream에 쓰고, 실패 전에 쓴 count/kind/QA와 cursor를 보존한다.

## 검증

최종 집중은 **Client35·Core5, 합계40통과·실패0·미실행0**이다. 새 검사는 실제 생성 VT83종, 거부9종의 불필요 TYPE 조회 생략, 벌룬의 음수/끝 프레임과 누락된 frames, 내용물 flags256가지, 정상 복귀 진단 뒤 현재 flags/head/kind/QA/ContentType 재조회, 저장된 next 유지, 중첩 깊이 우선 쓰기, QA 두 폭, 별도 current/앞뒤 canary, 목록 진단 실패 prefix, 잘못된 부모·순환·반납 stream을 확인한다. 기존 Core의 원본 fixture 기반 내용물/전체 부모/기본 항목 검사도 함께 실행했다. 이는 새 PE 관측이나 전체 snapshot 완료가 아니다.

Native 호스트 검사는 실제 Factory/Content 생성·부착 장치와 같은 Runtime/Pool/Template를 사용했다. 명시 kind/flags 입력을 가진 실제 Content가 `01 47 10`으로 저장됐고 부모·내용물 raw 바이트, 대여 owner와 NativeLoaded=false가 보존됐다. 반납 뒤 대여가 남지 않는다. 이 검사는 자연 생산 조작의 완료로 세지 않는다.

첫 집중 Client는33통과·2실패였다. 원인은 검사 준비의 원본 tail 압축 전 커서 되감기와 free 비트를 켠 뒤 검사 입력용 AllocatedBytes 재사용이었다. 새 섹션 생성의 원문 압축 뒤에 cursor를 지정하고, free/dead 조회 뒤에는 확보한 같은 raw 입력 범위로 후속 입력을 준비하도록 고쳤다. 제품 코드와 원문 압축/할당 정책은 바꾸지 않았다. 처음과 교정 후 TRX는 `extracted/dotnet-1233-tests/`와 `extracted/dotnet-1233-tests-corrected/`로 구별한다. 최초 빌드의 검사 코드 Clear 호출1오류와 실행기의 내부 관측 접근 오류도 별도 로그에 남겼으며 최종 빌드는 정상이다.

Client 검사 프로젝트의 최종 Release 빌드는45.87초·오류0·기존경고5다. 해당 의존 빌드에서 Client/Game 제품은 정상 생성됐으며 새 제품 파일의 경고는 없다. 일회성 실행기 빌드는 오류0·경고0이다. 첫 Core 집중은 이전 제품 DLL로 실행되어 최종 공유 DLL 감사에서 차이를 발견했다. Core 검사 프로젝트만25.41초·오류0·기존경고12로 재빌드하고 같은5건을 다시 통과했으며 최종 감사는 같은 제품 DLL을 확인했다(`extracted/dotnet-1233-tests-currentcore/`). 전체 정기 회귀를 다시 실행하지 않았으며 마지막 전체는1.232의7,807통과·기본 옵트인 음향2미실행이다. 새 주기는 **1/4**, 다음 정기는1.236이다.

실제 Game 진단은 메뉴·`thewarbegins`·`tutorial1`·`surrounded` 네 경로에서20프레임의 실제 reason0/1 정리,30프레임 GPU/논리 RGBA 전수 대조,60프레임 정상 종료를 확인했다. 세 미션에서는 정리 전에 현재 기술 부모5/Template owner1의 같은 장기 manager에 Temp를 만들고 이번 내용물 저장을 호출했다. 세 출력은 모두 `00`이며 현재 부분 적재 장면의 빈 기술 목록 그대로다. 비어 있지 않은 내용물의 실제 Native 장치 저장은 위 집중 검사에서 확인했다. NativeLoaded는 세 경로 모두false로 유지됐고 실제 Runtime/부모가 바뀌지 않았다. 메뉴에서는 이 내용물 분기를 실행하지 않았다. 보호 원본1,392파일은 전후 불변이다.

이 진단은 API를 명시 선택한 실행이며 전체 Fort/Battle 저장·파일 저장·원래 State3/7 부모 실행·GUI 왕복의 증거로 세지 않는다. 기존1.232와 같은 정리 진단을 유지하고 같은 장기 Template에 자식 저장만 추가했다. 인자·SHA·픽셀·종료·저장 결과는 `extracted/dotnet-1233-state-runtime-verified/run.json`에, 집중 결과와 Game/Client 검사/Core 검사/실행기의 공유 제품 DLL 일치는 `extracted/dotnet-1233-audit.json`에 있다.

fixture529개는 유지하고 `cpp_sync.py`는 종료0이다. PORT_MAP에 가상 조회.cpp/.h와 Snapshot.cpp의 Contents 부분3행만 추가했다. 가상 조회의 근거 커밋은 `8912d1ed1f3d890f226cb10416d65f0b513013df`, 내용물 연결은 `93d891ac8a1d3205ee73a30033094086c71cf730`이다. 대응표는 물리2,025줄/자료2,020행(port1,472·L1 486·session62)이며 CPP1,244단위170,280줄 중 DN 대응709단위118,923줄/미대응535단위51,357줄이다. ## 일회성 실행기와 다음 작업

`ContentProbe.exe`는 배포물이 아니다. `dotnet build extracted/dotnet-1233-state-probe/ContentProbe.csproj -c Release` 후 `ContentProbe.exe <보고서 절대 경로> [미션 키]`로 실행한다. 키 생략은 메뉴의 메타 정리 명시 입력이다. `NETSTORM_DATA`는 보호 사본, `NETSTORM_USER_DATA`는 격리 쓰기 루트, `NETSTORM_PROBE_SETTINGS`는 선택 옵션이다. 창·음소거·고정25ms·Unix1760000000·60프레임이며, 내부 stream 버퍼는 진단용 reflection으로 읽기만 한다. 네 경로 및 보호 해시는 `python -X utf8 extracted/dotnet-1233-run-state.py verified`, 결과 감사는 `python -X utf8 extracted/dotnet-1233-audit.py`로 확인한다.

다음은 같은 소유자의 Deck/Objects/Territory/Core/Mission/Badges와 Notify·파일 장치를 기존 Fort/Battle 전체 부모에 결합하는 H-1 나머지다. 장기 Player/생산 Deck·직렬화 scope/mask·템플릿 State view·실제 작업 파일을 재사용하고, Core 저장의 RNG/SP 작성은 선택된 원문 위치에서만 실행한다. 이어 원래 cleanup(reason0/1) 호출 위치, H-2 State7 시작 몸체, H-3 직접 진입 교체/결과 공유 순서를 유지한다.
