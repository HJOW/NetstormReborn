# 셰이프 데이터베이스 (`d/_shapes.shp`)

> 분석 상태: **완료** — 116개 블록, 3,783개 프레임 전체 디코딩 검증 (이미지 3,692 + 특수 레코드 91)
> 도구: [`tools/shp.py`](../../tools/shp.py) (`info`, `export`)
> 근거: `Netstorm.exe` 의 `Rifttype.cpp`(타입 로더), `Vfxdraw.cpp`(VFX 그래픽 라이브러리) 관련 함수 디컴파일

## 개요

게임의 모든 스프라이트(유닛·건물·지형·아이콘·효과·도움말 그림)를 담은 파일이다.
Miles Design **VFX 그래픽 라이브러리의 셰이프 형식**(버전 문자열 `"1.10"`) 블록을 이어 붙인 구조다.
정수는 모두 리틀 엔디언.

## 전체 구조

```
[블록 0 헤더][블록 1 헤더] ... [블록 115 헤더]   ← 파일 앞부분에 헤더만 연속 배치 (0x0000 ~ 0x79D7)
[프레임 데이터 ...]                              ← 나머지 전부
```

### 블록 헤더

| 크기 | 내용 |
|---|---|
| 4 | 매직 `"1.10"` |
| 4 | 프레임 수 N |
| 8×N | 프레임 테이블: [프레임 오프셋 u32][컬러맵 오프셋 u32 (항상 0)] |

* **프레임 오프셋은 해당 블록 헤더(`"1.10"`) 시작 위치 기준**이다. (파일 기준 아님)
  근거: 커서를 메모리에서 셰이프로 만드는 함수(`FUN_004a4260`)가 `오프셋 = 프레임 주소 - 블록 주소` 로 기록한다.
* 여러 프레임이 같은 오프셋을 공유할 수 있다 (고유 오프셋 3,323개).

### 블록 ↔ 타입 대응

게임은 `.type` 파일을 **고정된 순서**(`Netstorm.exe` 0x540DD0 의 포인터 배열 116개)로 읽으며,
타입 하나를 읽을 때마다 셰이프 데이터베이스에서 다음 `"1.10"` 블록을 찾아 그 타입에 배정한다 (`Rifttype.cpp` 0x944 부근).
따라서 **블록 i = 로딩 순서 i 번째 타입**이다. 순서 목록은 `tools/shp.py` 의 `TYPE_LOAD_ORDER` 참고
(`dude`, `sunArcher`, `sunAviary`, … , `RUIN`, `Monument`).

### 블록 안 프레임 배치

```
프레임 번호 = 레이어 × 클러스터 수 + 클러스터 순번
```

* **클러스터**: `.type` 파일의 `이름 : 플래그 : "그림.gif" #n [: "그림.gif" #n] ;` 줄 하나 ([type.md](type.md)). 파일에 나오는 순서대로 0, 1, 2 …
* **레이어**: 클러스터 줄에 나열된 그림 순서. 레이어 0 = 본체, 레이어 1 = 그림자(`typeflags shadow` 타입).
* 116개 중 115개 블록에서 `프레임 수 = 클러스터 수 × 최대 레이어 수` 가 정확히 성립한다.
  예외 `manabolt`: 패치판에서 `.type` 을 4개 클러스터로 줄였지만 셰이프는 옛 정의의 8프레임 그대로다.
* **런타임에는 GIF 파일 이름을 쓰지 않는다.** 이름은 셰이프 제작(빌드) 시점의 원본 그림 참조일 뿐이며, 게임은 클러스터 순번으로만 프레임을 찾는다.

## 프레임

### 헤더 (24바이트)

| 오프셋 | 형식 | 내용 |
|---|---|---|
| 0 | u16 ×2 | bounds — 원본 그림 크기로 추정 |
| 4 | u16 ×2 | origin — 원본 그림 안의 기준점(핫스팟)으로 추정 |
| 8 | i32 | xmin (기준점 대비) |
| 12 | i32 | ymin |
| 16 | i32 | xmax (포함) |
| 20 | i32 | ymax (포함) |

픽셀 영역은 폭 `xmax - xmin + 1`, 높이 `ymax - ymin + 1`. 기준점 (0,0) 을 화면 좌표에 두면 영역의 왼쪽 위는 `(xmin, ymin)` 이다.
bounds/origin 의 정확한 의미(가로·세로 순서)는 렌더링 구현 시 확정한다.

### 픽셀 데이터 (행 단위 RLE)

헤더 바로 뒤에서 시작하며, 높이만큼의 행이 이어진다. 각 행은 토큰의 연속이다.

| 토큰 | 뒤따르는 데이터 | 의미 |
|---|---|---|
| `0x00` | — | 행 끝. 남은 픽셀은 투명 |
| `0x01` | n (1바이트) | 투명 픽셀 n 개 건너뛰기 |
| 홀수 t (3 이상) | (t>>1) 바이트 | 팔레트 인덱스 (t>>1) 개를 그대로 복사 |
| 짝수 t (2 이상) | 1바이트 v | 인덱스 v 를 (t>>1) 번 반복 |

### 특수 레코드 (91개)

`xmin`~`ymax` 가 0x7FFFxxxx 범위이고 float 값(1.0625 등)을 포함하는 레코드. 이미지가 아니다.
주로 그림자 레이어가 없는 클러스터 자리 또는 추가 메타데이터로 추정되며, 용도는 4단계에서 확인한다.
도구는 `special: true` 로 표시하고 이미지로 변환하지 않는다.

## 색상

* 팔레트: **`d/GIFCLOUD.COL`** (Animator Pro .COL: 8바이트 헤더 + 256×RGB).
  근거: `setup.cfg` 의 `fortPal = "gifcloud"`, `battlePal = "gifcloud"`, `GamePalSpec = "{DataDir}\{local.1}.COL"` 과
  팔레트 로더(`FUN_004a4850`, 0x308 바이트 .COL 또는 0x400 바이트 RGBX 파일을 받음).
* exe 에는 테마별 팔레트 이름(`sunny.col`, `rainy.col`, `windy.col`, `thundery.col`)도 있으나 해당 파일은 없고,
  `ascendancyPalette` 설정이 켜졌을 때만 쓰인다.
* 그림자 레이어는 단일 인덱스(예: sunCannon 217, dude 150)로 모양만 표시한다. 실제 그리기는 색상 변환 테이블(`!color.dat`, [config.md](config.md))로 배경을 어둡게 하는 방식으로 추정한다.

## 클론 구현 메모

* 로더는 파일 전체를 읽고 블록 헤더만 파싱하면 된다 (프레임은 필요할 때 디코딩하거나 로드 시 텍스처 아틀라스로 변환).
* 8bit 인덱스를 유지해야 팔레트 교체·색상 변환 효과(그림자, 플레이어 색, 피격 깜빡임)를 원본과 같게 재현할 수 있다.
