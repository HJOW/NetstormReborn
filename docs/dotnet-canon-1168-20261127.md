# 1.168 실제 창 키 입력과 음향 핸들 관측

1.089에서 확인하지 못한 채팅 재열기를 Windows 제품 창에서 다시 시험했다. 동일 고정 프레임·빈 사용자 루트의 무입력 실행과 비교했다. Windows 스캔 코드 Enter(28)를 `SendInput`으로 누르고 뗀 제품 실행은 포그라운드·프로세스 생존·키 상태를 확인했고 종료0이다. 360프레임 화면에 채팅창이 열렸으며 무입력과 90,674픽셀이 다르고 차이 범위는 `(20,649)–(1024,768)`이다. 실행은 `extracted/dotnet-key-1168-final-retry/`, 무입력은 `extracted/dotnet-key-1168-final/baseline/`이다. 화면 비교와 별개로 실제 물리 키는 확인하지 않았다.

첫 가상 키 합성(`keybd_event`, 스캔 코드 0)은 Windows 키 상태가 눌려도 진단 빌드의 MonoGame 키·문자 이벤트에 도달하지 않아 화면 차이0이었다(`extracted/dotnet-key-1168/`, `extracted/dotnet-key-1169-diagnostic/`). 게임 내부 `GetAsyncKeyState`도 눌림을 11프레임 관측했지만 MonoGame 상태는 false였다(`extracted/dotnet-key-1170-diagnostic/`). 스캔 코드 입력을 쓴 진단은 MonoGame 문자13, 실제 메뉴 분배와 채팅 열기까지 기록했다(`extracted/dotnet-key-1171-diagnostic/`). 이 비교만으로 가상 키 방식이 전달되지 않은 내부 원인을 단정하지 않는다. 제품 첫 재시험에서는 포그라운드 전환이 거부되어 입력하지 않았고 해당 실패를 `extracted/dotnet-key-1168-final/keyboard/`에 보존했다.

별도 제품 시험에서 Enter로 연 뒤 스캔 코드 Esc를 전달했으나 채팅창은 유지됐다(`extracted/dotnet-key-1168-close/`). Esc의 원본 기대 동작과 해당 입력의 최종 소비는 대조하지 않았으므로 결함이나 닫기 성공으로 단정하지 않는다. 원본 디렉토리 1,392파일은 각 실행 전후 불변이다. 임시 진단 소스는 빌드 직후 원래 바이트로 복원했다.

진단 중 `Window.Handle`과 Windows HWND의 직접 비교는 유효하지 않음을 확인했다. 사용 중인 [MonoGame 3.8.5.1 GameWindow](https://github.com/MonoGame/MonoGame/blob/v3.8.5.1/MonoGame.Framework/GameWindow.cs)는 DesktopGL의 Handle을 SDL 창 핸들로 설명한다. 현재 `ClientHostGame.ColorMaps.cs`는 이를 `HostMissionAudio`에 넘기고 `WindowsSoundDevice`는 DirectSound `SetCooperativeLevel`의 HWND로 사용하므로 실제 HWND 획득과 음향 재검증이 필요하다. 이 작업에서는 음소거 실행만 했고 하드웨어 재생은 확인하지 않았다.
