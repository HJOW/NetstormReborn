## 입력 지연과 커서 증상

### 로그에서 직접 확인한 것

각 입력의 `sessionElapsedMs`와 Windows 훅의 `hookTimeMs` 차이에서 전체 구간의 최솟값을
빼 **발생→훅 진입의 상대 대기 증가**를 계산했다. 두 시계의 원점이 달라 절대 지연은
얻지 못하며, Windows 밀리초 시각의 양자화도 포함된다. **훅 반환 뒤 게임에 전달되고
화면에 반영되기까지의 시간, 훅 내부 파일 쓰기 시간은 이 수치에 들어가지 않는다.**

| 구간 | 입력 수(경계 제외) | 상대 지연 중앙값 | 95백분위 | 최대 |
|---|---:|---:|---:|---:|
| 시작~07:42.4 | 8,153 | 7.8 ms | 15.5 ms | 22.6 ms |
| 07:42.4~08:36.85 | 1,077 | 8.2 ms | 15.2 ms | 21.6 ms |
| 08:36.85~09:00 | 123 | 8.9 ms | 14.9 ms | 16.4 ms |
| 09:00~종료 전 | 71 | **155.5 ms** | **413.3 ms** | **1,051.5 ms** |

표는 영상 0초 이후의 입력만 포함한다. 첫 프레임보다 앞선 입력 2건과 녹화 경계 2건은 제외했다.

09:28.787의 오른쪽 누름·해제(sequence 9365/9366)는 약 1 ms 안에 훅으로 몰려 들어왔지만,
Windows 발생 시각은 296 ms 떨어져 있었다. 상대 대기 증가는 약 1,051/756 ms다.
이처럼 도착이 몰리는 현상은 사용자의 ‘과거 움직임이 늦게 반영됐다’는 설명과 양립한다.
다만 게임의 그리기 시각과 OS 커서 궤적을 독립적으로 채취하지 않아 이것만으로 확정하지 않는다.

07:42.4 직후부터 느꼈다는 지연은 위 도착 시각만으로 충분히 설명되지 않는다.
훅 내부 처리와 게임 쪽 처리 지연도 고려해야 한다.
09:00 이후에는 입력 로그도 드문드문 남아 사용자가 움직이지 않은 구간과
기록하지 못한 입력을 구분할 수 없다. Windows가 훅을 제거했는지도 확정하지 못했다.

### 분석기에서 발견한 구조와 수정

- 녹화 당시 저수준 훅은 **안내 창 UI 스레드**에 설치돼 있었다.
  각 입력에서 `FindWindow`로 최상위 창을 열거·제목을 조회하고 JSON 직렬화·파일 쓰기·Flush 뒤에
  `CallNextHookEx`를 호출했다. UI 타이머의 창 배치 처리와 디스크 대기가 입력 전달을 지연시킬 수 있다.
- Microsoft는 저수준 훅을 전용 스레드에 두고 작업을 다른 스레드로 넘겨 즉시 반환하도록 권고한다.
  지연 시 훅이 조용히 제거될 수도 있다.
  [공식 LowLevelMouseProc 문서](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc).
- 수정 후 두 녹화 모드 공통으로 훅을 **전용 메시지 스레드**에 설치한다.
  훅에서는 원시 입력·진입 시각과 현재 클라이언트 좌표만 채취한다.
  창 열거·제목 조회는 영상 스레드가 갱신한 창 정보로 대체하고 파일 저장은 별도 스레드로 보낸다.
  제목은 최근 영상 샘플(목표 100 ms 간격), 좌표·크기는 입력 당시 조회값이다.
- 저장 대기열은 4,096건으로 제한하고 훅에서 기다리지 않는다.
  포화·파일 쓰기 실패는 오류로 녹화를 중단한다. 정상 중단은 수락한 입력을 모두 저장한 뒤
  `stopped` 경계를 쓴다. 기존 조각·형식 2·순번·동기화 기준은 유지한다.
- 느린 저장 중 즉시 반환, 종료 전 저장, 포화 오류, 저장 실패 전달,
  키·마우스 순서와 원래 시각 보존을 게임 없는 회귀 테스트 4개로 검증했다.
- **수정 후 같은 게임 구간의 재녹화는 하지 않았다.** 구조적 지연 요인은 제거했지만
  이번 사용자 증상이 모두 해소됐다는 결론은 아직 내리지 않는다.

### 커서의 실제 이동과 지연 반영 구분

- 세션 이벤트에 `game_input` 자동 입력은 없다. `record-play`의 기록·캡처·상태 갱신에는
  `SetCursorPos` 호출이 없다. 안내 버튼 직후 초점을 돌리는 코드만 있고 매초 강제 초점 전환은 하지 않는다.
- 분석기의 `WindowsGame`에는 자동 탐험용 좌표 이동 코드가 있으나 이번 녹화 경로는 그것을 호출하지 않는다.
- 원본 exe의 `Clientmain.cpp` 메인 루프(`FUN_00438dc0`, 재진입 경로 `FUN_004395df`)에는
  `GetCursorPos` 직후 같은 좌표로 `SetCursorPos`를 호출하는 코드가 있다.
  `extracted/decomp/Netstorm.c`의 40939~40940·41212~41213행이다.
  이것은 특정 의식 상황만의 코드가 아니며, 호출 사이의 입력 지연으로 이전 좌표가 재적용되는
  가능성은 있으나 실제 발생·정확한 상호작용은 이번 녹화로 입증하지 못했다.
- `injected=false`만으로 물리 마우스 입력이라고 단정할 수 없다.
  이 표시는 생성 주체를 완전히 식별하지 못하며 `SetCursorPos`의 존재 여부도 증명하지 않는다.
  영상에는 OS 커서가 별도 합성돼 있지 않으므로 입력 좌표·화면 반응만으로 실제 궤적을 전부 복원할 수 없다.
- 결론: **분석기에 입력을 지연시킬 수 있는 구조가 있었고 후반 훅 도착 지연도 관찰됐다.**
  실제 커서 재배치와 이전 움직임의 지연 반영은 구분되지 않았다. 사용자가 제시한 후자의 가설을
  포함해 후속 재녹화에서 확인해야 한다. 원본 바이너리를 패치하지 않았다.
