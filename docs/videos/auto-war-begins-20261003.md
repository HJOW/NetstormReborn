## 4. 마우스 조작과 이동 애니메이션

### 4.1 유닛 선택과 이동 명령(사제·골렘 공통)

1. 유닛을 **왼쪽 클릭**하면 선택된다. 머리 위에 **초록 체력 막대**가 뜨고 발밑에 **청록색 모서리 브래킷**이 그려진다.
2. 선택한 채 **땅(섬 위·다리 칸)을 왼쪽 클릭**하면 그곳으로 걸어간다.
3. 명령을 내린 **바로 다음 프레임에 선택이 풀린다**(체력 막대가 사라짐). 이동 중인 유닛을 다시 움직이려면 다시 선택해야 한다. 이동 중 재명령은 CLI 호출 간격(수 초)이 도착 시간보다 길어 시험하지 못했다.
4. **허공·절벽 가장자리를 목적지로 클릭**하면 걷지 않고 선택만 풀린다. 1차 실행에서 절벽 윗선에 걸친 (680,395)를 눌렀을 때도 같았다. 2차의 허공 (300,200) 시험은 영상으로 확인했다(75.0~76.6초 선택, 이후 정지).
5. 선택·목적지 클릭 사이의 커서 호버는 필요하지 않았다. 2차 스크립트는 `Mv` 함수가 PowerShell 별칭 `mv`(Move-Item)와 충돌해 호버 이동이 전부 실행되지 않았고, 클릭 입력만 커서 이동 4~6ms 뒤에 눌렀지만 **메인 메뉴 버튼·미션 안 모든 조작이 정상 동작했다**. 1차의 200ms·500ms·1,000ms 호버도 모두 동작했다. 기존 문서의 "메인 메뉴 버튼은 커서를 먼저 올려야 한다"(Help 버튼 관찰)와 다른 결과이므로 Help 외 버튼에서는 호버가 필수가 아닌 것으로 본다. Help 버튼은 이번에 시험하지 않았다.

### 4.2 이동 애니메이션 측정

스프라이트 위치를 프레임마다 추적한 값이다(사제는 금발 픽셀, 골렘은 배경 차분 뒤 어두운 픽셀의 무게중심).

| 이동 | 거리(픽셀) | 클릭 → 출발 | 걷는 시간 | 속도 |
|---|---|---|---|---|
| 사제 2(직선, 동) | Δx +121 | 약 0.5초 | 4.33초 | 가로 약 **1.74칸/초**(27.9px/초) |
| 사제 3(직선, 동) | Δx +139 | 약 0.8초 | 4.77초 | 가로 약 **1.82칸/초**(29.1px/초) |
| 골렘 1(직선, 동) | Δx +174 | 약 0.4초 | 5.9초 | 약 **1.84칸/초**(29.5px/초) |
| 골렘 2(직선, 동) | Δx +208 | 약 0.5초 | 6.3초 | 약 **2.06칸/초**(33px/초) |
| 사제 4(대각선→직선) | Δ(+60,+120) | 약 0.5초 | 약 7초(눈으로 읽음) | 세로 약 1.5칸/초(자동 추적 실패) |

- 칸 하나 = 가로 16px × 세로 11px로 환산했다. exe `.type`의 `speed`는 사제 1.8, 골렘 2.0이며 직선 이동 측정(사제 1.74~1.82, 골렘 1.84~2.06)과 맞는다.
- 클릭 뒤 곧바로 걷지 않고 **0.4~0.8초 동안 방향을 바꾸는 준비 동작**이 먼저 나온다(프레임 7~14장). 이 지연의 변동은 18FPS 시각 오차(약 66ms)보다 크지만 원인(방향 전환 각도 등)은 가르지 않았다.
- 걷는 동안 **다리를 번갈아 움직이는 걷기 프레임**이 반복된다. 대각선 이동은 **대각선으로 먼저 간 뒤 직선으로 이어지는** 경로였다(사제 4: 63.1~66초 대각선, 이후 아래로 직선).
- 도착하면 곧바로 정지 자세로 돌아가며 선택은 이미 풀려 있다.

### 4.3 골렘 생산(덱 → 배치)

- 덱의 골렘 아이콘을 **왼쪽 클릭하면 집는다.** 집은 골렘 그림이 커서를 따라가며 **비용 400**(노란 글자 + Storm Power 보석)과 속성 아이콘(Sun 주황색)이 붙는다.
- 1차 실행 화면 기준 배치 미리보기: 땅 위에서 템플 에너지 범위 안이면 **흰 사각 칸 표시**, 허공 위면 붉은 표시와 **"Only on Controlled Island"**, 에너지 범위(템플에서 약 30칸) 밖이면 **"Energy not satisfied"**가 뜬다(2차 스크립트는 호버 단계를 건너뛰어 영상에는 없다).
- 배치 클릭(84.6초) 연출: ① "400"이 떠올랐다가 사라짐 ② 템플 쪽에서 **푸른 에너지 방울이 꼬리를 끌며 날아옴**(85.1초) ③ 골렘이 **반투명 상태**(85.4~85.8초)를 지나 불투명해짐(약 86.0초). 클릭에서 완성까지 약 1.4초다.
- **SP 숫자는 굴러서 내려간다**: 3000 → 2680(85.0초) → 2601(85.4초) → 2600(85.9초). 숫자가 3000·2600은 흰색, 1800(워크샵 뒤)은 노란색이었다.
- 골렘 아이콘은 배치 뒤에도 덱에 남아 있었다(2차 최종 화면 덱: 골렘·Rain Generator·Sun Cannon).

### 4.4 우클릭 메뉴(1차·2차 모두)

- 유닛·건물을 **오른쪽 클릭**하면 클릭 위치에서 정보 메뉴가 뜬다(화면 가장자리에서는 안쪽으로 밀림).
- 골렘: `Golem Level I / Owner: You / Alignment: Sun / Class: Ground Transport` + Salvage gains 100 / About / Player >.
- 사제: `High Priest Level I / Owner: You / Alignment: None / Class: High Priest` + Construct > / View Netstorm Knowledge / About / Player >.
- 워크샵: `Sun Workshop Level I / Owner: You / Alignment: Sun / Class: Production` + View Current Production > / Put Knowledge into Production > / Upgrade costs 800 / Salvage gains 200 / About / Player >.
- `>` 항목은 **왼쪽 클릭으로** 하위 창을 연다(Construct → Workshop 순서로 두 단계). 호버만으로 여는지는 시험하지 않았다.
- 메뉴는 **허공을 왼쪽 클릭하면 닫힌다**. 이 클릭은 이동·배치 같은 다른 명령으로 이어지지 않았다.

### 4.5 사제로 워크샵 건설

1. 사제 우클릭 → `Construct >` → `Construct Building` 창: **Temple >**(어둡게 표시), **Workshop >**, **Build Level 1 Altar for 500**.
2. `Workshop >` → **Build Sun Workshop for 800**(활성), Build Wind Workshop for 1000·Build Rain Workshop for 1000·Build Thunder Workshop for 1000(어둡게 표시).
3. 선택하면 **건물 그림이 커서에 붙고** 아래에 비용 "800"이 나온다. **발자국 사각형이 흰색이면 설치 가능, 반투명 붉은색이면 불가**였다. 동쪽 섬 (885,423)은 가능했고, 템플 남서쪽 평지는 위치를 세 번 옮겨도 모두 붉은색이었다(발자국이 땅 안에 들어가 보이는데도 불가). 이유(템플 근접 금지 칸·땅 칸 모양 등)는 확인하지 못했다.
4. 좌클릭으로 설치하면 SP가 800 줄고(2600 → 1800) **공사장 그림자**(어두운 실루엣 + 흩어진 나무 윤곽)가 나타난다.
5. **사제가 직접 걸어가서** 건설한다. 2차에서는 (600,388) 부근에서 출발해 설치 약 7초 뒤(154.5초) 공사장 왼쪽 가장자리에서 보이기 시작했고 약 158~159초에 도착했다. 도착 뒤(약 160초) 건물이 **바닥의 나무·화단부터 위로 차올라** 약 170.8초에 외형이 완성되고, 약 8초 뒤(178.9초) **창문에 불이 켜졌다**. 설치 클릭에서 완성까지는 약 23초이며, 이 중 걷기를 뺀 건설은 약 10~11초다(기존 문서의 관찰값 10초와 맞음).

### 4.6 워크샵으로 덱에 등록

1. 워크샵 우클릭 → `Put Knowledge into Production >` → **Knowledge Available / Production Slots Available:** 창에 Rain Generator·Sun Cannon·Whirlibase가 나온다(`Production Slots Available:` 뒤의 숫자는 두 번 모두 화면 오른쪽 밖으로 잘려 읽지 못했다).
2. 항목을 왼쪽 클릭하면 **그 항목이 목록에서 사라지고 덱에 아이콘이 생긴다**. Rain Generator는 클릭(198.9초) 다음 프레임에, Sun Cannon은 클릭(205.7초) 0.5~0.8초 뒤에 덱에 나타났다. 등록 비용은 없었다(SP 1800 유지).
3. 두 번째 등록 때 목록은 Sun Cannon·Whirlibase 둘뿐이었다.
4. `View Current Production >` 목록은 **Rain Generator·Sun Cannon·About**이었다.
5. 덱에는 위에서부터 다리 조각, 골렘, Rain Generator(푸른 결정), Sun Cannon(검은 포대)이 순서대로 들어갔다. 이전 [워크샵 문서](../gameplay/workshop-deck.md) 해석(수정=Rain Generator, 포대=Sun Cannon, Whirlibase는 미등록이라 돔 아이콘 없음)과 일치한다.

### 4.7 ESC 메뉴로 나가기

- ESC 한 번(키 누름·해제 93ms)으로 화면 맨 위에 **메뉴 막대**가 나타난다(Game·View·Options·Players·About). Game 글자 약 (104,9).
- Game 메뉴: Review Mission Objectives - F8 / **Restart Mission / Leave Mission** / Quit Game.
- Leave Mission → **"Leave Mission? Do you wish to quit this mission and return to the Main Menu now?"** 창과 **Main Menu / Replay Mission / Continue Mission** 버튼. Main Menu를 누르면 약 1초 안에 메인 메뉴(`9a5aa24c`)로 돌아온다. 확인하지 않은 항목(Restart Mission·Quit Game)은 누르지 않았다.

## 5. 이번 자료로 확정한 것과 남은 것

**확정(영상·입력 로그 근거)**

- 이동 명령 = 선택 → 땅 좌클릭 → 선택 해제. 허공은 거부. 출발 지연 0.4~0.8초, 직선 속도는 사제 약 1.8칸/초, 골렘 약 2.0칸/초.
- 골렘 배치 연출(에너지 방울 → 반투명 → 불투명, 약 1.4초)과 SP 숫자가 굴러 내려가는 방식.
- 워크샵 건설 흐름(공사장 그림자 → 사제 도착 → 아래에서 위로 건설 약 10~11초 → 창문 불), 덱 등록과 목록 갱신.

**미확인·다음에 볼 것**

- 이동 중인 유닛에 새 명령을 줄 때의 반응(경로 즉시 전환인지), 사제·골렘이 가로막힐 때 우회 방식.
- 대각선 경로의 전체 규칙(8방향인지, 대각선 먼저인지 항상 같은지)과 세로 속도(1.5칸/초 추정)의 정확한 값.
- 워크샵 설치 불가의 원인(템플 남서쪽 평지), `Production Slots Available` 숫자, Level I 슬롯이 2개인지.
- 소리: 명령 응답음·건설음·등록음의 파일 대응(`tools/audiomatch.py sfx`로 판별 가능).
- 이번 녹화의 FPS는 18.2였다. 짧은 사건(출발 지연 0.4~0.8초의 분산)은 더 높은 프레임률로 재측정해야 한다.

## 6. 녹화 도구에서 확인한 것과 고친 점

세 번의 실패와 수정은 `analyzeManager/`의 코드에 반영했다(→ [분석기 문서](../analyze-manager.md#2026-10-03-자동-녹화-일시-파일-충돌-재시도와-가림-중단-사례)).

1. **상태·기록 파일 교체 거부(수정함).** 자동 녹화가 8.5초 만에(`automatic-recording.json` 교체), 다른 세션이 시작 0.1초 만에(`session.json` 교체) `Access to the path is denied.`로 실패했다. Windows는 **다른 프로세스가 대상 파일을 열고 있으면 `FileShare.Delete`를 허용했더라도 `File.Move` 덮어쓰기를 오류 5로 거부**한다(`MoveFileEx` 직접 호출로 두 경우 모두 오류 5임을 확인). 녹화 프로세스가 상태 파일을 200ms마다 교체하므로, CLI의 상태 읽기나 백신 같은 다른 프로세스가 같은 순간 파일을 열면 걸린다(실제로 누가 열고 있었는지는 특정하지 못했다). `SessionStore.RetryTransient`(최대 20번·25ms 간격)를 `WriteSmallFile`·`SessionStore.Save`·`AppendPart`·`AutomaticRecording.SaveState`에 적용했고, 녹화 루프의 진행 상태 저장 실패가 녹화 자체를 끊지 않게 했다. 단위 테스트 1개(`StateSaveRetriesWhileAnotherHandleBlocksReplacement`)를 추가해 분석기 테스트 **103개 통과**·기존 1개 건너뜀이다.
2. **게임 창 가림으로 녹화가 영구 중단됨(수정하지 않음).** 1차의 녹화는 6분 48초에서 `게임 캡처 영역이 다른 창에 가려져 있습니다`로 멈췄다. 입력 로그에는 그 직전에 **사람의 물리 마우스(`injected=false`)가 게임 창 밖 (1551,905)로 이동해 클릭**한 기록이 있다. AI 도구 호출의 승인 프롬프트를 사용자가 VS Code에서 누르면서 VS Code가 전면으로 올라와 게임을 가린 것으로 **추정**한다. 가림은 게임 창의 세 표본 점(좌상단·우하단·중앙) 위에 다른 창이 있으면 판정되며, 한 번이라도 걸리면 녹화는 다시 시작되지 않는다. 이후 21분 50초(골렘·건설·등록·종료)가 영상에 없었다.
   - 대응: 2차는 **승인 프롬프트가 필요 없는 스크립트 한 개**로 실행하고 사용자에게 실행 중 조작하지 말라고 요청했다. 그 결과 오류 없이 끝까지 녹화됐다.
   - 제안(구현하지 않음): 가림을 영구 중단 대신 **해당 프레임만 건너뛰고 가림이 풀리면 이어서 녹화**하도록 바꾸면 일시적인 알림·승인 창으로 세션 전체를 잃지 않는다. 다른 프로그램 화면을 저장하지 않는 원칙은 그대로 유지된다. 기존 문서의 "가려지면 중단" 정책을 바꾸는 일이므로 사용자 결정이 필요하다.
3. **30FPS 미달.** 이번 환경에서 평균 18.2FPS(61%)였다. 기능은 정상이나 "30FPS 달성"은 확인되지 않았다([2절](#2-녹화-통계2차)).
4. **스크립트 함정 두 가지.** (a) 함수 이름 `Mv`는 PowerShell 별칭 `mv`(Move-Item)가 우선해 호버 이동이 실행되지 않았다. (b) **Windows PowerShell 5.1은 BOM 없는 UTF-8 `.ps1`을 ANSI로 읽어** 한글·`→` 같은 문자가 따옴표로 해석돼 구문 오류가 난다 — 한글이 들어간 스크립트는 UTF-8 BOM으로 저장한다.
