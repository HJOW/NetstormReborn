# 1280 렌더링 상한과 화면비별 FSR 출력

2026-11-28 사용자 요구와 후속 정정을 적용한다. `3840×2560`은 오타이며 16:9·16:10·4:3의 높이는 각각2160·2400·2880이다. AGENTS.md 자체는 수정하지 않는다.

| 화면비 | 기본 최대 / FSR 입력 | FSR 출력1920 폭 | 2560 폭 | 3840 폭 |
| --- | --- | --- | --- | --- |
| 16:9 | 1280×720 | 1920×1080 | 2560×1440 | 3840×2160 |
| 16:10 | 1280×800 | 1920×1200 | 2560×1600 | 3840×2400 |
| 4:3 | 1280×960 | 1920×1440 | 2560×1920 | 3840×2880 |
| 5:4 | 1280×1024 | 1920×1536 | 2560×2048 | 3840×3072 |

5:4는 요청한1280×1024에 대응한다. 원본640×480·800×600·1024×768도 유지한다. 1366×768·1600×900은 일반 목록에서 제거하고 저장값을 가장 가까운 화면비의1280 화면으로 옮긴다. 1920 이상의 목록은 실제 FSR 출력기가 준비돼야 허용하고 자동으로FSR을 켠다. FSR 미지원 환경은 같은 화면비의1280 출력으로 복구한다.

## cpppj — CP1384 완료

공유 ScreenResolutions 정책·두 Options 메뉴·Client 최초 설정 해석/논리 표면 할당에 적용했다. Direct3D11의 기존 공식 EASU/RCAS 출력을 재사용하며 입력은 각 화면비의1280 폭이다. 게임 Release 빌드와 정책3/3·기존 상수/실제 GPU 및 추가12출력 GPU 검사6/6이 통과했다. GPU 검사에서 실제1280 입력을 모든12출력으로 그린 뒤 크기·균일색을 읽었다. 장치 미지원/옛 설정 복구도 검사했다. 로그는 `extracted/resolution-1280-cpp-*.log`다.

원본 파일·디컴파일 자료는 변경하지 않았다. 마지막 디컴파일 PC와 이번 PC는 모두 **HJOW-Athlon**이다. ZIP은 재작성하지 않았다.

## dotnetpj — 계획1.216 완료, 제품1.215 유지

사용자 후속 지시로 R8의 실제 구현을 다음 작업으로 남기고 [DN-RES-1~4 계획](dotnet-resolution-1280-plan-20261128.md)에 정책·실제 GPU 연결·메뉴/현재 소유자 수명·검증을 명시했다. 준비한 후보는 최종 GPU 검증 실패 상태로 ignored 위치에 보관하고 제품 소스를 기존 상태로 복구했다. Game/검사 참조를 다시 빌드해 오류0(기존 경고7)이며 새FSR 구현을 완료한 것으로 세지 않는다. 정기 제품 회귀 주기0/4 유지다.

## webpj — WB04-E1488 완료

1280 폭/네 화면비 정책과 CSS/DPR 출력 분리를 적용했다. 작은4:3은 원본1024×768이며1280×960 이상 창부터1280×960을 쓴다.16:9는 모든 창에서1280×720,16:10은1280×800,5:4는1280×1024다. Canvas 표시 크기는 기기 픽셀 비율에 맞춰 별도로 확대하며FSR은 지원하지 않는다. 미션의Screen·Renderer·HUD·입력은 같은 제한 크기를 사용한다.

검증 결과는 다음과 같다.

- Node 집중/추적/재번들/webpack 관문 **25/25**, 변경 파일ESLint0, 운영 번들5,866,615바이트(한도9,900,000) 통과다.

- 새 cpppj CP1384 오라클과16:9 고정 시각1/1: 옛1366×768 크기의 브라우저에서 실제 논리는1280×720이며90프레임 픽셀 차이0,90/130프레임 덤프는 기존 허용(`sp`·`player:*`) 밖 차이0이다.
