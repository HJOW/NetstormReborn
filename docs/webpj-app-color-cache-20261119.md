# WB04-E900: 앱 시작 색상 캐시와 소유자 표

## 근거와 범위

cpppj `ClientMain.cpp`의 최초 TYPE 적재 후 경계는 Client의 고정 primary와 실제 TYPE 수·다리 TYPE·공유 redraw를 사용해 소유자 표를 초기화하고 색상 캐시의 9표를 읽거나 생성한다. 이후 같은 9표의 밝음·건설 행을 Screen에 연결한다. 앱은 실제 `GameAssets`와 E899의 Screen·ColorSort 소유자로 같은 순서를 실행한다.

파일 캐시는 기존 `MemoryColorMapFiles`를 사용하며 같은 앱 인스턴스의 종료·재시작에 걸쳐 유지한다. 페이지를 닫은 후 영구 저장은 아직 연결하지 않았다. 첫 실행 miss는 실제 계산으로 2,304바이트를 쓰고 같은 페이지의 다음 시작은 이 파일을 읽는다. 색상표와 소유자 표는 각 Client 수명마다 새로 구성하고 기존 표를 Session에 아직 대여하지 않는다. 실제 표시 장치·구름·전투 팔레트 변경과 미션 진입은 후속이다.

현재 앱은 원본과 달리 Surface 장기 저장소를 먼저 만든 다음 색상 캐시를 준비한다. 전체 시작 순서의 동일성은 아직 확인하지 않았다.

## 검증

- 실제 GIFCLOUD·TYPE·SHP 자산의 앱 초기화, 표 등록과 Screen 명암 행 별칭, 캐시 miss 및 내용을 바꾸어 확인한 hit를 검사했다.
- 기존 색상 캐시의 원본 관측, 단축 읽기·실패 경계와 앱 적재 관련 검사를 함께 실행했다.
- Chromium 첫 실행은 기존 시험의 redraw 기대값 1이 소유자 표 등록의 실제 증가를 반영하지 않아 실패했다. Renderer 초기화 1 뒤 소유자 표 등록이 같은 값을 2로 증가시키는 원본 순서에 맞게 기대값을 교정했다.
- 교정 후 Chromium의 시작·종료·재시작 1건과 집중·연관 Node 검사 38건이 통과했다.
