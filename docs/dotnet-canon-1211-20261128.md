# 1.211 실제 장기 음향 소유자와 옵션·음소거 수명

기존 HostMissionAudio에 실제 음악 파일 저장소·두 채널·Win32 Runtime·곡 선택기를 조립했다. 최초 초기화와 옵션 재해석을 구별하고 같은 효과음/음악의 공통 음소거를 연결했다. 첫 집중의 검사 조립/스레드 관측을 교정한 뒤 **최종 집중368/368·별도 Explicit 실제 하드웨어1/1**이 통과했다. 대표3진입과 같은 실제 Main의 sound0/music1 진단 진입은 모두 종료0이며 기존 덤프·여섯 화면·보호1,392파일은 불변이다. SceneMusic·메뉴 음향·State 왕복 완료 판정은 포함하지 않는다.

선행 본체는 [채널1.201](dotnet-canon-1201-20261128.md)·[파일1.202](dotnet-canon-1202-20261128.md)·[열기/선택1.203](dotnet-canon-1203-20261128.md)·[Fill/COM1.207](dotnet-canon-1207-20261128.md)·[Runtime1.208](dotnet-canon-1208-20261128.md)·[실제 HWND1.209](dotnet-canon-1209-20261128.md)다. 이번 조립과 선행 fixture 전수 대조의 결과를 서로 대신하지 않는다. 전체 회귀1.210의 기존 로그 검사 실패 및1.210a의 격리 교정도 [첫 실패](dotnet-canon-1210-20261128.md)·[교정 집중](dotnet-canon-1210a-20261128.md)에 그대로 보존한다.

## 같은 실제 장기 소유자

`dotnetpj/src/Netstorm.Game/HostMissionAudio.Music.cs`의 준비 생성자는 기존 SoundList/SoundState/WindowsSoundDevice/SoundPlayer와 같은 문맥에 다음 소유자를 만든다.

| 소유자 | 실제 공유와 수명 |
| --- | --- |
| WindowsMusicFileStore | 실제 Winmm 파일 토큰/위치를 소유한다. 준비 생성 시 파일은 열지 않으며 worker·장치 종료 뒤 최종 Dispose까지 저장소를 유지한다. |
| MusicChannelState 두 개와 MusicChannel 두 개 | 서로 다른96BYTE/채널 객체다. 기본 채널의 파일·버퍼·상태를 다른 모형으로 대체하지 않는다. 두 채널은 같은 파일/DirectSound 장치 함수를 빌린다. |
| SoundMusicControl.ForPrimary | 기존 효과음과 같은 SoundState를 쓰고 실제 기본 채널 identity와 SetVolume을 함께 보관한다. Play/Stop/Update/음량/Runtime이 같은 재귀 명령 잠금을 사용한다. |
| MusicRuntimeState·MusicRuntime | 같은 두 채널과 Control을 사용하며 실제 WindowsMusicRuntime 이벤트/스레드/협조 종료 함수를 빌린다. Runtime 생성 자체로 worker를 시작하지 않는다. |
| MusicSelectionState·MusicSelection | 현재256BYTE 이름과 음악 옵션을 장기 보관한다. 공개 재생 함수는 같은 기본 채널의 실제 Open/EnsureBuffer/Start/Stop과 실제 파일 조회를 사용한다. |
| 기존 SceneMusicState | 호출자가 넘긴 동일 객체를 빌린다. State와 공유하는 SongEnd도 같은8BYTE다. 감독·시계 읽기·난수 소비·Start/Frame은 준비 생성자에 추가하지 않는다. |

기존 window 생성자는 준비 생성자로 위임한 뒤 `InitializeStartup(window, muted)`만 호출한다. 최초 ColorMaps의 null 분기와1.209의 SDL 포인터→실제 HWND 입구를 유지한다. 새 미션의 BindPriest/소리 프로세스·UnbindMissionForState는 기존 수명을 유지하며, State 미션 반납에서 이 장기 owner나 worker/파일 저장소를 닫지 않는다.

## 서로 다른 세 옵션 입구

순수 값/호출 순서는 `dotnetpj/src/Netstorm.Client/Audio/ClientAudioOptions.cs`, 실제 장치는 `HostMissionAudio.Options.cs`에 있다. Read는 sound/music1·quality3·효과음/음악 음량 단계5·동시 한도8·좌우 교환0에서 원문 순서의 ReadInt로 명시 키만 덮는다. unsigned(step-1) 음량 표는1→-4000·2→-2000·3→-1000·4→-500이며 나머지는0이다. Read 단계에서 음질/한도를 임의 보정하지 않는다.

| 입구 | 순서와 범위 |
| --- | --- |
| 최초 Initialize | 옵션 전역→효과음 음량→음악 음량→sound와 무관한 실제 장치 Initialize→최초 thunderCrack.wav preload→Runtime.Initialize다. sound0/music1도 최초 실제 장치/worker 열기에 도달하며 효과음 Enabled와 음악 옵션을 구별한다. |
| 실제 음향 Interpret | 옵션 전역→sound별 OpenDevice(preload:false)/CloseDevice→효과음 음량→음악 음량→비어 있지 않은 현재 이름의 Select다. 열기의 자연 false 반환 뒤에도 뒤 음량/곡 적용을 진행하고 장치 실패가 끈 Enabled를 재차 덮지 않는다. |
| State 전체 InterpretOptions | 위 음향 적용과 다른 부모다. 현재 CPP ClientMain의 전체 옵션 부모는 ReadAudioOptions 결과를 읽으며 ClientAudio.Interpret를 호출하지 않는다. 이번 단위에서 State 장치에 음향 Interpret를 대신 연결하지 않는다. 실제 옵션 행/UI callback 결선도 별도 후속이다. |

현재 이름은 `CurrentMusicName`이 같은 MusicSelectionState.Current에서 읽고 길이는 `CurrentMusicDuration`이 같은 기본 채널+0x18의 실제 double에서 읽는다. 조회가 곡을 열거나 Scene 기한/시계/난수를 갱신하지 않는다. SelectMusic/StopMusic은 같은 선택기와 기본 채널을 사용한다.

## 공통 음소거와 반납·실패 경계

PushMute/PopMute는 같은 SoundMusicControl과 기존 SoundState의 보류 깊이·효과음/음악 예약 음량을 사용한다. 최초 mute는 실제 초기화 뒤 PushMute다. 보류 중 Initialize/Interpret의 음량 요청은 예약값만 바꾸고 현재 최소 음량을 유지한다. 재개용 CloseDevice와 재열기에서 깊이·예약값·현재 곡 이름·Scene·파일 저장소를 새로 만들거나 초기화하지 않는다.

CloseDevice는 Runtime.Shutdown 뒤 장치를 종료한다. Runtime의 기본 채널 Stop 예외도 실제 worker 합류/핸들 반납 뒤 전달되며 Host는 finally에서 장치를 닫는다. 최종 Dispose는 같은 경로 뒤 finally에서 FileStore.Dispose를 수행한다. 이미 닫힌 owner의 새 공개 음악/옵션 요청은 거부하며 반복 Dispose는 추가 반납을 하지 않는다. Runtime.Initialize의 정상 복귀 자체가 실제 핸들 생성 성공을 뜻하지 않는 원문 정책은 유지한다.

1.209의 장치 성공 HWND/실패 문장은 실제 장치 반환과 현재 Initialized를 구별해 기록한다. 이미 열린 장치의 false를 고장 로그로 바꾸지 않는다. Runtime 초기화 정상 복귀 직후와 Shutdown 반납 뒤에는 같은 RuntimeState의 실제 Thread/Shutdown 핸들 및 MusicInitialized를 별도로 관측한다. 이 INFO는 핸들의 유효성/worker 진행을 대신 증명하지 않으며, 정상 Note가 메모리에만 남는 점은1.209와 같다. 선행 진단 로그를 덮거나 삭제하지 않는다.

생성 중 부분 조립 실패는 준비한 Runtime→장치→파일을 보호 호출로 반납하고 최초 예외를 유지한다. window 생성자의 초기화/관측 예외도 같은 전체 owner 정리 후 원래 예외를 다시 전달한다. **준비 생성자 뒤 public Initialize를 직접 부르는 경우는 구별한다.** 실제 장치 성공 뒤 최초 thunder preload에서 예외가 나면 그 위치는 Runtime catch 밖이므로 호출자가 try/finally로 Close/Dispose해야 한다. 이는 CPP ClientAudio::OpenDevice의 부분 효과 정책과 같으며 모든 public 초기화 예외의 자동 전체 반납을 주장하지 않는다.

## 기록 실패가 종료를 중단하지 않는 adapter

새 `dotnetpj/src/Netstorm.Game/HostAudioLog.cs`의 기본 주 기록은 실제 ErrorLog.Note다. 주 기록 실패 뒤 Trace를 시도하고, 그 실패 뒤 Console.Error를 시도한다. 세 단계 모두의 예외가 Runtime 로그/합류·생성 실패 정리 밖으로 다시 전파되지 않게 한다. 실패를 정상 파일 기록으로 표시하지 않는다.

저장소는 각 단계의 첫 Exception 한 개와 실패 횟수만 보관한다. 보관되는 예외 참조는 최대3개이며 무제한 실패 목록을 만들지 않는다. Interlocked/Volatile로 worker/주 스레드 경쟁에서도 첫 실패와 횟수를 관측한다. 이 nonthrow 로그는 관리 환경에서 정리 수명을 지키는 안전 adaptation이며 CPP 원문 전체를 그대로 복제했다는 의미가 아니다. 원문 assertion의 ReportMusicAssertion은 throw가 허용된 별도 report 슬롯으로 유지한다.

## 실제 제품 진입과 별도 Main 진단

`extracted/dotnet-audio-owner-1211-baseline/run.json`은 apphost로 음소거 대표3미션 thewarbegins·tutorial1·surrounded를 실행한 결과다. `extracted/dotnet-audio-owner-1211-diagnostic/run.json`은 같은 실제 Program.Main을 PowerShell STA에서 호출한 sound0/music1의 thewarbegins 추가1회다. 모두120프레임·고정25ms·고정 Unix시각1760000000·종료0이며90프레임 덤프가 각각 기존1.173 DN 덤프와 바이트가 같다. 두 묶음 각각1-1의30/40/45/50/60/70 여섯 논리 화면은1.189 기준과0픽셀 차이이며 보호 originals1,392파일의 전후 SHA가 같다.

이 Main 진단은 실제 제품 최초 sound0/music1 장치·Runtime 준비/종료 입구를 확인한다. 실제 음악 파일 표본/COM 커서 전진과 최소 음량·두 재생 주기·원래 핸들 무효/복제 스레드 합류는 앞의 별도 Explicit 하드웨어가 확인한 범위다. Main 진입을 Scene 감독의 곡 선택·전체 스트리밍 또는 전체 State GUI 왕복 증거로 확대하지 않는다. 기존 덤프·화면 불변도 같은 게임 시각의 CPP 대조나 전체 L2 34경로 완료와 구별한다.
