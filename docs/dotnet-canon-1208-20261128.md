# 1.208 두 채널 음악 Runtime과 실제 협조 worker

같은 SoundState·명시 primary·두 채널과 기존 음악 명령 잠금으로 MusicRuntime을 조립했다. 초기화는 채널의0..13/18..39/3c..43만 지워 패딩과 원문 잠금 공간을 보존한다. worker는 첫 Update 뒤500ms 대기하며 WAIT_TIMEOUT일 때만 반복한다. 초기화/종료 진단·Stop 예외와 worker 예외도 원문 순서로 보존한다. 종료 대기 동안 명령 잠금을 풀어 worker/다른 명령이 반환할 수 있게 하고, Stop 예외는 자원 반납 뒤 다시 전달한다.

WindowsMusicRuntime은 실제 CreateEventW/CreateThread/Wait/SetEvent/CloseHandle과 고정 stdcall callback·GCHandle 수명을 사용한다. 강제 Thread 중단 대신 협조 종료 요청을 사용하며 자기 유효 스레드의 실제 합류 뒤 핸들, 그다음 이벤트를 반납한다. Windows 반환값을 임의 성공으로 만들지 않는다. 이벤트/스레드 생성 실패 뒤에도 원문 준비 표식이 세워지는 분기는 그대로이며, 그 표식을 실제 준비 성공 증거로 확대하지 않는다. 정상 소유권/클라이언트 Shutdown 계약에서 동작하며 외부 조기 Close/worker 자신의 Shutdown은 지원 경계가 아니다.

`musicruntime-x86.tsv` **4,800행(판본별1,600: 초기화64·종료576·잠금96·worker864)**의 두 raw96·음향 전역·핸들/번호·로그/커널/잠금 사건·worker 반환을 전수 대조했다. 다른 전역/primary 거부·초기화 진단 예외 정리·Stop 예외 뒤 반납·종료 중 명령 잠금 반납을 포함한다. 두 실제 OS 검사는 Win32 worker+실제 Winmm 파일 IO로 같은 소유자의3회 재시작과 예외 보존/다음 초기화 해제를 확인한다. COM 응답은 명시 검사 입력이며 음향 하드웨어 재생은 아니다.

팀 제품/검사 소스 동결 뒤 Release 솔루션 **오류0·기존 경고25·종료0**, 47.93초다(`extracted/dotnet-1208-build.log`). 출력은 `extracted/dotnet-1207-artifacts/`다. Runtime9건과 기존 채널/Fill/열기/선택/음량/효과음/파일/COM/목록을 합쳐 집중 **75/75 통과·실패0**, 12초다(`extracted/dotnet-1208-tests/runtime.trx`·로그). 새 잠금 검사는 async 대기와 검사 CancellationToken을 사용해 명령/채널 잠금의 실제 반납을 확인한다.

자료를 사본 없이 Client에 링크하고4,800행/SHA `73730a938998de015746d41b64c01d32d63f1e99cd5a74406fb9bb51ca9d734b`를 목록에 추가했다. 자료521개며 원문 대응6행을 PORT_MAP에 등록했고 전체 이식 기준은 바꾸지 않았다. 기존 독립 PE 감사의 추출 의존30파일 누락은 앞 인계를 유지한다. 이번 C# 전수/실제 worker 통과를 그 PE 재실행 완료로 세지 않는다.

아직 HostMissionAudio에 같은 장기 음악 소유자로 설치하지 않았다. 다음1.209에서 실제 SDL 창의 HWND를 얻어 기존 DirectSound 초기화에 전달하고 숨긴 SDL 창·별도 Explicit 하드웨어1건·비음소거 제품 진입을 구분해 확인한다. 그 뒤 정기1.210과 [실제 음향/SceneMusic/State 부모](dotnet-audio-owner-followup-1206-20261128.md)를 잇는다.
