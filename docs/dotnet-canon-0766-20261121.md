# 0.766 실제 일반 Chat 메시지와 패킷 연결

ClientChatMessageRuntime이 같은 장기 manager/Subscriber/Identity/현재 이름을 기존 일반 메시지 본체와 명시 패킷 장치에 연결한다. 두 전역은 같은 UIntBox를 빌리며 기존 독립0/0 생성도 유지한다. 이름 getter는 실제 Identity의 SOMEONE fallback과 비영 목적 포인터 계약을 재사용한다. 패킷 장치는 CPP의 값 캡처처럼 binding 시 대리자를 보존하고, say 지역256BYTE는 미작성 꼬리의 초기화를 요청하지 않는다. 현재 root0에서는 입력줄 장치를 조회하지 않는다.

실제 manager의 MakePacketHooks는 같은 물리와 기존 AddChatRecipient 확장/반납을 제공한다. Host의 BindNativeChatFlow는 대상 조회→일반 조합/명시 패킷→제출을 같은 Root 소유자로 연결한다. 실제 창 UI가 이를 설치·소비하는 호출자, 현재 전송/수신 장치 설치, 공유 로그와 자동완성은 후속이다. 임의의 전역 기본값이나 빈 송신 성공은 추가하지 않았다.

기존 RawChatPacket에서 현재 수신자 개수를 최초 값으로 고정한 차이와 사용자 음수 표식이 전투 접두에 유입되는 차이를 각각 검사로 재현했다(before2실패). 원문의 각 반복 현재 count 재조회와 고정 문화권 signed 십진수로 교정했다. 신규9건 포함 최종 집중32건은 모두 통과했다. 실제32→64 수신자 확장과 이전 배열 반납, 직접 대상의 현재 이름, binding 후 장치 교체, 미연결 송신의 선행 쓰기 보존, 제출→분배→Identity→일반 조합→패킷을 확인했다.

기존 원문 메시지524관측과 패킷256관측의 전체 manager/배열/입력/지역 바이트·반환·중단·효과 순서를 대조했다. 일반 헤더를 포함한 물리행은525/257이다. 기존388fixture 항목/헤더/기대값을 보존하고 두 원문 링크를 추가했다(총390). 원문 파일의 해시는 fixture-audit.json에 기록했다. PORT_MAP에 실제 메시지 부모 한 대응을 추가하고 기존 본체/할당 소유자 대응을 재대조했다.

대표3시작 모두 종료0·전체 덤프 바이트/지표0.764일치·원본1392파일 불변이다. cpp_sync와 최종 감사도 종료0이며 기존 Carrier의 null 경고 외 새 경고는 없다. CPP/디컴파일 변경·외부 접속은 없고 실제 포획/희생·특정 적 공격·승리는 재현하지 않았다.

근거는 extracted/dotnet-0766/의 before.log/.trx·test.log·client.trx·register.log·source-revisions.json·fixture-audit.json·cpp-sync.log·capture.py·capture.log·capture-summary.json·capture-originals-audit.json·capture/*/dn/*·audit.py·audit.log·final-audit.json이다. 다음0.767은 실제 ChatWindow의 공유 상태/로그/완성 및 UI 결선을 진행한다. 정기 전체 회귀는0.768이며 전체 목표는 미완료다.
