# dotnetpj 0.833 — 같은 경로 고리·검색 수명과 전체 파일 열기 정책

작업일2026-11-22, PC HJOW-Athlon. 실제 색표 캐시에 필요한 Source 장치명 조회·FileSpec 검색·파일 열기 정책을 이식했다. 실행 경로는 `dotnetpj/src/Netstorm.Game/bin/Release/net10.0/Netstorm.exe` 한 곳이다. 실제 CRT/TAFF metadata·캐시 FILE·Client 초기화 공급은 다음 작업이며 본체 검증을 실제 호스트 설치로 확대하지 않는다.

## 변경

- `RawFileName.Device`는 기존 Format과 같은10칸·Index/배열을 사용한다. 선행 현재 칸 clear→첫NUL/255BYTE 물리 확인→전체 입력 복사→UNC서버 끝 또는 colon 다음/첫BYTE에만NUL 순서다. 반환은 같은 고리 뷰이며 NUL 뒤 입력과 열번째 칸 alias 효과도 유지한다.
- `FileSpecQuery`는 생성 때 복사한 검색 장치와 같은 현재 핸들을 소유한다. 일반 이름은 원문 접두/slash 처리만 하며 파일 조회가 없다. 패턴은 정규화 전 입력을 Find에 전달하고 원래 backslash prefix와 첫 이름을 연결한다. Assign은 이전 핸들을 닫고 Next 종료는 마지막 이름을 보존한다. 실패 핸들도 Assign/Dispose에서 한 번 반납하며 생성/상위 열기 예외에서도 현재 수명이 정리된다.
- 실제 Windows 장치는 FindFirstFileW/FindNextFileW/FindClose를 사용한다. DirectoryHooks는 검색 시점의 가상 게임 폴더와 드라이브 상대/루트 디렉터리 상대를 처리하고 호스트 CWD는 바꾸지 않는다. OS 경계에서만 UTF-8/Unicode를 변환한다. Linux의 실제 패턴 검색 장치는 후속이며 선택 시 명시 진단한다.
- `RawBaseFileOpenPolicy`는 FileSpec과 같은 경로 고리/현재 파일·키 상태를 유지한다. 상대 이름의 기본 디스크→기본 TAFF→보조 디스크→보조 TAFF, 직접 장치 읽기 실패의 대소문자 구분 공통BYTE 접두 suffix, 직접 쓰기 실패의 즉시 예외를 이식했다. 등록 archive 한 번의 지역 메타데이터로 부분 FILE을 열고 성공 뒤에만 고정13BYTE 키와 NUL을 설치한다. 이미 찾은 archive 열기 실패를 다른 파일로 숨기지 않는다.
- 명시 OS 경로 매핑에서도 선행 Format 효과를 남긴다. 실패 뒤 다음 archive는 현재 NUL 이름을 다시 읽는다. 같은 소유자에서 root/이름/FILE을 Source 호출 위치에 재조회하며 미선택 장치는 요구하지 않는다. 원문 비복귀 예외 장치가 복귀하면 명시 오류다. 실제 FileSpec/경로/OS API를 전달할 수 있는 상태이며 빈 성공을 공급하지 않는다.

## 검증

독립 Device32행에서 현재 전체256BYTE·반환의 같은 주소/첫NUL 길이·원시 입력 불변을 비교했다. 전체 열기1364행은 모든 모드/create·출처/예외·키할당·호출순서/인자·최종6필드·같은 Index/전체256BYTE·할당 키를 비교했다. CPP 자료나 기대값은 변경하지 않았다.

Source의 일반/패턴/종료/실패 핸들 Assign/Next, 원래 패턴/첫NUL·slash/backslash prefix와 생성 때 장치 복사, 선택 누락/반납·열번째 alias/물리 실패의 선행 clear, root 예외 뒤 검색 반납, archive 실패/비복귀 요구를 확인했다. 실제 Unicode/보충 문자 폴더에서 상대·루트 디렉터리 상대·같은 드라이브 상대/절대 패턴과 다음 검색·실패를 실행하고 호스트 CWD 불변도 검사했다. OS 매핑 실패 뒤 현재 이름/고리, 직접 매핑 이름도 확인했다. 신규는 Assets10사례다.

첫9건과 추가 OS 매핑을 포함한10건 모두 통과했다. 최종 Release 오류0·기존 경고6이며 NETSTORM_DATA 없이 **Assets376·Core69·Client610, 합계1055통과/실패0**다. 이전 집중 이름을 모두 보존하고 전체0.832 대비 신규 Assets10을 실제 이름으로 확인했다. 새 Source 기준과 현재 파일 내용을 비교하고 자료2/대응8만 추가했다. 자료452/458물리행·대응1619/1624물리행(port1131·L1 481·session7)에서 이전 모든 값/순서/base를 보존했다.

준비 관문10724가 완료되기 전 생성 스크립트를 실행한 시도는 파일 없음으로 종료1이었고 빌드/검사는 시작하지 않았다. 준비 종료0 확인 뒤 실제 관문96007의 build/assets/core/client/cpp-sync/capture와 최종 종료0, 사후 감사 종료0을 확인했다. 조기 실행 로그도 별도 보존했다.

같은 최종 빌드의 thewarbegins/tutorial1/surrounded 모두 종료0이고 전체 시작 덤프/지표가0.832와 같다. 공격/포획/희생/승리 입력은 보내지 않았다. 원본1392·실행6·제품/검사/대응1910파일은 관문 전후 불변이다. 검사 사본 Assets2/Core4/Client6은 실제 실행본과 바이트 일치하며 AGENTS/README/공통 인계도 이전 LF 장부와 같다. CPP 제품/검사·원본/CD는 변경하지 않았고 원격 push도 하지 않았다. 실제 증빙은 `extracted/dotnet-0833/`다.
