## 1. 범위와 결과

| 대상 | 결과 |
|---|---|
| 방향 글자 | `neighborLetters(mask, x, y)` → 같은 영역 이웃의 직선·대각선 비트와 글자 두 개(방향 글자 `side`, 변형 글자 `variant`). `classifyCells(mask)` 는 모든 지면 칸에 대해 만든다 |
| 후보 검색 | `FrameCodeTable`(타입의 프레임 코드 배열) + `terrainFrameCandidates` — 정확히 → 정규화 → (방향, `A`) → 방향만 → 없음, 단계 이름과 후보 번호를 돌려준다. 글자 쌍 256가지를 모두 검사했다 |
| 고르기 | `chooseTerrainFrame(frames, side, variant, theme, random)` — 원소 −1 은 전체에서, 0~3 은 후보 수의 4분의 1 구간 `[q × theme + 1, q × (theme + 1))` 에서 난수 한 번 |

사용 예: `const frames = FrameCodeTable.fromDefinition(table.definitions[table.find('isle') - 70]); const tiles = buildTerrainFrames(mask, frames, { themeOf: (territory) => themes.get(territory) });` — `tiles[y * 256 + x]` 가 그 칸의 `isle` 클러스터 번호(셰이프 프레임 = 클러스터 번호 + 레이어 × 클러스터 수). 화면에 보이는 변화는 없고 웹 공개 데이터(`www/data`)도 늘리지 않았다.

## 2. 원본 규칙(cpppj·문서 근거)

* **안쪽/가장자리:** 원본은 먼저 `MarkEdges('x', '=')` 로 여덟 이웃(월드 경계·허공·다른 영역 포함) 중 하나라도 같은 영역의 지면이 아니면 `x` 를 `=` 로 바꾼다. 안쪽 칸이 `x`, 가장자리 칸이 `=` 이다. (앞 단위 인계의 `x → X` 는 오기였다 — `X` 는 별도 가장자리 타입 문자이고 일반 지형은 `=` 을 쓴다.) 두 문자 모두 같은 `isle` 타입을 만든다.
* **방향 글자:** 북부터 시계 방향 여덟 이웃 중 같은 영역인 칸의 비트를 모은다. 이웃별 비트표는 `1,2,2,4,4,8,8,1` 이고 짝수 번호(북·동·남·서)는 직선 mask, 홀수 번호(북동·남동·남서·북서)는 대각선 mask 에 더한다(대각선 비트: 북서 1·북동 2·남동 4·남서 8). 두 mask 를 비트 → 글자 표 `PNOILJFBMHKEGDCA`(앞 단위의 `orientationLetter`)로 바꾼 것이 (방향 글자, 변형 글자)이다. 여덟 이웃이 모두 같으면 (`A`, `A`) 이고 이것이 곧 안쪽 `x` 칸이다(두 판정이 같다는 것을 465개 맵 전체에서 확인).
* **안쪽 `AA` 칸:** 3 × 3 그림 네 변형 중 하나. `JJ00`(클러스터 172) 다음에 원소(해·천둥·바람·비)마다 36개씩 `AA00` 이 이어진다. 프레임 = `JJ00 번호 + 1 + 원소 × 36 + 변형 × 9 + (y % 3) × 3 + x % 3`, 변형 = `(표[(표[(x÷3) % 99] + 표[(y÷3) % 99]) % 99] + y÷3) % 4`. 같은 3 × 3 묶음은 한 변형을 공유한다.
  * **첫 도장**(`RawTerrainStamp::FrameAt`, `004c04b0`): 원소 항이 없다 → 항상 태양 묶음. 표는 CRT `_rand` 를 99번 이어 뽑아 만들고 앞 항목과 하위 2비트가 같으면 뒤 항목을 1 올린다. 원본은 이 표를 **첫 호출에서 한 번만** 만들어 전역에 둔다.
  * **지역 도장**(`RawRegionPaint::Select`, 신전을 세워 소유자가 정해질 때 `RawRegionOwnership::Update` 가 부름): 원소 × 36 이 붙는다. 표는 항목마다 시드 0 의 정수 난수 `Next(65536)` 을 새로 뽑으므로 **모든 항목이 같은 값 v**(= 11956) 이고 하위 2비트 교정으로 v, v+1 이 번갈아 나온다. 게임 난수를 쓰지 않으므로 항상 같다.
* **가장자리 `=` 칸**(`ChooseTerrainFrame`, `0049aa90`): 후보를 프레임 코드 저장 순서로 최대 256개 모은다 — ① (방향, 변형) 정확히 일치 → ② 없으면 `Normalize`(`0041cd20`: 양쪽 직선 이웃이 받쳐 주는 대각선만 남기고 직선 연결을 다시 만듦) 한 글자 → ③ 없으면 (방향, `A`) → ④ 없으면 방향만. 모두 비면 −1, 도장은 −1 을 프레임 0 으로 대체한다. 원소 `theme` 가 −1 이면 후보 전체에서 `Next(후보 수)`, 0~3 이면 `q = 후보 수 ÷ 4`(내림)로 `[q × theme + 1, q × (theme + 1))` 에서 `Next(high − low)`. 각 원소 묶음의 첫 클러스터는 제외되고, 범위가 비면(후보 7개 이하) 원본의 범위 검사 오류이다. **첫 도장은 10.78 에서 원소 0 을 쓰고(CD판 10.72 는 −1) 지역 도장은 신전의 원소를 쓴다.**
* **지역 도장은 지금 프레임의 코드를 읽는다**(`Code(sid)`): 첫 도장이 고른 클러스터의 (방향, 변형) 글자로 후보를 다시 찾는다. 그래서 정규화로 찾은 칸은 정규화된 글자의 묶음에서 다시 고르고, 후보가 없어 프레임 0(`AA01`, 글자 `AA`)으로 대체된 칸은 칠할 때 안쪽 3 × 3 그림으로 바뀐다(구현이 이 순서를 따른다).
* **원소 번호:** 신전 타입의 `theme` 속성(첫 글자 `w r t s` → 0~3 표, `RiftTypeTable.cpp` `ThemeNumber`)을 `RawRegionOwnership` 이 `바람 → 2 · 비 → 3 · 천둥 → 1 · 태양 → 0` 으로 바꾼다. 곧 클러스터 묶음 순서(해 0·천둥 1·바람 2·비 3)이다. 같은 소유자의 마지막 신전의 원소가 남고, 옵션 `themeMode` 가 꺼져 있으면 0 이다.
* **난수 시드**(`00455970`): 난수 모드 0 이면 CRT 시드 `0x38d535`, 아니면 현재 시각(Unix 초). 100개를 버리고 세 값의 32비트 곱을 게임 난수의 시작 상태로 쓴다. CRT 는 그 뒤에도 103번째 소비 상태를 유지한다.

## 4. 원본과 다르게 둔 점·가정

1. **난수로 고르는 변형은 원본과 같다고 보장하지 않는다.** 원본은 게임 전역 난수의 현재 상태(맵 적재 전의 모든 소비를 거친 값)로 가장자리 변형을 뽑고, 안쪽 첫 도장 표는 전역 캐시를 처음 만들 때의 CRT 상태에서 만든다. 이 구현의 기본값은 난수 모드 0 의 시작 상태(`seedGameRandoms()`, 시드 직후)이다 — 그 사이에 다른 난수 소비가 있다면 달라진다. 검증 대상은 **후보 집합과 결정적인 부분**(방향 글자·안쪽 판정·3 × 3 위치와 지역 도장의 표)이다. 난수를 바꿔 넣을 수 있게 `options.random`·`options.crt` 를 열어 두었다(실제 세션이 생기면 그 난수를 넘긴다).
2. **지역 도장은 영역 전체를 y·x 순서로 다시 고른다.** 원본은 신전 위치에서 번지는 flood(연결 비트를 따라 DFS)와 경계 후보 추가(`Boundary`)를 하므로 난수를 쓰는 순서와 일부 경계 칸의 처리가 다르다. 후보 집합과 안쪽 표는 같다. `themeOf(영역 번호)` 가 원소를 돌려주면 그 영역을 칠한 것으로 본다 — **신전 투표(소유자 결정)·`themeMode` 는 옮기지 않았다**(그림 단계에서 신전의 원소로 `themeOf` 를 만든다).
3. **10.78 패치판 규칙만 옮겼다.** CD판(10.72)은 첫 도장의 원소가 −1(전체에서 고름)이고 지역 도장 규칙도 다르다.
4. **첫 도장의 범위 `[16, 240)`:** 원본은 도장 범위 밖 칸을 만들지 않는다. 원본 `.fort` 465개의 지면 칸은 모두 범위 안이어서(검사로 확인) 범위 인자를 두지 않았다.
5. **후보가 4분할되지 않는 칸은 범위 오류**를 던진다(원본의 범위 검사 오류와 같다). 방향 글자가 `J`(세로 한 줄 통로: `JJ00` 하나뿐)이거나 (방향, `A`) 단계로 `AA` 묶음에 빠지는 칸이 그렇다. 원본 465개에는 이런 칸이 없다.
6. **`isle` 타입 하나만 다룬다.** `edgeFarm`·`fringe`·받침 타입의 같은 번호·이름 대응은 다음 단계에서 한다.
7. 이 단위의 검사는 **독립 구현(Python)과의 일치**가 근거이다. 원본 실행 중 지면 프레임·원본 화면과 대조한 것이 아니다(그림 단계에서 원본 캡처와 대조한다).

## 5. 검증(HJOW-Athlon, Node v24.21.0)

* `npm --prefix webpj test`: **225개 중 223개 통과**(신규 27). 실패 2개는 이 PC 의 `fonts/License.txt` 줄바꿈(CRLF) 때문에 자산 비교 2개가 실패하는 기존 현상이다(이전 단위 기록과 같음, 내용 차이 아님). 신규 검사 27개는 모두 통과한다(전체 약 25초, 신규 파일 약 17초).
* **이웃 비트·글자:** 이웃 하나씩 켜서 8가지 비트, 다른 영역 이웃 제외, 월드 밖(왼쪽 위·오른쪽 아래 모서리)은 이웃이 아님. **정규화:** 손으로 계산한 예 4가지와 256쌍 모두 한 번 정규화한 결과가 고정점.
* **프레임 코드 표·후보:** 글자 구간(`isle`: `J` 구간 172 에서 1개, `A` 구간 0 에서 200개)·저장 순서·256개 한계·합성 표로 5단계(정확히·정규화·(방향, A)·방향만·없음)·같은 표의 기억·원소 구간 계산(후보 8/20/24개, 7개 이하는 오류)·난수 호출 인자와 후보 선택(스크립트 난수).
* **글자 쌍 256가지**가 독립 기대값과 줄 단위로 같다: 후보 단계(정확히 14 · 정규화 80 · (방향, A) 3 · 방향만 63 · 없음 96)·후보 번호·원소 0~3 의 유효 후보. 기대값 표는 원소 구간이 **그림 파일 이름으로 나눈 원소 블록(첫 클러스터 제외)과 같은지**도 적었다 — 같은 쌍 140, 다른 쌍 19(`J` 묶음 16쌍 + `AJ`·`AK`·`AP` 의 `AA` 묶음 3쌍), 해당 없음 97. **원본 맵에 실제로 나오는 51쌍은 모두 정확히/정규화 단계에서 '같음'** 이다 — 곧 원본의 "후보 수의 4분의 1 구간 = 원소" 산술이 `isle.type` 의 그림 원소와 정확히 맞는다.
* **난수:** CRT 는 MSVC `srand(1)` 의 알려진 수열 10개와 같고, `seedGameRandoms`·첫 도장 표(103개 소비 뒤 99개, 하위 2비트 교정)·지역 도장 표(v, v+1)는 BigInt 독립 계산과 같다. **월드 전체 3 × 3 그림 프레임 해시 5개**(첫 도장 1·지역 도장 원소 4)가 Python(실제 CRT)과 같다.
* **원본 `.fort` 465개:** 방향 글자 분포(칸 수·안쪽/가장자리·글자 쌍별 칸 수·(x, y, 글자, 글자) 열의 SHA-256)가 Python 독립 계산과 줄 단위로 같고, 안쪽 칸은 (A, A) 와 같으며 모든 지면 칸이 `[16, 240)` 안이다.
* **`buildTerrainFrames`:** 465개 모두에서 첫 도장 결과가 안쪽 칸은 첫 도장 3 × 3 프레임, 가장자리 칸은 글자 쌍의 원소 0 유효 후보 안이고 허공은 −1. 일부(29개마다 + 공식 맵 둘 = 18개)에서 원소 0~3 으로 칠하면 안쪽 칸은 원소별 3 × 3 프레임, 가장자리 칸은 **첫 도장 프레임과 같은 글자 쌍**의 그 원소 유효 후보 안이며 `themeOf` 는 영역마다 한 번만 불리고, 후보가 4개 이상인 쌍(`BF`·`CG`·`DH`·`EI`)은 원소 구간의 후보가 **모두** 쓰인다. 칠하지 않은 영역은 첫 도장 그대로(Save the Island! 의 두 영역으로 확인). 난수·CRT 주입, 후보 없는 칸의 프레임 0 대체와 그 칸의 지역 도장(3 × 3 그림으로 바뀜), `J` 칸의 범위 오류, 같은 입력의 반복성.
* **변이 검사:** `terrain-tiles.js` **77곳 중 73곳 검출**(사본 `extracted/` 에서 한 곳씩 바꿔 신규 검사 파일을 돌림; 작업자 3개 병렬). 첫 실행은 75곳 중 68곳이었다. 놓친 7곳을 따져 보았다 — (1) `chooseTerrainFrame` 의 인덱스 상한(`>=` → `>`)은 난수가 범위 한계와 같은 값을 돌려주는 경우를 넣어 검출. (2) 난수 소비 순서(월드 y 바깥·x 안쪽)는 지역 도장이 첫 도장의 가장자리 선택을 모두 덮어써 순서가 가려지므로, 칠하지 않은 실행과 칠한 실행을 따로 호출 번호 % 한계 난수로 손계산해 검출(첫 도장 순서·지역 도장 순서 모두). (3) 칠하기에서 후보 없음(-1) 가드는 현재 프레임 자신이 같은 글자의 후보라 도달할 수 없어 제거했다. (4) 나머지 4곳은 동등 변이다 — 월드 아래쪽 밖 읽기(`y ≤ 256`)는 배열 밖이라 `undefined` 로 이웃이 되지 않고, 지면 칸 분류의 `null` 건너뜀 두 방식은 같은 결과이며, 지역 도장 표의 `Next(65536)` 과 `Next(65535)` 는 이 시드의 값(상위 16비트 < 65535)에서 같고, 표 첫 항목의 `i > 0` 비교 제거는 `values[-1]` 이 NaN 이라 같은 결과이다.
* 확인하지 않은 것: 브라우저에서의 동작(화면에 연결 전), 원본 실행 중 지면 프레임·원본 화면과의 대조, 난수로 고르는 변형이 원본과 같은지, CD판(10.72)의 도장, 신전 투표·`themeMode`, 원본 flood 순서.
