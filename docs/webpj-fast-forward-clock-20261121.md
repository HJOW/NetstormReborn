# Playwright 가짜 시계로 게임 시간 빨리 감기: 쓸 수 있는 것과 한계 (WB04-E1156)

긴 진행이 필요한 확인(AI 장기 행동·자연 패배·쉬움 난이도의 채취 유닛 절반)을 줄이려고 Playwright 의 가짜 시계(`page.clock`)로 게임 시간을 감는 방법을 시험했다. 결론: **게임 시간에 묶인 시스템은 빨리 감을 수 있지만 AI 는 프레임에 묶여 있어 결과가 왜곡된다.** 코드 변경은 없다.

## 방법

```js
await page.clock.install();            // 페이지 로드 전
await page.goto(url); await page.clock.resume();   // 평소처럼 메뉴·미션 시작까지 진행
await page.clock.pauseAt(new Date(Date.now() + 1000));
for (...) { await page.clock.fastForward(10000); await page.clock.runFor(200); }   // 10초 건너뛰고 짧게 프레임을 돌림
```

- `runFor(ms)` 는 `requestAnimationFrame` 을 16ms 마다 부르므로 프레임 비용 때문에 실제 시간과 1:1 이다(20초 감기에 21.8초).
- `fastForward(ms)` 는 시계를 한 번에 건너뛴다. 게임 시계(`gameSeconds`)가 그만큼 가고 Kernel 이 따라잡아 20초가 0.95초 만에 지났다. 60분(게임 시간)이 약 85초.

## 관찰

- The War Begins! 를 플레이어가 가만히 둔 채 61분(게임 시간) 감았다: 적 AI 의 다리 조각 21→604, 섬 1→13 으로 늘었고 오류는 없었다. 적은 새 유닛을 만들거나 플레이어 섬을 공격하지 않았다(초기 궁수 9·방벽 8·포대 3 그대로, 플레이어 객체 4개 그대로).
- 스커미시 AI(난이도별 1회): 60분에 쉬움은 windWalker 3·windBattery 2, 보통은 windWalker 7·windBattery 4, 어려움은 windWalker 1·windBattery 2. 46분 시점 3회씩은 쉬움 3·1·2, 보통 2·2·2 로 채취 유닛 수를 구분할 수 없었다.

## 한계 (왜 AI 확인에는 맞지 않는가)

- 기존 e2e(`skirmish-difficulty.spec.js`, 실제 시간 150초)는 AI 다리·섬 조각이 쉬움 57·보통 209·어려움 357 개로 난이도 순서가 뚜렷했다. 같은 시험을 빨리 감기로 바꾸자 28/34/29, 55/53/30 으로 **순서가 사라졌다**.
- 원인: AI 의 제어 주기가 짧아 한 프레임에 한 번의 동작만 하는 한계에 걸린다. 빨리 감기는 10초당 약 13프레임(실제는 약 600프레임)만 돌려 AI 가 프레임 수로 제한된다. 따라서 위의 61분 관찰("AI 가 공격하지 않음")도 AI 동작 횟수가 실제보다 훨씬 적은 상태의 결과라 **신뢰할 수 없다**.
- 게임 시간 구동 시스템(게임 시계·Kernel·시간 제한·구름/날씨 등)은 빨리 감기로 확인할 수 있다. AI·전투·패배 같은 프레임 구동 시스템은 실제 시간으로 확인해야 한다.

## 결론과 남은 것

- 쉬움 난이도의 채취 유닛 절반(최소 1)은 설정 단위(`applyAiDifficulty`, Node 시험)와 AI 생성 연결(E554·E555·E1096)로 검증돼 있고, 실제 진행의 수 비교는 편차가 커 구분하지 못했다. 필요하면 실제 시간의 장시간 e2e 로 여러 번 반복해 비교한다(옵트인).
- 자연스러운 패배(적 AI 가 사제를 쓰러뜨림)는 실제 시간의 장시간 진행으로만 확인할 수 있다. 승패 안내와 이어지는 흐름은 E1152 에서 판정 입력으로 확인했다.
- 가짜 시계 빨리 감기는 게임 시간 기반 확인(예: 시간 제한 미션, 날씨 주기)이 필요할 때 쓸 수 있다.
